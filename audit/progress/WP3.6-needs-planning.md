## What changed

* Needs (`departmental_needs/services/lifecycle.py`): `_Command` replaces `_existing` / `_fingerprint`. Order in every command: `actor` -> lock the Need -> authorise -> replay -> version check. A recorded result is returned only to the same actor, command and payload; anything else is `NDS_IDEMPOTENCY_CONFLICT`. A stale `expected_version` first reads the key as last committed: a duplicate of a command that committed while this request waited gets its original result, anything else `NDS_STALE_WRITE`. The locking read is used on that refusing path only, so a missing key never leaves a gap lock that a later insert in the same transaction could deadlock on. `create_need` replays after authorisation and again after taking the creation lock. A unique-key violation when recording the decision is `NDS_IDEMPOTENCY_CONFLICT`.
* Planning (`services/envelope.py`, `write_family.py`): `planning_command` names the command and the actor for the journal, runs the command in a savepoint (a failed command leaves no claim and no partial write even for an in-process caller), and releases a claim the command never recorded. `replay_or_none` claims the key with a unique insert; `record_command` completes the claim. Journal gains `standing`. Eight commands that were not decorated now are (`record_late_activation_explanation`, `submit_consolidated_plan`, `submit_corrected_plan`, `reverse_requisition_drawdown`, `start_plan_item_correction`, `close_plan_item_correction_without_change`, `retry_publication`, `record_treasury_submission`); a test checks every command that replays a key is decorated and records it.
* Reference generators: Planning `references._next` and `finance_task_reference`, Needs `_next_reference`.

## Follow-ups

1. **Planning authorise-before-replay is done by standing, not by reordering about 50 command bodies.** Planning commands authorise in different ways inside their bodies (site role, unit-scoped role, maker-checker). The journal stores the actor's active responsibilities (assignment id, role, unit) when it claims the key and answers a replay only while the actor still holds all of them; otherwise "not found". Same design as Evaluation. Option: move each command's authorisation above the replay (the Needs shape); recommended default: leave, no owner decision needed. What I did: standing.
2. **Legacy journal rows (documented behaviour, no conflict for in-flight retries).** Needs: a decision row written before the change has a payload-only fingerprint; it is replayed to the actor who wrote it (same payload), and is a conflict for anyone else. Planning: a row with no `standing` (written before) is replayed to the actor who wrote it for the same payload; no standing check (unknowable); a conflict for anyone else. So a retry by the same user across the deploy keeps working; only a different user replaying someone's old key now conflicts, which is intended. No follow-up needed unless the owner wants a patch to backfill (not recommended).
3. **Plan-root creation race (found while fixing the generators).** `Departmental Plan` has no unique (unit, year). Two requests starting the same plan used to be stopped by accident (duplicate `dpp_reference`); with a correct reference generator they would both succeed and make two roots. `open_departmental_plan` and `ensure_departmental_plan` now take an advisory lock for the unit and year and read the root as last committed. A DB-level unique index on (organisation_unit, fiscal_year) would be the durable guard; it needs a data check on existing rows first, so not done here. Recommended: raise as a separate schema finding.
4. **Advisory locks in Planning are held until the connection closes** (pre-existing, `get_lock` never released). Right for a web request (released after commit), but a long-lived connection (test process, worker) keeps them: a second connection asking for the same name waits 10 s and then fails "busy". My two-connection tests call `release_all_locks()` first. Anyone writing a similar test or worker must do the same. Needs releases its own lock before commit; that is safe now because of the probe.
5. **Same defects still in the other envelopes** (not touched, other agents): Requisitions `references.py:54-56` and Tenders `references.py:42-44` still read a plain `max + 1` after the named lock; they can reuse `kentender_core.utils.series.next_free_reference(doctype, field, prefix, highest_seen, width)`.
6. **Pre-existing failures seen on the test site, not caused by this package** (each fails identically with the pre-change `lifecycle.py`, `envelope.py`, `write_family.py`, `references.py`, `dpp_lifecycle.py` swapped in): Needs `test_departmental_needs_architecture` (2: Planning seed `kentender_mvp_v1.py` reads Needs directly), `test_departmental_needs_seed::test_the_cleared_variant_supplies_no_plan_references`, `departmental_needs.test_home_provider` (3), Planning `test_analytics_provider::test_a_departmental_author_gets_departmental_plans_only_and_no_plan_items`, `test_dead_end_matrix::test_every_annual_plan_state_leaves_every_reader_somewhere_to_go`, `test_home_provider::test_an_accepted_plan_missing_a_later_need_asks_the_department_to_update_it`. The Needs lifecycle suite also leaves committed Needs behind on the test site (200 created in the last hour; three titled "Saved exactly once"), not from this package's tests, which purge their own rows.

## Document follow-ups

* NDS v1.16 section 9 and PLN v1.29 section 8: state that an idempotency key is bound to the actor, the command and the payload; the same key from anyone else, for another command or with another payload is `NDS_IDEMPOTENCY_CONFLICT` / `PLN_IDEMPOTENCY_CONFLICT`; a replay is answered only after authorisation (Needs) or only to an actor who still holds the standing recorded with it (Planning); a duplicate that arrives while the first is running waits and returns the original result.
* PLN section 8 error list: `PLN_STALE_WRITE` is no longer used for key reuse.
