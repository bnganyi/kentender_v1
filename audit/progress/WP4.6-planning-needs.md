## Decimal contract (what changed, who reads it)
- Producer: `events.accepted_payload` (and so the nested `successor_accepted_payload` of `DepartmentalNeedSuperseded.v1`) and the §8.1 read `workspace.get_current_accepted_need` now emit `indicative_quantity` as an exact plain-decimal string (`"10"`, `"1.125"`) through `quantity.wire_text` (no float, no exponent, no trailing zeros). Event name and `v2` label are unchanged (decision of the lead; see Document follow-ups for the cutover record NDS §4.9 asks for).
- The content hash is unchanged: it is computed over the stored column (`cstr`), not over the wire value.
- Replay of older events: stored outbox rows written before this change hold a JSON number. `events.current_accepted_events` and `events.consume_events` pass every body through `quantity.normalise_wire_payload`, so every consumer sees one type whatever era the row is from. Stored rows are not rewritten (no patch).
- Consumers found by grepping every `kentender_*` app (py, js, vue, ts, seeds, patches, tests): the only reader of the quantity is Planning `needs_intake._facts` (feeds `current_accepted_sources` and `refresh_draft_entries`); it now parses the string exactly (`needs_intake._quantity`, `Decimal`) and narrows to the entry's Float column; non-decimal text fails `PLN_REFERENCE_UNAVAILABLE` instead of becoming 0 (a missing value still reads 0, as before). Other readers of the same payloads read other keys only: `dpp_autostart.on_need_event` (org unit, fiscal year), `procurement_home.home_pipeline` (need id), `patches/pln_start_plan_from_accepted_needs` (org unit). JS: `needsApi.getCurrentAcceptedNeed` is declared but has no caller. `workspace._version_facts` (the Needs UI read) still returns the stored number: it is not the published contract.

## Follow-ups
1. AUD-PLN-021 (owner decision). Unclear: PLN v1_29 §6.4 (line 892) lists "approve/return as statutory authority" as the prohibited later action for Planner-side, Finance and AO actors, and §11 (lines 461, 720, 847) makes "Withdraw for correction" a separate statutory-authority command that is not named in §6.4; `withdraw_approved_plan_for_correction` (`treasury.py:176-210`) checks the role and collective reference but never `require_not_segregated(... ACTION_STATUTORY_DECIDE ...)`. Options: (a) withdrawal is a statutory decision, so the same chain exclusion applies (a person who authored, confirmed Finance or adopted as AO cannot withdraw); (b) leave as is: withdrawal only releases a confirmed-unpublished plan back to Draft and repeats the whole governance, so it grants nothing; (c) apply only the AO exclusion (the AO who asked for the withdrawal may not also decide it, since the AO request is the maker step of §11). Recommended: (c) if the owner wants any rule; otherwise (b). Did: nothing; marked Blocked. Same-family note: `ReturnPlanVersion` by the statutory authority already checks the chain.
2. AUD-XC-134 scope. The audit text says "and other Planner commands"; only `SavePlanVersionDetails` is a missing authoring command, and `CancelPlanUpdate` is the only other command it names. I did not add `CancelPlanUpdate` (reasoned above); if the owner reads §6.4 as including it, it is a one-word addition to `PLANNER_CHAIN_COMMANDS`. Also not on the chain: `RequestBudgetRevision`, `SaveDirectRequirement`/other DPP-side commands (DPP validation has its own certifier rule) and `RecordTreasurySubmission` (AO side).
3. Wire contract cutover. `DepartmentalNeedAccepted.v2` kept its name while `indicative_quantity` changed type. NDS v1_16 §4.9 asks for either a documented coordinated cutover or an approved new event version. In-repo producer and consumer moved together and replays normalise old rows, but any external subscriber built to the numeric form would see a string. Option: introduce `v3` and keep `v2` as a numeric compatibility shape. Recommended: keep as done unless an external consumer exists (none found in this repository).
4. Residuals still open from WP3.5 follow-up 2: (b) Float column limits the quantity to 12 integral digits (NDS asks 18) and needs a migration; (c) no per-unit decimal scale in ERPNext UOM; (e) Requisition Item quantity is Int. The Planning Departmental Plan Entry `quantity` column is still a Float with precision 2 in its doctype JSON (display precision), so the string becomes a float on storage.
5. NDS-007 coverage. The hash recheck compares against the hash stored at submission; revisions submitted before this code existed have the same hash function, so none is rejected, but a Submitted revision whose stored `content_hash` is empty (none seen on the test site) would now be refused with `NDS_STATE_CONFLICT`. The required-by-in-year rule is not rechecked at acceptance (NDS §8.2 names unit, hash, task and concurrency only).
