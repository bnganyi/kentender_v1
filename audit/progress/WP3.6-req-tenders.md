## What changed

* `kentender_procurement/services/command_journal.py` (new, shared by the two envelopes): `claim_or_replay` inserts the journal row with a unique insert inside a savepoint (under `command_write`); on a duplicate key it reads the winner's row with a locking read (waits for an uncommitted claim, sees the committed one) and returns the original result only when actor, command and payload fingerprint all match, otherwise the module's typed `*_IDEMPOTENCY_CONFLICT`. A claim that never produced a result (a command that returned a refusal as data) may be reused by the same actor only. `complete` records the result on the claim; `release` frees a claim.
* Requisitions and Tenders `envelope.replay_or_none(key, payload, *, command, actor)` now claims; `record_command` completes the claim (inserts when a caller never claimed). Every command (21 Requisitions, 28 Tenders) passes its command name and actor and calls `replay_or_none` after its authorisation and before it reads anything else. Requisitions draft commands split `_draft_for_write` into `_writer` (locked root + edit scope, before the key) and `_draft_versions` (versions + Draft check, after it) so a replay is answered after the actor's scope check but before the state check the command itself changes.
* Tenders: `envelope.locked` is a locking read (`for_update=True`); `Tender Command Journal.idempotency_key` is now unique (the Requisitions journal already was); the three data-refusal returns (`save_tender_draft`, evidence commands, `update_addendum_draft`) release their claim; `close_tender_submission_period` and Requisitions `record_handoff_consumption` record the result of their "already done" branch.
* Reference generators (`procurement_requisitions/services/references.py`, `tenders/services/references.py`): after taking the named lock they no longer trust the snapshot's maximum; each candidate is probed with a locking read (`next_free_reference`), so a number committed by the request that held the lock is seen.
* Legacy rows: the journal columns used for the binding (`actor`, `command`, `request_fingerprint`) already existed and the fingerprint function is unchanged, so rows written before this change replay for their own actor and command and are a conflict for anyone else (tested with a hand-built row). No data patch.

## Follow-ups

1. **Installed STD Release is written by every Tender command that verifies its template (found by a real concurrent StartTender with two different keys; not changed, outside this package).** `std_templates/services/runtime.py::verify_integrity` (called from `binding.require` on every start, submit, approve, publish ...) saves the shared `Installed STD Release` row with a new `last_verified_at` each time. Two Tender commands at once (different Tenders, or two starts) therefore race on that one row and the loser dies with an untyped `TimestampMismatchError` on the release. Options: (a) write only when the verification result changes or the last write is older than a few minutes; (b) write with `frappe.db.set_value` (no timestamp check); (c) lock the release row with a locking read first. Recommended: (a) plus (b). Until then a concurrent start of two different handoffs can fail with a generic error and the caller retries. I removed my test of that scenario (two starts, two keys, one handoff) because it would assert on this unrelated defect; the same-key concurrent start is covered.
2. **Requisitions per-row scope checks still run after a replay in `update_requisition_item` and `remove_requisition_item`** (`records.require_unit(scope, line.contributing_org_unit)` needs the item, and a replay of a remove no longer finds it). The actor's edit scope over the requisition (`require_edit_units`) is checked before the key; the per-row unit check is not. Residual: a user who lost access to one contributing unit but kept another can replay their own old key for a row of the lost unit and read back their own earlier result. Recommended default: accept (they only see what they themselves submitted). Not changed.
3. **Named reference locks are session locks.** `get_lock` in both reference generators is released only when the connection closes, which a request does at its end; a test that keeps one connection open and then spawns another must `select release_all_locks()` first (`test_tnd_idempotency_envelope._commit` does). Recommended: leave; if the generators ever run in a long-lived worker, release the lock in `frappe.db.after_commit`/`after_rollback`.
4. **A claim left behind in a surviving transaction.** If an in-process caller catches a typed failure and keeps the transaction (a test, a seed), the claim row stays with an empty result; the same actor can reuse the key, nobody else can, and the Requisitions and Tenders test wipes (`wipe_requisition_rows`, `wipe_tender_rows`) delete such rows. In a web request the exception rolls the claim back with everything else.
5. **Tender journal unique index.** `migrate` on the dev site adds a unique index on `Tender Command Journal.idempotency_key`; it fails loudly if two rows already share a key. The test-site copy of dev has 122 rows and no duplicates. Pre-check on dev before migrating (see Dev site actions needed).
6. **Dependency on an uncommitted change by another agent.** `kentender_core/kentender_core/utils/series.py::next_free_reference` is in the working tree (modified by the Needs/Planning package) but was not committed when I finished; my two `references.py` changes import it. Commit that file before or with these commits; if its signature changes, the two call sites are `procurement_requisitions/services/references.py` and `tenders/services/references.py`.
7. **Planning and Needs** use their own copies of this shape (another agent). `kentender_procurement/services/command_journal.py` is written so they can adopt it (journal doctype, command-write family and the two typed refusals are parameters) if they want one implementation.
