## 3. New or residual defects (most severe first)

### REG-MONEY-01 (Medium, CODE DEFECT) - Budget's journal is read-then-effect-then-insert and the insert failure is swallowed, so a concurrent same-key release applies twice; governance replay is user-blind and precedes authorisation

- **Evidence.**
  - `kentender_budget/services/budget_idempotency.py:49-82`: `key` looked up with a plain read of `Budget Audit Event` by key alone (`:53-55`), then `result = fn()` (`:66`), then the journal row is written last by `safe_record_event(... idempotency_key=key, payload_digest=digest ...)` (`:71-79`).
  - `services/budget_audit_contracts.py:178-184`: `safe_record_event` catches every exception and returns `None`. The journal's only uniqueness guard is the unique index on `Budget Audit Event.idempotency_key` (`budget_audit_event.json`, `"unique": 1`). A duplicate insert therefore raises, is swallowed, and the second effect stays.
  - Money-moving use: `budget_commitment_contracts.py:55-66` (`_idempotent` -> `run_idempotent`), with `_release` at `:219-263`: `lock_budgets_of_lines` (`:223`), `locked_doc` (`:224`), then `release_amount = amount` when explicit (`:230`) and `doc.remaining_amount = new_remaining` (`:243`).
  - Governance use: `budget_readiness_contracts.py:593, :670, :728, :936`, `budget_contracts.py:1032`, `budget_line_contracts.py:91` all call `run_idempotent` first; the capability check is inside `fn` (`_submit_budget_version` `:598`, `_approve_budget_version` `:731-732`), so a recorded result is returned (`budget_idempotency.py:59-64`) to any authenticated caller who presents the key and the same payload, before any authorisation, and the payload digest does not include the command name or the actor (`:29-32`).
- **Rule violated.** BUD-BR-015 ("idempotent by correlation ID"); AUD-XC-002 acceptance ("Idempotency key replays return the first result"); AUD-XC-131 acceptance (authorise before replay, key bound to actor and command); AGENTS.md section 4 (server-side authorisation for every material action).
- **Repro sketch.** Two connections, Contract principal, one reservation with 10m remaining, `release_reservation(amount="1000000.00", idempotency_key=K)` from both with a barrier after each has run the journal lookup. Expected: one release (remaining 9m), the second replays. Today: remaining 8m (the second call's journal insert raised `UniqueValidationError` inside `safe_record_event` and was logged, not raised). For governance: user B who learns key K and payload from user A's request receives A's `command_result` (version summary) without holding any Budget responsibility.
- **Reach today.** The explicit-amount release is callable only by the Contract principal, which has no production caller (tracker follow-up 1), so the double release is latent. `convert` (natural key) and `adjust` (absolute target) and whole-reservation release (status check) are naturally idempotent. The governance replay is reachable now.
- **Classification.** CODE DEFECT. The shared fix pattern already exists in `services/command_journal.py` and `award/services/records.py:140-189`.

### REG-MONEY-02 (Low, CODE DEFECT) - Bid Opening and Proceedings still use the pre-audit lock helper and key-first journal

- **Evidence.**
  - `bid_opening/services/records.py:79-84`: `frappe.db.sql("select name from \`tabBid Opening Case\` where name=%s for update", name)` then `return frappe.get_doc(CASE, name)` (plain read, no `for_update`). Same shape at `proceedings/services/records.py:88-93`.
  - `bid_opening/services/records.py:113` and `proceedings/services/records.py:126`: `row = frappe.db.get_value(JOURNAL, {"idempotency_key": key}, ...)` (plain) before the lock and before the body; the journal row is inserted last inside the savepoint (a duplicate rolls the command back with a raw duplicate-key error, which fails closed). ## 4. Checked and clean

- **Lock order and locking reads.** `budget_locking.py` is the single source; reserve (`budget_check_reserve_contracts.py:384`), release (`budget_commitment_contracts.py:223`), convert (`:302`), adjust (`:421`), approve (`budget_readiness_contracts.py:746`), close (`:957`), successor creation (`budget_contracts.py:1237`), draft save (`:1105`), submit/return (`:607`, `:689`), line save (`budget_line_contracts.py:112`) and the Finance decision (`:694`) all take Versions first, then Lines. Every outcome-deciding read after the lock is `for_update` (`_active_version`, `_draft_version`, `_line_version_for`, `_line_position_exact`, `_version_totals`, `_line_version_rows(locked=True)`, `_closure_status_for(locked=True)`). I found no remaining plain read of a position, status or sum after a Budget lock.
- **Budget money-moving surface.** The six functions are not whitelisted anywhere; no `override_whitelisted_methods`, no `frappe.call` path; raw writes to `Funding Reservation` / `Procurement Commitment` exist only in seeds and clean-up helpers (grep above); the doctype controllers carry the command-write guard (`doctype/*/*.py`, `budget_write_family.py`). The D3 table is encoded exactly in `ALLOWED_ACTIONS`; Planning, Tenders, Evaluation and Award hold an empty set.
- **Authorise-before-replay in the fixed envelopes.** AST scan: all Requisitions and Tenders commands that call `replay_or_none` authorise before it, except two that authorise inline (system-only close; in-process handoff consumption). Needs (`lifecycle.py:608-611, :681-684, :734-737` ...), Award (`records.py:148-149`), Strategy (`strategy_idempotency.py:105-106`) authorise first. Planning authorises inside the body but gates the replay on the recorded standing (`envelope.py:143-144`); I judge that equivalent for replay (the replay returns only the actor's own earlier result and the claim row is rolled back with the command's savepoint when the body then refuses).
- **Claim by unique insert.** `command_journal._insert_claim`, `planning/envelope._claim`, `award/records._claim`, `strategy_idempotency._claim` insert inside a savepoint and treat both `UniqueValidationError` and `DuplicateEntryError` as "claimed"; the loser reads with `for_update=True`. All 12 `*command_journal*` doctypes have `idempotency_key` unique.
- **Atomic series.** `raise_series_to` is one `INSERT ... ON DUPLICATE KEY UPDATE ... GREATEST` (`series.py:27-31`); Frappe's `getseries` takes `FOR UPDATE` and increments (`naming.py:408-423`). Budget's four allocators and Strategy's use it (`budget_reference.py:83, :95, :119, :131`).
- **Decimal handling.** `budget_money._parse` refuses bool, NaN, Infinity, exponent, excess scale, 13+ integral digits and negatives; `stored()` converts storage floats through `repr`; `_line_position_exact` reads sums as `cast(... as char)`; `_reconcile` is `diff == 0`; no 0.01 / 0.0001 / 1e-9 remains in Budget (grep). Planning decisions use `money.exceeds` / `same_amount` / `sum_money`. Need quantity is exact (`quantity.py`).
- **Currency scale in Budget decisions.** `_position_scale` -> `scale_for(currency)` -> native `Currency.fraction_units` (`budget_money.py:53-71`); a missing or unsupported currency blocks (`CURRENCY_ERROR`), tested at `test_budget_exact_money.py:214-248`.
- **Funding facts at Evaluation and Award.** Evaluation reads Budget through the in-process `read_reservation_funding` (not whitelisted, no session-role dependency, `budget_funding_read.py`) and keeps a typed `Unavailable` fact; Award re-reads Budget now and treats unknown as a stop (`checks.py:78-96`).
- **Lock order across modules.** Requisition root before handoff in authorise, revoke and consumption (`records.py:113-116`, `handoff.py:121-127`); a journal claim by one key cannot form a cycle with the root lock because the keys differ.
- **Reservation uniqueness.** `Funding Reservation.drawdown_line_id` unique (doctype JSON) plus the locked check at `budget_check_reserve_contracts.py:393`; `Requisition.open_slot_key` unique (`records.py:212`); `Budget Audit Event.idempotency_key`, `generated_reference` on Version, Line Version, Reservation and Commitment unique.
- **Journals on `ok: False`.** Award deletes the claim (`records.py:176-177`), Requisitions/Tenders `release` and Planning `release_unrecorded` do; a refused attempt leaves the key free (tested: `test_req_idempotency_envelope.py:86`, `test_tnd_idempotency_envelope.py:82`, `test_pln_idempotency_envelope.py:124`).
- **Not examined.** Browser behaviour of the Budget editor (BUD-007 UI half), anything on the dev or test site, the isolation level of the live server, Strategy endpoints other than the journal, the `core` reference-data and supplier-account journals (`reference_data_idempotency.py:30-73` is also key-first with swallowed duplicates; configuration commands, no money; recorded here so it is not mistaken for unexamined).
