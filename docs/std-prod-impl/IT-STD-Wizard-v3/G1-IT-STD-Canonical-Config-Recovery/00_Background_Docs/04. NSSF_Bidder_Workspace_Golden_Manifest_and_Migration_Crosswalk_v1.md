## 1. Purpose

This artifact instantiates the canonical PPRA Information Technology bidder-submission model against the NSSF ERP tender and records how the earlier NSSF-specific checklist and schema must be recovered.

It provides:

- the approved NSSF calibration decisions;
- the exact golden section structure;
- immutable source and resource bindings;
- the tender-specific requirement, schedule, price, evaluation, and contract counts;
- a digest-bearing logical manifest projection;
- complete legacy section and field dispositions;
- criterion and evaluation mappings;
- response migration and reconfirmation rules;
- expected compiler diagnostics;
- Cursor fixture and conformance requirements; and
- the acceptance boundary for subsequent design and implementation work.

This artifact does not make NSSF the canonical model. It proves that the canonical IT STD model can compile the NSSF tender without importing NSSF-specific structure into the platform.

## 2. Controlling Result

The earlier `10_NSSF_Electronic_Bidder_Submission_Schema.json` is not a valid canonical Bidder Workspace contract.

It remains useful as:

- extraction evidence;
- a legacy response-shape inventory;
- a migration source;

- a production runtime schema;

### 3.3 Source conflict rule

The NSSF source contains physical-submission instructions and states that electronic tenders were not permitted. KenTender is an electronic-only PoC.

This artifact therefore applies an explicit calibration policy:

1. retain the historical source statement as provenance;
2. do not claim that the historical NSSF tender was electronically published;
3. replace physical copies, envelopes, signatures, and delivery mechanics with the approved KenTender electronic equivalents;
4. retain all substantive bidder obligations;
5. record the policy decision in the manifest decision resource; and
6. prohibit production reuse of the fixture without a newly approved tender publication.

### 4.1 Tender-security determination

The source heading is misleading, but the operative characteristics are those of a tender security.

| Source characteristic | Classification effect |
|---|---|
| Furnished as part of the tender | Pre-award submission instrument |
| Fixed amount of KES 500,000 | Configured security amount |
| Original bank guarantee or insurance bond | Permitted guarantee instrument forms |
| Absence makes the tender non-responsive | Mandatory preliminary responsiveness control |
| May be forfeited on tender withdrawal | Tender-security remedy |
| May be forfeited if the successful bidder fails to sign or furnish performance security | Tender-security remedy |
| Located against ITT 22.1 in the TDS extraction | Canonical ITT 22 security control |

The golden fixture therefore applies:

- security mode: `security_instrument`;
- amount: `KES 500,000.00`;
- minimum validity: 30 days beyond the tender-validity end;
- permitted source forms: bank guarantee or qualifying insurance bond;
- bidder or JV-party identity validation;
- issuer and instrument metadata;
- authenticated evidence;
- mandatory preliminary-evaluation route; and
- non-responsive blocking status when absent or invalid.

`PRELIM-05` remains visible as a published preliminary criterion, but it is satisfied by a live cross-link to the Tender Security response. It does not request a duplicate upload.

### 7.2 Resource binding rules

Each descriptor must use:

- `storage_mode = content_addressed`;
- an immutable opaque repository reference;
- the stated schema version;
- the stated count;
- the stated logical ordering;
- the stated logical digest; and
- source references to the NSSF extraction and canonical mapping decision.

The runtime must reject a resource when:

- its count differs;
- its digest differs;
- its schema differs;
- its item keys are duplicated;
- its declared order cannot be reconstructed; or
- a section references an absent resource.

## 21. Response Migration Policy

### 21.1 Migration dispositions

| Disposition | Meaning |
|---|---|
| `carry_exact` | Copy a value only when source and target semantics, identity, type, and version are identical |
| `transform_review` | Transform using a declared mapping and require deterministic validation or human review |
| `link_existing_evidence` | Preserve the exact evidence version and create canonical links |
| `recalculate` | Discard the derived legacy value and calculate from migrated source values |
| `require_reconfirmation` | Preserve prior data for reference but require a new confirmation against current text and context |
| `audit_only` | Retain for lineage; never use for completion |
| `reject` | Do not migrate because the value is ambiguous, invalid, or has no lawful target |

### 21.2 Default policy by object

| Object | Default disposition |
|---|---|
| Verified organization particulars | `transform_review` |
| Narrative response with unchanged owner and source | `carry_exact` |
| Evidence file | `link_existing_evidence` |
| Generic acknowledgement | `audit_only` |
| Legal confirmation | `require_reconfirmation` |
| Derived total | `recalculate` |
| Requirement response after requirement-text change | `require_reconfirmation` |
| Non-blank deviation note where deviations are prohibited | `reject` plus blocker |
| Legacy submission event | `audit_only` |

### 21.3 Migration procedure

1. Freeze the legacy workspace and compute a source snapshot digest.
2. Bind the workspace to the exact legacy schema digest.
3. Create a migration run with an idempotency key.
4. Resolve bidder, JV, user, and authority identities.
5. Map each legacy object using this crosswalk.
6. Preserve original value, source path, timestamp, actor, and evidence digest.
7. Deduplicate evidence without deleting historical versions.
8. Recalculate price summaries.
9. Recompute criterion, task, section, and workspace states.
10. Generate migration findings for every rejected, ambiguous, stale, or incomplete item.
11. Require current document acknowledgements.
12. Require current Form of Tender and statutory-declaration confirmations.
13. Require Tender Security completion under the corrected classification.
14. Run full current-manifest validation.
15. Permit submission only through the canonical seal transaction.

### 21.4 PoC default

For non-production PoC workspaces, regeneration is preferred to in-place migration. In-place migration is justified only when preservation of representative response data is necessary for testing.

## 22. Invalidation and Reconfirmation Matrix

| Change | Carry-forward result | Required action |
|---|---|---|
| Tender package version changes without substantive impact | Unaffected responses may remain | Acknowledge the new package version |
| Active addendum changes legal or response content | Impact plan controls affected responses | Revisit affected tasks and reconfirm dependent forms |
| Tender deadline changes | Draft content may remain | Recalculate validity and security dates; reconfirm Form of Tender; revalidate security |
| Tender-validity period changes | Technical content may remain | Recalculate validity; reconfirm Form of Tender; revalidate security |

| Bidder or JV identity changes | Entity-scoped responses become stale | Revalidate CBQ, declarations, security, qualification, and authority |
| Authorized signatory or authority evidence changes | Legal confirmations become stale | Verify authority and reconfirm affected forms |
| Form of Tender legal text changes | Form data may remain where compatible | Reconfirm the complete current form |
| CBQ legal text or entity branch changes | Compatible data may remain | Complete new fields and recertify |
| Declaration text changes | No confirmation carries | Reconfirm the affected declaration |
| Preliminary criterion changes | Unaffected criterion links remain | Re-resolve only changed and dependent criteria |
| Qualification threshold or period changes | Source data may remain | Re-evaluate completeness and eligibility; update affected responses |
| Personnel criterion changes | Unaffected nominees remain | Update affected position/candidate records |
| Requirement statement changes | Unaffected rows remain | Re-answer the changed row and downstream links |
| Requirement evidence rule changes | Statement may remain | Supply or relink required evidence |
| Requirement group changes only | Response may remain | Reproject navigation; no legal reconfirmation unless meaning changes |
| Technical schedule row changes | Unaffected rows remain | Re-answer changed schedule row; revalidate linked price and technical tasks |
| Price quantity, unit, currency, tax, or row changes | Affected price graph becomes stale | Reprice or confirm explicit inclusion; totals recalculate |
| Any price value changes | Other section content remains | Recalculate summaries and reconfirm Form of Tender |
| SCC changes a bidder commitment | Affected technical/price response becomes stale | Update response and reconfirm dependent legal form |
| Renderer-only change with identical response/display contract digest | Responses remain | No bidder action |

### 22.1 Confirmation rule

No legal confirmation is silently migrated or carried across a material change. The platform records:

- the old confirmation;
- the invalidation cause;
- the new manifest and text versions;
- the actor notified;
- the reconfirmation event; and
- the new immutable confirmation digest.
