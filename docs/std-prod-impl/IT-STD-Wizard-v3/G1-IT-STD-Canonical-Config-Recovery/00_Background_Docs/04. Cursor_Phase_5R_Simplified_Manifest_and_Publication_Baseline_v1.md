# KenTender e-Procurement System

# Cursor Phase 5R Directive — Simplified Manifest and Publication Baseline v1

## 1. Status and authority

This directive replaces the proposed Phase 5A hardening work.

It also supersedes the Phase 4 and Phase 5 implementation requirements in the earlier recovery directive wherever they require:

- separately content-addressed manifest collections;
- per-resource publication bindings;
- descriptor-set or projection digest chains;
- parallel tender-publication authorities; or
- separate records for each intermediate governance action.

Do not start Phase 6 until this directive is complete and reviewed.

The site is a development environment. Existing BWMF test, fixture, and publication data may be cleared and reseeded. Do not implement production migration, backward-compatibility, or zero-downtime provisions.

## 2. Objective

Reduce the current BWMF implementation to the smallest architecture that still guarantees:

1. STD-family-neutral bidder sections;
2. deterministic compilation from an exact tender configuration;
3. one immutable electronic bidder-workspace manifest;
4. one digest over the complete manifest payload;
5. approval bound to that exact digest;
6. one authoritative tender-publication record;
7. atomic visibility of the tender and its matching manifest;
8. immutable published versions;
9. governed supersession and cancellation; and
10. an audit trail of material state transitions.

The target flow is:

```text
Approved STD definition
    + confirmed tender configuration/package
    → deterministic compiler
    → immutable self-contained Compile Artifact
    → submit for approval
    → approve exact payload digest
    → atomic publication
    → IT Tender Publication Record + immutable Manifest Version
    → manifest-driven Bidder Workspace
```

The final bidder manifest must be generated at configuration/publication time. It must not be reconstructed from PDFs, inferred from labels, or regenerated during bidder page requests.

## 3. Architectural decision

PPRA STD families are curated and versioned legal templates. They are not expected to change continuously.

Tender-specific content remains dynamic because each tender may configure different:

- TDS and SCC values;
- forms and declarations;
- eligibility and qualification criteria;
- technical requirements;
- schedules;
- price lines;
- lots and alternatives;
- tender security rules; and
- addenda.

Therefore:

- retain a metadata-driven manifest compiler;
- compile only when a confirmed tender configuration is prepared for publication;
- store the complete runtime manifest as one immutable payload;
- hash that complete payload once; and
- do not create a general-purpose content-addressed resource platform.

## 4. Binding source hierarchy

Use this authority order:

1. approved canonical STD-family definition and version;
2. confirmed tender configuration snapshot;
3. confirmed tender document package;
4. deterministic compiler output;
5. approved manifest payload digest;
6. `IT Tender Publication Record`;
7. immutable `BWMF Manifest Version`;
8. bidder workspace bound to that publication and manifest version.

NSSF is a calibration fixture only. It must prove that the canonical PPRA IT STD configuration produces the expected tender-specific result. It must not define production section structure or labels.

Legacy `10_NSSF_Electronic_Bidder_Submission_Schema.json` remains a negative or compatibility fixture only.

## 5. Target persistence model

### 5.1 Retain

| Record | Purpose |
|---|---|
| `Tender Configuration` | Editable wizard/configuration aggregate |
| `Confirmed Tender Document Package` | Exact confirmed tender package and configuration snapshot |
| `BWMF Compile Artifact` | Immutable, self-contained successful compiler output or failed-result evidence |
| `BWMF Manifest Approval` | One governed submission/decision record bound to an exact artifact and payload digest |
| `BWMF Manifest Version` | Immutable published runtime manifest |
| `IT Tender Publication Record` | Sole authority for bidder-visible tender publication |
| `BWMF Audit Event` | Append-only BWMF governance/publication events |

Existing compile requests, runs, traces, diagnostics, and validation reports may remain as internal compiler diagnostics. They are not publication authorities and must not create additional digest or approval chains.

Existing Phase 7 and Phase 8 runtime records may remain dormant. Do not redesign responses, evidence, confirmations, submissions, sealing, or receipts in this phase.

### 5.2 Consolidate

| Current concern | Simplified owner |
|---|---|
| Logical requirement, criterion, schedule, price, SCC, and decision collections | Inline ordered arrays inside the manifest payload |
| Resource materialization | Compiler stage C22 |
| Publication readiness | Server-derived from the successful Compile Artifact and its validation result |
| Review package | Exact Compile Artifact plus its immutable validation/warning snapshot |
| Approval decision | `BWMF Manifest Approval` |
| Publication request/idempotency | One approved manifest may produce at most one authoritative tender publication; retry returns it |
| Tender public state and active pointer | `IT Tender Publication Record` |
| Manifest publication record | `IT Tender Publication Record` linked to `BWMF Manifest Version` |
| Lifecycle history | `BWMF Audit Event` |

- independently governed reusable manifest resources;
- chunked manifest collections;
- cross-tender resource deduplication;

- bidder response migration;
- exhaustive concurrent-publication hardening;
- exhaustive storage-corruption recovery;
- legacy NSSF migration; or
- Phase 6 bidder UI cutover.

Bidder-uploaded evidence is not a manifest resource. Future evidence versioning and file integrity are unaffected by removing manifest CAS.

## 6. Self-contained manifest contract

Revise the v1 manifest schema so the complete bidder runtime contract is available from one payload.

At minimum, the payload must contain:

- schema version;
- manifest ID;
- STD family and STD version;
- tender and configuration identity;
- immutable source/provenance references and digests;
- ordered content sections;
- groups and tasks;
- field and collection contracts;
- applicability rules;
- evidence requirements;
- validation rules;
- dependencies and invalidation declarations;
- workflow gates;
- renderer keys;
- permissions/authority requirements;
- requirement groups and requirements;
- preliminary criteria;
- qualification criteria;
- technical scoring criteria;
- schedule rows;
- price lines;
- contract/SCC carry-forward values;
- controlled tender decisions; and
- stable object IDs and declared ordering.

Dynamic collections must be inline ordered arrays. Sections may reference objects in those arrays by stable ID or collection key. They must never reference array positions as identity.

The payload must contain no arbitrary file paths, URLs, credentials, bidder values, or NSSF-only constants.

Use the existing NFC plus RFC 8785 JCS implementation to calculate:

```text
payload_digest = SHA-256(JCS(NFC-normalized complete payload))
```

This is the only manifest-content digest used for approval, publication, retrieval verification, and workspace binding.

Source-file digests may remain in `provenance`. They are inputs represented inside the hashed payload; they do not require a second approval digest chain.

## 7. Compiler correction

Preserve the pure, STD-family-neutral compiler and stable identity rules established in Phase 3.

Change successful compilation as follows:

1. C01–C21 resolve and validate the exact STD and tender configuration.
2. C22 inserts the ordered dynamic collections directly into the complete payload.
3. C22 calculates the final payload digest.
4. The successful `BWMF Compile Artifact` stores the exact payload bytes and digest.
5. A successful artifact is immutable and may be submitted for approval without Phase 4 materialization.

A successful artifact must expose:

- `artifact_kind = final_manifest_candidate`;
- `final_runtime_manifest = true`;
- exact `payload_json`;
- exact `payload_digest`;
- exact source/configuration/package references;
- validation result;
- warnings;
- `eligible_for_approval`, derived by the server.

A failed compile must retain the current fail-closed behavior:

- no valid manifest payload;
- no payload digest represented as successful;
- no approval eligibility;
- deterministic diagnostics; and
- no publication action.

Do not treat display labels as identity. Label changes may preserve stable object IDs while changing the complete payload digest.

## 8. Governance and approval

Use `BWMF Manifest Approval` as the only manifest-governance record.

### 8.1 State model

```text
SubmittedForApproval → Approved
                     → Returned
```

The Compile Artifact represents the prepared state. Creating the approval record represents formal submission.

### 8.2 Minimum approval fields

- approval ID;
- organization;
- compile artifact reference;
- manifest ID;
- proposed tender-publication version, if known;
- payload digest;
- confirmed configuration/package references;
- submitter and submitted time;
- state;
- approver and decision time;
- warning acknowledgements;
- approval comments; or
- return reason and correction owner.

The approval record may transition only once from `SubmittedForApproval` to a terminal decision. Terminal records are immutable.

Any new compile artifact or payload digest requires a new approval record.

### 8.3 Roles and separation

| Role | Authority |
|---|---|
| Tender Configurator | Configure and compile |
| Procurement Reviewer | Submit exact artifact for approval |
| Tender Approver | Approve or return |
| Publication Service | Publish an approved artifact |
| Auditor | Read governance and publication history |

The submitter must not approve the same record.

Do not grant governance authority implicitly to `Administrator`. Development seed users must receive explicit roles.

Approval does not publish.

## 9. Single publication authority

`IT Tender Publication Record` is the sole authority for whether a tender version is bidder-visible.

Do not use `BWMF Tender Publication State`, `BWMF Manifest Publication`, or another mutable active-pointer record.

Extend the existing publication record only as required to bind:

- tender/configuration lineage;
- tender-publication version;
- `Confirmed Tender Document Package`;
- configuration snapshot reference and digest;
- STD family and version;
- approved `BWMF Manifest Approval`;
- published `BWMF Manifest Version`;
- manifest payload digest;
- lifecycle state;
- published/superseded/cancelled timestamps and actors;
- prior publication/manifest version for addenda; and
- workspace availability.

Required lifecycle states:

```text
Prepared → Published → Superseded
                     → Cancelled
```

If the repository already uses different equivalent labels, map them explicitly in the implementation report and retain only one authoritative state machine.

## 10. Atomic publication

Implement one transaction that:

1. locks the relevant tender/configuration lineage;
2. loads the approved `BWMF Manifest Approval`;
3. loads the exact Compile Artifact;
4. recalculates and verifies the complete payload digest;
5. verifies the approval, package, configuration, organization, and digest match;
6. allocates the next tender-publication/manifest version;
7. creates the immutable `BWMF Manifest Version` using the exact artifact payload;
8. creates or transitions the authoritative `IT Tender Publication Record`;
9. supersedes the prior active publication when this is an addendum;
10. appends the publication audit event; and
11. commits.

No bidder-visible publication may exist without the matching Manifest Version.

Use native database uniqueness for:

- `(manifest_id, manifest_version)`;
- one publication version within a tender lineage;
- one active publication within a tender lineage; and
- one authoritative publication per approved manifest approval.

The approval reference is the publication idempotency boundary. Repeating publication for the same approved record must return the existing authoritative publication when the fingerprint matches and reject a conflicting request.

Do not create a separate Publication Request record.

## 11. Retrieval

Bidder-facing retrieval must resolve:

```text
IT Tender Publication Record
    → BWMF Manifest Version
    → exact complete payload
```

On retrieval:

1. require the publication to be currently bidder-visible;
2. load its exact Manifest Version;
3. recalculate the one complete payload digest;
4. compare it with both the Manifest Version and publication record;
5. return the manifest; and
6. fail closed if the record, payload, or digest is inconsistent.

Do not perform per-resource retrieval or verification.

Phase 6 will consume this service. Do not modify the A0–A4 bidder screens in Phase 5R.

## 12. Addenda and cancellation

An addendum must:

1. compile a new self-contained artifact from the amended confirmed configuration;
2. compare it with the exact prior published manifest using stable IDs;
3. record a concise diff summary on the artifact;
4. undergo a new approval;
5. publish a new version; and
6. supersede, but never mutate, the prior publication and manifest.

Do not implement bidder-workspace response carry-forward or invalidation in this phase. That belongs to the later addendum/workspace phase once responses exist.

Cancellation must change authoritative publication/manifest lifecycle state and preserve immutable payload and history.

## 14. Required tests

Create a focused Phase 5R gate. At minimum prove:

1. identical confirmed inputs produce identical payload bytes and digest;
2. a second synthetic STD family compiles without NSSF constants;
3. the NSSF semantic counts and canonical section keys pass;
4. successful compilation requires no Phase 4 materialization;
5. removed CAS/resource/publication-state records are not created;
6. a failed compile cannot be submitted or published;
7. approval is bound to the exact artifact digest;
8. return requires a reason and correction owner;
9. submitter self-approval is rejected;
10. approval does not publish;
11. publication without approval is rejected;
12. one injected failure after Manifest Version creation rolls back the publication and Manifest Version;
13. retrying the same approved publication is idempotent;
14. corrupting the complete stored payload causes retrieval to fail;
15. an addendum creates the next version and supersedes the prior version without payload mutation;
16. cancellation removes bidder visibility without deleting history; and
17. the existing A0–A4 Stitch files and bidder UI remain unchanged.

Do not retain tests that pass only because the removed architecture still exists.

## 18. Hard blockers

Do not declare Phase 5R complete if:

- the runtime manifest still depends on external BWMF resource records;
- more than one digest is required to establish manifest-content integrity;
- more than one record can independently make a tender bidder-visible;
- approval does not bind the exact complete payload digest;
- `Administrator` receives implicit governance authority;
- the NSSF fixture defines canonical production structure;
- an unsupported or failed artifact can be published;
- a partial transaction can expose a tender or Manifest Version;
- published payloads can be mutated;
- addenda overwrite earlier published content;
- obsolete Phase 4/5 DocTypes remain active in the canonical path; or
- Phase 6 bidder UI work is included.
