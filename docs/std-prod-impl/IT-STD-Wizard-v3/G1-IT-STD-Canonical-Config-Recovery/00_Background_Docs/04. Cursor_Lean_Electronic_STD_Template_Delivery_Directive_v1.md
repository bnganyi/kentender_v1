# KenTender e-Procurement System

# Cursor Directive — Lean Electronic STD Template Delivery v1

## 1. Governing decision

KenTender is an electronic tendering system. It is not an automated STD interpretation or template-generation platform.

PPRA STD templates may be prepared manually because they change infrequently. The system must concentrate on:

- legally faithful electronic templates;
- clear bidder tasks;
- complete electronic responses;
- validation before submission;
- controlled publication and addenda;
- authorized final submission; and
- an auditable receipt.

This directive supersedes:

- `Cursor_Phase_5R_Simplified_Manifest_and_Publication_Baseline_v1.md`;
- the Phase 4 content-addressed-resource implementation direction;
- the Phase 5 multi-record governance/publication direction; and
- the generic C01–C22 compiler as the required production architecture.

Historical reports remain evidence of work performed, but they do not govern the new runtime path.

## 2. Immediate objective

Deliver the first visible vertical slice:

1. a manually curated PPRA Information Technology STD electronic template;
2. an NSSF tender instance populated from its confirmed configuration;
3. the bidder checklist generated from that electronic template; and
4. a complete, editable, validated **Form of Tender** section.

Stop after this vertical slice and its implementation report. Do not attempt to implement every bidder section at once.

## 3. Product model

Use this simple flow:

```text
Official PPRA IT STD
    → manually authored electronic template
    → legal/product review and approval
    → tender configuration supplies tender-specific values
    → one immutable published electronic-template snapshot
    → bidder checklist and section screens
    → bidder responses
    → review, submit, receipt
```

“Dynamic” means that a template receives tender-specific requirements, criteria, schedules, prices, lots, security rules, TDS values and SCC values.

It does not mean that the system must automatically interpret an STD or provide a generic rules language.

## 4. Reuse the existing system

Prefer these existing records:

| Existing record | Lean responsibility |
|---|---|
| `Tender Configuration` | Tender-specific configuration prepared by the wizard |
| `Confirmed Tender Document Package` | Confirmed configuration and tender-document package |
| `IT Tender Publication Record` | Authoritative bidder-visible tender version |
| `Electronic Bid Submission` | Bidder draft and final electronic submission |
| `Electronic Bid Audit Event` | Material bidder and submission events |
| `File` | Tender documents and bidder evidence |

Do not introduce a new DocType when an existing record can own the required field safely.

The canonical bidder runtime must not depend on BWMF content objects, resources, materialization reports, resource bindings, review packages, publication requests, publication-state records or per-resource digests.

Do not begin a large cleanup project. Disconnect obsolete BWMF infrastructure from the runtime path and remove only code or metadata that blocks this implementation. Dead experimental infrastructure can be deleted later after the vertical slice works.

## 5. Manual electronic template

Create one version-controlled template file for the PPRA IT STD.

Suggested location:

```text
kentender_procurement/.../electronic_std_templates/ppra_it_std_v1.json
```

Follow the repository’s established package layout if a more suitable existing location is found.

The template is prepared manually from:

- the official PPRA IT STD;
- the canonical obligation catalogue;
- the canonical bidder-section blueprint;
- the Form of Tender electronic section specification; and
- the NSSF mapping pack as calibration data only.

### 5.1 Minimum top-level structure

```json
{
  "template_id": "PPRA-IT-STD",
  "template_version": "1.0",
  "std_family": "information_technology",
  "source": {},
  "sections": []
}
```

The exact schema may follow repository conventions, but it must remain understandable to a product or legal reviewer without reading application code.

### 5.2 Each section must declare

- stable `section_key`;
- exact bidder-facing title;
- order;
- renderer;
- bidder instructions;
- source STD clause/form references;
- whether it is required;
- simple applicability condition, where needed;
- locked legal text;
- tender-owned values;
- bidder-owned fields;
- repeatable tables;
- evidence requirements;
- validation rules;
- completion rule; and
- whether deliberate confirmation is required.

Do not introduce:

- a general-purpose expression language;
- a typed rules AST;
- content-addressed collections;
- resource descriptors;
- chunking;
- a template-authoring UI; or
- automatic extraction from PDF pages.

Where the IT STD requires special behavior, use explicit template fields or small, named adapter code. Prefer readable template-specific code over a generic framework.

## 6. Canonical IT STD sections

The manually curated IT STD template must contain these content sections:

1. `tender_documents_and_addenda`
2. `form_of_tender`
3. `confidential_business_questionnaire`
4. `statutory_declarations`
5. `tender_security`
6. `preliminary_requirements_and_evidence`
7. `qualification_and_capability`
8. `technical_proposal_and_implementation_plan`
9. `requirements_compliance`
10. `price_schedule`

Evidence and Issues are cross-cutting facilities, not checklist sections.

Review, Submit and Receipt are workflow steps, not checklist sections.

Do not add a separate Contract Conditions Acknowledgement section unless the official STD expressly requires a bidder response that is not already captured by the Form of Tender, declarations or tender-specific forms.

## 7. Legal-safety controls

The lean design must preserve these controls:

1. Every mandatory bidder obligation has a stable ID and source clause/form reference.
2. Locked legal text cannot be changed by a bidder.
3. Tender-owned values cannot be edited by a bidder.
4. Bidder-entered values are clearly distinguished.
5. Required fields, tables, declarations and evidence are validated.
6. Saving a draft does not constitute legal confirmation or submission.
7. Published tender versions retain an immutable template snapshot and one integrity hash.
8. Addenda create a new published snapshot; they do not overwrite the old one.
9. Final declarations identify the actor, capacity, authority and server time.
10. Submitted bids retain an immutable response snapshot and integrity hash.
11. The server enforces the submission deadline.
12. A receipt is issued only after successful persistence of the final submission.
13. Material transitions are audited.

These controls are mandatory. The discarded resource and compiler architecture is not.

## 8. Template review and approval

Template preparation may occur through source-controlled files rather than an application screen.

Use a simple maker-checker process:

```text
Draft → Reviewed → Approved → Retired
```

Record, using an existing suitable registry or minimal metadata:

- template ID and version;
- source STD identity/version;
- template file hash;
- prepared by/at;
- reviewed by/at;
- approved by/at; and
- status.

The preparer must not be the final approver.

Only an approved template version may be selected for tender publication.

Do not build a template preparation UI in this phase.

## 9. Tender instantiation

Implement one small service that creates the electronic bidder template for a confirmed tender configuration.

Logical capability:

```text
build_electronic_submission_template(configuration_id)
```

It must:

1. load the approved PPRA IT STD template;
2. load the confirmed tender configuration and document package;
3. populate explicit tender-owned values;
4. insert configured requirements, criteria, schedules, price lines and decisions;
5. resolve simple applicability;
6. verify every required binding;
7. produce one self-contained JSON snapshot;
8. calculate one canonical SHA-256 integrity hash; and
9. store the snapshot and hash on the authoritative publication version.

Use the existing canonical JSON hashing helper where practical. One stable hash over the complete published snapshot is sufficient.

Do not persist intermediate compile requests, runs, artifacts or materialization records for this path.

If a required configuration value is missing, fail with a clear configuration error. Do not invent a value or silently omit a mandatory obligation.

## 10. Publication ownership

`IT Tender Publication Record` remains the sole authority for whether a tender is bidder-visible.

Add or reuse fields for:

- template ID and version;
- confirmed package/configuration reference;
- published template snapshot;
- snapshot hash;
- publication version;
- prior publication version, where applicable;
- status;
- published by/at;
- superseded by/at; and
- cancelled by/at.

Use the existing tender publication approval process. Ensure the approver is not the same actor who prepared the publication.

Once Published, the template snapshot and hash are immutable.

No separate BWMF Manifest Version or Manifest Publication is required for the lean runtime.

## 11. NSSF calibration

Use the NSSF ERP tender only to populate and verify the PPRA IT STD template.

The NSSF instance must produce:

- 10 content sections;
- Tender Security;
- 23 requirement groups;
- 190 requirements;
- 9 preliminary criteria;
- 9 qualification criteria;
- 7 technical scoring criteria;
- maximum score `100`;
- qualification threshold `75`;
- 6 schedule rows;
- 22 price lines;
- 8 SCC/contract-condition values; and
- 8 controlled decisions.

NSSF names, products, currencies, thresholds and entity-specific values must stay in NSSF fixture/configuration data.

The production template must remain PPRA IT STD-focused and reusable for another IT tender.

## 12. Bidder checklist

Replace `schema_compiler.SECTION_KEYS` and the legacy NSSF schema as checklist authority.

The checklist must read the exact published electronic-template snapshot and:

- show applicable content sections only;
- use template order and titles;
- display required/optional status;
- derive section status from the bidder’s saved response state;
- show issues/blockers;
- select Start, Continue, Resolve or View from the current state; and
- calculate progress from applicable required sections.

For this first slice:

- Form of Tender must be fully functional;
- other sections may remain `Not Started` with their correct route;
- no section may use hard-coded NSSF structure;
- Review and Submit remain locked until their later implementation.

Preserve the approved Stitch A2 layout.

## 13. Form of Tender vertical slice

Implement the Form of Tender from:

```text
KenTender_Form_of_Tender_Electronic_Section_Specification_v1.md
```

The page must:

1. display locked legal wording from the approved IT STD template;
2. display tender-owned values as read-only;
3. collect all bidder-owned fields electronically;
4. support the required bidder/JV and lot context;
5. validate required values and declared formats;
6. save a draft without confirming or submitting;
7. show field-level and section-level issues;
8. derive Not Started, In Progress, Needs Attention or Complete;
9. retain last-saved actor/time; and
10. return to the checklist with updated status.

Do not use a PDF upload as the primary Form of Tender response.

Do not treat Save as signature, acceptance, confirmation or submission.

Deliberate authorized confirmation belongs to the later Review and Submit flow.

Preserve the established bidder visual language. Stitch controls design; Cursor implements functionality.

## 14. Response storage for this slice

Use the existing `Electronic Bid Submission` draft.

Store Form of Tender responses under stable section and field keys in its response payload, using the existing service pattern where safe.

Minimum requirements:

- authenticated bidder access;
- bidder/tender isolation;
- server validation;
- optimistic draft version or modified-time conflict protection;
- audit event for material saves;
- no client-set completion status; and
- submitted records remain immutable.

Do not create a general response-versioning subsystem in this slice.

## 15. Implementation order

Cursor must work in this order:

1. Inventory the existing simple models and bidder routes.
2. Disconnect the legacy NSSF schema from checklist authority.
3. Add the manually curated IT STD electronic template and a small validator.
4. Implement tender instantiation and publication snapshot/hash.
5. Seed the NSSF instance from its confirmed configuration.
6. Cut the A2 checklist over to the published snapshot.
7. Implement the Form of Tender route, service and response storage.
8. Add focused domain, integration and UI tests.
9. Produce the completion report.

Do not pause for a separate architecture-design cycle unless the repository contradicts an explicit instruction.

## 16. Focused tests

At minimum prove:

1. the manual template passes schema validation;
2. every required canonical IT STD obligation used by the first slice has a source reference;
3. an unapproved template cannot be published;
4. missing required tender bindings block publication;
5. identical approved template/configuration inputs produce the same snapshot and hash;
6. the NSSF instance produces the expected sections and counts;
7. a second small IT tender fixture uses the same template without NSSF constants;
8. the checklist is read from the published snapshot;
9. the legacy `SECTION_KEYS` order is no longer authoritative;
10. Form of Tender drafts save and reload correctly;
11. field and section validation errors are returned clearly;
12. completion is server-derived;
13. one bidder cannot read or modify another bidder’s draft;
14. Save does not confirm or submit;
15. a published template snapshot cannot be edited; and
16. the existing A0–A4 visual contracts remain intact.

Do not retain large test suites whose only purpose is to validate the abandoned BWMF architecture.

## 17. Explicit non-scope

Do not implement in this slice:

- the remaining eight editable bidder sections;
- final review and validation;
- authorized confirmation;
- submission sealing and receipt;
- addendum response carry-forward;
- evaluator views;
- generic support for every PPRA STD family;
- template-authoring screens;
- automated STD extraction;
- legacy data migration; or
- production data-preservation measures.

## 18. Completion report

Create:

```text
LEAN_IT_STD_TEMPLATE_AND_FORM_OF_TENDER_SLICE_REPORT.md
```

Include:

- exact template path and version;
- source documents used;
- simple template structure;
- existing records reused and fields added;
- legacy/BWMF runtime dependencies disconnected;
- NSSF instantiation results;
- published snapshot/hash evidence;
- checklist cutover evidence;
- Form of Tender fields and validation implemented;
- named tests, counts and commands;
- screenshots or route evidence for the checklist and Form of Tender;
- known gaps for the next section; and
- confirmation that non-scope work was not implemented.

## 19. Acceptance gate

Do not declare completion unless a bidder can:

1. open the NSSF tender;
2. see the correct 10-section IT STD checklist;
3. start Form of Tender;
4. complete and save its electronic fields;
5. see validation issues;
6. return to the checklist; and
7. see the server-derived section status.

The implementation is rejected if it adds substantial architecture without producing this user-visible journey.

## 20. Direct Cursor instruction

Read this directive and the referenced canonical IT STD documents. Inspect the repository, then implement the vertical slice.

Use explicit, readable template data and small services. Reuse existing records. Make only the abstractions required by the working IT STD bidder journey.

Do not implement or repair the abandoned BWMF Phase 4/5 architecture.

Stop after the working Form of Tender vertical slice and the completion report.
