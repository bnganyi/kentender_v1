## Purpose of This Document

---

## The Core Idea

A Standard Tender Document is **not** an uploaded Word/PDF. It is a **legal and procedural template** that must control:

- Tender document generation
- Bidder submission structures
- Evaluation matrices
- Contract formation outputs
- Post-publication addenda

The governing principle across all three source documents:

> **The STD Engine owns the official structure, locked legal text, allowed configuration surfaces, validation rules, rendered outputs, and downstream schemas. Tender Management and other modules consume those outputs — they do not recreate or override them.**

The earlier **Works PoC** (`KE-PPRA-WORKS-BLDG-2022-04-POC.json5`) proved the approach works. Production must **generalize** that learning, not copy the PoC architecture wholesale.

---

## What the PoC Got Right vs. What Must Change

| PoC validated | Production correction |
|---|---|
| Structured template packages | JSON is **import/export only** — not the runtime store |
| Section mutability classification | Richer universal mutability model + domain extensions |
| Controlled fields, rules, forms | Every element needs source trace, lifecycle, render targets |
| Conditional form activation | Full form schemas with evidence, respondent type, workflow stage |
| Domain modules (e.g. BoQ for Works) | Same pattern for IT: requirements, inventory, schedules |
| Assembled tender packages | First-class **render model** with deterministic hashes |

**Verdict:** PoC = learning artifact and seed design. Production = **database-backed, version-controlled, source-traced, approval-governed, render-deterministic, domain-extensible**.

---

## Architecture: Generalized Engine, IT First

The engine must support **multiple STD families** from day one:

- Works, IT, Goods, Non-Consulting Services, Consulting Services, Framework Agreements, and future categories.

**First full production digitization:** PPRA **Standard Tender Document for Procurement of Information Technology** (Doc. 10).

**Why IT first?** It exercises real complexity (structured requirements, conformance matrices, implementation schedules, system inventory, recurrent costs, software/IP, acceptance, SLAs, change orders) **without** Works-specific BoQ, drawings, and measurement/valuation machinery.

**Calibration fixture (not master source):** NSSF SPS ERP tender `NSSFSPS/ICT/ERP/001/2025-2026` — used to test realistic tender configuration, scoring, compliance matrices, payment milestones, professional indemnity, etc. The **official PPRA IT STD remains authoritative**.

## Conceptual Model: What an STD Is in the System

An STD is decomposed into interlocking models:

1. Template family → versioned official template
2. Section/clause hierarchy
3. Mutability classification
4. Parameters (TDS, SCC, tender identity, etc.)
5. Declarative rules
6. Form schemas (PE, bidder, evaluator, contract officer)
7. Requirement schemas (PE-authored structured content)
8. Price schedule schemas
9. Evaluation schemas
10. Contract output schemas
11. Render blocks
12. Governance/audit
13. Tender-specific instance + configuration values

Users see a **guided configuration experience**; the system enforces the legal structure underneath.

---

## Universal Mutability Model

Every section, clause, field, form, and render block gets a mutability type. Examples:

| Type | Meaning |
|---|---|
| `LOCKED_TEXT` | ITT, GCC — no PE editing |
| `PARAMETERIZED_TEXT` | Fixed text with approved placeholders |
| `CONTROLLED_CONFIG` | TDS, SCC parameters |
| `CONTROLLED_REQUIREMENTS` | Structured PE-authored requirements |
| `STRUCTURED_TABLE` | Price schedules, implementation schedule, inventory |
| `BIDDER_RESPONSE_SCHEMA` | Forms, declarations, conformance matrix |
| `EVALUATION_SCHEMA` | Checklists, scoring, financial comparison |
| `CONTRACT_OUTPUT_SCHEMA` | Post-award forms and appendices |
| `GENERATED_OUTPUT` | Published bundles, audit summaries |
| `REFERENCE_ONLY` | Background material — not binding unless linked |

Mutability is **enforceable behavior** at UI, API, and database/service layers — not just a label.

## Two Lifecycles

### 1. STD Template Version (master)

```text
Draft → Structuring → Internal Review → Legal/Procurement Review
  → Approved → Active → Superseded → Archived
```

Hard rules:

- Only **Approved** versions can become **Active**
- **Active versions are immutable** — any structural change = new version
- Versions used by tenders are **never deleted**
- Superseded versions remain for audit and existing tenders

### 2. Tender STD Instance (per tender)

```text
Not Started → In Configuration → Validation Failed → Ready for Review
  → Procurement Review → Approved for Tender Creation → Bound to Tender
  → Published → Addendum Required → Superseded by Addendum
```

Hard rules:

- Bind only to **Active** STD versions
- Mandatory fields + blocking rules must pass before publication
- Published bundles are **hashed and immutable**
- Post-publication changes go through **addendum governance** with impact analysis

## Storage Architecture

**Hybrid relational + JSON + immutable blobs:**

| Layer | Holds |
|---|---|
| Relational records | Identity, lifecycle, hierarchy, approvals, usage, audit, joins |
| JSON schema columns | Form schemas, validation expressions, render metadata, domain extensions |
| Immutable blobs | Locked clause text, source extracts, rendered HTML/PDF/DOCX, publication bundles |
| Hashes | Source doc, clauses, template package, rendered output, addendum |
| Event log | Import, review, approval, activation, publication, addendum, supersession |

**~25 core persistent objects** are defined (e.g. `STDTemplateFamily`, `STDTemplateVersion`, `STDSection`, `STDClause`, `STDParameter`, `STDRule`, `STDFormSchema`, `TenderSTDInstance`, `TenderGeneratedBundle`, `TenderAddendumImpact`, etc.).

**Source traceability is non-negotiable** — every extractable object links back to official source with page refs, anchors, text hashes, and review status.

---

## IT-Specific Domain Extensions

On top of the universal engine, IT adds native objects such as:

- `ITRequirementGroup` / `ITRequirementItem` / conformance fields
- Functional, architectural, performance, service, technology specifications
- Implementation milestones, system inventory items, price schedule lines
- Software categories, license requirements, acceptance tests, support SLAs
- Contract appendix items

The **IT Requirements Composer** is the key PE-facing surface — it prevents technical requirements from becoming uncontrolled Word attachments. Requirements should be written as obligations ("The System must…"), with governance for brand/platform-specific requirements (e.g. NSSF's Dynamics 365 requirement needs justification + approval trail).

**Price model chain:**

```text
Requirement → Deliverable → Milestone → Inventory item → Price line
  → Supplier response → Evaluation → Contract obligation → Acceptance test
```

## Downstream Consumers (Integration Boundaries)

The STD Engine **does not replace** Tender Management, Supplier Portal, Evaluation, or Contract Management. It **feeds** them:

| Module | Consumes from STD Engine |
|---|---|
| Tender Management | Active versions, config schemas, preview/publication bundles, addenda |
| Supplier Portal | Bidder response schemas, forms, evidence, conformance matrix, price schedules |
| Evaluation | Published criteria, checklists, scoring, financial rules |
| Contract Management | Contract output schemas, carry-forward of tender/award data |
| Audit | Source trace, approvals, hashes, addendum history, alignment logs |

---

## Governance, Security, and Smoke Contracts

**Roles** span central STD administration, legal/procurement reviewers, template approvers, PE procurement officers/reviewers, bidders, evaluators, contract officers, and auditors.

**Approval gates** exist at template activation and tender publication. System administrators cannot bypass legal approvals.

**Smoke contracts** are mandatory acceptance checks — examples:

- Active template immutability
- Locked ITT/GCC protection
- Required TDS/SCC completion blocks publication
- Render determinism (same inputs → same hash)
- Evaluation alignment with published tender
- Addendum impact identification
- Contract carry-forward from tender/award data

## Implementation Sequence (Critical Constraint)

All three source documents strongly agree: **do not build the IT tender wizard first**.

```text
Meta-model / PRD
  → Domain model tables
  → Governance & state transitions
  → Roles/permissions & API boundaries
  → Import/export package contract
  → IT STD extraction matrix & seed package
  → Smoke contracts
  → Implementation pack
  → THEN tender configuration wizard
  → THEN supplier/evaluation/contract integration
```

Phased roadmap (Blueprint/PRD):

| Phase | Focus |
|---|---|
| 0–1 | Confirm design; build core foundation (families, versions, sections, rules, forms, render, lifecycle, smoke runner) |
| 2–3 | IT domain profile + digitize official IT STD (`KE-PPRA-IT-2022-04`) |
| 4 | IT tender configuration wizard (17 guided tabs) |
| 5–7 | Supplier response, evaluation, contract formation, NSSF round-trip calibration |

PRD v0.1 maps this into **5 releases**: Core Foundation → Tender Binding/Publication → Schema Consumers → Addendum/Contract → IT STD Seed/Calibration.

## Key Risks

1. Engine becomes IT-specific → keep IT in seed/extension schemas, not core code
2. Monolithic JSON becomes runtime store → normalized DB is mandatory
3. Locked text becomes editable → enforce at all layers
4. Evaluation drifts from published tender → generate/lock schemas from published instance only
5. Addenda handled manually → build impact model into core early
6. Incomplete source traceability → block activation without it
7. Non-deterministic rendering → render blocks + output hashes

---

## Overall Conclusion

KenTender is building an **Official Standard Tender Document Library** implemented as a **generalized STD Engine** — a legally defensible, auditable platform layer that turns PPRA STDs into governed, versioned, structured template systems. The Works PoC proved feasibility; production elevates it into full procurement infrastructure.

The **IT STD** is the first end-to-end proof that the generalized engine works in practice, validated against the **NSSF ERP tender** as a real-world calibration case. The immediate implementation work is **core engine foundation and domain modeling** — not UI wizard work — with strict enforcement of immutability, traceability, deterministic rendering, and addendum governance throughout.
