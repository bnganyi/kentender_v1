# KenTender Procuring Entity and Organisation Scope Model

**Status:** Approved MVP 1 structural baseline  
**Version:** 1.0  
**Date:** 6 August 2026  
**Applies to:** All KenTender modules

## 1. Purpose

This document defines how KenTender represents procuring entities, their internal organisation structures, data ownership and strategy flow-down.

KenTender is a national public e-procurement platform. It must support ministries, county governments, the Judiciary, commissions, state corporations, public universities and other public entities without assuming a fixed Ministry–State Department–Directorate structure.

This model replaces organisation-specific ownership fields with one generic and enforceable structure.

## 2. Structural principles

1. A **Procuring Entity** is the legal and operational procurement boundary.
2. An **Organisation Unit** is an internal unit of a Procuring Entity.
3. Organisation depth and unit labels are configurable by Procuring Entity.
4. Organisational reporting structure does not determine cross-entity strategy applicability.
5. Every owned business record has one Procuring Entity and may have one owning Organisation Unit.
6. Ownership, approval authority and read access are enforced server-side.
7. Downstream records preserve their originating ownership and versioned Strategy references.
8. Users do not maintain technical codes; stable references are generated by the system.

## 3. Core records

### 3.1 Procuring Entity

Represents the public body operating procurement processes in KenTender.

Minimum fields:

| Field | Requirement |
|---|---|
| `entity_reference` | Immutable, system-generated identity |
| `legal_name` | Official entity name |
| `short_name` | Optional display name |
| `entity_type` | Configured type such as Ministry, County Government, Judiciary, Commission, State Corporation or Public University |
| `external_reference` | Optional authoritative government or finance-system identifier |
| `status` | Active or Inactive |
| `effective_from` / `effective_to` | Effective dates |

An optional oversight or reporting relationship between Procuring Entities may be stored for reporting. It shall not grant data access, transfer ownership or create automatic strategy inheritance.

### 3.2 Organisation Unit Type

Provides the display vocabulary used by each Procuring Entity.

Examples include:

- State Department, Directorate, Division and Facility;
- County Department, Directorate, Sub-county and Facility;
- Court, Registry, Directorate and Court Station;
- Faculty, Campus and Department;
- Branch, Programme Office and Project Unit.

Unit types are configuration, not schema columns.

### 3.3 Organisation Unit

Represents an internal ownership or operating unit.

Minimum fields:

| Field | Requirement |
|---|---|
| `org_unit_reference` | Immutable, system-generated identity |
| `procuring_entity` | Required; the owning Procuring Entity |
| `parent_org_unit` | Optional; must belong to the same Procuring Entity |
| `unit_type` | Required configured Organisation Unit Type |
| `unit_name` | Required display name |
| `status` | Active or Inactive |
| `effective_from` / `effective_to` | Effective dates |

The hierarchy uses a primary parent relationship. It may be one level or several levels deep. No module may assume a specific depth.

### 3.4 User Scope Assignment

Assigns a role to a user within a Procuring Entity or Organisation Unit.

Minimum fields:

| Field | Requirement |
|---|---|
| `user` | Required |
| `role` | Required functional role |
| `procuring_entity` | Required |
| `organisation_unit` | Optional for entity-wide roles |
| `include_descendants` | Whether the assignment covers descendant units |
| `effective_from` / `effective_to` | Effective dates |

Approval authority and record visibility shall be resolved from active scope assignments. UI filtering alone is not a security control.

## 4. Business-record ownership contract

All Strategy, Budget, Demand, Planning, Tender, Contract, Stores, Assets and Disposal records that carry ownership shall use:

| Field | Meaning |
|---|---|
| `procuring_entity` | Required legal procurement boundary |
| `owner_org_unit` | Optional internal owner; blank only for entity-owned records |
| `delivery_org_unit` | Optional unit receiving or delivering the result |

The following organisation-specific fields shall not be introduced:

- `ministry`
- `state_department`
- `owner_state_department`
- `directorate`
- `owner_directorate`
- `county_department`

Those concepts are represented as Organisation Units with configured unit types.

Rules:

1. `owner_org_unit`, when present, must belong to `procuring_entity`.
2. `delivery_org_unit`, when present, must belong to the same Procuring Entity unless an authorised cross-entity arrangement is recorded.
3. Entity-owned headers may have no `owner_org_unit`; their lines or children may have unit ownership.
4. Ownership transfer requires an explicit audited action. It is never inferred from a user editing the record.
5. Downstream records inherit ownership unless an authorised transfer is recorded.

## 5. Strategy ownership and flow-down

### 5.1 Plan ownership

A Strategic Plan is owned by:

- a Procuring Entity, with `owner_org_unit` blank; or
- one Organisation Unit within that Procuring Entity.

Each logical plan has one stable identity and one or more immutable versions. Only one Active version of the same logical plan may exist at a time. Separate plans may overlap where they have different purposes, types or ownership scopes.

### 5.2 Internal applicability

A `Strategy Scope Assignment` links a Plan, objective, outcome, target or value commitment to the Organisation Units allowed or required to use it.

Minimum assignment data:

| Field | Requirement |
|---|---|
| Strategy item and version | Required immutable reference |
| Procuring Entity | Required |
| Organisation Unit | Optional for entity-wide applicability |
| Include descendants | Yes or No |
| Applicability | Required, Recommended or Available |
| Effective dates | Required |

Flow-down is therefore explicit and auditable. Strategy items are not copied into every descendant unit.

### 5.3 Cross-entity frameworks

A national, sector or whole-of-government strategy shall be represented as an external or centrally managed `Strategic Framework`, not as the organisational parent of another Procuring Entity.

A Procuring Entity may adopt or align to that framework through an explicit framework assignment. The local Plan retains its own ownership, approvals and targets. This supports, for example, a national health framework influencing a county health plan without making the county organisationally subordinate to a Ministry.

For MVP 1, KenTender needs to store the framework reference, issuer, version, applicability and local adoption link. Full external-framework authoring is not required.

### 5.4 Downstream Strategy references

Budget and Demand records may reference only Strategy items that are:

- owned by their Procuring Entity; or
- assigned to their permitted organisational scope; or
- adopted from an authorised external Strategic Framework.

Downstream records store the immutable Strategy item version. A later Strategy revision shall not silently change historical Budget, Demand or Tender records.

## 6. Access and segregation rules

1. Unit-scoped users may maintain records owned by their assigned unit and permitted descendants.
2. Unit-scoped users may not read protected Draft data owned by unrelated units.
3. Entity-wide reviewers may view and act across assigned units according to their role.
4. Cross-entity access requires a separate explicit assignment.
5. A user belonging to one Procuring Entity receives no access to another entity by default.
6. The creator of a record does not automatically gain approval authority.
7. Every access-sensitive API validates entity, unit, role and record state.

## 7. UI requirements

1. Display the configured unit labels and names; do not display fixed fields for State Department or Directorate.
2. Show a compact ownership path such as `Ministry of Health / State Department for Medical Services / Directorate of Digital Health and Policy`.
3. Use searchable organisation selectors restricted to the user's permitted scope.
4. Hide generated technical references from routine data-entry screens.
5. Entity-level views may aggregate authorised units while retaining visible ownership.
6. Strategy views distinguish `Owned by`, `Applicable to` and `Aligned with`.

## 8. Clean MVP implementation change

Existing MVP data is disposable. Implement the model as a clean structural replacement rather than retaining parallel legacy fields.

Required change:

1. Create or rebuild Procuring Entity, Organisation Unit Type, Organisation Unit, User Scope Assignment and Strategy Scope Assignment structures.
2. Replace organisation-specific ownership fields with `procuring_entity`, `owner_org_unit` and optional `delivery_org_unit`.
3. Rebuild Strategy and Budget fixtures against the new identities.
4. Remove code paths, filters and tests that assume Ministry-specific levels.
5. Do not maintain dual-write compatibility with disposable MVP data.
6. Retain only reusable non-organisational logic, components and audit patterns.

## 9. Seed-data proof

The canonical fixture must include structurally different Procuring Entities:

- a detailed Ministry of Health hierarchy; and
- a minimal County Government of Kisumu hierarchy.

The fixture shall prove:

- different hierarchy depths and unit labels;
- unit-level data ownership;
- entity-wide consolidated access;
- cross-unit denial within one entity;
- cross-entity denial;
- explicit Strategy applicability without copied Strategy records.

The Ministry remains the main end-to-end procurement story. The county fixture exists to prove architectural neutrality and does not need an equally deep transaction history.

## 10. Acceptance criteria

The structural change is complete when:

1. No business schema or permission rule requires a Ministry, State Department, Directorate or County Department field.
2. A new Procuring Entity can configure its own unit types and hierarchy without code changes.
3. Every owned record resolves to exactly one Procuring Entity.
4. Every owning unit belongs to that Procuring Entity.
5. Strategy scope assignments control valid downstream references.
6. Users cannot access another unit or entity without explicit scope.
7. Ministry and county fixtures seed idempotently and pass the same generic verification rules.
8. Existing module screens display the correct configured ownership path.

## 11. Out of scope for MVP 1

- synchronising the national government organisation register;
- modelling every dotted-line or matrix reporting relationship;
- full authoring of external national or sector frameworks;
- cross-entity joint procurement governance;
- automatic organisational restructuring and historical record migration.

These may be added without changing the core Procuring Entity and Organisation Unit ownership contract.
