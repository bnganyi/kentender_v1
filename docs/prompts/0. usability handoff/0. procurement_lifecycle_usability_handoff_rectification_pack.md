## 1. Executive Summary

The completed modules are technically meaningful but currently feel like separate verticals. This creates a product adoption risk.

The first modules are relatively usable because their business logic is naturally simple:

```text
Strategy defines priorities.
Budget funds priorities.
Demand requests a funded need.
```

The disconnect begins from Procurement Planning onward because the system starts exposing increasingly technical concepts:

```text
Procurement Package
STD Template
STD Instance
Tender STD Binding
Bundle
DSM
DOM
DEM
DCM
Publication Snapshot
Derived Outputs
Readiness Models
```

These concepts are legally necessary, but they should not be the primary user-facing mental model for ordinary procurement users.

This rectification pack establishes a **Procurement Lifecycle Spine** that connects all completed modules into one coherent journey, centered on the preserved WORKS scenario:

```text
District Hospital Renovation Works
```

The correction strategy is:

1. preserve existing module investments;
2. add a cross-module journey view;
3. make module handoffs visible as business artifacts;
4. simplify primary UI terminology;
5. move technical/legal details into Legal Basis, Evidence, Advanced, and Audit views;
6. normalize seed data around one WORKS master scenario;
7. add usability smoke tests alongside legal smoke tests;
8. give Cursor explicit implementation instructions so no critical UX or handoff behavior is guessed.

This pack does not replace the completed module documentation. It overlays a unifying product spine and defines exact patch instructions.

## 2. Problem Statement

The system is legally safer than before, but the user journey has become fragmented and intimidating.

### 2.1 Current User Experience Problem

Users currently experience the system as separate modules:

```text
Strategy workspace
Budget workspace
Demand workspace
Procurement Planning workspace
STD Admin workspace
Tender Management workspace
```

Each module has its own objects, statuses, workspaces, seeds, and technical concepts. This is acceptable for developers and auditors, but not for procurement users who need to understand:

```text
Where is this procurement item now?
What happened before?
What is blocking it?
What do I need to do next?
What evidence supports this step?
Where does it go after this?
```

### 2.2 Main Symptoms

| Symptom | Cause | Risk |
|---|---|---|
| Later modules feel isolated. | Handoffs are hidden in hooks, references, or backend relationships. | Users lose trust and context. |
| STD/Tender flow feels too technical. | Internal model names leak into primary UI. | Procurement users become intimidated. |
| WORKS story appears late. | Seed data was not designed end-to-end from Strategy onward. | Test/UAT story feels inconsistent. |
| Tender Management feels overloaded. | It exposes lifecycle, STD, publication, supplier, audit, handoff, and legal concepts at once. | Users may avoid or misuse the system. |
| Legal controls are strong but hard to understand. | Controls are implemented as technical readiness objects rather than visible business gates. | Compliance appears like friction rather than guidance. |

### 2.3 Corrective Thesis

The system should be strict underneath and simple on top.

```text
Backend: rigorous, stateful, auditable, STD-native, legally constrained.
Frontend: guided, role-based, next-action-oriented, business-readable.
```

## 4. Rectification Principles

| Principle ID | Principle | Meaning |
|---|---|---|
| UX-PRIN-001 | One procurement item, one visible journey. | Users should trace an item from strategy to tender without opening six disconnected modules. |
| UX-PRIN-002 | Handoffs must be visible. | A module handoff must appear as a business artifact, not only as a backend hook or hidden reference. |
| UX-PRIN-003 | Hide complexity without removing controls. | Technical objects remain available in Legal Basis, Evidence, Advanced, and Audit areas. |
| UX-PRIN-004 | Use business-readable terminology first. | Show “Supplier submission checklist ready” before “DSM ready.” |
| UX-PRIN-005 | Preserve strict source-of-truth boundaries. | Usability changes must not weaken legal control. |
| UX-PRIN-006 | Use one WORKS master scenario. | Seeds, demos, UAT, and tests should tell one story from Strategy to Tender. |
| UX-PRIN-007 | Next action beats object navigation. | Default screens should answer “what should I do now?” |
| UX-PRIN-008 | Audit remains deep. | Simplified UI must still allow auditors to inspect the full technical and legal chain. |
| UX-PRIN-009 | No raw DocType-first user journey. | Workspaces and journeys should wrap DocTypes into business flows. |
| UX-PRIN-010 | Cross-module status must be standardized. | A consistent lifecycle status language must appear across modules. |

## 7. Handoff Card Standard

Every module handoff must be represented by a visible handoff card.

### 7.1 Handoff Card Purpose

A handoff card tells the user:

1. what was completed;
2. who completed or approved it;
3. what is locked;
4. what is passed forward;
5. what the next module/user must do;
6. what evidence supports the handoff.

### 7.2 Standard Handoff Card Fields

| Field | Required | Description |
|---|---:|---|
| Handoff title | Yes | Business-readable name. |
| Handoff code | Yes | Stable business identifier. |
| Source module | Yes | Module that produced the handoff. |
| Target module | Yes | Module expected to consume the handoff. |
| Source object code | Yes | Business object that produced handoff. |
| Target object code | Conditional | Created or expected downstream object. |
| Status | Yes | Draft, Ready, Handed Off, Consumed, Blocked, Superseded. |
| Approved / generated by | Yes | Actor/system. |
| Approved / generated at | Yes | Timestamp with timezone. |
| What is locked | Yes | Values no longer editable through ordinary flow. |
| What is passed forward | Yes | Values consumed by next module. |
| Next action | Yes | Business-readable action. |
| Blockers | Conditional | Blocking issues. |
| Evidence links | Yes | Audit/evidence references. |
| Technical references | Conditional | For advanced/audit view only. |

### 7.3 Handoff Card States

```text
Draft
Ready
Handed Off
Consumed
Blocked
Returned
Superseded
Cancelled
Audit Only
```

## 9. Procurement Journey View

### 9.1 Purpose

The Procurement Journey View is the main usability correction. It gives users one place to understand where a procurement item is across modules.

It must answer:

```text
Where is this procurement item in the lifecycle?
What happened before?
What is blocking it?
Who owns the next action?
What evidence exists?
```

### 9.2 Recommended Route

```text
/desk/procurement-journey
/desk/procurement-journey/<journey_code>
```

Alternative Frappe route naming may be used, but the user-facing name must be:

```text
Procurement Journey
```

### 9.3 Journey Object

Introduce a lightweight cross-module object or view model:

```text
Procurement Journey
```

This may be a DocType, query-backed page, or materialized view. The important rule is that it must not become the legal source of truth. It is a navigation and status aggregation layer.

9. Demo/UAT views must default to this WORKS story.

### 15.5 Desktop information architecture (Procurement shell)

### Goal (IA)

End users should experience **one public-sector procurement lifecycle** inside a **single Desk shell (“Procurement”)**, not disconnected top-level products. **Procurement Home** remains the **canonical entry point** for ordinary procurement work.

### Two-layer rule (non-negotiable)

| Layer | What it is | Rule |
|---|---|---|
| **Technical / code** | Separate Frappe apps and services (`kentender_strategy`, `kentender_budget`, `kentender_procurement`, …) | **Keep** strong boundaries for permissions, tests, governance, and data ownership. |
| **User-facing Desk IA** | App switcher, module tiles, workspace sidebars, labels | **Do not** present **Strategy** and **Budget** as independent “front-door” apps for **general procurement users**. Surface them as **lifecycle capabilities** inside **Procurement**. |

### Procurement shell — lifecycle navigation (target)

Under **Procurement**, primary navigation should read as **lifecycle-first** (journey spine), for example:

1. **Procurement Home** (canonical landing for lifecycle work)
2. **Procurement Journeys**
3. **My Work** (queue / next-action entry)
4. **Strategy Alignment** (user-facing name for strategy-aligned work — not a standalone “Strategy app” tile for general users)
5. **Budget & Funding** (user-facing name for budget-line / funding context — not a standalone “Budget app” tile for general users)
6. **Demand Intake & Approval**
7. **Procurement Planning**
8. **Tender Document Readiness** (user-facing bridge for STD-bound tender document readiness; technical STD governance may remain under **Configuration**)
9. **Tender Management**
10. **Bid Opening** — placeholder/disabled until implemented, unless hidden by feature flag
11. **Evaluation & Award** — placeholder/disabled until implemented
12. **Contract Management** — placeholder/disabled until implemented
13. **Supplier Management**
14. **Evidence & Audit**
15. **Configuration** (specialist / admin-oriented), including at minimum: **Official STD Library**, **Procurement Templates**, **Risk / KPI / Decision Criteria / Vendor Management** profiles (as today’s planning configuration surfaces)

### Role-based presentation

- **General procurement users:** Desk should emphasise **Procurement** only; avoid a three-tile mental model (“Strategy app”, “Budget app”, “Procurement app”).
- **Specialist / admin users:** Full **Strategy** and **Budget** management workspaces may remain available, but should be reached via **Configuration / Administration / Governance** (or equivalent grouped entry) and **role gates**—not as the default path for requisitioners, planners, or officers.
