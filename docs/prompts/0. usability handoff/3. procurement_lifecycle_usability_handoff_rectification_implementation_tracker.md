## 0.1 Document Precedence

If the rectification documents conflict, Cursor must apply the following precedence order:

| Rank | Document | Controls |
|---:|---|---|
| 1 | Procurement Lifecycle WORKS Master Seed Data Specification | Master seed codes, record values, dates, amounts, statuses, handoff JSON, checkpoint semantics, validation output, negative fixtures. |
| 2 | Procurement Lifecycle Usability & Handoff Rectification — Implementation Tracker | Execution rows, gates, evidence requirements, review controls, no-go conditions. |
| 3 | Procurement Lifecycle Usability & Handoff Rectification — Cursor Implementation Pack | Technical implementation structure, services, APIs, UI components, test selectors. |
| 4 | Procurement Lifecycle Usability & Handoff Rectification Pack | Product intent, lifecycle spine, handoff model, usability direction. |
| 5 | Original module documents | Module-specific source behavior, except where rectification explicitly overlays usability/navigation behavior. |

For **Tender Management legal behavior**, the **Tender Management v2 Cursor Implementation Pack** and **Tender Management v2 Smoke Contract** remain controlling. This rectification tracker controls lifecycle usability, handoff visibility, cross-module journey navigation, and WORKS master seed alignment. It must not weaken TM2 legal controls.

## 0.2 Seed Checkpoint Rule

The base implementation checkpoint is:

```text
TENDER_PUBLISHED
```

At this checkpoint, the seed ends with:

```text
Tender Published
Addendum 01 Issued
Current publication snapshot V2
Submission window still open
Opening not yet conducted
```

The following handoff cards are required for the base checkpoint:

```text
STRATREF-MOH-2026-001
BUDCONF-MOH-2026-001
DEMAPP-MOH-2026-001
PLANINCL-MOH-2026-001
PKGREL-MOH-2026-001
STDREADY-TND-MOH-2026-001
PUBCERT-TND-MOH-2026-001
```

The optional extended checkpoint is:

```text
OPENING_READY
```

Only under `OPENING_READY`, or where existing TM2 fixtures safely provide closing/opening readiness records, the following are required:

```text
CLOSECERT-TND-MOH-2026-001
OPENREADY-TND-MOH-2026-001
```

Cursor must not invent closing or opening readiness records for the base `TENDER_PUBLISHED` checkpoint.

## 0.3 Source Record Mutation Rule

The rectification implementation may create or link master seed records. It must not silently overwrite existing source-module records.

If an existing source record conflicts with the WORKS Master Seed Data Specification, Cursor must stop and report the conflict unless both conditions are true:

1. `reset=True` was explicitly requested; and
2. the conflicting record is marked `is_master_seed=true` or its business code is explicitly listed in the seed specification.

Conflict report format:

```text
Conflict:
Expected object:
Existing repository object:
Mismatch:
Options:
Recommended option:
Requires human approval: Yes/No
```

## 0.4 Desktop information architecture (Procurement shell)

These rules implement the **lifecycle-first Desk** direction (see also rectification pack **§15.5**):

1. **Technical reality:** `kentender_strategy`, `kentender_budget`, and `kentender_procurement` remain separate apps for code, permissions, and data ownership.
2. **Ordinary user perception:** Strategy and Budget are **not** independent top-level Desk “products”. They appear as **Strategy Alignment** and **Budget & Funding** **inside** the **Procurement** workspace / sidebar journey spine.
3. **Canonical entry:** **Procurement Home** is the default front door for lifecycle work (aligned with §15 of the rectification pack).
4. **Specialists:** Full strategy/budget admin surfaces stay available **only** behind **Configuration / Administration / Governance** (or equivalent) and **appropriate roles**.
5. **Implementation evidence:** navigation changes require **screenshots or Playwright** per role, plus file paths for `Workspace`, `Desktop Icon`, `Module Def`, or `hooks.py` patches—see **G0-010–G0-017** and **§18.0**.

## 1. Tracker Purpose

This tracker controls implementation of the Procurement Lifecycle Usability and Handoff Rectification work.

The rectification must solve a product problem without creating a legal architecture problem. It must make the procurement journey usable and connected while preserving module ownership and legal source-of-truth boundaries.

Cursor must use this tracker to implement and report progress. Each row requires:

1. implementation evidence;
2. test evidence;
3. reviewer notes where needed;
4. blocker status;
5. explicit acceptance decision.

This tracker is not optional project management decoration. It is an execution gate.

## 2. Status Values

Use only these status values.

| Status | Meaning |
|---|---|
| Not Started | No work begun. |
| In Progress | Work started but not complete. |
| Blocked | Cannot proceed without decision or dependency. |
| Implemented | Code/config/UI completed but not fully verified. |
| Evidence Submitted | Implementation and test evidence attached. |
| Accepted | Reviewed and accepted. |
| Rework Required | Reviewer found gap. |
| Deferred | Explicitly deferred with reason and owner approval. |
| Not Applicable | Confirmed not applicable to repository. |

A row is not complete until status is **Accepted**.

### 4.2 How parent rows (§5–§17) relate to low-level tickets (§18)

Sections **5–17** stay the **phase / parent** checklist for sign-off. **Section 18** is the **atomic ticket backlog** (one PR-sized slice per row). A parent row (for example **R3-011**) is not **Accepted** until every child ticket listing that **Parent** id is **Evidence Submitted** or **Not Applicable**, and required regression proofs exist.

**Child ticket id convention:** `LV-<PARENT>-##` (example `LV-R3-011-02`). Do not renumber closed tickets; append new suffixes if work splits further.

**Column contract (§18 tables):**

| Column | Meaning |
|---|---|
| **Ticket** | Atomic id (`LV-…`). |
| **Parent** | Existing row id in this document (`G0-001`, `R1-005`, …). |
| **App** | Owning Frappe app or `cross-app` / `bench-root` for glue. |
| **Stream** | `data-model` · `backend-svc` · `api` · `desk-ui` · `seed` · `test` · `docs` · `ops`. |
| **Deliverable** | Single mergeable outcome. |
| **Depends** | Other `LV-…` ids and/or `G0 accepted`, `R1-003`, etc. |
| **Primary evidence** | Expected proof type (test path, `bench execute` output, Playwright selector, screenshot). |
| **Status** | Same vocabulary as §2. |
