**STD Library, Configuration, and Tender Document Readiness — UX and Workflow Specification**

**1\. Purpose**

This document defines the user experience, workflow, governance model, and user-friendly data model for **STD Library, Configuration, and Tender Document Readiness** in KenTender.

STD means **Standard Tender Document**.

This capability sits between **Procurement Planning** and **Tender Management**.

Its purpose is to make sure that every tender uses the correct approved tender document template, the correct supplier submission requirements, the correct evaluation structure, and the correct contract carry-forward terms before the tender is published.

The module must protect the legal quality of the tender process while keeping the user experience simple.

**2\. Why This Comes Before Tender Management**

Tender Management cannot safely publish a tender until the system knows:

which standard tender document applies;

which document version is approved;

which procurement category and method the document supports;

which supplier forms are required;

which mandatory supplier documents are required;

which evaluation sections are expected;

which contract terms carry forward;

which tender-specific fields must be completed;

which changes after publication require an addendum.

Therefore, STD configuration and Tender Document Readiness should be designed before the broader Tender Management UI.

Tender Management publishes and manages the tender.

STD Readiness determines whether the tender document package is valid enough to publish.

**3\. Core Design Principle**

The system should separate **official STD governance** from **tender-specific document setup**.

Do not make ordinary Tender Managers manage the entire STD library while preparing one tender.

Use two layers:

| **Layer** | **Owner** | **Purpose** |
| --- | --- | --- |
| STD Library & Configuration | STD Admin / Procurement Governance | Maintain official templates, versions, rules, forms, approvals, and applicability |
| Tender Document Readiness | Tender Manager / Procurement Officer | Confirm the correct STD is selected for a specific tender and complete tender-specific document setup |

Normal users should see:

Tender document selected

Supplier forms ready

Required documents ready

Evaluation structure ready

Contract terms ready

Publication document package ready

Normal users should not see technical labels such as:

template payload

schema object

JSON rules

internal bundle object

DSM

DOM

DEM

DCM

source object

target object

unless they open Technical Details with permission.

**4\. Lifecycle Placement**

The lifecycle position is:

Procurement Planning  
→ STD / Tender Document Readiness  
→ Tender Management  
→ Supplier Participation and Bid Submission  
→ Tender Closing  
→ Bid Opening  
→ Evaluation and Award  
→ Contract Management

Planning passes forward:

released package;

procurement category;

procurement method;

estimated value;

package lines/lots;

scope;

budget reference;

required standard document category;

attachments and specifications;

release approval evidence.

STD Readiness produces:

selected STD version;

tender-specific document setup;

supplier submission checklist;

mandatory document requirements;

evaluation structure;

contract carry-forward terms;

readiness result;

document snapshot for publication;

evidence.

Tender Management then uses this output to publish the tender.

**5\. What This Capability Does**

This capability performs two major jobs.

**5.1 STD Library and Configuration**

This is the governance side.

It manages the official library of approved standard tender documents.

It includes:

creating STD records;

uploading or configuring STD templates;

defining applicability rules;

versioning STDs;

submitting STD versions for approval;

activating approved STD versions;

retiring old versions;

configuring required supplier forms;

configuring mandatory supplier documents;

configuring evaluation sections;

configuring contract carry-forward terms;

recording approvals and evidence.

**5.2 Tender Document Readiness**

This is the tender-specific side.

It confirms the correct document setup for one tender.

It includes:

receiving the released planning package;

selecting or confirming the correct STD;

checking whether the STD matches category, method, value, and entity;

completing tender-specific fields;

confirming supplier submission requirements;

confirming evaluation structure;

confirming contract terms;

checking required attachments/specifications;

running readiness checks;

submitting for document readiness review where required;

approving the tender document package for publication;

creating a publication-ready document snapshot.

**6\. What This Capability Does Not Do**

It does not:

approve demand;

create procurement plans;

create procurement packages;

publish tenders;

receive bids;

open bids;

evaluate bids;

award contracts;

manage contract execution.

It also must not silently edit a released Planning baseline.

If the released package is materially wrong, the issue must be returned through the proper correction path.

**10\. STD Library Workflow**

**10.1 Standard Flow**

Create Draft STD Version

Configure Applicability

Configure Supplier Requirements

Configure Evaluation Setup

Configure Contract Terms

Submit for Review

Reviewer Checks Version

Approver Approves Version

Activate Version

Version Becomes Available for Tender Readiness

**10.2 State Model**

Use simple states:

| **State** | **Meaning** |
| --- | --- |
| Draft | Version is being configured |
| Submitted | Version is awaiting review |
| Returned | Version needs correction |
| Approved | Version is approved but not yet active |
| Active | Version can be used for tenders |
| Retired | Version is no longer available for new tenders |
| Superseded | Version was replaced by a newer version |
| Cancelled | Draft/version stopped before activation |

**10.3 Transition Rules**

| **Transition** | **Guard** |
| --- | --- |
| Draft → Submitted | Required configuration complete |
| Submitted → Returned | Reviewer gives reason |
| Submitted → Approved | Reviewer/authority approves |
| Approved → Active | No conflicting active version for same applicability |
| Active → Retired | Authorized user and reason required |
| Active → Superseded | New approved version replaces it |
| Any non-final → Cancelled | Authorized user and reason required |

**10.4 Approval Roles**

| **Role** | **Responsibility** |
| --- | --- |
| STD Admin | Creates and maintains draft STD configuration |
| STD Reviewer | Reviews completeness and correctness |
| Procurement Governance Authority | Approves and activates official versions |
| System | Enforces required fields, version locking, evidence, and active-version rules |
| Auditor | Reviews approval and version history |

| **Role** | **Main Responsibility** |
| --- | --- |

| Evaluation Lead | Receives evaluation setup later |

| System Administrator | Technical configuration only |

**16.1 Permission Rules**

Only governance users can approve or activate official STD versions.

Tender Managers can select or confirm an active STD for a tender.

Tender Managers cannot edit the official STD library during tender setup.

Any override from recommended STD must require justification and review.

Supplier users cannot access internal STD configuration.

After publication snapshot is locked, changes must follow governed correction/addendum rules.

**18\. Override and Exception Handling**

Sometimes a Tender Manager may need to choose a different STD or modify a supplier requirement.

This must be controlled.

**18.1 STD Override**

If the user chooses a non-recommended STD:

require justification;

show mismatch reason;

require review approval;

record evidence.

Example:

You selected a different standard tender document from the recommended one.

Reason required before continuing.

**18.2 Requirement Override**

If the user changes a mandatory supplier requirement:

require justification;

show legal/governance warning;

require review if configured.

Example:

This requirement is mandatory under the selected standard tender document.

Removing it requires approval.

**18.3 Post-Snapshot Correction**

After the publication snapshot is locked:

ordinary edits are blocked;

correction requires authorized reopen, supersession, or addendum path;

evidence must preserve old and new snapshots.

**19\. Relationship With Tender Management**

Tender Management should receive a clean output from STD Readiness.

Tender Management should not have to reconfigure the official STD library.

Tender Management should use:

selected STD version;

supplier checklist;

mandatory document requirements;

evaluation setup;

contract terms;

tender-specific values;

attachments/specifications;

publication snapshot;

readiness approval.

Tender Management may still manage:

publication approval;

public tender notice;

publication date;

clarifications;

addenda;

submission deadline;

tender status;

closing and opening handoff.

Boundary rule:

STD Readiness prepares the legally valid document package.

Tender Management publishes and manages the tender process.

**22\. No-Go Conditions**

The design fails if:

Tender Managers must edit the official STD library during tender setup;

users can publish a tender without an approved STD version;

users can select an incompatible STD without justification and review;

supplier submission requirements are unclear;

evaluation setup is missing when the tender reaches evaluation;

contract carry-forward terms are lost;

the publication snapshot is not locked;

post-publication changes can be made silently;

technical objects dominate the ordinary UI;

suppliers can see internal configuration or audit data;

auditors cannot tell which STD version was used for a published tender.

**23\. Final Product Rule**

STD Library and Tender Document Readiness succeeds if:

governance users can manage official standard tender documents;

only approved active STD versions can be used for new tenders;

Tender Managers can easily confirm the correct STD for a tender;

supplier requirements are clearly generated;

evaluation and contract carry-forward structures are prepared;

readiness checks explain what is missing;

approval and evidence are captured;

Tender Management receives a clean, locked document package for publication.

The UX should make the document setup feel simple, while the system silently preserves the governance, versioning, and audit controls required for a legally defensible tender process.
