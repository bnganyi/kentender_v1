**STD Recommended UI Structure**

**1\. Split the UI into three layers**

STD Library  
→ STD Version Configurator  
→ Tender-Specific Readiness View

**Layer 1 — STD Library**

This is the catalogue.

It shows:

| **Item** | **Purpose** |
| --- | --- |
| STD title | Name of the standard document |
| Category | Works, Goods, Services, Consultancy |
| Method | Open Tender, RFQ, Restricted Tender, etc. |
| Active version | Current approved version |
| Status | Draft, Submitted, Active, Retired |
| Used by tenders | Where this STD version is already in use |

This page should be simple.

Example:

Standard Tender Document for Building Works  
Works · Open Tender · April 2022 · Active  
\[Open\] \[Configure\] \[View Usage\]

**Layer 2 — STD Version Configurator**

This is where JSON complexity is managed.

Do **not** show one giant JSON editor.

Use a section-based configurator:

Overview  
Applicability  
Tender Fields  
Supplier Requirements  
Forms & Attachments  
Evaluation Setup  
Contract Terms  
Rules & Validations  
Preview  
Approval  
Evidence  
Technical JSON

The important one is **Technical JSON** should be permission-controlled and hidden by default.

**Recommended Configurator Tabs**

**1\. Overview**

Basic STD identity.

Fields:

STD Title  
Document Family  
Category  
Procurement Method  
Version Label  
Effective Date  
Owner  
Status  
Change Summary

This tab is normal form data.

**2\. Applicability**

This determines when the STD can be used.

Fields:

Category  
Method  
Value Range  
Entity Scope  
Funding Source  
Contract Type  
Works/Goods/Services Subtype  
Lot Support

Example:

Applies to:  
Works · Open Tender · Building Works · All Entities · KES above threshold

This should drive recommendation logic during Tender Document Readiness.

**3\. Tender Fields**

This is where variable tender-specific fields are defined.

Examples:

Tender title  
Tender reference  
Submission deadline  
Opening date  
Bid validity period  
Bid security amount  
Site visit date  
Completion period  
Clarification deadline  
Contact person

UI pattern:

Field Builder

Each field has:

| **Field** | **Meaning** |
| --- | --- |
| Label | What user sees |
| Field Type | Text, number, date, money, select, file, table |
| Required | Yes/No |
| Default Value | Optional |
| Help Text | Guidance |
| Validation | Date rule, amount rule, required rule |
| Visibility Rule | When field appears |

This lets JSON vary, but the UI remains controlled.

**4\. Supplier Requirements**

This is one of the most important sections.

It defines what suppliers must submit.

Examples:

Form of Tender  
Bill of Quantities  
Bid Security  
Tax Compliance Certificate  
Company Registration  
Technical Proposal  
Financial Proposal  
Signed Declarations  
JV Agreement  
Power of Attorney  
Site Visit Certificate

UI pattern:

Requirement Matrix

Columns:

| **Requirement** | **Type** | **Mandatory** | **Applies To** | **Blocks Submission** | **Used In Evaluation** |
| --- | --- | --- | --- | --- | --- |

This is much better than a JSON editor.

**5\. Forms & Attachments**

This defines supplier-facing forms and tender documents.

Examples:

Form of Tender  
Price Schedule  
BOQ Template  
Confidential Business Questionnaire  
Declaration Forms  
Technical Schedules

UI pattern:

Document/Form List

Each form should have:

Form name  
Purpose  
Supplier must complete?  
Upload required?  
Generated by system?  
Template attached?  
Applies to lot?

**6\. Evaluation Setup**

This prepares the evaluation structure.

It should not evaluate bids yet. It only configures what Evaluation will later receive.

UI pattern:

Evaluation Sections

Example:

Preliminary Evaluation  
Technical Evaluation  
Financial Evaluation  
Post-Qualification  
Award Recommendation

Each section has:

| **Field** | **Meaning** |
| --- | --- |
| Section Name | Preliminary, Technical, Financial |
| Evaluation Type | Pass/Fail or Scored |
| Required Documents | Documents used |
| Minimum Score | If applicable |
| Carries Forward | Sent to Evaluation module |

**7\. Contract Terms**

This defines what flows into Contract Management after award.

Examples:

Performance security  
Advance payment  
Retention  
Liquidated damages  
Warranty / defects liability period  
Completion period  
Payment terms  
Insurance requirements

UI pattern:

Contract Terms Table

Each term has:

Term name  
Default value  
Required?  
Editable per tender?  
Approval required if changed?  
Carries to contract?

**8\. Rules & Validations**

This is where JSON complexity lives, but the UI should expose it as plain rules.

Use a rule builder.

Examples:

If bid security is required, supplier must upload bid security document.  
If site visit is mandatory, supplier must upload site visit certificate.  
If procurement method is Open Tender, publication period must be at least X days.  
If lotting is enabled, supplier must submit price schedule per lot.  
If JV supplier is selected, JV agreement is mandatory.

UI pattern:

When \[condition\] then \[requirement/action\]

Example:

When Supplier Type is Joint Venture  
Then Require Joint Venture Agreement

Avoid exposing raw expressions unless in advanced mode.

**9\. Preview**

This is critical.

The user must be able to preview what the STD will produce.

Preview modes:

Tender Manager View  
Supplier Submission Checklist  
Evaluation Setup Preview  
Contract Carry-Forward Preview  
Publication Readiness Preview

This catches configuration mistakes early.

**10\. Approval**

STD versions need governance.

Actions:

Submit for Review  
Return for Correction  
Approve Version  
Activate Version  
Retire Version  
Supersede Version

The JSON must be locked once the version is active.

No silent edits to active STD versions.

**11\. Technical JSON**

This should exist, but behind permissions.

Use it for:

View JSON  
Validate JSON  
Export JSON  
Import JSON  
Compare JSON Versions

Only admin/technical users should access it.

Normal STD admins should not need it.

**Core Design Pattern**

Use this pattern:

Business UI section  
→ writes to structured JSON  
→ validates against schema  
→ renders preview  
→ locks approved version

So instead of users editing JSON directly, they configure business objects.

Example:

User configures:

Requirement: Bid Security  
Mandatory: Yes  
Blocks Submission: Yes  
Applies To: All Suppliers

System stores JSON:

{  
"name": "bid_security",  
"label": "Bid Security",  
"mandatory": true,  
"blocks_submission": true,  
"applies_to": "all_suppliers"  
}

The user should never need to see that unless they open Technical JSON.

**Recommended JSON Architecture**

Even though STDs vary, keep the top-level JSON structure stable.

Example:

std_config  
├── metadata  
├── applicability  
├── tender_fields  
├── supplier_requirements  
├── forms_and_attachments  
├── evaluation_setup  
├── contract_terms  
├── rules  
├── validations  
├── ui_schema  
└── output_mappings

This is the key. The **contents** can vary, but the **sections** should be predictable.

That gives the UI a stable structure.

**Most Important Rule**

Do not build one custom UI for each STD.

Build one configurable STD composer that renders different STD versions from JSON.

Stable UI shell.  
Variable JSON-driven sections.  
Business-readable controls.  
Raw JSON hidden.

That is the safest path.

**Final Recommendation**

Structure the UI like this:

STD Library  
↓  
STD Version Configurator  
├── Overview  
├── Applicability  
├── Tender Fields  
├── Supplier Requirements  
├── Forms & Attachments  
├── Evaluation Setup  
├── Contract Terms  
├── Rules & Validations  
├── Preview  
├── Approval  
└── Technical JSON  
<br/>Tender Document Readiness  
↓  
Uses active STD version  
↓  
Renders tender-specific setup screen  
↓  
Runs readiness checks  
↓  
Locks publication snapshot

This gives you flexibility without turning the product into a JSON management console.
