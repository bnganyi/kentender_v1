# KenTender Strategy Module UI Refactor Recommendations

This document captures recommendations for simplifying the Strategy Management module UI. The current screenshots show that the module is drifting away from its intended purpose: a simple, guided workspace for creating and maintaining the strategic hierarchy that downstream modules consume.

The Strategy module should remain a foundation layer. It should define a clean hierarchy and enforce linkages. It should not feel like a complex admin console, a detached form system, or a separate builder application.

---

# 1. Current Assessment

The current Strategy module has four main problems:

1. **The landing page is visually sparse but not informative enough.**
   - It shows large KPI cards, a small plan list, and a selected plan summary.
   - But it does not clearly show the strategy hierarchy or what is complete/incomplete.

2. **The user is forced into a separate builder page.**
   - Opening the builder changes context.
   - The left application menu changes or becomes less useful.
   - The user feels like they have moved into a different tool instead of continuing within Strategy Management.

3. **The builder tree view is not convincing.**
   - The hierarchy is technically present, but it feels visually weak.
   - The tree does not clearly communicate the full chain: Plan → Program → Objective/Sub-program → Indicator → Target.
   - Selection, nesting, and object type distinction are not strong enough.

4. **New/Edit Plan pages introduce unnecessary navigation.**
   - The user leaves the workspace to create or edit a plan.
   - This violates the goal of a simple guided workspace.
   - Strategy is supposed to be simple; creating and editing plan metadata should not feel like a separate document-management flow.

---

# 2. What the Strategy Module Should Be

The Strategy module should answer one question:

```text
What strategic structure must downstream Budget, Requisition, and Planning records link to?
```

It should provide:

- Strategic Plan creation
- Program definition
- Sub-program / objective definition, depending on the chosen model
- Output indicator definition
- Performance target definition
- Strict hierarchy enforcement
- Submission, approval, activation workflow

It should not behave like:

- a reporting dashboard
- a generic Frappe document form
- a detached builder application
- a procurement tracking module
- a complex performance-monitoring system

---

# 3. Major Design Direction

Replace the current split experience:

```text
Strategy Management landing page
→ Open Strategy Builder
→ Separate builder page
→ Separate plan form page
```

with one unified workspace:

```text
Strategy Management Workspace
├── Plan list
└── Selected plan workspace
    ├── Plan header
    ├── Progress / readiness bar
    ├── Step tabs
    ├── Structured tables
    └── Review + Submit
```

The user should not feel like they are moving between different tools. They should feel like they are managing one selected strategic plan in one workspace.

# 5. Replace Generic KPI Cards with Status Chips or Readiness Summary

## Current Problem

Large KPI cards such as:

```text

Programs Total
My Drafts
```

are not wrong, but they are low-value. They do not guide the user.

## Better Option

Use compact status filters:

```text
All 1   Draft 0   Submitted 0   Approved 0   Active 1   Archived 0
```

Then use a selected-plan readiness summary:

```text
Structure completeness
Programs: 1
Sub-programs: 1
Indicators: 1
Targets: 1

```

This is more useful because Strategy is about creating a complete hierarchy.

# 6. Do Not Make “Builder” a Separate Mental Place

## Current Problem

The button `Open Strategy Builder` takes the user into another page. That page uses a different layout and loses the broader Strategy Management context.

This makes the module feel more complicated than it is.

## Recommendation

Either:

1. open the structure builder inside the selected plan workspace, or
2. rename it from `Open Strategy Builder` to `Manage Structure` and keep consistent navigation/context.

Preferred direction:

```text
Strategy Management
└── Selected Plan
    ├── Plan Info
    ├── Structure
    ├── Review
    └── Audit
```

Do not make the user feel like they have gone to a separate app called Builder.

# 8. Better Strategy Workspace Tabs

The PRD suggests a step-based workspace:

```text
Plan Info → Programs → Sub-programs → Indicators → Targets → Review
```

This is a strong direction, but it should not become a page-per-step navigation maze.

## Recommended Tabs

Use primary tabs:

```text
Plan Info | Structure | Review | Audit
```

Inside `Structure`, use sub-tabs or segmented controls:

```text
Programs | Sub-programs | Indicators | Targets
```

or use a single structured hierarchy view with inline editing.

## Why This Is Better

The full six-step tab set is clear for creation, but can feel heavy after the plan exists. A simplified tab model works better long-term:

- `Plan Info`: metadata
- `Structure`: all hierarchy objects
- `Review`: readiness, validation, submit/approve/activate
- `Audit`: history and governance evidence

# 9. Fix the Builder Tree View

## Current Problem

The current tree view technically shows hierarchy, but it feels weak:

```text
Program — Healthcare Infrastructure Rehabilitation
  Objective — Improve district hospital infrastructure readiness
    Target — 2026: Renovate priority district hospital facilities
```

Problems:

- It skips or collapses the full PRD hierarchy depending on implementation.
- Object types are not visually strong enough.
- The selected row styling is heavy but not informative.
- It does not show enough useful metadata.
- It does not clearly show whether each level is complete.

## Recommended Tree Model

Use a structured outline that clearly communicates type, name, and completeness:

```text
MOH Strategic Plan 2026–2030

Program
Healthcare Infrastructure Rehabilitation
Linked national objective: Health infrastructure access
Status: Complete

  Sub-program
  District health facility rehabilitation
  Parent: Healthcare Infrastructure Rehabilitation
  Status: Complete

    Indicator
    Improve district hospital infrastructure readiness
    Unit: projects · Baseline: 0
    Status: Complete

      Target
      FY2026/2027 · 1 project
      Responsible department: Infrastructure
      Status: Complete
```

Use badges for object type:

```text
[P] Program
[SP] Sub-program
[IND] Indicator
[TGT] Target
```

But avoid making the badges visually noisy.

# 12. Recommended Final Structure: Hybrid View

Use both:

1. a simple hierarchy outline for overview
2. tables for editing each object type

Recommended structure:

```text
Plan Info | Structure | Review | Audit

Structure tab:

Left: Strategy hierarchy outline
Right: Selected object detail or table

Sub-tabs:
[Overview] [Programs] [Sub-programs] [Indicators] [Targets]
```

Example:

```text
Structure
[Overview] [Programs] [Sub-programs] [Indicators] [Targets]

Overview:
- Shows hierarchy outline
- Shows completeness
- Lets user select an object

Programs:
- Table of programs
- Add/edit/delete program

Sub-programs:
- Table of sub-programs
- Parent program dropdown required

Indicators:
- Table of indicators
- Sub-program dropdown required

Targets:
- Table of targets
- Indicator dropdown required
```

This satisfies both needs:

- users understand the hierarchy
- the system remains simple and enforceable

## Current Problem

The create/edit plan page is a standard document form with side metadata. It feels like leaving the Strategy module.

It also has too much vertical space and form weight for basic plan metadata.

## Recommendation

Use a modal or right-side drawer for plan metadata.

### New Strategic Plan Drawer

```text
New Strategic Plan

Plan name *
[ Ministry of Health Strategic Plan 2026–2030 ]

[ Ministry of Health ]

[ 2026 ] to [ 2030 ]
```

After creation, the user stays in the workspace and sees the new plan selected.

### Edit Plan Info Drawer


This prevents unnecessary navigation and preserves context.

# 14. Do Not Use Long Scrolling Forms for Strategy Objects

The PRD explicitly rejects long scrolling forms. The current target editor is already becoming a long form:

- target definition
- measurement
- timeframe
- baseline

## Recommendation

Use compact edit drawers per object type.

### Add Indicator Drawer

### Add Target Drawer

# 15. Remove Procurement Journey Impact from Default Strategy Editing

The current builder shows:

```text
Procurement Journey Impact
Linked procurement journeys
Linked budget lines
```

This makes the Strategy module feel like it is monitoring downstream execution.

That is not the default job of Strategy Management.

## Recommendation

Move downstream impact into a collapsed `Downstream usage` section or an Audit/Usage tab.

Default Strategy editing should focus on:

- defining the hierarchy
- enforcing required linkages
- validating completeness
- approving/activating the plan

Downstream references should be read-only and secondary.

Suggested placement:

```text
Audit / Usage
- Linked budget lines
- Linked requisitions
- Linked procurement plans
- Linked tender packages
```

Do not show this while the user is defining an objective, indicator, or target unless they explicitly open usage details.

# 16. Clarify the Object Model in the UI

There is a naming issue across the screenshots:

- The landing page shows `Programs`, `Objectives`, `Targets`.
- The PRD model uses `Programs`, `Sub-programs`, `Indicators`, `Targets`.
- The builder shows `Objective` where the PRD expects Sub-program and Indicator layers.

This is dangerous because downstream Budget/Requisition/Planning modules depend on these linkages.

## Recommendation

Pick one hierarchy and enforce it consistently.

Recommended PRD-aligned hierarchy:

```text
Strategic Plan
└── Program
    └── Sub-program
        └── Output Indicator
            └── Performance Target
```

Use these exact labels everywhere:

- Plan
- Program
- Sub-program
- Indicator
- Target

Avoid mixing `Objective` unless it is formally part of the model.

If Objective must remain, then update the model to:

```text
Plan
└── Program
    └── Objective
        └── Indicator
            └── Target
```

But do not mix both informally.


This gives the user confidence without cluttering editing screens.

# 19. Workflow Actions Should Be State-Aware

Do not show all workflow buttons at all times.

Use state-aware actions:

## Draft

```text
[Edit Plan Info] [Manage Structure] [Submit Plan]
```

## Submitted

```text
[Review Structure] [Approve] [Return for Correction]
```

## Approved

```text
[Activate Plan] [Return for Correction]
```

## Active

```text
[View Structure] [Archive] [More]
```

Do not show actions that are not available in the current state unless there is a specific reason to explain why they are blocked.

# 23. Immediate Changes to Make

In order:

1. **Stop using a separate Strategy Builder page as the main editing experience.**
   - Keep the user inside Strategy Management.

2. **Replace `Open Strategy Builder` with `Manage Structure`.**
   - The wording is simpler and less technical.

3. **Move create/edit plan into a drawer or modal.**
   - Do not navigate to a separate form page for basic metadata.

4. **Replace landing KPI cards with compact status filters and selected-plan readiness.**
   - Show completeness, not generic portfolio counts.

5. **Use consistent hierarchy labels.**
   - Plan → Program → Sub-program → Indicator → Target.

6. **Make Structure the heart of the module.**
   - Use overview hierarchy plus editable tables.

7. **Move downstream procurement/budget impact out of the default editing view.**
   - Put it in Audit/Usage or a collapsed section.

8. **Use state-aware workflow actions.**
   - Draft: edit/manage/submit.
   - Submitted: approve/return.
   - Approved: activate.
   - Active: view/archive.

9. **Add a Review tab with validation checks.**
   - This should be the user’s confidence screen before submission.

10. **Avoid long scrolling object forms.**
   - Use compact drawers for Program, Sub-program, Indicator, and Target creation/editing.

---

# 24. Final Recommendation

The Strategy module should not look or behave like a complex builder. It should be a simple structured workspace.

The best target model is:

```text
Plan list → selected plan → structure overview → editable tables → review/submit
```

Do not scatter the user across:

```text
landing page → builder page → form page → desktop → another form
```

That is exactly how a simple module becomes confusing.

The Strategy module is the foundation. Keep it boring, clear, and strict:

```text
Define the hierarchy.
Validate the links.
Approve and activate.
Expose clean references downstream.
```

Everything else should be secondary.
