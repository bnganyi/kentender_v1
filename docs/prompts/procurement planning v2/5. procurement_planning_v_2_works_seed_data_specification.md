## 1. Purpose

This document defines the Procurement Planning v2 seed data for the master KenTender WORKS scenario:

```text
District Hospital Renovation Works
```

It specifies the exact records, codes, relationships, field values, evidence events, validation checks, and negative fixtures required to align Procurement Planning with the end-to-end lifecycle.

The seed must prove that Procurement Planning is not an isolated package builder. It must prove this governed chain:

```text
Approved Demand
→ Planning Inclusion
→ Procurement Plan
→ Procurement Package
→ Package Line
→ Method Decision
→ Readiness Result
→ Review Decision
→ Planning Release Package
→ Tender Management Consumption
→ TM2 Tender
```

For the master WORKS scenario, the required chain is:

```text
DEM-MOH-2026-001
→ PLANINCL-MOH-2026-001
→ PLAN-MOH-2026
→ PKG-MOH-2026-001
→ PKGLINE-MOH-2026-001-001
→ PKGREL-MOH-2026-001
→ TND-MOH-2026-001
```

## 2. Seed Principles

| Principle ID | Principle | Meaning |
|---|---|---|
| PP2-SEED-001 | WORKS seed is controlling. | Generic medical/ICT/emergency examples may exist later, but the master path is District Hospital Renovation Works. |
| PP2-SEED-002 | Idempotent loading. | Running the seed repeatedly must update or skip existing records without duplicates. |
| PP2-SEED-003 | Stable business codes. | Tests and UI must use business codes, not opaque IDs. |
| PP2-SEED-004 | Planning Inclusion is explicit. | The seed must create or validate `PLANINCL-MOH-2026-001`. |
| PP2-SEED-005 | Package line traceability is mandatory. | `PKGLINE-MOH-2026-001-001` must link to `DEMITEM-MOH-2026-001-001` and `BUD-MOH-INFRA-2026-001`. |
| PP2-SEED-006 | Release handoff is explicit. | The seed must create or validate `PKGREL-MOH-2026-001`. |
| PP2-SEED-007 | Tender consumption is explicit. | The seed must create or validate consumption linking `PKGREL-MOH-2026-001` to `TND-MOH-2026-001`. |
| PP2-SEED-008 | Do not fake upstream authority. | Strategy, Budget, and Demand seed records must exist or be loaded by their owning modules; Planning only references them. |
| PP2-SEED-009 | Do not fake Tender authority. | Tender Management remains authoritative for `TND-MOH-2026-001`; Planning records only release and consumption references. |
| PP2-SEED-010 | Negative fixtures must be separate. | Invalid examples must not pollute the happy-path WORKS journey. |

## 3. Seed Checkpoints

The seed loader should support checkpoints so development and testing can load the scenario at different Planning stages.

| Checkpoint | Meaning | Required Planning State |
|---|---|---|
| `APPROVED_DEMAND_READY` | Upstream demand exists and is approved, but Planning has not acted. | Demand appears in Approved Demands queue; no Planning Inclusion yet. |
| `INCLUDED_IN_PLAN` | Demand has been included in the procurement plan. | `PLANINCL-MOH-2026-001` exists; package may not exist. |
| `PACKAGE_DRAFT` | Package and package line exist. | `PKG-MOH-2026-001` and `PKGLINE-MOH-2026-001-001` exist in Draft. |
| `READY_FOR_RELEASE` | Package approved and readiness passed. | Readiness and review records exist; package state Ready for Release. |
| `RELEASED_TO_TENDER` | Planning Release Package exists. | `PKGREL-MOH-2026-001` exists; package state Released to Tender. |
| `CONSUMED_BY_TENDER` | Tender Management consumed release. | `PKGREL-MOH-2026-001` consumed; `TND-MOH-2026-001` linked. |

Default master seed checkpoint:

```text
CONSUMED_BY_TENDER
```

Reason:

```text
The end-to-end Procurement Journey already proceeds through STD and Tender Management. Planning seed must align with that downstream reality.
```

6. treat generic old Planning seed records as the master journey;
7. overwrite real production records;
8. expose internal Planning seed records to suppliers.
