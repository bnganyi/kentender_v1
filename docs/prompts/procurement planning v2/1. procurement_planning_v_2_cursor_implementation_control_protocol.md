## 1. Purpose

The KenTender documentation is intentionally rigorous. The implementation must now become equally disciplined.

This protocol exists because prior Cursor implementations have sometimes treated detailed PRD and UI documents as flexible guidance instead of binding implementation requirements. That has caused rework, refactoring, context loss, and avoidable rebuilding.

For Procurement Planning v2 and future complex modules, Cursor must work under a stricter operating model:

```text
1. Inventory the repository before coding.
2. Map the documentation to actual files, models, services, APIs, routes, tests, and seed loaders.
3. Stop when there is conflict or ambiguity.
4. Implement against an explicit contract.
5. Prove each requirement with evidence.
6. Use tests and screenshots as acceptance mechanisms.
7. Never mark implementation as accepted without human review.
```

The goal is not to slow implementation. The goal is to prevent expensive reimplementation caused by early uncontrolled decisions.

## 2. Implementation Fidelity Problem Being Solved

## 2.1 Observed Problem

Previous implementation attempts showed a pattern:

| Problem | Result |
|---|---|
| Cursor inferred architecture from broad documentation. | Implementation diverged from intended module design. |
| Cursor implemented UI through raw or fragmented screens. | Navigation/context loss reappeared. |
| Cursor treated some details as optional. | Critical handoffs, seed alignment, and UX controls were missed. |
| Cursor lacked a repository inventory gate. | It made premature implementation decisions. |
| Cursor lacked explicit deviation protocol. | It silently chose alternatives. |
| Cursor lacked evidence-backed acceptance rows. | Review discovered gaps only after implementation. |

## 2.2 Corrective Position

The Cursor implementation pack must not be a narrative guide.

It must become:

```text
A phase-gated implementation contract with required repository inventory, exact task rows, explicit no-go conditions, test mappings, evidence requirements, and a stop/report deviation protocol.
```

## 4. Document Precedence Rule

If implementation documents conflict, Cursor must apply this precedence order unless the product owner overrides it.

| Rank | Document | Controls |
|---:|---|---|
| 1 | WORKS Seed Data Specification | Business codes, record values, dates, relationships, seed checkpoints, validation outputs, negative fixtures. |
| 2 | Governance, State, and Approval Model | State transitions, approval gates, locks, correction, return, cancellation, supersession. |
| 3 | Strict Domain Model | Objects, fields, relationships, mutability, ownership, source-of-truth rules. |
| 4 | Roles and Permissions Matrix | Role/action access, visibility, permission boundaries. |
| 5 | UI Specification and Wireframes | Navigation, surfaces, workspace layout, tabs, drawers, selectors, UI behavior. |
| 6 | Smoke Contract | Acceptance tests and go/no-go test outcomes. |
| 7 | Cursor Implementation Control Protocol | Implementation operating rules, evidence, stop/report process. |
| 8 | Cursor Implementation Pack | Concrete implementation tasks and repository-specific mapping. |
| 9 | Existing module docs | Legacy or already-implemented behavior not superseded by v2 documentation. |

If a lower-ranked document conflicts with a higher-ranked document, the higher-ranked document wins.

## 7. Mandatory Deviation Protocol

Cursor must stop and report if repository reality conflicts with the implementation pack or controlling documents.

## 7.1 Stop Conditions

Cursor must stop if any of these occur:

| Stop ID | Condition |
|---|---|
| STOP-001 | Existing repository structure conflicts with required module architecture. |
| STOP-002 | Required DocType/model does not exist and creating it would alter source-of-truth design. |
| STOP-003 | Existing service cannot preserve required business codes or lifecycle state. |
| STOP-004 | UI framework cannot support required workspace/tab/drawer pattern without architectural choice. |
| STOP-005 | Seed loader cannot create/validate exact WORKS scenario safely. |
| STOP-006 | Permission system cannot cleanly enforce supplier/internal separation. |
| STOP-007 | Existing Tender Management consumption path conflicts with Planning Release Package. |
| STOP-008 | Implementing a requirement would weaken legal/state controls. |
| STOP-009 | Existing tests fail after a patch and the cause is not obvious. |
| STOP-010 | Cursor would need to choose between multiple implementation paths not explicitly approved. |

## 7.2 Required Deviation Report Format

Cursor must report deviations using this format:

```text
Deviation Report

Requirement:
Expected by documentation:
Found in repository:
Conflict / gap:
Options:
1. Option A
2. Option B
3. Option C
Recommended option:
Impact if accepted:
Impact if rejected:
Tests affected:
Requires human approval: Yes
```

Cursor must not proceed until approval is provided.

## 8. Language Rules for Implementation Packs

Implementation packs must use binding language.

## 8.1 Allowed Binding Language

Use:

```text
MUST
MUST NOT
REQUIRED
BLOCKING
ACCEPTANCE REQUIRED
NO-GO
STOP AND REPORT
```

## 8.2 Discouraged Language

Avoid these in implementation packs unless accompanied by a binding decision:

```text
should
could
prefer
consider
where feasible
recommended
if possible
```

If any of those terms are used, the pack must also state whether the variation is allowed.

Example:

```text
Allowed variation: repository route naming may differ, but the user-facing route must preserve Planning Home, Approved Demands, Packages, Released to Tender, and Planning Evidence as the five persistent surfaces.
```

|---|---|

## 14. Final Instruction to Cursor

Cursor must implement Procurement Planning v2 as a governed, usable, evidence-backed conversion workflow:

```text
Approved Demand
→ Planning Inclusion
→ Procurement Package
→ Readiness / Review
→ Planning Release Package
→ Tender Management Consumption
```

Cursor must not treat the documents as suggestions.

Cursor must not improvise architecture when implementation path is unclear.

Cursor must not substitute a generic implementation for the specified WORKS scenario.

Cursor must not prioritize fast code generation over fidelity.

If there is uncertainty, the required behavior is:

```text
Stop. Report. Ask for approval.
```
