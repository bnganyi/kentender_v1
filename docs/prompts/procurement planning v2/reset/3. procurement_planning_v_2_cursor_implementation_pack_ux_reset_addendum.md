## 1. Executive Instruction to Cursor

Cursor must stop implementing the previous handoff-card-heavy Planning UI.

The UI must now be rebuilt or refactored into a simple planning workbench.

Cursor must preserve:

```text
backend services;
server-side readiness checks;
state transitions;
approval gates;
release locking;
Planning Inclusion records;
Planning Release Package records;
Tender consumption records;
audit/evidence persistence;
WORKS seed data;
role and permission controls.
```

Cursor must not expose those internal records as the ordinary default work surface.

The user-facing Planning UI must be governed by this rule:

```text
Users manage work queues, approved demands, plans, packages, and released packages.
The system records handoffs and evidence silently.
Evidence is shown only when the user clicks View Evidence.
Technical details are shown only when the user expands Technical Details and has permission.
```

## 2. Supersession and Conflict Rules

## 2.1 This Contract Supersedes Prior P5 UI Instructions

This contract supersedes any previous Procurement Planning P5 UI instruction that requires or implies ordinary default display of:

```text
handoff card stacks;
Planning Workflow Status panels;
multiple What happened cards as primary screen content;
raw lifecycle trace panels;
technical evidence panels visible before user request;
right-side implementation-stage panels;
Planning Evidence as a persistent ordinary Planning sidebar item;
raw handoff IDs in package lists;
source object / target object labels in default work screens;
JSON field labels in default work screens;
audit IDs in default work screens;
large Planning Inclusion / Release / Consumption cards as primary package content.
```

## 2.2 This Contract Does Not Supersede Backend Rigor

This contract does not change the required database, services, APIs, permissions, audit, or legal controls.

The following still exist and must still be tested:

```text
PLANINCL-MOH-2026-001
PKGREL-MOH-2026-001
PKGCONSUME-MOH-2026-001
readiness records
review records
release records
consumption records
audit events
locked release snapshots
passed-forward release summaries
```

They are simply not primary ordinary UI content.

## 2.3 If Prior UI Spec Conflicts

If this contract conflicts with the earlier UI Specification, Cursor must apply this contract for P5 UI implementation.

If this contract appears to conflict with domain/governance/security/backend rules, Cursor must stop and report.

## 5. Global UX Rules

## 5.1 Workbench Rule

Every Planning screen must follow this order:

```text
1. Page title and one-line purpose
2. Small queues or simple filters
3. Work list or selected item
4. Selected item summary
5. Blockers
6. One primary next action
7. Secondary actions
8. View Evidence
```

## 5.2 One Primary Action Rule

For a selected item, show only one primary action. Other actions are secondary.

Examples:

| State | Primary Action | Secondary Actions |
|---|---|---|
| Demand ready to plan | Include in Plan | View Demand, View Evidence |
| Demand included but no package | Create Package | View Demand, View Evidence |
| Package draft | Open Package | View Evidence |
| Package needs review | Review Package | View Evidence |
| Package ready to release | Release to Tender Management | Open Package, View Evidence |
| Package released/consumed | Open Tender | Open Package, View Evidence |
| Package blocked | Resolve Blocker | Open Package, View Evidence |

## 5.3 Evidence-on-Demand Rule

Evidence is always available where permitted, but it is not pushed into the main work area.

Use:

```text
[View Evidence]
```

Do not show evidence cards by default.

## 5.4 Technical Details Rule

Technical details must be behind an explicit toggle inside Evidence Drawer or Advanced.

Default UI must not show:

```text
PLANINCL-MOH-2026-001
PKGREL-MOH-2026-001
PKGCONSUME-MOH-2026-001
source_object_code
target_object_code
locked_summary_json
passed_forward_summary_json
technical_refs_json
audit_event_ref
package_release
handed_off
```

Exception: package/tender/demand/budget business codes may appear as secondary metadata where useful, but never as the title or primary explanation.

Acceptable:

```text
Tender: TND-MOH-2026-001
Budget linked: BUD-MOH-INFRA-2026-001
```

Not acceptable:

```text
Target object: TND-MOH-2026-001
Next handoff: PKGREL-MOH-2026-001
Stage / status: package_release / Handed Off
```

## 5.5 No Implementation-Stage Copy Rule

Product UI must not contain implementation-stage text such as:

```text
shell baseline active
feature content deferred
P5 surfaces completed
stub content
this will be implemented later
technical placeholder
```

Use proper empty states instead.

## 24. Final Acceptance Statement

Procurement Planning P5 UI is acceptable only if this statement is true:

```text
A normal procurement planner can open Planning, find the demand or package they need, understand the next action, complete the planning task, and view evidence only when they intentionally ask for it.
```

It is not acceptable if this statement is true:

```text
The screen is technically accurate but looks like an audit log, handoff registry, lifecycle debugger, or implementation status board.
```
