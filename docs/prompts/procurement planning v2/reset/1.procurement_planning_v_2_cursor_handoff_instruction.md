# Procurement Planning v2 — Cursor Handoff Instruction

# KenTender Public Procurement Platform

---

## 0. Purpose

This is the first document Cursor must read before resuming Procurement Planning v2 P5 UI implementation.

Its purpose is to remove ambiguity about which documents control the UI reset and to prevent Cursor from accidentally continuing the superseded handoff-card-heavy implementation path.

---

## 1. Controlling Documents for Procurement Planning P5 UI

Cursor must implement Procurement Planning P5 UI using these documents, in this order:

| Rank | Document | Controls |
|---:|---|---|
| 1 | Procurement Planning v2 — P5 UX Reset Implementation Tracker | Execution rows, phase gates, required evidence, screenshots, no-go conditions. |
| 2 | Procurement Planning v2 — P5 UX Reset Implementation Contract | Detailed implementation rules, route contracts, components, view-models, state/action behavior, tests. |

| 5 | Older Procurement Planning v2 UI Specification and Wireframes | Superseded for P5 UI where it conflicts with the reset documents. Do not use for ordinary Planning UI implementation. |

---

## 2. Documents Cursor Must Not Use for P5 UI Direction

Cursor must not use the older UI specification to implement the ordinary Procurement Planning P5 interface where it conflicts with the reset pack.

The following older UI patterns are superseded:

```text
Planning Evidence as a persistent ordinary Planning submenu
Planning Home with handoff cards or evidence cards
Packages with Planning Inclusion / Release / Consumption card stacks
Package workspace with Evidence and Advanced as default tabs
large Journey Context Header dominating ordinary Planning screens
Planning Workflow Status as ordinary default package content
right-side implementation-stage shell panels
technical details links attached to every ordinary card or row
raw lifecycle keys, handoff codes, source/target labels, JSON labels, and audit IDs in ordinary default views
```

These patterns may exist only in Journey, Evidence, Advanced, Technical Details, Audit, or cross-module Evidence & Audit contexts where explicitly requested and permission-appropriate.

---

## 3. Product Rule

Cursor must implement Planning as a simple workbench:

```text
Users manage work queues, approved demands, plans, packages, and released packages.
The system records handoffs and evidence silently.
Evidence is shown only when the user clicks View Evidence.
Technical details are shown only when the user expands Technical Details and has permission.
```

Do not build Procurement Planning as a visible audit/evidence browser.

---

## 4. Required Persistent Planning IA

Persistent Planning navigation must be exactly:

```text
Procurement Planning
├── Planning Home
├── Approved Demands
├── Plans
├── Packages
└── Released to Tender
```

Do not add these as ordinary persistent Planning submenu entries:

```text
Planning Evidence
Planning Inclusion Detail
Release Package Detail
Readiness Review
Review & Approval
Package Lines
Technical Details
Audit Trail
Planning Release Package
Tender Consumption Status
Handoff History
```

Evidence must be contextual through `View Evidence` from the relevant demand, plan, package, release, or journey.

## 5. Current Implementation Reset Instruction

Before continuing feature work, Cursor must inspect the current P5 implementation and remove or refactor anything that violates the reset documents.

The immediate refactor target includes:

| Current / Risky Pattern | Required Action |
|---|---|
| Handoff cards shown under shell/navigation work | Remove from ordinary shell; move behind Evidence/Journey where applicable. |
| Planning Workflow Status panel | Replace with selected item summary, blockers, and next action. |
| Planning Evidence persistent submenu | Remove from ordinary Planning navigation. |
| Technical details on ordinary cards | Move to Evidence Drawer → Technical Details expansion. |
| Implementation-stage copy such as shell baseline, feature deferred, stub, P5 | Delete from product UI. Use real empty/loading states. |
| Package screen as handoff/evidence card grid | Replace with Packages workbench: list + selected summary + one primary action. |

Cursor must not proceed to Planning Home, Approved Demands, Packages, Package Detail, or Released to Tender feature completion until this reset refactor is done.

## 8. Handoff Visibility Boundary

Handoff cards and technical evidence are still important, but they belong in the correct product context.

Allowed contexts:

```text
Procurement Journey
Evidence Drawer
Technical Details
Advanced
Audit View
Cross-module Evidence & Audit
```

Not allowed as ordinary default Planning workbench content:

```text
Planning Home
Approved Demands default list
Plans default list
Packages default workbench
Package Detail default Overview
Released to Tender default list
```

In ordinary Planning screens, show business outcomes instead:

```text
Budget linked
Demand approved
Ready to plan
Ready to release
Released to Tender Management
Tender created
Open Tender
View Evidence
No blockers
```

## 11. Final Instruction

The acceptable outcome is:

```text
A normal procurement planner can open Planning, find the demand or package they need, understand the next action, complete the planning task, and view evidence only when they intentionally ask for it.
```

The unacceptable outcome is:

```text
The Planning UI is technically accurate but looks like an audit log, handoff registry, lifecycle debugger, implementation status board, or evidence browser.
```

Cursor must implement the first outcome and reject the second.
