## 1. Reason for Reset

The previous Procurement Planning UI direction was technically rigorous but operationally poor. It exposed handoff cards, lifecycle traces, evidence records, status blocks, and technical explanations too early.

The visible result was a Planning UI that looked like:

```text
journey trace + status explanation + handoff cards + technical details + shell status
```

instead of:

```text
queue + selected item + blocker summary + next action
```

That is not acceptable. KenTender must be legally safe and also usable by ordinary procurement users.

This reset establishes a strict UI model:

```text
Primary UI = work queues, selected item summary, blockers, next action, task completion.
Secondary UI = evidence, handoff records, lifecycle trace, audit history, technical references.
```

The backend remains rigorous. The default UI must be calm.

## 2. Binding UX Principles

| ID | Principle | Binding Meaning |
|---|---|---|
| PP2-UXR-001 | Work first, evidence second. | Default screens show tasks and decisions. Evidence is behind View Evidence. |
| PP2-UXR-002 | One screen, one job. | Each persistent Planning screen has one clear purpose and one primary user question. |
| PP2-UXR-003 | No handoff stacks in ordinary views. | Handoff cards must not appear as stacked primary content in Planning Home, Packages, or Package Detail. |
| PP2-UXR-004 | No lifecycle trace panels by default. | Users should not see process history unless they open Evidence, History, or Technical Details. |
| PP2-UXR-005 | One primary action per selected item. | A selected item may have secondary actions, but only one visually primary next action. |
| PP2-UXR-006 | Queues must be small. | Default queues must be few, plain, role-relevant, and limited. |
| PP2-UXR-007 | Package detail is a workbench. | Package detail answers: what is this package, what state is it in, what is missing, what can I do now? |
| PP2-UXR-008 | Handoffs are system evidence. | Handoffs are created, stored, tested, and auditable, but ordinary users do not manage them directly. |
| PP2-UXR-009 | Advanced mode is explicit. | Technical details require intentional action: View Evidence, Technical Details, or Advanced. |
| PP2-UXR-010 | Cursor must not add UI. | If a card, panel, queue, tab, route, chip, or button is not specified here, do not add it to ordinary default UI. |
| PP2-UXR-011 | Product copy must be business copy. | No implementation-stage text, raw field labels, JSON labels, or lifecycle keys in ordinary UI. |
| PP2-UXR-012 | The selected item matters. | Lists are useful only when paired with a selected summary or clear row action. |

## 3. Supersession Rules

This reset pack controls the **P5 Procurement Planning UI implementation**.

Where previous documents require or imply the following as ordinary default UI, those instructions are superseded:

```text
Planning handoff cards displayed directly on Planning Home.
Planning handoff cards displayed directly on Packages.
Planning Workflow Status panels as default package content.
Multiple What happened cards stacked as primary UI.
Raw or semi-raw lifecycle explanations in shell/navigation.
Right-side panels that explain implementation stage instead of user action.
Default technical details links attached to every shell stub.
Persistent Planning Evidence submenu for ordinary Planning users.
Evidence or Advanced as default Package Detail tabs.
```

The following remain required underneath, but must be moved behind user request or audit/evidence mode:

```text
Planning Inclusion Record
Planning Release Package
Tender consumption evidence
handoff codes
locked values
passed-forward values
technical references
audit trail
source/target object references
readiness result records
review decision records
```

Procurement Planning must remain inside the main Procurement app shell. The main Procurement navigation remains visible. Planning appears as a parent item with the five children above.

## 5. Screen Set

The Planning UI has five persistent screens and one contextual detail workbench.

| Surface | Type | Job | Main User Question |
|---|---|---|---|
| Planning Home | Persistent | Orient the planner and show small work queues. | What needs my attention? |
| Approved Demands | Persistent | Convert approved demand into planning/package work. | What approved demand can I plan now? |
| Plans | Persistent | See procurement plans and plan-level progress. | Which plan owns this work? |
| Packages | Persistent | Manage packages by work state. | Which package needs work, review, release, or follow-up? |
| Package Detail | Contextual | Work on one package. | What is missing and what can I do now? |
| Released to Tender | Persistent | See packages that left Planning. | What has been released, and can I open the tender? |
| Evidence Drawer | Contextual | Inspect audit/evidence on request. | What evidence supports this item? |

Everything else is contextual or outside Planning.

## 6. Global Layout Standard

## 6.1 Quiet Workbench Layout

All Planning screens use this simple layout:

```text
┌ Page Header ────────────────────────────────────────────────────────────────┐
│ Title                                                                       │
│ One-line purpose                                                            │
│ Optional primary button                                                     │
└─────────────────────────────────────────────────────────────────────────────┘

┌ Queue / Filters ────────────────────────────────────────────────────────────┐
│ Small queue chips or simple tabs                                             │
│ Search and Advanced Filters where relevant                                   │
└─────────────────────────────────────────────────────────────────────────────┘

┌ Main Work Area ─────────────────────────────────────────────────────────────┐
│ Left/Main: compact list/table                                                │
│ Right/Drawer: selected item summary and next action                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 6.2 Selected Item Summary Pattern

For any selected demand, plan, package, or release, show this pattern:

```text
Title
Status
Key business facts
Blockers
Next action
[Primary Action] [Secondary Action] [View Evidence]
```

## 6.3 Default Row Pattern

Rows show:

```text
Title
Short metadata line
Business status
Optional blocker marker
```

Rows do not show:

```text
handoff IDs
source/target object labels
JSON field labels
audit IDs
implementation notes
```

## 6.4 Prohibited Default Layout

Do not use this in ordinary views:

```text
Journey context block
Status pill
Handoff card 1
Handoff card 2
Handoff card 3
Technical details link under each card
Right panel with implementation-stage explanation
```

This pattern is rejected.

```text
Build Planning as a workbench for doing planning work.
```

```text
handoff records still exist;
release locking still works;
readiness still runs server-side;
permissions still apply;
evidence still exists;
```

## 23. Final Acceptance Statement

Procurement Planning v2 UI is acceptable only if this statement is true:

```text
A normal procurement planner can open Planning, find the demand or package they need, understand the next action, complete the planning task, and view evidence only when they intentionally ask for it.
```

It is not acceptable if this statement is true:

```text
The screen is technically accurate but looks like an audit log, handoff registry, lifecycle debugger, or implementation status board.
```
