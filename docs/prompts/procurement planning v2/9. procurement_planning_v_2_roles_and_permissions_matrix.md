## 1. Purpose

This document defines the roles, permissions, object access rules, state-transition permissions, UI visibility, handoff visibility, supplier restrictions, auditor access, and administrator boundaries for Procurement Planning v2.

It exists to prevent three implementation failures:

1. giving too much power to ordinary users;
2. blocking legitimate planning work through vague role definitions;
3. allowing Cursor to guess who may perform legally sensitive actions.

Procurement Planning v2 must be usable, but it must remain legally defensible.

The key rule is:

```text
A user may perform a planning action only when all of these are true:

1. the user's role permits the action;
2. the object state permits the action;
3. the user's procuring entity / department scope permits access;
4. the action does not violate source-of-truth boundaries;
5. required prerequisites and guards pass.
```

## 2. Permission Design Principles

| Principle ID | Principle | Meaning |
|---|---|---|
| PP2-PERM-001 | Role alone is insufficient. | State, entity scope, and guard checks must also allow the action. |
| PP2-PERM-002 | Planning owns planning records only. | Planning permissions cannot authorize editing Strategy, Budget, Demand, STD, Tender, or Supplier objects. |
| PP2-PERM-003 | Supplier users have no internal Planning access. | Supplier users must not see internal planning evidence, package review notes, or planning handoff internals. |
| PP2-PERM-004 | Release is high-sensitivity. | Release to Tender requires explicit authority and passed readiness. |
| PP2-PERM-005 | Post-release changes are exceptional. | Editing locked release baseline values requires correction/supersession authority. |
| PP2-PERM-006 | Auditor access is read-only. | Auditors can inspect evidence but cannot transition planning state. |
| PP2-PERM-007 | System Administrator is not a business approver by default. | Technical admin rights must not substitute for procurement approval authority. |
| PP2-PERM-008 | UI must hide unavailable actions. | Disabled/hidden actions must still be server-enforced. |
| PP2-PERM-009 | Handoff visibility is permission-filtered. | A handoff card does not grant access to its source or target object unless the user has permission. |
| PP2-PERM-010 | Entity scoping is mandatory. | Users should see records only for authorized procuring entities/departments unless oversight rights apply. |

## 4. Role Descriptions and Boundaries

## 4.1 Requesting Officer

### Allowed Purpose

The Requesting Officer may track whether their approved demand has entered Planning.

### Allowed Access

```text
Read own department demand planning status.
View limited Planning status after demand approval.
Open Journey View if permitted by entity/department scope.
```

### Not Allowed

```text
Include demand in plan.
Create procurement package.
Edit package.
Approve package.
Release package.
View internal Planning review notes unless explicitly permitted.
```

## 4.2 Department Approver

### Allowed Purpose

The Department Approver may verify that approved demand is progressing into Planning.

### Allowed Access

```text
Read demand planning status.
View high-level planning inclusion/package status.
View business-level handoff status.
```

### Not Allowed

```text
Edit package.
Approve planning package.
Release package.
Access internal planning correction discussions unless permitted.
```

## 4.3 Procurement Planner

### Allowed Purpose

The Procurement Planner performs day-to-day planning work.

### Allowed Access

```text
View approved demands awaiting planning.
Create Planning Inclusion Record.
Create Procurement Package.
Create/edit package lines before release.
Record method/category basis before review/release.
Run readiness checks.
Submit package for review.
Correct returned package.
View planning handoff/evidence for packages they can access.
```

### Conditional Access

```text
Release to Tender only if entity policy permits planner release after approval/readiness.
```

Default v2 rule:

```text
Planner prepares and submits. Planning Authority releases.
```

### Not Allowed

```text
Approve own package unless explicitly configured.
Bypass readiness.
Edit released package baseline.
Supersede released package without authority.
Consume release in Tender Management unless also assigned Procurement Officer role.
```

## 4.4 Planning Reviewer

### Allowed Purpose

The Planning Reviewer checks package correctness before approval or release.

### Allowed Access

```text
View packages in review.
Review source demand, budget link, package lines, method/category, readiness result.
Approve package.
Return package for correction.
Run or view readiness checks.
Add review decision reason.
```

### Conditional Access

```text
Authorize release only if configured.
Approve method override if assigned method authority.
```

### Not Allowed

```text
Edit package content directly while reviewing, unless acting under correction workflow.
Consume release in Tender Management.
Access supplier bid data.
```

## 4.5 Planning Authority / Head of Procurement

### Allowed Purpose

The Planning Authority performs high-sensitivity approval and control actions.

### Allowed Access

```text
Approve package where required.
Authorize release to Tender Management.
Cancel package where allowed.
Approve post-release correction.
Approve supersession.
Return package for correction.
View all planning evidence within entity scope.
```

### Not Allowed

```text
Bypass upstream demand approval.
Bypass budget linkage.
Bypass readiness without explicit exception governance if such exception is legally allowed.
Silently edit released baseline.
```

## 4.6 Budget Officer

### Allowed Purpose

The Budget Officer verifies funding context.

### Allowed Access

```text
View packages linked to budget lines within scope.
View budget line usage by package.
View funding confirmation handoff.
Confirm or comment on funding context if Budget module exposes such workflow.
```

### Not Allowed

```text
Create package.
Approve package release by default.
Edit planning package lines.
Override procurement method.
Consume Tender release.
```

## 4.7 Procurement Officer

### Allowed Purpose

The Procurement Officer consumes released packages in Tender Management.

### Allowed Access in Planning Context

```text
View Planning Release Package.
View locked values and passed-forward values.
Consume release into TM2 Tender if also authorized in Tender Management.
Return release for correction before non-returnable tender state if authorized.
```

### Not Allowed

```text
Edit Planning package baseline.
Change method/category/scope during consumption.
Bypass Planning Release Package.
```

## 4.8 Tender Manager

### Allowed Purpose

The Tender Manager may identify and return Planning release issues before tender process becomes legally non-returnable.

### Allowed Access

```text
View Planning Release Package.
Return release for correction with reason before non-returnable state.
View release evidence relevant to Tender creation.
```

### Not Allowed

```text
Silently change Planning baseline.
Return Planning release after Tender Published unless legal correction path allows it through Tender Management, not Planning alone.
```

## 4.9 Auditor / Oversight

### Allowed Purpose

Auditors inspect evidence and reconstruct the planning chain.

### Allowed Access

```text
Read Procurement Plan.
Read Planning Inclusion.
Read Package.
Read Package Lines.
Read Readiness Results.
Read Review Decisions.
Read Planning Release Package.
Read Consumption Record.
Read Correction/Supersession Records.
Read Audit Events.
View Journey and Handoff cards.
```

### Not Allowed

```text
Create, edit, approve, release, consume, return, cancel, or supersede planning records.
```

## 4.10 System Administrator

### Allowed Purpose

The System Administrator manages technical configuration, permissions, seed/test support, and troubleshooting.

### Allowed Access

```text
Configure roles/permissions.
Manage technical metadata.
Run seed loaders in development/test environments.
Resolve technical data issues under controlled procedures.
```

### Not Allowed by Default

```text
Act as business approver.
Release package as business authority.
Approve method override as business authority.
Cancel/supersede business records without delegated business role.
```

## 4.11 Supplier User

### Allowed Purpose

Supplier users participate in supplier-facing tender processes only.

### Planning Access Rule

```text
Supplier users have no access to internal Procurement Planning records, review notes, readiness details, Planning Release Package internals, internal handoff evidence, or planning audit trail.
```

Supplier-facing tender information is handled by Supplier Portal / Tender Management rules, not Procurement Planning.

Procurement Plan internals

## 10.3 Public Restriction

Public visitors must not access internal Planning records. Public tender notices and published documents are governed by Public Portal / Tender Management publication rules.

## 11. Entity, Department, and Scope Filtering

## 11.1 Entity Scope

All Planning records must be scoped by procuring entity.

For the WORKS seed:

```text
PE-MOH
```

Internal users without cross-entity authority may view only records in their authorized entity.

## 11.2 Department Scope

Requesting Officers and Department Approvers may see limited planning status for their own department's approved demands.

They should not automatically see all package review details.

## 11.3 Oversight Scope

Auditors / Oversight users may have broader scope, but access must still be explicit and logged where required.

## 11.4 System Admin Scope

System Administrator may technically access configuration and support data, but business approval authority must come from a separate business role.
