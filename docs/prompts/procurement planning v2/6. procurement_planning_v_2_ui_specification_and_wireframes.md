## 1. Purpose

This document defines the Procurement Planning v2 user experience, screen inventory, workflows, wireframes, UI behavior, validation messages, selectors, and implementation requirements.

The main planner workflow is:

```text
Approved Demand Queue
→ Select approved demand item(s)
→ Include in Procurement Plan
→ Create / Add to Procurement Package
→ Review package lines
→ Confirm method/category/STD path
→ Run readiness checks
→ Submit / approve
→ Release to Tender
→ Tender Management consumes release
```

The UI must not make ordinary users assemble this flow from raw DocTypes.

Procurement Planning must feel like a guided workbench that answers:

```text
What approved demands need planning?
What plan should this demand go into?
What package will be created?
What is missing before release?
Who must review or approve?
What exactly will be handed to Tender Management?
Has Tender Management consumed it?
```

## 2A. Default Visibility Hierarchy and Progressive Disclosure Rules

This section is binding for implementation. It corrects the risk that rigorous lifecycle evidence becomes intimidating, technical, or unusable for ordinary users.

## 2A.1 Default Visibility Hierarchy

Every ordinary Planning screen must present information in this order:

```text
1. Business summary
2. Current state in business language
3. Next action
4. Blockers, if any
5. Primary action button
6. Secondary action buttons
7. Evidence link
8. Technical details only after explicit expansion or inside Evidence / Advanced / Audit views
```

Cursor must not invert this hierarchy by showing lifecycle keys, handoff IDs, internal object codes, JSON labels, or audit references before the user understands what happened and what to do next.

## 2A.2 Ordinary User Default View

The default view for planners, reviewers, procurement officers, and department users must use business-readable phrases.

Use this style:

```text
Planning status: Package released to Tender Management
Previous step: Approved demand was included in the procurement plan
Next step: Continue in Tender Management
Action: Open Tender
Evidence: View evidence
```

Do not use this style in default views:

```text
Stage / status: package_release / Handed Off
Previous handoff: PLANINCL-MOH-2026-001
Next handoff: PKGREL-MOH-2026-001
source_object_code: PKG-MOH-2026-001
target_object_code: TND-MOH-2026-001
```

## 2A.3 Technical Details Placement Rule

The following must be hidden from ordinary default screens and shown only in **Evidence**, **Advanced**, **Technical Details**, or **Audit Mode**, subject to permission:

```text
raw lifecycle stage keys, for example package_release
raw lifecycle status keys, for example handed_off
handoff codes, for example PLANINCL-MOH-2026-001 or PKGREL-MOH-2026-001
source_object_code / target_object_code labels
source_module / target_module labels when shown as raw fields
JSON field names
technical_refs_json
source snapshots
internal audit event IDs
internal DocType names where a business label exists
```

Business codes such as package, tender, demand, and budget references may appear where useful, but they must be attached to business labels and must not dominate the screen.

Acceptable:

```text
Tender: TND-MOH-2026-001
Budget linked: BUD-MOH-INFRA-2026-001
```

Not acceptable as primary default content:

```text
Target object: TND-MOH-2026-001
budget_line_code: BUD-MOH-INFRA-2026-001
```

## 2A.4 Handoff Display Modes

Planning handoff information must support two modes.

### Business Mode — Default

Business Mode is shown to ordinary internal users by default.

It must answer:

```text
What happened?
What is locked or protected?
What happens next?
What action can I take?
Where can I view evidence?
```

Example:

```text
Planning release
Status: Consumed by Tender Management
What happened: This package was released to Tender Management.
Protected details: method, category, scope, budget, and estimated value are locked.
Next step: Continue in Tender Management.
[Open Tender] [View Evidence]
```

### Audit / Technical Mode — Explicit and Permission-Aware

Audit / Technical Mode may show:

```text
PKGREL-MOH-2026-001
PLANINCL-MOH-2026-001
source_object_code
target_object_code
handoff_code
technical_refs_json
audit_event_ref
```

It must be accessed through:

```text
View Evidence
Advanced
Technical Details
Audit View
```

It must not be the default display.

## 2A.5 Default Queue Filter Rule

Default package queue filters must be compact and understandable.

Use only:

```text
All
My Work
Needs Review
Ready for Release
Released / Consumed
Blocked
```

The following may exist only under **Advanced Filters** unless a specific role has opted into specialist mode:

```text
Draft Packages
In Review Packages
High-Risk Packages
Emergency Packages
Pending Approval
High-Risk Requiring Escalation
Method Override Cases
Approved Not Yet Handed Off
Handoff Status
Readiness Status
Procurement Method
Procurement Category
```

## 2A.6 Usability No-Go Rule

The UI must be rejected if ordinary default Planning screens expose raw lifecycle keys, raw handoff codes, JSON labels, internal technical object labels, or audit identifiers before business-readable labels.

This is a no-go usability defect, even if the underlying data and tests are technically correct.

## 3. Navigation Model

## 3.1 Procurement App Placement

Procurement Planning appears inside the main **Procurement** app shell.

The permanent sidebar must stay small. Procurement Planning is already the lifecycle area; its submenu should not list every technical detail screen.

### 3.1.1 Recommended Persistent Procurement Planning Sidebar

Use these persistent entries under **Procurement Planning**:

```text
Procurement Planning
├── Planning Home
├── Approved Demands
├── Packages
├── Released to Tender
└── Planning Evidence
```

### 3.1.2 Do Not Add These as Permanent Sidebar Items

The following are important screens or views, but they must open contextually from Planning Home, Approved Demands, Packages, Released to Tender, or Evidence:

```text
Procurement Plan Detail
Planning Inclusion Detail
Package Detail
Package Lines
Method & Category
Readiness Review
Review & Approval
Release to Tender Review
Planning Release Package View
Evidence Timeline for a package
Advanced / Technical Details
```

Reason:

```text
These are work-context screens, not primary navigation destinations.
Putting all of them in the sidebar recreates the navigation and context-loss problem.
```

### 3.1.3 Full Procurement IA Context

Recommended Procurement IA section:

```text
Procurement
├── Procurement Home
├── Procurement Journeys
├── Strategy Alignment
├── Budget & Funding
├── Demand Intake & Approval
├── Procurement Planning
│   ├── Planning Home

│   ├── Packages
│   ├── Released to Tender
│   └── Planning Evidence
├── STD / Tender Document Readiness

├── Supplier Participation & Bid Submission
├── Tender Closing
├── Bid Opening
├── Evaluation & Award
├── Contract Management
└── Evidence & Audit
```

## 3.2 Navigation Pattern

Procurement Planning must use a **guided master-detail workspace** pattern.

The normal user flow should be:

```text
Planning Home / Workbench
→ Approved Demand Drawer
→ Include in Plan Modal
→ Package Workspace
   ├ Overview
   ├ Source Demand
   ├ Budget
   ├ Lines
   ├ Method
   ├ Readiness
   ├ Review
   ├ Release
   └ Evidence
```

Most detail experiences are tabs, drawers, panels, or modals inside the package workspace. They are not independent navigation silos.

## 3.4 Cross-Module Navigation

Every Planning detail page linked to a journey must include:

```text
Open Procurement Journey
Open Source Demand
Open Budget Line
Open Tender if consumed
View Evidence
Back to Planning Home
Back to Packages
```

Navigation must respect permissions. A link may appear disabled with reason where the user lacks access.

## 3.5 Context Preservation Rules

To prevent context loss:

1. The package workspace must keep the same package header visible across tabs.
2. The journey context header must remain visible or collapsible, not disappear completely.
3. Opening Source Demand, Budget Line, or Release Package should prefer drawer/side panel where feasible.
4. After completing a modal action, the user should land on the next logical step, not a raw list.
5. Breadcrumbs must always show:

```text
Procurement Planning → Packages → PKG-MOH-2026-001
```

or equivalent for the current context.

6. The primary next action must be visually obvious.

## 7.4 Planner Interaction

The planner may:

1. filter approved demands;
2. open demand planning drawer;
3. select one or more demand items where allowed;
4. include selected demand/items in plan;
5. create package from included demand.

For v2 WORKS baseline:

```text
one demand item → one planning inclusion → one package line
```

Splitting/merging should not be available unless explicitly implemented later.

## 22. Permission-Aware UI Rules

0. The sidebar must expose only Planning Home, Approved Demands, Packages, Released to Tender, and Planning Evidence. All other Planning views are contextual.
1. Supplier users must not see Procurement Planning screens.
2. Requesting Officers and Department Approvers may see limited status only for their own demands.
3. Auditors may view evidence but cannot perform actions.
4. System Administrators do not receive business approval buttons unless also assigned business roles.
5. Disabled buttons must show reason where helpful.
6. Hidden buttons must still be enforced server-side.
7. Release buttons must never appear merely because the package looks complete; state and permission checks must pass.
8. Technical details must be permission-filtered. 8A. Technical details must also be progressively disclosed. Permission to see technical details does not mean they appear in ordinary default views. 8B. Ordinary default views must not show raw lifecycle keys, raw handoff codes, JSON field names, source\_object\_code/target\_object\_code labels, audit event IDs, or internal lifecycle labels before business-readable content. 8C. Handoff cards must render Business Mode by default and Audit/Technical Mode only after explicit expansion.
9. The package workspace must preserve context across readiness, review, release, and evidence work.
10. After modal completion, the user must be taken to the next logical step, not dropped into a raw DocType list.

## 24. Cursor Implementation Notes

Cursor must map these screens to existing Frappe/Vue/React/custom UI conventions after repository inventory.

Cursor must not:

1. implement only raw DocType list views;
2. omit Planning Inclusion from the UX;
3. make release a hidden backend event;
4. show Supplier users internal Planning screens;
5. allow UI actions that backend will reject without a clear explanation;
6. expose technical evidence as the first thing ordinary users see;
7. skip stable selectors;
8. create permanent sidebar entries for every contextual Planning view;
9. implement Readiness, Review, Release, and Evidence as disconnected pages without the package header/context;
10. drop users into raw lists after completing Include in Plan, Create Package, Release, or Consume actions;
11. show raw lifecycle keys, handoff codes, JSON labels, source\_object\_code/target\_object\_code labels, or audit IDs in ordinary default views;
12. create intimidating technical workflow panels where a business-readable What happened / What next / Evidence panel is required;
13. expose specialist filter chips by default instead of placing them under Advanced Filters.

Cursor must implement stable selectors even if CSS/class conventions differ.
