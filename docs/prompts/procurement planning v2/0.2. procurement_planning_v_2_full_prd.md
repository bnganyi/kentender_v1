## 1. Executive Summary

Procurement Planning v2 corrects the weakness in the original Planning module by redefining it as a governed handoff module rather than a generic package builder.

The original module contained useful ideas: procurement plans, packages, package lines, templates, planning profiles, method/category defaults, package readiness, and approval. Those ideas remain valid. But they were not sufficient to produce a legally safe and usable cross-module journey. The implementation became too package-centric, too template-centric, and insufficiently explicit about the handoff from approved demand to Tender Management.

Procurement Planning v2 must implement this business responsibility:

```text
Approved Demand
→ Planning Inclusion
→ Procurement Plan
→ Procurement Package
→ Package Readiness Review
→ Planning Release Package
→ Tender Management Consumption
```

The module must answer these questions clearly for users, auditors, and downstream modules:

```text
What approved demand was consumed?
Which budget line funds it?
When was it included in the procurement plan?
What package was created?
What package lines preserve demand and budget traceability?
What procurement method/category was selected?
What readiness checks passed?
Who reviewed/approved release?
What exactly was locked at release?
What was handed to Tender Management?
Has Tender Management consumed the release?
```

The design goal is not to make Planning bureaucratic. It is to make Planning reliable, auditable, and understandable.

The state model must be complete but not overcomplicated. The first implementation should use a compact package lifecycle:

```text
Draft
In Review
Returned for Correction
Approved
Ready for Release
Released to Tender
Consumed by Tender Management
Superseded
Cancelled
```

Readiness, review, release, consumption, correction, and audit details should be modeled through supporting records and evidence rather than a sprawling list of top-level states.

## 2. Product Context

KenTender is a government-facing public procurement platform. The system must be legally defensible, auditable, and usable by ordinary procurement users.

The current cross-module lifecycle is:

```text
Strategy Priority
→ Budget Line
→ Demand
→ Approved Demand
→ Procurement Plan
→ Procurement Package
→ Planning Release Package
→ STD Readiness
→ Tender Publication
→ Supplier Participation & Bid Submission
→ Tender Closing
→ Opening Readiness
→ Bid Opening
→ Evaluation / Award
→ Contract Handoff
```

Procurement Planning owns this segment:

```text
Approved Demand
→ Planning Inclusion
→ Procurement Plan
→ Procurement Package
→ Package Readiness
→ Planning Release Package
→ Tender Management Consumption
```

The primary user-facing application shell is **Procurement**. Strategy and Budget may remain technical domains, but ordinary procurement users should experience Strategy Alignment and Budget & Funding as lifecycle capabilities inside Procurement.

## 3. Module Purpose

Procurement Planning v2 exists to convert approved and funded demand into a legally traceable, tender-ready procurement package.

It must:

1. receive approved demand from Demand Intake and Approval;
2. verify that the demand has valid funding context;
3. include the demand in the appropriate procurement plan;
4. create a procurement package and package lines;
5. preserve traceability to strategy, budget, demand, and demand item;
6. determine procurement category, procurement method, contract type expectation, and required STD path;
7. apply templates/rule profiles to guide package structure;
8. run readiness checks before release;
9. support governed review, return, approval, and release;
10. create a Planning Release Package handoff;
11. lock released package baseline values;
12. allow Tender Management to consume the release;
13. update journey and evidence views;
14. prevent silent post-release edits.

Procurement Planning v2 does not include:

| Area | Reason |

## 4.3 Boundary Rule

Procurement Planning may consume upstream references and produce downstream release artifacts. It must not become a hidden editor of upstream or downstream legal state.

### Requirement PP2-FR-001

The system must provide a queue of approved demands awaiting planning.

### Acceptance Rules

A demand appears in the queue only if:

1. demand status is Approved;
2. demand has at least one approved demand item;
3. demand references a valid budget line;
4. demand is not already fully included in an active released package;
5. demand belongs to the user's procuring entity or authorized scope.

### Requirement PP2-FR-010

The system must allow an authorized Procurement Planner to include an approved demand in a procurement plan.

### Required Behavior

On inclusion, the system must create or update:

```text

```

### Required Fields

| Field | Required | Notes |

| demand_code | Yes | Example: DEM-MOH-2026-001. |

## 8.4 Procurement Package Creation

### Requirement PP2-FR-030

The system must create a Procurement Package from a Planning Inclusion Record or approved demand included in a plan.

For the WORKS seed:

```text
PKG-MOH-2026-001
```

### Required Behavior

Package creation must:

1. copy approved demand title/scope as baseline;
2. link to procurement plan;
3. link to planning inclusion;
4. link to demand;
5. link to demand item(s);
6. link to budget line;
7. set procurement category;
8. derive or require procurement method;
9. apply planning template/rule profile where configured;
10. create package line(s);
11. calculate estimated value from package lines;
12. set initial state to Draft.

### Prohibited Behavior

Package creation must not:

1. change approved demand scope;
2. change the budget line silently;
3. bypass inclusion;
4. create a package without traceability to demand item;
5. auto-release to tender without readiness/review/release controls.

## 8.6 Template and Rule Profile Application

### Requirement PP2-FR-050

The system must use planning templates or approved rule profiles to guide package defaults.

### Required Capabilities

1. Suggest planning template based on procurement category, method, value, entity, and demand type.
2. Apply defaults for category, method, contract type, risk profile, KPI profile, and decision criteria profile where available.
3. Allow controlled override before release with justification.
4. Record template/profile used.
5. Preserve downstream handoff values.

### Rule

Templates are required for ordinary package creation unless the system uses an equivalent approved planning rule profile.

### Non-Goal

Templates must not become a substitute for readiness checks or approval workflow.

## 8.12 Return / Correction / Supersession

## 10. State Model Requirements

The detailed state model will be produced in the dedicated Governance, State, and Approval Model document. This PRD establishes the required baseline.

## 10.1 Package State Model

The first implementation should use this compact package lifecycle:

```text
Draft
In Review
Returned for Correction
Approved
Ready for Release
Released to Tender
Consumed by Tender Management
Superseded
Cancelled
```

## 10.2 State Meaning

| State | Meaning | Ordinary Editing Allowed? |
|---|---|---:|
| Draft | Package is being prepared. | Yes |
| In Review | Package submitted for review/approval. | No, except recall/authorized return. |
| Returned for Correction | Reviewer returned package with reasons. | Yes, within correction scope. |
| Approved | Package approved but readiness/release may still be pending. | Limited |
| Ready for Release | Readiness checks passed and release may be performed. | No material edits without re-readiness. |
| Released to Tender | Planning Release Package created and handed to Tender Management. | No ordinary edits. |
| Consumed by Tender Management | Tender Management consumed release and linked/created tender. | No ordinary edits. |
| Superseded | Package/release replaced by newer governed version. | No |
| Cancelled | Package stopped with reason. | No |

## 10.3 Supporting Records Instead of Excessive States

Do not create top-level states for every operational concern.

Use supporting records for:

| Concern | Supporting Object/Record |
|---|---|
| Readiness | Package Readiness Result |
| Review decision | Package Review / Approval Record |
| Release | Planning Release Package |
| Consumption | Planning Release Consumption Record |
| Return reason | Review/Return Decision Record |
| Supersession | Supersession link/record |
| Audit | Planning Audit Event |

## 10.4 Required Transition Guards

| Transition | Guard |
|---|---|
| Draft → In Review | Required package fields and package lines exist. |
| In Review → Returned for Correction | Reviewer provides reason and required correction. |
| In Review → Approved | Reviewer has authority and critical checks pass or are not yet release-blocking. |
| Approved → Ready for Release | Readiness checks pass. |
| Ready for Release → Released to Tender | Authorized release user; handoff generated. |
| Released to Tender → Consumed by Tender Management | Tender Management consumes release and records tender code. |
| Any non-final state → Cancelled | Authorized user and reason required. |
| Released/Consumed → Superseded | Governed correction/supersession process only. |

## 16. Error and Blocker Requirements

| Blocker Code | Message | Owner / Required Action |
|---|---|---|

| PP2-BLOCK-NO-PACKAGE-LINE | Package has no package lines. | Add package line from approved demand item. |
| PP2-BLOCK-LINE-NO-DEMAND | Package line is not linked to approved demand item. | Restore demand item reference. |
| PP2-BLOCK-METHOD-MISSING | Procurement method is not selected. | Select or derive method. |
| PP2-BLOCK-STD-CATEGORY-MISSING | Required STD category is missing. | Identify required STD category. |
| PP2-BLOCK-READINESS-FAILED | Package readiness checks failed. | Resolve failed checks and rerun readiness. |
| PP2-BLOCK-APPROVAL-MISSING | Package approval is missing. | Submit for review/approval. |
| PP2-BLOCK-RELEASE-STALE | Release handoff is stale. | Regenerate/reapprove Planning Release Package. |
