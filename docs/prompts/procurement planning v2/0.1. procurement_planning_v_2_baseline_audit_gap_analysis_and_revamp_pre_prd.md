## 1. Executive Summary

The original Procurement Planning documentation established useful foundations: plans, packages, package lines, templates, profiles, template-driven package creation, method governance, and planning approval. Those ideas remain valid.

However, the original module documentation is no longer sufficient for KenTender's current architecture and implementation standard. It was produced before the later rigor was established for module documentation, governance/state design, seed alignment, handoff visibility, journey continuity, and implementation-grade Cursor packs.

The current result is predictable: Procurement Planning behaves like a package-management island rather than the legal and operational bridge between approved demand and tender creation.

Procurement Planning v2 must correct this.

The new design must treat Procurement Planning as the governed conversion layer that performs this exact responsibility:

```text
Approved Demand
→ Planning Inclusion
→ Procurement Plan
→ Procurement Package
→ Package Readiness Review
→ Planning Release Package
→ Tender Management Consumption
```

The module must not be understood merely as:

```text
Create packages from templates.
```

That is too shallow.

The correct interpretation is:

```text
Procurement Planning receives approved and funded demand, validates whether it can be planned, includes it in the correct procurement plan, structures it into a compliant package, confirms method/category/scope/readiness, obtains the required review/approval, locks the release baseline, and hands a legally traceable Planning Release Package to Tender Management.
```

The v2 revamp must therefore produce a full module documentation set in the new KenTender standard:

```text
1. Baseline Audit, Gap Analysis, and Revamp Pre-PRD
2. Full PRD
3. Strict Domain Model
4. Governance, State, and Approval Model
5. Roles and Permissions Matrix
6. UI Specification and Wireframes
7. WORKS Seed Data Specification
8. Smoke Contract
9. Cursor Implementation Pack
10. Implementation Tracker
```

This document is the first artifact. It audits the current documents, identifies the gaps, preserves the valid design ideas, and defines the v2 Pre-PRD scope and design direction.

## 3. Baseline Summary of the Current Procurement Planning Design

The current documentation defines Procurement Planning as the module that converts approved demand into:

```text
Procurement Plans
Procurement Packages
Package Lines
Template-driven method/category/profile defaults
Ready-for-Tender execution units
```

It correctly identifies these important concepts:

1. approved demand is the input;
2. procurement package is the execution unit;
3. package lines preserve traceability to demand and budget;
4. every package should use a planning template;
5. templates provide defaults for method, contract type, profiles, grouping, thresholds, and approvals;
6. package approval is required before readiness/tendering;
7. package totals should reconcile to package lines;
8. roles should be enforced server-side;
9. UI should use a workbench and package builder pattern.

These are not wrong. They are simply incomplete.

The core defect is that the design stops at package management and does not fully define the governed planning-to-tender handoff.

## 4. What Remains Valid and Should Be Preserved

The revamp should not discard everything. Several ideas remain valuable.

### 4.1 Preserve the Plan / Package / Package Line Separation

The distinction remains valid:

| Concept | Meaning |
|---|---|
| Procurement Plan | Governance container for a fiscal period or planning cycle. |
| Procurement Package | Execution unit that becomes a future tender or procurement process. |
| Procurement Package Line | Traceability link from package back to approved demand item and budget line. |

This distinction should be sharpened, not removed.

### 4.2 Preserve Templates as Planning Control Objects

The current template deep design correctly treats templates as planning control objects, not document stubs.

Procurement Planning v2 should preserve the principle:

```text
Every package must be created under a governed planning template or an explicitly approved planning rule profile.
```

However, templates must not become the whole mental model of Procurement Planning. They are one control mechanism inside a broader planning lifecycle.

### 4.3 Preserve Profile Defaults

The following profile types remain useful:

```text
Risk Profile
KPI Profile
Decision Criteria Profile
Vendor Management Profile
Threshold / Method Rule Profile
```

But v2 must clarify which profile belongs in Procurement Planning, which belongs in Tender Management, and which is only a planning-time recommendation passed downstream.

### 4.4 Preserve Template-Driven Method Derivation

The current idea that method can be derived from templates, thresholds, value, category, and demand type remains valid.

v2 must strengthen it with:

1. method justification;
2. override governance;
3. approval requirement;
4. release lock;
5. downstream tender creation constraints.

### 4.5 Preserve Workbench and Builder UI Pattern

The existing UI direction of:

```text
Planning Workbench
Package Builder / Editor
Template Review / Selection Surface
```

is valid.

But v2 must extend it with:

```text
Approved Demands Awaiting Planning
Plan Inclusion Review
Package Readiness Review
Release to Tender Review
Planning Release Handoff View
Journey Context Header
Evidence / Audit Timeline
```

### 4.6 Preserve Role-Based Server-Side Enforcement

The current roles and permission design correctly states that permissions must be enforced server-side.

v2 must add more precise transition authority and release governance.

## 5. Critical Gaps in the Current Procurement Planning Design

## 5.1 Gap 1 — Planning Is Not Explicitly Positioned as a Handoff Module

The current module treats Planning as a transformation layer from demand to package, but it does not sufficiently model the planning-to-tender handoff as a first-class business artifact.

The missing object/evidence is:

```text
Planning Release Package
PKGREL-MOH-2026-001
```

This handoff must clearly show:

1. source approved demand;
2. source budget line;
3. plan inclusion;
4. package scope;
5. procurement category;
6. procurement method;
7. estimated value;
8. required STD category;
9. what has been locked;
10. what Tender Management must do next;
11. whether Tender Management has consumed the release.

Without this, Tender Management appears disconnected from Planning.

## 5.2 Gap 2 — Planning Inclusion Is Under-Modeled

The current design jumps from approved demand into packages. It does not sufficiently define the formal moment when an approved demand becomes included in a procurement plan.

v2 requires a first-class or at least formally represented object:

```text
Planning Inclusion Record
PLANINCL-MOH-2026-001
```

This is not the same thing as a package.

Planning inclusion answers:

```text
Has this approved demand been accepted into the procurement plan?
Under which plan?
By whom?
When?
Against which budget line?
Is it now eligible for packaging?
```

## 5.3 Gap 3 — Plan, Inclusion, Package, Readiness, and Release Are Blurred

The current design has plans and packages, but not enough separation between these stages:

```text
Approved Demand
Planning Inclusion
Package Preparation
Package Readiness
Package Approval
Release to Tender
Tender Consumption
```

This causes implementation shortcuts where a package can move toward Tender Management without enough visible governance.

## 5.4 Gap 4 — State Model Is Too Shallow, But v2 Must Not Overcomplicate It

The current state model is too simple:

```text
Draft → Structured → Submitted → Approved → Ready for Tender
```

This is not enough for a government procurement planning process because it does not clearly distinguish readiness, approval, release, downstream consumption, return, cancellation, and post-release correction.

However, v2 must avoid the opposite mistake: creating a large state machine that ordinary users and implementers struggle to understand.

The correct design direction is:

```text
Complete enough to be legally safe.
Simple enough to be usable and implementable.
```

The Full PRD and Governance/State Model should start with a compact baseline state model, then add sub-statuses or reason fields only where they are genuinely needed.

Recommended baseline package lifecycle:

```text
Draft
In Review
Returned for Correction
Approved
Ready for Release
Released to Tender
Consumed by Tender Management
Superseded
Cancelled
```

Supporting readiness and handoff details should usually be modeled as separate fields or child records, not as excessive top-level states.

Examples:

| Concern | Preferred v2 Treatment |
|---|---|
| Readiness checks | Package Readiness Result / checklist, not many separate package states. |
| Review comments | Review/Approval record with decision and reason. |
| Tender consumption | Handoff status and consumption record. |
| Correction reason | Return/correction reason field and audit event. |
| Supersession | Explicit superseded_by / supersedes relationship. |

The final state model must explicitly cover review, return, readiness, release, downstream consumption, supersession, cancellation, and locking — but it should do so with the smallest clear set of states.

## 5.5 Gap 5 — Release Lock Rules Are Under-Specified

Once a package is released to Tender Management, it must not be casually edited.

v2 rule:

```text
A released package is a legal planning baseline. Material changes require governed correction, re-release, or supersession.
```

This must be enforced server-side.

## 5.6 Gap 6 — WORKS Master Seed Alignment Is Weak

The current seed data uses generic examples such as medical equipment, ICT, and emergency procurement.

Those examples may remain as non-master coverage seeds, but they cannot control the main KenTender journey.

The master v2 Planning seed must align to:

```text
District Hospital Renovation Works
```

Mandatory Planning records:

```text
PLAN-MOH-2026
PLANINCL-MOH-2026-001
PKG-MOH-2026-001
PKGLINE-MOH-2026-001-001
PKGREL-MOH-2026-001
```

Mandatory upstream references:

```text
DEM-MOH-2026-001
DEMITEM-MOH-2026-001-001
BUD-MOH-INFRA-2026-001
OBJ-MOH-HOSP-RENOV
JRN-MOH-2026-001
```

Mandatory downstream reference:

```text
TND-MOH-2026-001
```

## 5.7 Gap 7 — Procurement Category and STD Category Handoff Is Too Weak

Planning must tell Tender Management what kind of STD/tender document path is required.

For the WORKS scenario, the package must carry:

```text
procurement_category: Works
procurement_method: Open Tender
required_std_category: Works
required_std_type: Building and Associated Civil Engineering Works
```

This must flow into STD/Tender Document Readiness.

## 5.8 Gap 8 — Budget Reservation and Funding Confirmation Need Stronger Treatment

Planning should not mutate Budget, but it must preserve funding context.

At release, Planning must prove:

```text
budget line exists
budget line is approved
budget line is linked to the approved demand
estimated package value is within the approved/reserved funding envelope
```

Planning must not release a package where the funding link is missing, stale, or inconsistent.

## 5.9 Gap 9 — Demand Consumption Rules Are Under-Specified

Planning must define whether a demand item can be:

1. packaged once only;
2. split across packages;
3. merged with other demands;
4. re-planned after cancellation;
5. superseded after release.

For the WORKS v2 baseline, use the simplest strict rule:

```text
One approved demand item maps to one package line in one active released package.
```

Splits and merges may be designed later but must not be implicit.

## 5.10 Gap 10 — Readiness Checks Are Not Strong Enough

Before release to Tender Management, v2 must require a formal readiness review.

Minimum readiness checks:

```text
Approved demand exists
Demand approval certificate exists
Budget funding confirmation exists
Demand included in plan
Package line exists
Package line maps to demand item
Package value equals line value
Procurement category selected
Procurement method selected
Method justification valid where required
Required STD category identified
Schedule dates present
Approval/review complete
Release handoff ready
```

## 5.11 Gap 11 — UI Does Not Make Handoff Visible Enough

The current UI is package-centric.

v2 must be journey- and handoff-aware.

Every package detail page must show:

```text
Journey Context
Approved Demand Source
Planning Inclusion
Package Readiness
Release to Tender Handoff
Tender Consumption Status
Evidence / Audit
```

## 5.12 Gap 12 — Cursor Pack Was Too Permissive

The current Cursor pack gave implementation steps, but because the underlying design was shallow, it still left room for Cursor to implement a technically functional but product-weak module.

v2 Cursor pack must be built only after the Pre-PRD, PRD, domain model, governance model, UI spec, seed pack, and smoke contract are complete.

## 6. Root Cause of Scrappy Implementation

The implementation became scrappy for four reasons.

### 6.1 The Module Was Documented Before the Later Standard Matured

The later KenTender standard requires:

```text
rigorous pre-PRD
full PRD
strict domain tables
governance/state model
roles/permissions matrix
UI specification
seed data
smoke contract
Cursor implementation pack
implementation tracker
```

The Planning module did not receive that full treatment originally.

### 6.2 The Design Focused on Templates Before Handoffs

Templates are important, but they became the most detailed part of the design.

The more important legal/product question was not fully answered:

```text
What exact business artifact does Planning hand to Tender Management, and what does that artifact lock?
```

### 6.3 The Seed Was Not Designed End-to-End

The generic seed helped test Planning in isolation, but it did not tell the same story as Strategy, Budget, Demand, STD, and Tender.

The result is weak UAT continuity.

### 6.4 The UI Was Designed Around Package Work, Not Journey Continuity

A package workbench is necessary, but it is not sufficient.

Users need to see:

```text
Where did this package come from?
What is locked?
Where does it go next?
Has Tender Management consumed it?
What evidence proves release?
```

## 7. Procurement Planning v2 Design Principles

| Principle ID | Principle | Meaning |
|---|---|---|
| PP2-PRIN-001 | Planning is a governed conversion layer. | It converts approved demand into a tender-ready procurement package through controlled steps. |
| PP2-PRIN-002 | Handoff is a first-class outcome. | The Planning Release Package is a core artifact, not a hidden hook. |
| PP2-PRIN-003 | Plan inclusion is separate from package creation. | A demand can be accepted into a plan before it is fully packaged. |
| PP2-PRIN-004 | Package readiness must be explicit. | Release requires visible checks, not just status changes. |
| PP2-PRIN-005 | Released package is locked. | Material post-release changes require governed correction, supersession, or re-release. |
| PP2-PRIN-006 | Planning must preserve upstream truth. | Strategy, Budget, and Demand remain source modules; Planning consumes references and evidence. |
| PP2-PRIN-007 | Planning must serve downstream tendering. | Tender Management receives a complete, validated, business-readable package baseline. |
| PP2-PRIN-008 | Templates guide, but governance controls. | Templates provide defaults; states, approvals, checks, and release rules determine legality. |
| PP2-PRIN-009 | UI must guide ordinary users. | Users should work through queues, readiness, and next actions, not raw DocTypes. |
| PP2-PRIN-010 | WORKS seed is controlling. | Master implementation must use District Hospital Renovation Works as the end-to-end story. |
| PP2-PRIN-011 | Audit is designed in, not attached later. | Every inclusion, readiness check, approval, release, and consumption must leave evidence. |
| PP2-PRIN-012 | Cursor must not guess. | Later implementation pack must specify object names, APIs, selectors, services, tests, and no-go rules. |
| PP2-PRIN-013 | State model must be complete but not overbuilt. | Use a compact baseline state machine with supporting readiness, review, handoff, correction, and audit records rather than too many top-level statuses. |

## 9. Source Modules Consumed

## 9.1 Strategy

Planning consumes strategy context indirectly through Demand and Budget, but v2 must preserve traceability to:

```text
OBJ-MOH-HOSP-RENOV
PROG-MOH-INFRA
STRAT-MOH-2026
```

Planning must not edit strategy records.

## 9.2 Budget

Planning consumes funding context:

```text
BUD-MOH-INFRA-2026-001
```

Planning must not approve, reserve, unreserve, or reclassify budget unless a formal Budget module API explicitly permits a controlled reservation status update.

Default v2 rule:

```text
Planning reads budget and validates funding link. Budget remains authoritative.
```

## 9.3 Demand Intake and Approval

Planning consumes approved demand:

```text
DEM-MOH-2026-001
DEMITEM-MOH-2026-001-001
```

Planning must not edit approved demand scope.

If scope correction is required, Demand must be returned/amended through governed upstream correction, or Planning must create a governed planning exception with source evidence.

## 10. Downstream Modules Served

## 10.1 STD / Tender Document Readiness

Planning must provide enough information to identify the correct STD path:

```text
Procurement category: Works
Method: Open Tender
Required STD family: Works
Works subtype: Building and Associated Civil Engineering Works
BOQ required: Yes
Drawings/site information required: Yes
```

## 10.2 Tender Management

Tender Management consumes the Planning Release Package.

The release must be sufficient to create:

```text
TND-MOH-2026-001
```

without re-deciding the planning baseline.

Tender Management may configure tender-specific details, but it must not silently change package method/category/scope/budget baseline.

## 10.3 Supplier Participation & Bid Submission

Planning does not manage suppliers, but its package baseline determines later supplier-facing tender structure.

Planning must therefore pass downstream expectations:

```text
submission method implied by tender method
works document requirements
BOQ requirement
evaluation baseline category
contract type expectation
```

## 10.4 Bid Opening, Evaluation, and Contract Management

Planning sets early downstream intent through:

```text
method
category
estimated value
scope
risk profile
KPI profile
decision criteria profile
contract type expectation
```

The later modules may refine legal details but should not lose planning intent.

## 11. Procurement Planning v2 Scope

### 11.1 In Scope

Procurement Planning v2 includes:

1. approved demand intake into planning queue;
2. planning inclusion decision;
3. procurement plan container;
4. procurement package creation;
5. package lines linked to demand items;
6. template/rule-based package defaults;
7. method/category/contract type planning decision;
8. package readiness validation;
9. planning review/approval workflow;
10. release-to-tender workflow;
11. Planning Release Package handoff card;
12. release consumption tracking by Tender Management;
13. journey linkage and evidence timeline;
14. WORKS master seed alignment;
15. role and permission enforcement;
16. audit event creation;
17. UI workbench, queues, package detail, readiness review, and handoff views.

### 11.2 Out of Scope

Procurement Planning v2 does not include:

1. creating or approving strategy objectives;
2. creating or approving budget lines;
3. approving demand;
4. editing approved demand content;
5. STD library governance;
6. tender document generation;
7. tender publication;
8. supplier participation or bid submission;
9. tender closing;
10. bid opening;
11. evaluation and award;
12. contract execution;
13. payments;
14. supplier performance management execution.

### 11.3 Boundary Rule

Procurement Planning may read upstream references and produce downstream release artifacts. It must not become a hidden editor of upstream or downstream modules.

## 14. Core Use Cases

## 14.1 Approved Demand Appears in Planning Queue

As a Procurement Planner, I need approved demands to appear in a queue so that I can decide whether and how to include them in a procurement plan.

Required system behavior:

```text
Only approved demand appears.
Demand must include budget line.
Demand must not already be fully planned in an active package.
Demand shows source department, category, estimated value, priority, and budget line.
```

## 14.2 Include Demand in Procurement Plan

As a Procurement Planner, I need to include an approved demand in a procurement plan before packaging it.

Required system behavior:

```text
Create Planning Inclusion Record.
Link to demand, demand item, budget line, plan, fiscal year, entity.
Record actor and timestamp.
Update Journey step.
```

## 14.3 Create Package from Included Demand

As a Procurement Planner, I need to create a procurement package from included demand.

Required system behavior:

```text
Select or apply appropriate planning template/rule profile.
Create package header.
Create package line from demand item.
Preserve budget line.
Derive category/method/contract/profile defaults.
Calculate estimated value from lines.
```

## 14.4 Review and Adjust Package Within Policy

As a Planner or Reviewer, I need controlled ability to adjust package metadata before release.

Allowed examples:

```text
schedule window
package title/description within approved scope
method override with justification and approval
risk/profile selection where allowed
```

Forbidden examples:

```text
changing approved demand scope silently
changing budget line silently
changing method after release without governed correction
removing traceability to demand item
```

## 14.5 Run Package Readiness Review

As a Procurement Planner, I need the system to show whether the package is ready for release to Tender Management.

Readiness checks must be business-readable and server-backed.

## 14.6 Submit Package for Review / Approval

As a Procurement Planner, I need to submit the package for review before release.

The system must validate required fields and block incomplete packages.

## 14.7 Approve / Return / Reject Package

As a Planning Reviewer or Planning Authority, I need to approve, return, or reject a package with reasons.

Every decision must be auditable.

## 14.8 Release Package to Tender Management

As an authorized Procurement Planner / Head of Procurement / Planning Authority, I need to release an approved package to Tender Management.

The release must create:

```text
Planning Release Package
PKGREL-MOH-2026-001
```

and lock the package baseline.

## 14.9 Tender Management Consumes Release

As a Procurement Officer, I need to create or open the TM2 Tender from the released Planning package.

The system must update the handoff status to:

```text
Consumed
```

and link:

```text
PKG-MOH-2026-001 → TND-MOH-2026-001
```

## 14.10 View Planning Evidence

As an Auditor, I need to see all planning decisions, approvals, readiness checks, release locks, and consumption events.

## 16. Governance and State Philosophy

The v2 governance model must be designed before implementation.

The state model must be complete, but it must not be unnecessarily complicated at the first implementation stage.

Procurement Planning v2 should use a compact, understandable baseline state machine and then attach supporting records for review decisions, readiness checks, release handoffs, consumption, correction, supersession, and audit evidence.

The module must distinguish these concerns, but not necessarily as separate top-level package statuses:

```text
Plan state
Planning inclusion state
Package preparation state
Package review decision
Package readiness result
Release handoff state
Tender consumption state
Correction/supersession state
Cancellation/audit state
```

The final state model will be produced in the dedicated governance document, but the Pre-PRD requires the following baseline direction.

### 16.0 Recommended Baseline State Model

The initial v2 package lifecycle should prefer this compact state set:

```text
Draft
In Review
Returned for Correction
Approved
Ready for Release
Released to Tender
Consumed by Tender Management
Superseded
Cancelled
```

This set is intentionally smaller than the full list of possible operational conditions.

Supporting details should be represented separately:

| Concern | Recommended Representation |
|---|---|
| Package readiness | Package Readiness Result / checklist. |
| Review/approval decision | Package Review / Approval Record. |
| Planning release | Planning Release Package handoff status. |
| Tender consumption | Planning Release Consumption Record. |
| Return reason | Return/correction reason and audit event. |
| Post-release change | Correction, re-release, or supersession record. |
| Cancellation reason | Cancellation reason and audit event. |

The Governance/State Model document may refine names, but it must preserve the principle that the state model should be understandable to users and implementable by Cursor without a sprawling status explosion.

### 16.1 Source-of-Truth Rule

Procurement Planning is authoritative only for planning records.

It is not authoritative for:

```text
Strategy approval
Budget approval
Demand approval
STD readiness
Tender publication
Supplier bid submission
Bid opening
Evaluation
Contract
```

### 16.2 Release Lock Rule

After release to Tender Management:

```text
package scope
method
category
budget link
package lines
estimated value
required STD category
```

are locked for ordinary editing.

### 16.3 Material Change Rule

If a material change is required after release, v2 must support a governed path:

```text
Correction Request
Return from Tender Management
Re-readiness Review
Re-release
Supersession
Audit trail
```

The exact design may be finalized in the governance/state document, but implementation must not allow silent edits.

### 16.4 Handoff Status Rule

The Planning Release Package can have statuses such as:

```text
Draft
Ready
Handed Off
Consumed
Returned
Stale
Superseded
Cancelled
Audit Only
```

### 16.5 Rejection / Return Rule

Any return or rejection must require:

```text
reason
actor
timestamp
previous state
next state
required correction
```

### 16.6 Audit Rule

Every significant planning transition must emit or store an audit event.

## 21. Open Decisions for v2

These must be resolved before or during the Full PRD.

| Decision ID | Decision | Recommended Default |
|---|---|---|
| PP2-DEC-001 | Is Planning Inclusion a real DocType/table or a handoff/evidence-only object? | Real object if feasible; otherwise formal handoff/evidence object with equivalent fields. |
| PP2-DEC-002 | Can one demand item be split across multiple packages? | No for v2 baseline. One active demand item → one package line. |
| PP2-DEC-003 | Can multiple demands be merged into one package? | Not for WORKS baseline; allow future controlled design. |
| PP2-DEC-004 | Who approves package release? | Planning Authority or Head of Procurement depending existing role model. |
| PP2-DEC-005 | Does `Ready for Tender` equal `Released to Tender`? | No. Ready means checks pass; Released means governed handoff created. |
| PP2-DEC-006 | Should Tender Management be able to return a release? | Yes, through governed return/correction path. |
| PP2-DEC-006A | How complex should the first state model be? | Use the compact baseline: Draft, In Review, Returned for Correction, Approved, Ready for Release, Released to Tender, Consumed by Tender Management, Superseded, Cancelled. Add separate readiness/review/handoff records rather than many extra statuses. |
| PP2-DEC-007 | Are templates mandatory for every package? | Yes, or equivalent approved planning rule profile. |
| PP2-DEC-008 | Does Planning reserve budget? | No by default; Budget remains authoritative. Planning validates reservation/funding context. |
| PP2-DEC-009 | Should generic medical/ICT/emergency seeds remain? | Yes as secondary coverage, clearly non-master. |
| PP2-DEC-010 | Should Planning create TM2 Tender directly? | Prefer controlled handoff consumed by Tender Management; automatic creation only if existing architecture supports it without bypassing tender governance. |
