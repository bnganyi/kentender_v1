## 1. Purpose of This Domain Model

This document defines the strict domain model for Procurement Planning v2.

It translates the v2 PRD into implementation-ready business objects, relationships, fields, constraints, indexes, ownership rules, validation rules, and source-of-truth boundaries.

The purpose is to prevent Cursor from guessing:

```text
what objects exist;
which fields are required;
which module owns each object;
which values are copied, referenced, locked, or passed forward;
which objects are authoritative;
which objects are evidence/supporting records;
which relationships are mandatory;
which fields must be indexed;
which fields must be auditable;
which fields must align to the WORKS seed.
```

This domain model is intentionally stricter than a normal product description. It is meant to be converted into DocTypes, database tables, child tables, JSON structures, services, and tests with minimal interpretation.

## 2. Domain Boundary

## 2.1 Objects Owned by Procurement Planning v2

Procurement Planning v2 owns these objects:

| Object | Ownership Level | Purpose |
|---|---|---|
| Procurement Plan | Authoritative planning object | Fiscal/planning container for procurement activity. |
| Planning Inclusion Record | Authoritative planning object | Formal inclusion of approved demand into a procurement plan. |
| Procurement Package | Authoritative planning object | Tender-ready execution unit created from included demand. |
| Procurement Package Line | Authoritative planning child object | Traceability from package to demand item and budget line. |
| Package Method Decision | Authoritative/supporting planning object | Records category/method derivation, confirmation, or override. |
| Package Readiness Result | Authoritative supporting object | Server-backed readiness result before release. |
| Package Review Decision | Authoritative supporting object | Review/approval/return/cancel decision evidence. |
| Planning Release Package | Authoritative planning handoff object | Locked handoff from Planning to Tender Management. |
| Planning Release Consumption Record | Authoritative supporting object | Records Tender Management consumption of release. |
| Planning Correction / Supersession Record | Authoritative supporting object | Records governed post-release correction or replacement. |
| Planning Audit Event | Evidence object | Ordered planning audit trail. |
| Planning Evidence Link | Evidence child/JSON object | Links source/evidence objects to planning records. |
| Planning Template / Rule Profile Reference | Configuration/reference object | Template/rule basis for package defaults. |

## 2.2 Objects Consumed but Not Owned

Procurement Planning consumes these objects but must not own or silently mutate them:

| External Object | Owning Module | Planning Usage |
|---|---|---|
| Strategy Objective | Strategy | Traceability context. |
| Budget Line | Budget | Funding context and validation. |
| Demand | Demand Intake and Approval | Source approved need. |
| Demand Item | Demand Intake and Approval | Source package line basis. |
| Demand Approval Certificate | Demand Intake and Approval / Journey Handoff | Evidence that demand is approved. |
| Budget Funding Confirmation | Budget / Journey Handoff | Evidence that funding exists. |
| STD Template Version | STD Admin | Required STD path / downstream reference. |
| Tender STD Instance | STD / Tender Management | Downstream tender document setup. |
| TM2 Tender | Tender Management | Downstream tender created from release. |
| Procurement Journey | Lifecycle overlay | Navigation/evidence aggregation. |
| Procurement Handoff Card | Lifecycle overlay | Cross-module handoff visibility. |

## 2.3 Source-of-Truth Rule

Procurement Planning is authoritative for planning records only.

Planning must not be authoritative for:

```text
strategy approval
budget approval
budget availability calculation unless exposed by Budget service
demand approval
STD library activation
tender creation/publication
supplier bid submission
bid opening
evaluation
award
contract formation
```

If a Planning record conflicts with an upstream source, the upstream source wins and Planning must be marked blocked, stale, returned, or requiring correction.

## 3.3 Code Immutability Rule

Once created, business codes must not be changed by ordinary users.

If a correction requires replacement, create a new correction/supersession record. Do not mutate historical codes.

## 5. Object 1 — Procurement Plan

## 5.1 Purpose

A Procurement Plan is the fiscal or planning-cycle container into which approved demand is included and from which packages are prepared.

It answers:

```text
Which procurement plan does this approved demand belong to?
Which fiscal year and procuring entity govern this planning activity?
Which packages are being prepared, reviewed, released, or consumed under this plan?
```

## 5.2 Required Fields

| Field | Type | Required | Mutable After Active? | WORKS Value | Notes |
|---|---|---:|---:|---|---|
| procurement_plan_code | Data/String | Yes | No | PLAN-MOH-2026 | Unique business code. |
| plan_title | Data/String | Yes | Limited | Ministry of Health Procurement Plan FY 2026/2027 | Business title. |
| procuring_entity_code | Link/Data | Yes | No | PE-MOH | Entity owning plan. |
| fiscal_year | Data/String | Yes | No | 2026/2027 | Use repository fiscal-year convention. |
| planning_cycle_code | Data/String | Optional | No | BUDGET-MOH-2026 | Link to budget cycle if available. |
| plan_description | Text | Optional | Yes | Procurement plan for approved MOH needs in FY 2026/2027. | Description. |
| status | Select | Yes | Yes through guarded action | Active / Approved | See plan states below. |
| approved_by | Link/User | Conditional | No after set | USER-PLAN-001 | Required if status Approved/Active. |
| approved_at | Datetime | Conditional | No after set | 2026-04-10T10:00:00+03:00 | Required if status Approved/Active. |
| created_by | Link/User | Yes | No | USER-PLAN-001 | Creator. |
| created_at | Datetime | Yes | No | System / seed | Timestamp. |
| updated_at | Datetime | Yes | System | System | Timestamp. |
| is_master_seed | Boolean | Yes | No | true | Seed marker. |

## 5.3 Allowed Plan States

```text
Draft
Active
Closed
Cancelled
Superseded
```

Repository may use `Approved` instead of `Active`. If so, map `Approved` to active planning behavior.

## 5.4 Constraints

| Constraint ID | Rule |
|---|---|
| PLAN-CON-001 | `procurement_plan_code` must be unique. |
| PLAN-CON-002 | A plan must belong to one procuring entity. |
| PLAN-CON-003 | A plan must belong to one fiscal year/planning cycle. |
| PLAN-CON-004 | Closed/cancelled plans cannot accept new inclusions. |
| PLAN-CON-005 | Superseded plans must reference the successor plan if applicable. |

## 5.5 Required Indexes


| Procurement Plan → Procurement Package | 1:N | Yes after package creation |

## 6. Object 2 — Planning Inclusion Record

## 6.1 Purpose

A Planning Inclusion Record is the formal acceptance of approved demand into a procurement plan.

It is separate from package creation.

It answers:

```text
Was this approved demand accepted into a procurement plan?
Which plan?
Who included it?
When?
Against which budget line?
Is it eligible for packaging?
```

## 6.2 Implementation Requirement

Prefer a real DocType/table.

If the current repository cannot support a standalone inclusion object immediately, Cursor may implement it as a formal handoff/evidence object only if all required fields below are stored and queryable.

The implementation must still allow:

```text
PLANINCL-MOH-2026-001
```

to appear as a visible journey/handoff artifact.

## 12. Object 8 — Planning Release Package

It is the most important object in the v2 redesign.

It answers:

```text
What exactly did Planning release?
What values were locked?
What values were passed forward?
What must Tender Management consume?
Has Tender Management consumed it?
```

For the WORKS seed:

```text
PKGREL-MOH-2026-001
```

1. a Procurement Planning object; or
