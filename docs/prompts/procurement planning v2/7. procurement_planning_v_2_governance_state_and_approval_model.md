## 1. Purpose

This document defines the governance, state, approval, locking, correction, and audit model for Procurement Planning v2.

It converts the PRD and Strict Domain Model into explicit operational rules:

```text
who may act;
when they may act;
what state changes are allowed;
what checks must pass;
what records must be created;
what values are locked;
what happens when work is returned;
what happens after release;
how Tender Management consumes or returns a release;
how audit evidence is produced.
```

The goal is not to create an oversized state machine. The goal is to make the module legally safe and implementable without confusing users.

The design therefore uses:

1. a compact primary package lifecycle;
2. separate records for readiness checks;
3. separate records for review/approval decisions;
4. separate handoff object for Planning Release Package;
5. separate consumption record for Tender Management;
6. separate correction/supersession records for post-release changes;
7. audit events for all significant transitions.

## 2.1 In Scope

This governance model covers:

| Area | Covered |
|---|---|
| Approved demand entry into planning | Yes |
| Planning inclusion | Yes |
| Package creation | Yes |
| Package editing before release | Yes |
| Package line governance | Yes |
| Method/category decision | Yes |
| Readiness checks | Yes |
| Review and approval | Yes |
| Release to Tender Management | Yes |
| Release locking | Yes |
| Tender Management consumption | Yes |
| Tender Management return for correction | Yes |
| Correction and re-release | Yes |
| Supersession | Yes |
| Cancellation | Yes |

## 2.2 Out of Scope

This governance model does not govern:

| Area | Owning Module |
|---|---|
| Strategy approval | Strategy |
| Budget approval and appropriation | Budget |
| Demand approval | Demand Intake and Approval |
| STD template approval/activation | STD Admin |
| Tender approval/publication | Tender Management |
| Supplier submission | Supplier Participation & Bid Submission |
| Tender closing | Tender Closing / Tender Management |
| Bid opening | Bid Opening |
| Evaluation and award | Evaluation & Award |
| Contract execution | Contract Management |

## 2.3 Source-of-Truth Rule

Procurement Planning state may not override upstream or downstream source modules.

If Planning references an upstream record that becomes invalid, stale, cancelled, or superseded, Planning must become blocked, stale, returned, or require correction. It must not silently rewrite upstream records.

## 3. Governance Principles

| Principle ID | Principle | Meaning |
|---|---|---|
| PP2-GOV-001 | Compact main lifecycle | Keep the primary package status understandable. |
| PP2-GOV-002 | Supporting records carry detail | Use readiness, review, release, consumption, and correction records instead of many top-level statuses. |
| PP2-GOV-003 | Release is a legal handoff | Release creates a locked baseline for Tender Management. |
| PP2-GOV-004 | No silent post-release edits | Any material change after release requires governed correction, re-release, or supersession. |
| PP2-GOV-005 | Readiness must be server-backed | UI checklists cannot substitute for backend validation. |
| PP2-GOV-006 | Every adverse decision needs a reason | Return, rejection, cancellation, and supersession require reasons. |
| PP2-GOV-007 | Authority is role- and state-based | A user may act only if the object state and the user's role allow it. |
| PP2-GOV-008 | Handoffs are visible and auditable | Planning Release Package must show locked values, passed-forward values, and evidence. |
| PP2-GOV-009 | Tender consumption is explicit | Tender Management must consume the release and record the tender code. |
| PP2-GOV-010 | Audit is immutable | Transition decisions and evidence must not be overwritten. |

## 4. Primary Package State Model

## 4.1 Baseline Package States

Use the following compact package lifecycle:

```text
Draft
In Review
Returned for Correction
Approved
Ready for Release
Released to Tender
Consumed by Tender Management
Superseded
Cancelled
```

This is the authoritative user-facing state model for Procurement Package.

## 4.2 State Definitions

| State | Meaning | Ordinary Editing Allowed? | Final? |
|---|---|---:|---:|
| Draft | Package is being prepared by Planning. | Yes | No |
| In Review | Package has been submitted for review/approval. | No, except recall/return flow if configured. | No |
| Returned for Correction | Reviewer or downstream consumer returned it with reasons. | Yes, within correction scope. | No |
| Approved | Package has been approved as structurally acceptable. | Limited; material edits require re-review. | No |
| Ready for Release | Readiness checks passed and package may be released. | No material edits without re-readiness. | No |
| Released to Tender | Planning Release Package has been created and handed to Tender Management. | No ordinary editing. | No |
| Consumed by Tender Management | Tender Management consumed the release and linked/created the tender. | No ordinary editing. | No for historic tracking; active planning is complete. |
| Superseded | Package/release has been replaced by a newer governed package/release. | No | Yes |
| Cancelled | Package is stopped with reason. | No | Yes |

## 4.3 State Grouping for UI

For dashboard grouping, map states as follows:

| State | Workbench Group |
|---|---|
| Draft | My Work / In Preparation |
| In Review | Needs Review |
| Returned for Correction | Needs My Action |
| Approved | Approved Packages |
| Ready for Release | Ready for Handoff |
| Released to Tender | Handed Off |
| Consumed by Tender Management | Completed / Consumed |
| Superseded | Audit / Historical |
| Cancelled | Audit / Historical |

## 5. Supporting State Models

## 5.1 Procurement Plan State

Procurement Plan uses a simple state model:

```text
Draft
Active
Closed
Cancelled
Superseded
```

| State | Meaning |
|---|---|
| Draft | Plan is being prepared. |
| Active | Plan is approved/active and may receive inclusions/packages. |
| Closed | Planning cycle closed; no new inclusions. |
| Cancelled | Plan was cancelled. |
| Superseded | Plan replaced by another plan. |

For the WORKS seed:

```text
PLAN-MOH-2026 = Active / Approved
```

Repository may use `Approved`; map it to `Active` behavior.

## 5.2 Planning Inclusion State

Planning Inclusion Record uses:

```text
Included
Packaged
Returned
Cancelled
Superseded
```

| State | Meaning |
|---|---|
| Included | Approved demand included in plan. |
| Packaged | Procurement Package created from inclusion. |
| Returned | Inclusion returned/corrected before package completion. |
| Cancelled | Inclusion stopped. |
| Superseded | Replaced by newer inclusion/package baseline. |

For the WORKS seed:

```text
PLANINCL-MOH-2026-001 = Packaged / Consumed
```

## 5.3 Readiness Result State

Readiness Result uses:

```text
Not Run
Passed
Failed
Passed With Warnings
Stale
```

| State | Meaning | Release Allowed? |
|---|---|---:|
| Not Run | Readiness has not been run. | No |
| Passed | All blocking checks passed. | Yes |
| Failed | One or more blocking checks failed. | No |
| Passed With Warnings | No blocking failures; warnings exist. | Configurable; default Yes with reviewer awareness. |
| Stale | Source changed after readiness was run. | No |

## 5.4 Planning Release Package State

Planning Release Package uses:

```text
Draft
Ready
Handed Off
Consumed
Returned
Stale
Superseded
Cancelled
Audit Only
```

| State | Meaning |
|---|---|
| Draft | Release being prepared. |
| Ready | Release generated but not handed off. |
| Handed Off | Release handed to Tender Management. |
| Consumed | Tender Management consumed it. |
| Returned | Tender Management returned it for correction. |
| Stale | Source package changed or source inconsistency detected. |
| Superseded | Replaced by newer release. |
| Cancelled | Release cancelled. |
| Audit Only | Historical/evidence-only. |

For the WORKS seed:

```text
PKGREL-MOH-2026-001 = Consumed
```

## 5.5 Tender Consumption State

Planning Release Consumption Record uses:

```text
Consumed
Returned
Failed
```

| State | Meaning |
|---|---|
| Consumed | Release successfully linked to TM2 Tender. |
| Returned | Tender Management returned release for correction. |
| Failed | Consumption attempted but failed validation. |

For the WORKS seed:

```text
PKGCONSUME-MOH-2026-001 = Consumed
```

## 7.2 UI Action Rule

Buttons must not appear merely because a user has a role. Buttons must appear only if both are true:

```text

object state allows action
```

If an action is blocked, the UI should show a business-readable blocker where useful.

Example:

```text
Release to Tender is unavailable because package readiness is stale. Re-run readiness checks before release.
```

## 8. Transition Guard Details

## 8.1 Create Package from Inclusion

### Allowed Actor

```text
Procurement Planner
Planning Authority
```

### Preconditions

1. Demand status is Approved.
2. Demand Approval Certificate exists or can be referenced.
3. Budget line exists.
4. Procurement Plan is Active/Approved.
5. Planning Inclusion exists or is created in the same guarded action.
6. Demand item is not already included in an active package line for v2 baseline.
7. User has access to procuring entity.

### Creates

```text
Procurement Package
Procurement Package Line(s)
Method Decision draft/current record where possible
Audit Event
```

### Blocks

| Blocker Code | Message |
|---|---|
| PP2-BLOCK-DEMAND-NOT-APPROVED | Demand is not approved. |
| PP2-BLOCK-BUDGET-MISSING | Budget line is missing. |
| PP2-BLOCK-DEMAND-ITEM-ALREADY-PACKAGED | Demand item is already part of an active package. |
| PP2-BLOCK-PLAN-INACTIVE | Procurement plan is not active. |

## 8.2 Submit for Review

### Preconditions

1. Package state is Draft or Returned for Correction.
2. Package has at least one package line.
3. Package title, scope, category, method, estimated value, currency, budget line are present.
4. Package total equals active package line total.
5. Required template/rule profile/manual basis exists.

### Creates

```text
Package Review Decision: Submitted
Audit Event
```

### State Change

```text
Draft / Returned for Correction → In Review
```

## 8.3 Return for Correction

### Preconditions

1. Package is In Review, Approved, Released, or Consumed depending return source.
2. Actor has reviewer/downstream return authority.
3. Reason is provided.
4. Required correction is provided.

### Creates

```text
Package Review Decision or Correction Record
Audit Event
```

### State Change

```text
In Review → Returned for Correction
```

or, for downstream return:

```text
Released / Consumed → Returned for Correction
```

### Mandatory Reason Fields

```text
return_reason
required_correction
affected_fields_json if post-release
```

## 8.4 Approve Package

### Preconditions

1. Package is In Review.
2. Reviewer has approval authority.
3. No critical structural blockers exist.
4. Method override, if any, has required justification.
5. Budget link and demand link are intact.

### Creates

```text
Package Review Decision: Approved
Audit Event
```

### State Change

```text
In Review → Approved
```

## 8.5 Run Readiness

### Preconditions

1. Package exists.
2. User/system has authority to run readiness.
3. Package is not Cancelled or Superseded.

### Creates

```text
Package Readiness Result
Readiness Check Items
Audit Event
```

### Does Not Necessarily Change Package State

Running readiness creates evidence. It moves the package only if the action explicitly marks it ready or if implementation combines run + mark-ready.

Recommended first implementation:

```text
Run readiness → creates result.
Mark ready for release → guarded transition using current readiness result.
```

This is clearer for audit and easier to test.

## 8.6 Mark Ready for Release

### Preconditions

1. Package state is Approved.
2. Current readiness result is Passed or accepted Passed With Warnings.
3. Readiness result is not stale.
4. User has authority.

### State Change

```text
Approved → Ready for Release
```

### Creates

```text
Audit Event
```

## 8.7 Release to Tender

### Preconditions

1. Package state is Ready for Release.
2. Current readiness result is Passed or accepted Passed With Warnings.
3. Readiness result is not stale.
4. Package has at least one line.
5. Package line(s) link to approved demand item(s).
6. Package line(s) link to budget line.
7. Procurement category is present.
8. Procurement method is present.
9. Required STD category is present.
10. User has release authority.
11. No active release already exists unless this is re-release/supersession.

### Creates

```text
Planning Release Package
Procurement Handoff Card if shared lifecycle layer exists
Planning Audit Event
```

### State Change

```text
Ready for Release → Released to Tender
```

### Locks

```text
package_code
package_title
procurement_plan_code
planning_inclusion_code
demand_code
demand_item_code(s)
budget_line_code
procurement_category
procurement_method
estimated_value
currency
required_std_category
package_scope
package_lines
release timestamp
release actor
```

## 8.8 Consume Release in Tender Management

### Allowed Actor

```text
Procurement Officer
Tender Manager
System service acting under Tender Management
```

### Preconditions

1. Planning Release Package exists.
2. Release status is Handed Off or equivalent active state.
3. Release is not stale.
4. Tender Management user/system has authority.
5. Tender creation or link preserves planning baseline.

### Creates / Updates

```text
TM2 Tender reference
Planning Release Consumption Record
Planning Release Package status = Consumed
Package state = Consumed by Tender Management
Audit Event
```

### WORKS Result

```text
PKGREL-MOH-2026-001 → TND-MOH-2026-001
```

## 8.9 Return Release from Tender Management

### Allowed Actor

```text
Tender Manager
Authorized Procurement Officer
Planning Authority by agreement
```

### Preconditions

1. Release exists.
2. Tender has not reached a non-returnable downstream state.
3. Return reason is provided.
4. Required correction is provided.

### Creates / Updates

```text
Release status = Returned
Package state = Returned for Correction
Planning Correction Record
Audit Event
```

### Must Not

Tender Management must not silently edit Planning baseline fields.

## 8.10 Supersede Package / Release

### Preconditions

1. Original package/release exists.
2. Supersession reason is provided.
3. Replacement package/release exists or is created through governed action.
4. Planning Authority approves.
5. Downstream impact is recorded.

### Creates / Updates

```text
Planning Correction / Supersession Record
Old package state = Superseded
Old release state = Superseded
New package/release active
Audit Events
```

## 9. Approval Model

## 9.1 Approval Levels

Use a compact approval model for first implementation.

| Approval Level | Applies To | Required For v2 Baseline |
|---|---|---:|
| Planner Preparation | Draft package and inclusion work | Yes |
| Planning Review | Package review and approval | Yes |
| Release Authorization | Final handoff to Tender Management | Yes |
| Post-Release Correction Approval | Material changes after release | Yes |
| Cancellation Approval | Cancellation after review/release | Conditional |

## 9.2 Recommended Role Authority

| Role | Authority |
|---|---|
| Procurement Planner | Create inclusion/package; edit draft/returned package; run readiness; submit for review; may release only if configured. |
| Planning Reviewer | Review package; approve; return for correction; run/read readiness. |
| Head of Procurement / Planning Authority | Approve release; cancel; supersede; approve post-release correction. |
| Procurement Officer | Consume release in Tender Management; return release before non-returnable tender state if authorized. |
| Procurement Manager / Tender Manager | Return consumed release before tender non-returnable state if authorized. |
| Budget Officer | View/confirm funding context; not package approval authority by default. |
| Auditor / Oversight | Read-only. |
| System Administrator | Technical configuration only; not business approval by default. |
| Supplier User | No internal Planning authority. |

## 9.3 Release Authority Default

Default first implementation:

```text
Planning Authority / Head of Procurement releases package to Tender Management.
```

Optional configuration may allow Procurement Planner to release after approval/readiness if the procuring entity's governance policy allows it.

If implemented, that configuration must be explicit and auditable.

## 9.4 Method Override Approval

If the package method is overridden from template/rule/threshold recommendation:

```text
override_flag = true
override_reason required
reviewer approval required
approval stored in Package Method Decision or Review Decision
```

## 10. Readiness Governance

## 10.1 Readiness Is a Release Gate

Readiness checks are mandatory before release.

A package cannot move to Ready for Release unless the current readiness result is:

```text
Passed
```

or, where configuration permits:

```text
Passed With Warnings
```

## 10.2 Blocking Readiness Checks

Minimum blocking checks:

| Check ID | Blocking? |
|---|---:|
| PP2-READY-001 Approved demand exists | Yes |
| PP2-READY-002 Demand approval certificate exists | Yes |
| PP2-READY-003 Budget funding confirmation exists | Yes |
| PP2-READY-004 Demand included in procurement plan | Yes |
| PP2-READY-005 Package line exists | Yes |
| PP2-READY-006 Package line maps to demand item | Yes |
| PP2-READY-007 Package line maps to budget line | Yes |
| PP2-READY-008 Package total matches package lines | Yes |
| PP2-READY-009 Procurement category selected | Yes |
| PP2-READY-010 Procurement method selected | Yes |
| PP2-READY-011 Method justification/derivation recorded | Yes |
| PP2-READY-012 Required STD category identified | Yes |
| PP2-READY-014 Required review/approval complete | Yes before release |
| PP2-READY-015 Release handoff can be generated | Yes |

Schedule dates may be warning-level in first implementation unless the business requires them as release blockers.

## 10.3 Stale Readiness

Readiness must become stale if any locked/release-critical source value changes after the readiness run.

Stale triggers include:

```text
package title/scope changed
package lines changed
estimated value changed
budget line changed
method/category changed
required STD category changed
planning inclusion changed
source demand or budget reference became stale/cancelled/superseded
```

A stale readiness result blocks release.

## 11. Release Locking Rules

## 11.1 Locked Values

After Release to Tender, ordinary editing is forbidden for:

```text
package_code
package_title
package_description/scope
procurement_plan_code
planning_inclusion_code
demand_code
demand_item_code(s)
budget_line_code
procurement_category
procurement_method
contract_type_expectation
required_std_category
required_std_type
estimated_value
currency
package_lines
release actor/timestamp
```

## 11.2 Allowed Post-Release Updates

Allowed without correction/supersession:

```text
handoff status updates
consumed_by / consumed_at
stale flag generated by validation
technical audit references
non-material internal comments if permitted and audit logged
```

## 11.3 Material Change Rule

Any change to a locked value after release is a material change.

Material changes require:

```text
Correction / Supersession Record
reason
authority approval
re-readiness
new or updated release evidence
full audit trail
```

## 11.4 Server-Side Enforcement

Release locks must be enforced server-side.

UI hiding alone is not acceptable.

## 12. Tender Management Return / Consumption Governance

## 12.1 Consumption Rule

Tender Management consumes Planning Release Package, not a loose package reference.

Consumption must verify:

1. release exists;
2. release status is Handed Off or active equivalent;
3. release is not stale;
4. package is Released to Tender;
5. tender baseline matches locked release values;
6. target tender code is recorded.

## 12.2 Return Rule

Tender Management may return a release only before downstream non-returnable tender states.

Non-returnable states should include, at minimum:

```text
Tender Published
Supplier Participation Open with legal publication effect
Tender Closed
Bid Opening Started
```

If a release problem is discovered after non-returnable state, it must be handled under Tender Management's own legal correction/addendum/cancellation process, not by silently editing Planning.

## 12.3 Baseline Mismatch Rule

If Tender Management attempts to consume a release but changes locked planning values, consumption must fail or require authorized return.

Examples of baseline mismatch:

```text
method changed from Open Tender to Restricted Tender
category changed from Works to Goods
budget line changed
estimated value changed without approved planning correction
scope changed materially
required STD category changed
```

## 13. Cancellation Governance

## 13.1 Cancellation Before Release

A package may be cancelled before release by authorized Planning Authority with reason.

Required fields:

```text
cancelled_by
cancelled_at
cancellation_reason
from_state
audit_event_ref
```

## 13.2 Cancellation After Release

Cancellation after release requires heightened control.

Preconditions:

1. Planning Authority approval;
2. downstream state allows cancellation/return;
3. Tender Management impact assessment where tender exists;
4. reason recorded;
5. audit event emitted.

If downstream tender has already been published or progressed into non-returnable states, cancellation must be governed by Tender Management/tender legal process, not Planning alone.

---

## 14. Supersession Governance

## 14.1 When Supersession Is Required

Supersession is required when a planning baseline must be replaced after release or consumption.

Examples:

```text
approved scope materially changes
budget line changes
procurement method changes
procurement category changes
package lines materially change
release was consumed but downstream return requires replacement baseline
```

## 14.2 Supersession Requirements

A supersession must record:

```text
old_package_code
old_release_code
new_package_code
new_release_code
reason
affected_fields_json
approved_by
approved_at
downstream_impact_json
audit_event_ref
```

## 14.3 Supersession Effect

Old package/release becomes:

```text
Superseded
```

New package/release becomes the active baseline.

For the master WORKS seed, the expected governance path is:

```text
DEM-MOH-2026-001 approved upstream.
USER-PLAN-001 includes demand in PLAN-MOH-2026.
PLANINCL-MOH-2026-001 is created.
USER-PLAN-001 creates PKG-MOH-2026-001.
PKGLINE-MOH-2026-001-001 is created from DEMITEM-MOH-2026-001-001.
Method decision records Works / Open Tender.
Readiness checks pass.
Package is approved.
Package is marked Ready for Release.
USER-PLAN-001 or Planning Authority releases package.
PKGREL-MOH-2026-001 is created.
Package state becomes Released to Tender.
USER-PO-001 consumes release in Tender Management.
TND-MOH-2026-001 is created/linked.
PKGREL-MOH-2026-001 status becomes Consumed.
Package state becomes Consumed by Tender Management.
Journey step updates to Package Released / Handed Off or Consumed.
```

The implementation may seed the final state directly if the loader is deterministic, but tests must still prove the governed path is possible.
