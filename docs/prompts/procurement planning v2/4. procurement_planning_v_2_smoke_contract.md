## 1. Purpose

This Smoke Contract defines the minimum tests and acceptance evidence required before Procurement Planning v2 can be considered implementation-ready.

It is not a full QA plan. It is the non-negotiable implementation proof set.

The contract verifies that:

```text
approved demand appears in Planning;
planner can include demand in a plan;
planner can create a procurement package;
package lines preserve demand and budget traceability;
method/category/STD path is correct for WORKS / Open Tender;
readiness checks are server-backed;
review and approval gates work;
release to Tender Management creates a locked Planning Release Package;
Tender Management consumption is explicit;
released package cannot be silently edited;
UI stays usable and context-preserving;
permissions and supplier confidentiality are enforced;
seed data is deterministic and aligned with the WORKS journey.
```

## 8. UI Smoke Tests

## 8.1 UI Structure Rule

The Planning UI must use the corrected usability model:

```text
5 persistent surfaces:
Planning Home
Approved Demands
Packages
Released to Tender
Planning Evidence
```

Detailed planning views must open as contextual workspace tabs, drawers, panels, or contextual deep links. They must not appear as noisy permanent sidebar items.

The Planning UI must also use a business-first default visibility model. Ordinary users must see business meaning before technical evidence.

Default Planning views must show information in this order:

```text
1. Business summary
2. Current state in business language
3. Next action
4. Blockers, if any
5. Primary action
6. Secondary actions
7. Evidence link
8. Technical details only after explicit expansion or inside Evidence / Advanced / Audit views
```

The following must not appear in ordinary default views before business-readable labels:

```text
raw lifecycle keys, for example package_release
raw lifecycle statuses, for example Handed Off
raw handoff codes, for example PLANINCL-MOH-2026-001 or PKGREL-MOH-2026-001
source_object_code / target_object_code labels
JSON field names
technical_refs_json
internal audit event IDs
internal DocType names where a business label exists
```

Handoff cards must render in **Business Mode** by default. Audit / Technical Mode may exist only through explicit Evidence, Advanced, Technical Details, or Audit View controls.

## 10. Regression Tests

## 10.1 PP2-REG-001 — Planning Does Not Edit Upstream Demand

### Expected

Planning actions do not mutate upstream approved demand fields such as:

```text
demand title
approved amount
approval decision
budget line source approval
```

Planning may store snapshots or references, not rewrite source authority.

## 10.2 PP2-REG-002 — Planning Does Not Edit Budget Authority

### Expected

Planning package does not directly approve, increase, decrease, or reclassify budget line authority.

## 10.3 PP2-REG-003 — Planning Does Not Create Tender Without Release

### Expected

Tender creation from Planning must require a valid Planning Release Package.

## 10.4 PP2-REG-004 — Planning Release Does Not Bypass STD/Tender Controls

### Expected

Planning release passes method/category/STD requirement to Tender Management, but does not itself publish tender or mark STD readiness complete.

## 10.5 PP2-REG-005 — Cross-Module Journey Does Not Override Planning State

### Expected

Procurement Journey/Handoff layer displays Planning state and evidence, but cannot approve, release, or override package status.
