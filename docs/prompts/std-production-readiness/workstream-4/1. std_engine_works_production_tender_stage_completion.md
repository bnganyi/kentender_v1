## 1. Purpose

This document defines the production completion workflow for a Works tender STD Instance after a procurement package has been released to Tender and the STD Instance has been created.

It explains how the Procuring Entity completes the tender-specific content required by the Works STD, without allowing downstream modules to invent submission requirements, opening fields, evaluation criteria, or contract terms.

This document answers:

1. What must be completed for a Works tender before publication?
2. Which STD sections require tender-stage input?
3. Which fields are parameters and which are structured components?
4. How are specifications, drawings, and BOQ handled?
5. What must be generated before readiness can pass?
6. What blocks publication?
7. What evidence must be retained?
8. How does the final tender Bundle look?
9. How do DSM, DOM, DEM, and DCM become operational outputs?

---

## 2. Position in Overall Workflow

This artifact starts after Planning-to-Tender release.

The preceding release process has already created:

```text
Procurement Package
        ↓
Tender
        ↓
Tender STD Binding
        ↓
STD Instance
```

This artifact covers what happens next:

```text
STD Instance Draft
        ↓
Complete tender-specific values and structured inputs
        ↓
Generate Bundle / DSM / DOM / DEM / DCM
        ↓
Run readiness validation
        ↓
Create configuration snapshot
        ↓
Lock for approval/publication
```

It does not design the full Tender module UI, but it defines the functional and legal completion model the future UI must implement.

---

## 3. Core Principle

A Works tender is not completed by uploading a tender document.

A Works tender is completed by filling a structured STD Instance:

```text
Active Works STD Template
        ↓
Tender-specific parameter values
        ↓
Works Requirements and section-bound documents
        ↓
Structured BOQ
        ↓
Generated tender Bundle and operational models
```

The final supplier-facing document is generated from the structured instance.

## 4. Actors and Responsibilities

### 4.1 Procurement Officer

Primary owner of tender-stage STD completion.

Responsibilities:

- complete tender identity and TDS values;
- coordinate SCC values;
- ensure specifications and drawings are attached;
- ensure BOQ is complete;
- generate outputs;
- run readiness;
- mark STD Instance ready where authorized;
- submit tender for approval/publication.

### 4.2 Procurement Assistant

Supports data entry and document upload.

May:

- enter draft parameter values;
- upload section-bound attachments;
- assist with BOQ data entry/import;
- run readiness checks if permitted;
- generate outputs if permitted.

May not:

- mark ready for publication;
- approve publication;
- override blockers;
- modify published content.

### 4.3 Technical Department / Engineer

Provides technical Works content.

May contribute:

- specifications;
- drawings;
- site information;
- BOQ quantities;
- technical schedules;
- HSE/environmental requirements.

Whether this is a formal system role or represented through workflow assignment is implementation-specific.

### 4.4 Approving Authority

Reviews the completed tender for approval/publication.

May:

- review readiness snapshot;
- approve tender publication if governance allows.

May not:

- directly edit STD Instance content;
- modify evaluation criteria;
- alter BOQ quantities silently.

### 4.5 STD Administrator

Does not complete tender-specific Works content.

May view template/library-level configuration only.

## 5. Works STD Sections and Tender-Stage Completion Responsibility

| STD Area | Section | Tender-Stage Completion Required? | Completion Type | Primary Owner |
|---|---|---:|---|---|
| Invitation to Tender | Invitation | Yes | Parameter/rendered fields | Procurement Officer |
| Instructions to Tenderers | Section I | No | Locked legal text | STD Template |
| Tender Data Sheet | Section II | Yes | Parameter values | Procurement Officer |
| Evaluation and Qualification Criteria | Section III | Limited | Template-derived rules + tender-specific thresholds/options where parameterized | Procurement Officer / STD Engine |
| Tendering Forms | Section IV | No template edit; supplier completion later | Generated DSM requirements | STD Engine |
| Bills of Quantities | Section V | Yes | Structured BOQ bills/items/quantities | Procurement Officer / Technical Department |
| Specifications | Section VI | Yes | Structured content and/or section-bound attachments | Technical Department / Procurement Officer |
| Drawings | Section VII | Yes | Drawing register and attachments | Technical Department / Procurement Officer |
| General Conditions of Contract | Section VIII | No | Locked legal text | STD Template |
| Special Conditions of Contract | Section IX | Yes | Parameter values | Procurement Officer / Contract/Technical input |
| Contract Forms | Section X | No template edit; later contract completion | DCM contract carry-forward | STD Engine / Contract stage |

## 6. Completion Stages

Works tender completion shall be organized into clear stages.

```text
1. Confirm Tender and STD Context
2. Complete Tender Data Sheet Values
3. Complete Evaluation/Qualification Options
4. Complete Works Requirements
5. Complete Drawings Register
6. Complete Bills of Quantities
7. Complete Special Conditions of Contract Values
8. Generate Outputs
9. Run Readiness Validation
10. Create Configuration Snapshot and Lock for Approval
```

These stages are functional requirements. The final UI may be wizard-based or section-based, but it must preserve the same logical completion gates.

## 7. Stage 1 — Confirm Tender and STD Context

### 7.1 Purpose

Confirm that the STD Instance was created from the correct Tender, package, template, and profile.

### 7.2 Required Data

| Field | Source | Editable? |
|---|---|---:|
| tender_code | Tender | No |
| package_code | Planning release | No |
| procurement_category | Package/Tender | No |
| procurement_method | Package/Tender | No |
| template_version_code | STD Binding | No |
| applicability_profile_code | STD Binding | No |
| procuring_entity | Package/Tender | Limited if governance permits |
| tender title | Package/TDS parameter | Yes before publication |

### 7.3 Required Validation

| Validation | Failure Result |
|---|---|
| STD Instance belongs to Tender | Block completion |
| Template version active at creation | Block if invalid lineage |
| Profile compatible with Works | Block |
| Procurement category = Works | Block for Works completion flow |
| BOQ-required profile detected | Activate BOQ completion requirement |

### 7.4 Output Impact

This stage affects:

- Bundle;
- DSM where tender identity appears;
- DOM where tender identity appears;
- DCM where employer/project identity appears.

## 8. Stage 2 — Complete Tender Data Sheet Values

### 8.1 Purpose

The TDS turns locked ITT rules into tender-specific instructions.

The system must collect parameter values only. It must not allow editing of ITT clauses.

### 8.2 Required Parameter Groups

| Group | Examples |
|---|---|
| Tender Identity | Tender title, employer/procuring entity, project location |
| Procurement Method | Open tender, eligibility route, e-GP submission mode |
| Dates and Deadlines | submission deadline, opening time, clarification deadline |
| Tender Security | required/not required, form, amount, validity |
| Bid Validity | bid validity period |
| Site Visit | mandatory/optional, date/time/location |
| Pre-Tender Meeting | required/not required, date/time/location |
| Language and Currency | tender language, bid currency, exchange rules |
| Submission Instructions | submission method, number of copies if applicable |
| Eligibility and Qualification References | parameterized thresholds where STD permits |
| Preference/Reservation | margin/preference applicability where legally allowed |
| Complaints/Review | complaints address/process parameters |

### 8.3 Representative TDS Data

```yaml
tds_values:
  tender_title: Rehabilitation of District Health Centre
  procuring_entity_name: Ministry of Health
  project_location: Kijani District
  procurement_method: Open Tender
  submission_deadline: 2026-06-30T11:00:00
  opening_datetime: 2026-06-30T11:30:00
  clarification_deadline: 2026-06-20T17:00:00
  bid_validity_days: 120
  tender_security_required: true
  tender_security_type: Bank Guarantee
  tender_security_amount: 50000
  tender_security_currency: USD
  site_visit_required: true
  site_visit_datetime: 2026-06-10T10:00:00
  site_visit_location: District Health Centre Site Office
  pre_tender_meeting_required: false
  bid_currency: USD
  language: English
  margin_of_preference_applicable: false
```

### 8.4 Validation Rules

| Rule | Severity |
|---|---|
| submission_deadline required | Critical |
| opening_datetime required | Critical |
| opening_datetime must be after submission_deadline | Critical |
| tender_security_amount required if security required | Critical |
| tender_security_currency required if security required | Critical |
| site_visit details required if site visit mandatory | High/Critical depending policy |
| bid_validity_days must be positive | Critical |
| clarification deadline must precede submission deadline | High |

### 8.5 Output Impact

| Parameter Group | Affected Outputs |
|---|---|
| Dates/deadlines | Bundle, DSM, DOM |
| Tender security | Bundle, DSM, DEM |
| Bid validity | Bundle, DSM, DEM |
| Site visit | Bundle, DSM, DEM if mandatory compliance applies |
| Preference | Bundle, DEM |
| Complaints | Bundle |

## 9. Stage 3 — Complete Evaluation and Qualification Options

### 9.1 Purpose

Section III must remain STD-derived. The Procuring Entity may only fill parameterized thresholds/options disclosed by the STD.

No manual evaluation criteria may be added.

### 9.2 Allowed Tender-Stage Inputs

Allowed inputs are only those defined as parameters or structured options in the active Works STD template.

Examples:

| Input | Type |
|---|---|
| minimum average annual turnover | Parameter |
| experience in similar works | Parameter/structured threshold |
| key personnel requirements | Structured requirement |
| equipment requirements | Structured requirement |
| margin of preference applicability | Parameter |
| domestic preference factor, if legally enabled | Parameter |
| subcontracting disclosure requirement | Parameter/form requirement |

### 9.3 Prohibited Inputs

The system must prohibit:

- free-form evaluation criteria;
- hidden scoring rules;
- post-publication criteria creation;
- evaluation committee-created rules;
- manual technical pass/fail rules outside mapped STD sources.

### 9.4 Representative Data

```yaml
evaluation_options:
  minimum_average_annual_turnover:
    amount: 1500000
    currency: USD
    years: 3
  similar_works_experience:
    minimum_contracts: 2
    minimum_value_each: 750000
    period_years: 5
  key_personnel_required: true
  equipment_schedule_required: true
  margin_of_preference_applicable: false
```

### 9.5 Output Impact

- Bundle: Section III rendered criteria.
- DSM: required qualification submissions/forms.
- DEM: executable evaluation rules and thresholds.

## 10. Stage 4 — Complete Works Requirements

### 10.1 Purpose

Works Requirements define the technical scope and performance requirements of the Works.

They are structured components and section-bound documents, not arbitrary attachments.

### 10.2 Required Components

| Component | Required? | Completion Type | Output Impact |
|---|---:|---|---|
| Specifications | Yes | Structured text and/or attachment | Bundle, DSM, DEM, DCM |
| Site Information | Usually yes | Structured text/attachment | Bundle, DSM, DEM, DCM |
| HSE Requirements | Policy-dependent | Structured text/attachment | Bundle, DSM, DEM, DCM |
| Environmental/Social Requirements | Policy-dependent | Structured text/attachment | Bundle, DSM, DEM, DCM |
| Method Statement Requirement | Usually yes | Parameter/requirement flag | DSM, DEM |
| Work Programme Requirement | Usually yes | Parameter/requirement flag | DSM, DEM |
| Quality Requirements | Usually yes | Structured text/attachment | Bundle, DEM, DCM |

### 10.3 Representative Data

```yaml
works_requirements:
  specifications:
    status: Complete
    structured_summary: Renovation of outpatient block, roofing, electrical rewiring, plumbing repairs, and external drainage improvements.
    attachments:
      - file_name: specifications_v1.pdf
        section: Section VI
        classification: Supplier Facing
  site_information:
    status: Complete
    structured_summary: Facility will remain partially operational during works. Contractor must phase works to maintain access to emergency unit.
    attachments:
      - file_name: site_information_report.pdf
        section: Section VI
        classification: Supplier Facing
  hse_requirements:
    status: Complete
    structured_summary: Contractor shall submit site-specific HSE plan before commencement.
  method_statement_required: true
  work_programme_required: true
```

### 10.4 Validation Rules

| Rule | Severity |
|---|---|
| required specifications missing | Critical |
| supplier-facing specification attachment not section-bound | Critical |
| required site information missing | High/Critical |
| HSE requirement missing where required by profile | High/Critical |
| required method statement flag unresolved | High |
| required work programme flag unresolved | High |

### 10.5 Attachment Rules

1. Specifications must bind to Section VI.
2. Drawings must bind to Section VII.
3. Site reports must bind to a defined Works component.
4. Attachments cannot create evaluation criteria by themselves.
5. Attachments cannot override locked ITT/GCC/SCC terms.

## 12. Stage 6 — Complete Bills of Quantities

### 12.1 Purpose

The BOQ is the structured pricing schedule for Works.

The Procuring Entity defines:

- bill structure;
- item numbers;
- descriptions;
- units;
- quantities;
- provisional/fixed sums where applicable.

The Supplier later enters:

- rates only where required.

### 12.2 BOQ Control Rules

| Rule | Required Behavior |
|---|---|
| Quantity owner | Procuring Entity |
| Supplier input | Rate only |
| Amount calculation | System-computed |
| Arithmetic correction | Evaluation only |
| Opening | May disclose submitted total only; no correction |
| Contract price | Corrected evaluated BOQ total from DEM/Award |

### 12.3 Required BOQ Structure

```text
BOQ
  ↓
Bills
  ↓
Items
```

### 12.4 Representative BOQ Data

```yaml
boq:
  currency: USD
  pricing_model: Bills of Quantities
  quantity_owner: Procuring Entity
  supplier_input_mode: Rate Only
  arithmetic_correction_stage: Evaluation
  bills:
    - bill_number: 1
      title: Preliminaries
      items:
        - item_number: 1.1
          description: Mobilization and demobilization
          unit: LS
          quantity: 1
          item_type: Preliminary
          supplier_input_mode: Rate Only
        - item_number: 1.2
          description: Site establishment and temporary facilities
          unit: LS
          quantity: 1
          item_type: Preliminary
          supplier_input_mode: Rate Only
    - bill_number: 2
      title: Building Works
      items:
        - item_number: 2.1
          description: Concrete works to outpatient block
          unit: m3
          quantity: 120
          item_type: Normal
          supplier_input_mode: Rate Only
        - item_number: 2.2
          description: Roof replacement including timber framing and sheets
          unit: m2
          quantity: 450
          item_type: Normal
          supplier_input_mode: Rate Only
        - item_number: 2.3
          description: Electrical rewiring to outpatient block
          unit: m2
          quantity: 850
          item_type: Normal
          supplier_input_mode: Rate Only
    - bill_number: 3
      title: Provisional Sums
      items:
        - item_number: 3.1
          description: Provisional sum for utility relocation
          unit: Sum
          quantity: 1
          item_type: Provisional Sum
          supplier_input_mode: None
          provisional_sum_amount: 25000
```

### 12.5 BOQ Validation Rules

| Rule | Severity |
|---|---|
| BOQ missing where Works profile requires BOQ | Critical |
| bill has no items | High/Critical depending profile |
| item description missing | Critical |
| unit missing | Critical |
| quantity missing | Critical |
| quantity negative | Critical unless controlled exception |
| supplier input mode invalid | Critical |
| provisional sum amount missing for provisional item | Critical |
| duplicate item number within BOQ | Critical |
| BOQ currency missing | Critical |

### 12.6 BOQ Output Impact

| Output | Impact |
|---|---|
| Bundle | Includes BOQ and pricing instructions. |
| DSM | Creates supplier rate-entry requirements. |
| DOM | May disclose submitted total only. |
| DEM | Generates arithmetic correction and financial evaluation rules. |
| DCM | Carries final BOQ/contract price source after evaluation. |

## 13. Stage 7 — Complete Special Conditions of Contract Values

### 13.1 Purpose

SCC values complete contract-specific conditions that modify or supplement GCC within allowed parameters.

The system must collect parameter values only. It must not allow editing GCC text.

### 13.2 Required SCC Parameter Groups

| Group | Examples |
|---|---|
| Contract Identity | Employer, project, site |
| Time for Completion | completion period, commencement rules |
| Securities | performance security, advance payment security |
| Retention | retention percentage, release conditions |
| Defects Liability | defects liability period |
| Liquidated Damages | rate and cap |
| Payment | payment schedule, certificates, currency |
| Insurance | required cover types/amounts |
| Dispute Resolution | adjudicator/arbitration references where applicable |

### 13.3 Representative SCC Data

```yaml
scc_values:
  completion_period_days: 180
  defects_liability_period_days: 365
  performance_security_percent: 10
  retention_percent: 5
  liquidated_damages_percent_per_day: 0.1
  maximum_liquidated_damages_percent: 10
  advance_payment_allowed: false
  payment_currency: USD
  insurance_required: true
  minimum_insurance_cover: 1000000
```

### 13.4 Validation Rules

| Rule | Severity |
|---|---|
| completion period missing | Critical |
| performance security value missing where required | Critical |
| defects liability missing | Critical |
| liquidated damages cap less than daily rate | Critical |
| payment currency missing | High/Critical |
| insurance missing where required | High/Critical |

### 13.5 Output Impact

SCC values affect:

- Bundle;
- DCM;
- contract evidence package.

Some values may also affect DEM where eligibility/evaluation uses contract compliance undertakings, but this must be explicitly mapped.

## 14. Stage 8 — Generate Outputs

### 14.1 Purpose

After all required values and structured inputs are complete, the system generates the formal outputs.

### 14.2 Required Outputs

| Output | Required? | Purpose |
|---|---:|---|
| Bundle | Yes | Supplier-facing tender document. |
| DSM | Yes | Submission requirements. |
| DOM | Yes | Opening register model. |
| DEM | Yes | Evaluation rules/model. |
| DCM | Yes | Contract carry-forward model. |

### 14.3 Generation Rules

1. Outputs are generated from the STD Instance.
2. Outputs must record source template version and instance input hash.
3. Outputs must not be manually edited after generation.
4. If source inputs change, affected outputs become stale.
5. Readiness requires all required outputs to be current.

### 14.4 Bundle Requirements

The generated Works tender Bundle must include:

```text
Invitation to Tender
Section I — Instructions to Tenderers
Section II — Tender Data Sheet
Section III — Evaluation and Qualification Criteria
Section IV — Tendering Forms
Section V — Bills of Quantities
Section VI — Specifications
Section VII — Drawings
Section VIII — General Conditions of Contract
Section IX — Special Conditions of Contract
Section X — Contract Forms
```

### 14.5 DSM Requirements

DSM must include:

- required tendering forms;
- tender security submission requirement;
- qualification submissions;
- technical proposal/method statement requirements;
- work programme requirement;
- BOQ rate-entry requirements;
- addendum acknowledgement requirements where applicable.

### 14.6 DOM Requirements

DOM must include opening register fields only.

DOM must not include:

- responsiveness results;
- arithmetic correction;
- ranking;
- evaluation comments.

### 14.7 DEM Requirements

DEM must include:

- responsiveness rules;
- eligibility rules;
- tender security compliance;
- technical compliance;
- qualification rules;
- BOQ arithmetic correction;
- financial evaluation;
- ranking logic.

No manual criteria allowed.

### 14.8 DCM Requirements

DCM must include:

- GCC/SCC carry-forward;
- Works scope references;
- BOQ contract price source;
- performance security;
- completion period;
- defects liability;
- contract forms.

For Works BOQ procurement, contract price source must be:

```text
Corrected evaluated BOQ total from DEM/Award
```

## 15. Stage 9 — Readiness Validation

### 15.1 Purpose

Readiness determines whether the Works tender STD Instance is legally and operationally complete for approval/publication.

### 15.2 Required Readiness Checks

| Category | Checks |
|---|---|
| Tender context | Tender, package, template, profile compatible. |
| TDS | Required parameters valid. |
| Evaluation options | Thresholds/options valid and mapped. |
| Works Requirements | Required components complete. |
| Drawings | Required drawing register complete. |
| BOQ | Required BOQ complete and valid. |
| SCC | Required contract parameters valid. |
| Outputs | Bundle, DSM, DOM, DEM, DCM generated and current. |
| Attachments | Required supplier-facing attachments section-bound. |
| Audit | Required completion and generation events recorded. |
| No stale outputs | All affected outputs current. |
| No blockers | Critical blockers resolved. |

### 15.3 Readiness Statuses

```text
Not Run
Incomplete
Blocked
Warning
Ready
Invalidated
```

### 15.4 Blocker Examples

| Blocker Code | Meaning |
|---|---|
| TDS_SUBMISSION_DEADLINE_MISSING | Submission deadline not provided. |
| TDS_OPENING_DATETIME_INVALID | Opening date/time invalid. |
| TENDER_SECURITY_AMOUNT_MISSING | Security amount missing while security required. |
| WORKS_SPECIFICATIONS_MISSING | Required specifications missing. |
| DRAWING_REGISTER_MISSING | Drawings required but not registered. |
| BOQ_MISSING | Required BOQ not provided. |
| BOQ_ITEM_QUANTITY_MISSING | BOQ item quantity missing. |
| SCC_COMPLETION_PERIOD_MISSING | Completion period missing. |
| DEM_NOT_GENERATED | Evaluation model missing. |
| OUTPUT_STALE | One or more generated outputs stale. |
| BUNDLE_RENDER_FAILED | Bundle could not be rendered. |

### 15.5 Ready Result

Readiness may return Ready only if:

```text
All critical checks pass
All required outputs are current
No publication-blocking findings remain
```

## 16. Stage 10 — Configuration Snapshot and Lock for Approval

### 16.1 Purpose

Once readiness passes, the system creates a configuration snapshot and locks the STD Instance for approval workflow.

### 16.2 Required Snapshot Contents

The configuration snapshot must include hashes/references for:

- tender context;
- template version;
- profile;
- TDS values;
- evaluation options;
- Works Requirements;
- drawings register;
- BOQ;
- SCC values;
- generated Bundle;
- DSM;
- DOM;
- DEM;
- DCM;
- readiness result;
- audit events.

### 16.3 Lock Rules

After lock for approval:

- ordinary edits prohibited;
- changes require unlock/return-to-preparation workflow before publication;
- all changes after unlock invalidate snapshot/readiness;
- after publication, direct unlock is prohibited.

### 17.1 Bundle as Supplier-Facing Document

The Bundle must be downloadable and reviewable as a full tender document.

It should look like a conventional tender document, not a collection of database records.

### 17.2 Required Formats

| Format | Requirement |
|---|---|
| HTML Preview | Required for internal review. |
| PDF | Required for publication/audit. |
| DOCX | Strongly recommended for formal review and records. |

### 17.3 Bundle Document Outline

```text
Invitation to Tender

Section IV — Tendering Forms
Section V — Bills of Quantities
Section VI — Specifications
Section VII — Drawings

Section IX — Special Conditions of Contract
Section X — Contract Forms
```

### 17.4 Bundle Must Show

| Content | Source |
|---|---|
| locked ITT | Template |

| evaluation criteria | Template + parameterized thresholds |
| forms | Template form definitions |
| BOQ | Instance BOQ |

| locked GCC | Template |

## 18. Addendum Sensitivity During Completion

Before publication, changes are normal edits.

After publication, the following require addendum impact analysis:

| Change | Expected Impact |
|---|---|
| submission deadline | Bundle, DSM, DOM |
| opening datetime | Bundle, DOM |
| tender security | Bundle, DSM, DEM |
| evaluation threshold | Bundle, DEM |
| specification change | Bundle, DSM, DEM, DCM depending mapping |
| drawing change | Bundle, DEM, DCM depending mapping |
| BOQ quantity/item change | Bundle, DSM, DEM, DCM |
| SCC value change | Bundle, DCM |

---

## 19. Audit Requirements

The system must audit:

1. TDS parameter changes;
2. evaluation option changes;
3. Works Requirement completion;
4. attachment upload/replacement;
5. drawing registration;
6. BOQ creation/import/change;
7. SCC parameter changes;
8. output generation;
9. output staleness;
10. readiness run;
11. blocker resolution;
12. configuration snapshot creation;
13. lock for approval;
14. denied edits after lock/publication.
