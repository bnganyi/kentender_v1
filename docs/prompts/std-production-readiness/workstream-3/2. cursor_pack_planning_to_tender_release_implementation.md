## 1. Implementation Mandate

Cursor must implement the Planning-to-Tender release bridge as a controlled, auditable, transaction-safe process.

This implementation must ensure that tenders are not created arbitrarily and that, where an STD is required, no tender proceeds without a compatible active STD template/profile and Tender-bound STD Instance.

The system must enforce:

1. Approved procurement package required before release.
2. Package context constrains Tender creation.
3. Eligible STD lookup must use procurement category, method, contract type, Works profile, and effective status.
4. If STD is required, Tender creation and STD Instance creation must be transactionally linked.
5. Release blockers must prevent invalid Tender creation.
6. Release attempts, blockers, STD selection, Tender creation, and STD Instance creation must be audited.
7. STD Administrator does not release packages to Tender.
8. Tender users must not create orphan STD Instances.
9. Planning release must preserve package-to-tender lineage.
10. Future Tender v2 must consume the release and binding model without redesign.

## 15. Release Orchestration Transaction

## Ticket REL-0500 — Implement Release-to-Tender Orchestration Service

### Objective

Coordinate the entire release flow transactionally.

### Service Name

```text
PlanningToTenderReleaseService
```

### Required Method

```text
releasePackageToTender(package_code, selected_std_option, actor, release_note = null)
```

### Required Transaction Sequence

```text
Begin transaction
  1. Create Pending release record.
  2. Build package context.
  3. Check actor authorization.
  4. Check package release eligibility.
  5. Resolve eligible STD options.
  6. Resolve selected STD option / release mode.
  7. If blockers exist, mark release Blocked and commit blocked attempt.
  8. Create Tender from package.
  9. Create STD Instance for Tender where STD applies.
  10. Create Tender STD Binding.
  11. Auto-initialize safe STD values from package.
  12. Mark release Released.
  13. Emit audit events.
Commit transaction
```

### Failure Behavior

| Failure Point | Required Behavior |
|---|---|
| Eligibility blocker | Release record Blocked; no Tender created. |
| Tender creation fails | Release record Blocked or transaction rollback with audit-safe failure record. |
| STD Instance creation fails | Tender creation rolled back or release marked Blocked with no active Tender. |
| Binding creation fails | Rollback Tender/STD Instance or mark release Blocked with cleanup. |
| Audit write fails | Critical failure; do not silently proceed if audit required. |

### Implementation Note

If the framework does not allow audit record creation inside failed transaction, create a pre-transaction release attempt record or post-failure error record in a safe error/audit channel.

### Acceptance Criteria

- Valid release creates release, tender, instance, binding.
- Invalid release creates blocked release record and no tender.
- Partial tender without STD binding cannot occur when STD required.

## 16. Release Status State Machine

## Ticket REL-0510 — Implement Release Status State Machine

### Objective

### Allowed Transitions

| From | To |
|---|---|
| Pending | Released |
| Pending | Blocked |
| Pending | Cancelled |
| Blocked | Pending |
| Blocked | Superseded |
| Released | Superseded |

### Prohibited Transitions

| Transition | Reason |
|---|---|
| Released → Pending | Released record is historical evidence. |
| Released → Blocked | Cannot convert successful release into failed attempt. |
| Cancelled → Released | Must create new release attempt. |

### Acceptance Criteria

- Invalid transitions denied.
- Transitions audited.
- Released record remains stable.
