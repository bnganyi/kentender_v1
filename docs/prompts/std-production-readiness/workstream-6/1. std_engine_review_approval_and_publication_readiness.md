## 1. Purpose

This document defines the controlled gate between a completed tender-stage STD Instance and a legally published tender.

It answers:

1. When is a tender ready for approval?
2. What does the approving authority review?
3. What is locked during approval review?
4. What happens when the tender is returned for correction?
5. What must exist before publication?
6. What is captured in the publication snapshot?
7. What becomes immutable after publication?
8. How are Bundle, DSM, DOM, DEM, and DCM bound to publication?
9. What evidence package must be retained?
10. What happens if a change is needed after publication?

---

        ↓
Completed WORKS tender-stage content
        ↓

```text

        ↓
Lock for Approval
        ↓
Approval Review
        ↓
Publication Snapshot
        ↓
Publication Lock
        ↓
Published Tender
```

## 3. Core Principle

A tender must not be published merely because a user clicks “Publish”.

A tender may be published only if:

1. the Tender exists and is in the correct lifecycle state;
2. the STD Instance is complete;
3. all required generated outputs exist and are current;
4. the readiness gate passes;
5. the approval workflow is complete;
6. a publication snapshot is created;
7. the published outputs are immutable and traceable.

Publication is a legal state transition, not a display action.

---

## 4. Key Definitions

### 4.1 Readiness Gate

The readiness gate is the system validation that determines whether the Tender and STD Instance are complete enough to proceed to approval and publication.

### 4.2 Configuration Snapshot

A pre-approval immutable capture of the completed tender configuration at the time it is submitted for approval.

### 4.3 Approval Review

The governance step in which an authorized Approving Authority reviews the completed tender package before publication.

### 4.4 Publication Snapshot

The immutable legal evidence capture of the tender package exactly as published.

### 4.5 Publication Lock

The irreversible lock that prevents direct modification of published tender artifacts. Post-publication changes require addendum or controlled reissue.

### 4.6 Evidence Package

The complete audit-grade record of the tender publication decision, including planning, tender, STD, generated outputs, snapshots, approval events, and publication artifacts.

## 6. Publication Readiness Gate

### 6.1 Purpose

The publication readiness gate determines whether the tender package is complete enough for approval/publication.

It combines checks from:

- Tender lifecycle;
- Procurement package release;
- STD Instance completion;
- generated outputs;
- approval workflow;
- audit/evidence integrity.

### 6.2 Readiness Statuses

| Status | Meaning |
|---|---|
| Not Run | Readiness has not been evaluated. |
| Incomplete | Required data is missing but completion can continue. |
| Blocked | Critical blocker prevents approval/publication. |
| Warning | No critical blockers, but non-blocking issues exist. |
| Ready | All publication-critical checks pass. |
| Invalidated | Previously ready state was invalidated by changes. |

### 6.3 Required Readiness Check Categories

| Category | Required Checks |
|---|---|
| Planning Release | Tender was created from approved package and release record exists. |
| Tender State | Tender is in preparation/review-eligible state. |
| STD Binding | Tender has valid STD Instance binding. |
| Template/Profile | Template and applicability profile lineage valid. |
| STD Completion | TDS, SCC, Works Requirements, Drawings, BOQ complete where required. |
| Generated Outputs | Bundle, DSM, DOM, DEM, DCM exist and are current. |
| Output Traceability | Generated outputs have source trace and hashes. |
| Staleness | No required output is stale. |
| Attachments | Required supplier-facing attachments are section-bound. |
| Review Preconditions | No unresolved critical blockers. |
| Audit Integrity | Required audit events exist. |
| Evidence Exportability | Evidence package can be assembled. |

### 6.4 Critical Blockers

The following blockers shall prevent approval and publication.

| Blocker Code | Meaning |
|---|---|
| RELEASE_RECORD_MISSING | Tender lacks Planning-to-Tender release record. |
| STD_BINDING_MISSING | Tender lacks STD binding. |
| STD_INSTANCE_MISSING | STD Instance missing. |
| STD_INSTANCE_NOT_READY | STD Instance readiness not Ready. |
| TEMPLATE_LINEAGE_INVALID | Template/profile lineage invalid. |
| TDS_INCOMPLETE | Required TDS values missing/invalid. |
| SCC_INCOMPLETE | Required SCC values missing/invalid. |
| WORKS_REQUIREMENTS_INCOMPLETE | Required Works components incomplete. |
| DRAWINGS_INCOMPLETE | Required drawings missing/invalid. |
| BOQ_INCOMPLETE | Required BOQ missing/invalid. |
| BUNDLE_NOT_CURRENT | Bundle missing/stale/not current. |
| DSM_NOT_CURRENT | DSM missing/stale/not current. |
| DOM_NOT_CURRENT | DOM missing/stale/not current. |
| DEM_NOT_CURRENT | DEM missing/stale/not current. |
| DCM_NOT_CURRENT | DCM missing/stale/not current. |
| OUTPUT_TRACE_MISSING | Required generated output traceability missing. |
| SNAPSHOT_CREATION_FAILED | Required snapshot could not be created. |
| APPROVAL_REQUIRED | Approval not complete. |
| EVIDENCE_PACKAGE_FAILED | Evidence package cannot be assembled. |

### 6.5 Warning Examples

Warnings may permit approval/publication depending policy.

| Warning Code | Meaning |
|---|---|
| AUDIT_NONCRITICAL_EVENT_MISSING | Non-critical audit event missing. |
| SOURCE_HASH_MISSING | Source evidence hash missing but source reference exists. |
| OPTIONAL_ATTACHMENT_MISSING | Optional attachment not provided. |
| REVIEW_NOTE_UNRESOLVED | Non-blocking review note remains. |

## 7. Configuration Snapshot Before Approval

### 7.1 Purpose

Before the tender is submitted for approval, the system must capture a configuration snapshot.

This ensures that the Approving Authority reviews a stable package, not a moving target.

### 7.2 Snapshot Type

```text
Configuration Snapshot
```

### 7.3 Snapshot Contents

The configuration snapshot shall include references/hashes for:

| Area | Required |
|---|---:|
| procurement package | Yes |
| release record | Yes |
| tender record | Yes |
| STD Instance | Yes |
| selected template version | Yes |
| applicability profile | Yes |
| TDS values | Yes |
| evaluation/qualification options | Yes |
| Works Requirements | Yes where applicable |
| drawings register | Yes where applicable |
| BOQ | Yes where applicable |
| SCC values | Yes |
| Bundle output | Yes |
| DSM output | Yes |
| DOM output | Yes |
| DEM output | Yes |
| DCM output | Yes |
| readiness result | Yes |
| audit event range | Yes |

### 7.4 Lock for Approval

After configuration snapshot creation, the STD Instance and tender publication package move to:

```text
Locked for Approval
```

Allowed:

- Approving Authority review;
- read-only preview;
- evidence inspection;
- return for correction.

Not allowed:

- ordinary parameter edits;
- BOQ edits;
- output regeneration;
- attachment replacement;
- manual rule creation;
- publication without approval.

## 8. Approval Workflow

### 8.1 Purpose

Approval workflow provides governance review before tender publication.

The Approving Authority reviews the completed tender package and readiness evidence.

### 8.2 Approval Actors

| Role | Permission | Responsibility |
|---|---|---|
| Procurement Officer | submit for approval | Submits completed tender package. |
| Procurement Assistant | none/limited | May assist before submission only. |
| Approving Authority | approve/reject/return | Reviews and decides. |
| Auditor | read-only | May inspect evidence. |
| STD Administrator | none for tender approval | Does not approve tender publication. |

### 8.3 What Approving Authority Sees

The Approving Authority shall see a review package, not editable STD internals.

Required review sections:

1. Tender summary;
2. Procurement package reference;
3. STD template/profile used;
4. Readiness result;
5. Bundle preview/download;
6. DSM summary;
7. DOM summary;
8. DEM summary;
9. DCM summary;
10. BOQ summary;
11. Works Requirements/specification/drawing summary;
12. critical blockers/warnings;
13. audit/evidence summary;
14. approval decision controls.

### 8.4 Approval Decisions

| Decision | Meaning | Result |
|---|---|---|
| Approve for Publication | Tender may proceed to publication. | Approval status Approved. |
| Return for Correction | Tender package requires correction. | Unlock/return to preparation with reason. |
| Reject | Tender should not proceed. | Approval status Rejected. |
| Request Clarification | Non-final request if workflow supports it. | Approval status Clarification Requested. |

### 8.5 No Silent Edit Rule

Approving Authority shall not directly edit:

- TDS values;
- SCC values;
- BOQ;
- specifications;
- drawings;
- DSM;
- DOM;
- DEM;
- DCM.

Corrections must be made by returning the tender to preparation.

## 9. Return to Preparation

### 9.1 Purpose

If approval review identifies issues, the tender may be returned to preparation.

### 9.2 Return Rules

When returned:

1. approval status becomes Returned for Correction;
2. instance state returns to In Configuration or Validation Blocked;
3. prior configuration snapshot is marked superseded/invalidated;
4. generated outputs may be marked stale if changes are made;
5. readiness must be rerun;
6. a new configuration snapshot is required before resubmission.

### 9.3 Required Return Reason

Approving Authority must provide:

| Field | Required |
|---|---:|
| return_reason_code | Yes |
| return_comment | Yes |
| affected_area | Yes |
| criticality | Yes |

### 9.4 Audit

Return to preparation must be audited.

## 11. Publication Snapshot

### 11.1 Purpose

The publication snapshot captures the exact legal state of the tender at publication.

It is the authoritative record of what was issued to suppliers and what downstream modules must use.

### 11.2 Snapshot Type

```text
Publication Snapshot
```

### 11.3 Required Contents

The publication snapshot shall include:

```yaml
publication_snapshot:
  snapshot_code: string
  tender_code: string
  package_code: string
  std_instance_code: string
  template_version_code: string
  applicability_profile_code: string
  configuration_snapshot_code: string
  bundle_output_code: string
  dsm_output_code: string
  dom_output_code: string
  dem_output_code: string
  dcm_output_code: string
  readiness_result_code: string
  approval_decision_code: string
  evidence_package_code: string
  complete_publication_hash: string
  created_by: user
  created_at: datetime
```

### 11.4 Snapshot Rules

1. Publication snapshot is append-only.
2. Publication snapshot is immutable once finalized.
3. Publication snapshot must reference exact output versions.
4. Publication snapshot must not reference stale outputs.
5. Publication snapshot must be created before or atomically during publication.

## 12. Publication Lock

### 12.1 Purpose

Publication lock prevents direct mutation of the published tender package.

### 12.2 Effects of Publication Lock

After publication:

| Object | Effect |
|---|---|
| Tender | Moves to Published/Open state. |
| STD Instance | Published Locked. |
| Bundle | Published. |
| DSM | Published. |
| DOM | Published. |
| DEM | Published. |
| DCM | Published. |
| Configuration Snapshot | Final/Superseded by publication context. |
| Publication Snapshot | Final. |
| Attachments | Published/immutable. |
| BOQ | Published/immutable. |

### 12.3 Prohibited After Publication

The system shall prohibit direct edits to:

- TDS values;
- SCC values;
- evaluation options;
- Works Requirements;
- specifications;
- drawings;
- BOQ;
- Bundle;
- DSM;
- DOM;
- DEM;
- DCM;
- publication snapshot.

### 12.4 Allowed After Publication

Allowed only through controlled workflow:

- addendum;
- cancellation;
- reissue/supersession;
- downstream consumption of published outputs;
- evidence export;
- audit review.

## 13. Publication Transaction

### 13.1 Required Transaction Sequence

Publication should be transactionally controlled.

```text
Begin transaction
  1. Verify actor permission.
  2. Verify approval decision is Approved.
  3. Rerun or verify publication readiness.
  4. Verify outputs are current.
  5. Assemble evidence package or verify assembly readiness.
  6. Create Publication Snapshot.
  7. Mark Bundle/DSM/DOM/DEM/DCM Published.
  8. Mark STD Instance Published Locked.
  9. Mark Tender Published/Open.
  10. Record audit events.
Commit transaction
```

If any step fails, publication must fail and no partial published state may remain.

### 13.2 Failure Handling

| Failure | Required Result |
|---|---|
| readiness fails | publication denied |
| output stale | publication denied |
| snapshot creation fails | publication denied |
| evidence package fails | publication denied |
| audit write fails | publication denied or critical failure depending audit policy |
| output publish marking fails | rollback publication |

## 15. Post-Publication Change Rule

After publication, direct changes are prohibited.

### 15.1 Addendum Required

Use addendum where the tender remains valid but requires controlled correction or clarification.

Examples:

- deadline extension;
- drawing revision;
- specification clarification;
- BOQ correction;
- tender security clarification;
- SCC correction before submission deadline where legally allowed.

### 15.2 Reissue / Supersession Required

Use reissue/supersession where the change is too material or legally incompatible with addendum.

Examples:

- change of procurement method;
- material scope change;
- change of applicable STD template after publication;
- cancellation and re-advertisement;
- legally invalid published tender package.

### 15.3 Addendum Effects

Addendum may:

1. create addendum record;
2. identify affected outputs;
3. regenerate affected outputs as new versions;
4. create addendum snapshot;
5. publish addendum bundle/reference;
6. require supplier acknowledgement;
7. supersede affected prior current outputs while retaining history.

## 17. State Model

### 17.1 Tender Publication States

| State | Meaning |
|---|---|
| Preparation | Tender content being prepared. |
| Ready for Approval | Readiness passed and configuration snapshot created. |
| Under Approval | Approving Authority reviewing package. |
| Returned for Correction | Approval returned package for changes. |
| Approved for Publication | Approval complete. |
| Published | Tender published and outputs locked. |
| Addendum Pending | Post-publication change under addendum workflow. |
| Cancelled | Tender cancelled. |
| Superseded/Reissued | Replaced by reissue. |

### 17.2 Normal Flow

```text
Preparation
  → Ready for Approval
  → Under Approval
  → Approved for Publication
  → Published
```

### 17.3 Return Flow

```text
Under Approval
  → Returned for Correction
  → Preparation
  → Ready for Approval
```

### 17.4 Post-Publication Flow

```text
Published
  → Addendum Pending
  → Published
```

or

```text
Published
  → Superseded/Reissued
```

## 20. Smoke Contracts
