## 2. Purpose

The purpose of this workstream is to define production-grade governance for Standard Tender Document templates before they are used as the legal and operational basis for creating tenders.

The previous POCs proved that STDs can be represented as controlled packages, inspected by administrators, configured by procurement officers, validated, used to generate required forms, used to support Works BoQ readiness, and rendered into preview/audit outputs.

This workstream moves from successful POC control to production governance.

It shall define how STD templates are:

1. imported;
2. validated;
3. reviewed;
4. approved;
5. activated for tender creation;
6. versioned;
7. superseded;
8. retired;
9. audited;
10. protected against casual mutation;
11. linked to tenders and future tender STD instances.

This workstream is foundational because a public procurement system cannot legally rely on mutable, casually editable, or weakly governed STD templates.

---

## 3. Strategic Principle

The STD governance module shall implement this principle:

> A Standard Tender Document template may influence tender creation only after it has been imported through a controlled process, validated structurally, reviewed by authorized users, approved, activated, versioned, and made auditable.

This means:

1. uploaded or imported STD packages are not automatically usable for tenders;
2. validation success does not equal approval;
3. approval does not equal activation unless activation is explicitly granted;
4. activation must be version-specific;
5. active templates must not be casually edited;
6. retired or superseded templates must remain historically auditable;
7. tenders must reference the exact STD template version or tender STD instance used;
8. future template changes must not silently affect existing tenders.

## 5. Problem Statement

Without production STD governance, the system risks:

1. using unapproved templates for live tenders;
2. confusing draft/imported templates with active templates;
3. allowing template package changes after tenders are created;
4. losing evidence of who approved a template and when;
5. failing to distinguish template validation from legal/business approval;
6. failing to preserve old template versions used by historical tenders;
7. creating tenders from superseded or retired templates;
8. allowing administrators to alter legal tender logic without formal review;
9. undermining downstream tender, bidder, evaluation, and contract audit trails.

This workstream shall close those risks.

---

## 6. Core Governance Hypothesis

The workstream shall test and implement this hypothesis:

> STD templates can be governed as versioned, immutable-after-activation packages with formal validation, review, approval, activation, supersession, retirement, and audit controls, while preserving administrator visibility and preventing ordinary users from editing template internals.

The workstream succeeds if an authorized administrator can import and validate an STD package, submit it for review, obtain approval, activate a specific version for tender creation, prevent unauthorized mutation, supersede or retire it safely, and preserve historical audit evidence.

## 8. In-Scope Capabilities

### 8.1 Template Import Governance

The system shall support controlled import of STD template packages.

Required behavior:

| Capability | Requirement |
|---|---|
| Import package | Authorized users may import package files or seed packages |
| Capture source metadata | Source document, source authority, import timestamp, importer |
| Compute package hash | Hash must be generated and stored |
| Mark as imported/draft | Import does not make template usable |
| Preserve raw package payload | Read-only package payload must be retained for traceability |
| Reject malformed packages | Structural errors must block validation/approval |

---

### 8.2 Package Validation Governance

The system shall distinguish package validation from approval.

Required behavior:

| Capability | Requirement |
|---|---|
| Run validation | Authorized users can run validation checks |
| Store validation result | Validation status, findings, timestamp, actor, and package hash are stored |
| Re-run validation | Revalidation is allowed before approval/activation |
| Block approval on critical findings | Critical validation findings must block approval |
| Preserve validation history | At least latest result must be stored; production should support history |
| Show validation evidence | Admin UI must expose validation results clearly |

Validation success means the package is structurally and logically acceptable for review. It does not mean the package is legally approved or active.

---

### 8.3 Review and Approval Governance

The system shall support formal review and approval before activation.

Required behavior:

| Capability | Requirement |
|---|---|
| Submit for review | Validated templates can be submitted for approval |
| Review decision | Authorized reviewer can approve, reject, or return |
| Review comments | Reviewer must be able to record decision comments |
| Approval evidence | Approver, timestamp, decision, comments, and validation result reference must be stored |
| Block self-approval where required | Production policy should prevent importer from approving own template unless explicitly allowed |
| Block approval without valid validation | Approval requires current passing validation |

---

### 8.4 Activation Governance

Approval and activation are separate controls.

Required behavior:

| Capability | Requirement |
|---|---|
| Activate approved version | Only approved versions can be activated |
| Restrict active versions | Active version policy must be explicit by template family/category |
| Allow tender creation | Only active and allowed templates may be selected for new tenders |
| Record activation evidence | Activator, timestamp, reason, approval reference, and template hash must be stored |
| Deactivate / retire | Active templates can be retired or superseded through controlled action |
| Prevent use of inactive templates | Inactive, draft, rejected, retired, or superseded templates cannot create new tenders |

---

### 8.5 Versioning Governance

The system shall support versioned STD templates.

Required behavior:

| Capability | Requirement |
|---|---|
| Version identity | Each template version has stable code/version identifiers |
| Hash identity | Each version has package hash |
| New version creation | New version may be imported as a separate governed package |
| Supersession relationship | New version may supersede prior version |
| Historical preservation | Old versions remain viewable for historical tenders |
| Tender binding | Tenders bind to exact version or tender STD instance |
| No silent mutation | Active version cannot be overwritten in place |

---

### 8.6 Immutability and Mutation Control

Active and historically used templates must be protected.

Required behavior:

| Template condition | Mutation rule |
|---|---|
| Draft / Imported | Editable only through controlled package replacement/import process |
| Validated | Re-import or content mutation resets validation status |
| Submitted for Approval | Content mutation blocked unless returned to draft |
| Approved | Content mutation blocked |
| Active | Content mutation blocked |
| Used by tender | Content mutation blocked permanently; create new version instead |
| Retired / Superseded | Content mutation blocked except archival metadata |

Any change to package content, rule definitions, form definitions, field definitions, legal text, or BoQ schema must produce a new package hash and normally a new version.

---

### 8.7 Supersession and Retirement

The system shall support controlled supersession and retirement.

Required behavior:

| Capability | Requirement |
|---|---|
| Supersede template | New approved/active version may supersede prior version |
| Retire template | Authorized user may retire template for future tender creation |
| Preserve historical use | Existing tenders remain linked to retired/superseded version |
| Prevent new use | Retired/superseded versions cannot create new tenders unless explicitly allowed under controlled exception |
| Impact note | Supersession/retirement must record reason and effective date |

---

### 8.8 Template Usage Tracking

The system shall track tender usage of STD templates.

Required behavior:

| Capability | Requirement |
|---|---|
| Usage count | Show number of tenders using template/version |
| Usage list | Show linked tenders where permission allows |
| Usage status | Show tender lifecycle status for linked tenders |
| Block destructive changes | Used templates cannot be deleted or mutated |
| Impact analysis | Before retirement/supersession, show affected tenders and future-use impact |

---

### 8.9 Admin Console Production Hardening

The existing Admin Console POC shall evolve into production-safe admin governance surfaces.

Required admin views:

1. STD Template Catalogue.
2. STD Template Version Detail.
3. Package Validation Dashboard.
4. Approval Decision Panel.
5. Activation Panel.
6. Supersession / Retirement Panel.
7. Usage Impact Panel.
8. Audit Trail Panel.
9. Technical Package Inspector.
10. Rule Trace and Form/BoQ Inspector.

Technical package internals remain admin-only and read-only after activation.

## 11. Proposed Lifecycle States

The STD template lifecycle shall include these states.

| State | Meaning |
|---|---|
| `Imported` | Package imported but not yet structurally validated |
| `Validation Failed` | Validation ran and blocking findings exist |
| `Validated` | Package validation passed with no blocking findings |
| `Submitted for Approval` | Template submitted for formal review/approval |
| `Returned for Correction` | Reviewer returned template for correction |
| `Rejected` | Template rejected and not eligible for activation |
| `Approved` | Template approved but not yet active for tender creation |
| `Active` | Template version available for tender creation |
| `Superseded` | Template replaced by a newer approved/active version |
| `Retired` | Template removed from future use but retained historically |
| `Archived` | Historical record retained; no operational use |

Exact fieldname/options shall be locked in the later governance state model and implementation pack.

---

## 12. Proposed Lifecycle Flow

Primary lifecycle:

```text
Imported
→ Validated
→ Submitted for Approval
→ Approved
→ Active
→ Superseded / Retired
→ Archived
```

Correction path:

```text
Imported / Validation Failed / Returned for Correction
→ corrected by new import or controlled replacement
→ Validated
```

Rejection path:

```text
Submitted for Approval
→ Rejected
```

Invalid validation path:

```text
Imported
→ Validation Failed
```

No tender may be created from a template unless it is in:

```text
Active
```

and specifically allowed for tender creation.

## 13. Required Governance Decisions

The following decisions must be formally resolved in this workstream.

| Decision | Required outcome |
|---|---|
| Can importer approve own template? | Default: No, unless System Manager override policy exists |
| Can multiple active versions exist for same family/category? | Must be explicit |
| Can retired templates be used for emergency/exception tenders? | Default: No |
| Can active templates be edited? | No; create new version |
| Can package JSON be edited directly? | No; import controlled package |
| Does validation need to be current before approval? | Yes |
| Does activation require approval? | Yes |
| Can activation and approval be same user? | Policy decision required; default separate where practical |
| What happens when package content changes after validation? | Validation resets |
| What happens when a template has been used by a tender? | Content immutable forever |

## 23. Server-Side Enforcement Scope

Governance cannot rely on UI alone. The server must enforce:

1. only active allowed templates can be selected for new tenders;
2. package mutation is blocked in protected states;
3. used templates cannot be deleted or overwritten;
4. approval requires current passing validation;
5. activation requires approval;
6. state transitions are role-checked;
7. transition comments/evidence are captured;
8. package hash must match the hash validated/approved/activated;
9. retired/superseded templates cannot create new tenders;
10. any template used by a tender remains historically accessible.

## 24. Relationship to Tender STD Instance Workstream

This workstream governs reusable STD templates and versions.

The later Tender STD Instance workstream shall govern tender-specific binding and snapshotting.

Relationship:

```text
Governed Active STD Template Version
→ selected during package-to-tender release or officer tender creation
→ creates Tender STD Instance / configuration snapshot
→ future tender lifecycle uses instance/snapshot, not mutable template
```

This workstream must therefore expose enough template identity, version, status, hash, and activation evidence for tender instance creation.

---

## 25. Relationship to Planning-to-Tender Release

Planning-to-Tender release may resolve STD templates only from governed active templates.

Rule:

```text
Release to Tender must fail if no active approved STD template/version can be resolved.
```

For the WORKS path:

```text
Procurement Package: Works / Open Tender
→ resolved active STD template/version: KE-PPRA-WORKS-BLDG-2022-04-POC or production successor
```

---

## 26. Relationship to WORKS Hardening

WORKS hardening requires reliable STD governance because BoQ, Works Requirements, required forms, and derived model readiness depend on the governing STD version.

This means:

1. Works hardening results must reference the exact template/version/hash;
2. hardening should not operate on unapproved mutable templates except in explicit development/test mode;
3. production Works tenders must not use draft/failed/rejected templates;
4. template supersession must not mutate Works tenders already created.

## 28. Risk Register

| Risk | Severity | Control |
|---|---|---|
| Active template edited in place | Critical | Immutability and hash enforcement |
| Unapproved template used for tender | Critical | Active-only server checks |
| Validation confused with legal approval | High | Separate states and permissions |
| Old tenders affected by new template version | Critical | Tender STD instance/snapshot model |
| Superseded template deleted | High | Historical retention and usage lock |
| Approval without current validation | High | Validation-hash approval gate |
| Same user imports and approves | Medium/High | Separation-of-duty policy |
| Admin UI exposes raw mutation path | Critical | Read-only inspector after protected states |
