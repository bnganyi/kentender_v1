## 2. Purpose

The purpose of this document is to define the role, permission, and separation-of-duty model for STD Template Governance and Lifecycle.

The STD governance module controls legal and operational template packages that determine tender configuration, bidder forms, Works requirements, BoQ posture, downstream submission/opening/evaluation models, and contract carry-forward fields. Therefore, access cannot be treated as ordinary administrator convenience.

This matrix defines:

1. governance roles;
2. role responsibilities;
3. state-transition permissions;
4. read/write permissions;
5. technical-inspection permissions;
6. separation-of-duty rules;
7. System Manager override controls;
8. server-side enforcement requirements;
9. audit requirements for privileged actions;
10. acceptance criteria.

---

## 3. Permission Principle

The role and permission model shall implement this principle:

> No single ordinary user should be able to import, approve, activate, and mutate an STD template package for production tender creation without controlled review, server-side guards, and audit evidence.

This means:

1. import is separate from approval;
2. approval is separate from activation where practical;
3. package mutation is restricted and state-dependent;
4. technical inspection is not the same as governance authority;
5. ordinary procurement officers cannot govern STD templates;
6. used or active templates cannot be changed through permission alone;
7. System Manager override must be audited and should not bypass immutability where tender usage exists.

## 4. Role Catalogue

The governance module shall use these roles.

| Role | Purpose | Production role? |
|---|---|---:|
| `STD Template Importer` | Imports controlled STD packages | Yes |
| `STD Template Administrator` | Manages imported/draft templates and runs validation | Yes |
| `STD Template Reviewer` | Reviews package evidence and recommends/returns | Yes |
| `STD Template Approver` | Approves or rejects templates | Yes |
| `STD Template Activator` | Activates, suspends, supersedes, or retires approved/active templates | Yes |
| `STD Template Auditor` | Read-only audit and historical review | Yes |
| `STD Technical Inspector` | Views technical package internals, rule trace, validation diagnostics | Yes |
| `Procurement Officer` | Consumes active templates during tender configuration | Yes, but not governance authority |
| `Procurement Planning Officer` | Uses template mappings indirectly during package release | Yes, but not governance authority |
| `System Manager` | Technical override under strict audit | Yes, restricted override |
| `QA / Test User` | Executes test/smoke scenarios in non-production | Non-production only |

Role names may later be adapted to repository conventions, but the implementation pack must lock exact names. These names are the intended default.

## 5. Role Responsibility Definitions

### 5.1 STD Template Importer

Responsibilities:

1. imports prepared STD packages;
2. captures source metadata;
3. may view own imported templates;
4. may correct package imports before approval through controlled replacement if allowed;
5. cannot approve or activate templates by default.

Must not:

1. approve own package;
2. activate package;
3. mutate protected package states;
4. use draft templates for tender creation.

---

### 5.2 STD Template Administrator

Responsibilities:

1. manages imported and draft candidate STD templates;
2. runs package validation;
3. views validation findings;
4. submits validated templates for review/approval;
5. manages controlled correction before approval;
6. prepares admin evidence for reviewers.

Must not:

1. approve templates unless separately granted `STD Template Approver` and separation-of-duty rules permit;
2. activate templates unless separately granted `STD Template Activator`;
3. mutate submitted, approved, active, suspended, superseded, retired, or archived packages.

---

### 5.3 STD Template Reviewer

Responsibilities:

1. reviews package summary;
2. reviews validation evidence;
3. reviews technical trace where permitted;
4. records review comments;
5. returns for correction where required;
6. may recommend approval depending on policy.

Must not:

1. activate templates;
2. mutate package payload;
3. use non-active templates for tender creation.

---

### 5.4 STD Template Approver

Responsibilities:

1. approves templates submitted for approval;
2. rejects templates with recorded reasons;
3. returns templates for correction;
4. confirms validation and package hash evidence;
5. records approval rationale.

Must not:

1. approve when validation is missing, failed, stale, or hash-mismatched;
2. approve own imported package unless explicit override policy allows;
3. mutate package payload;
4. activate templates unless separately granted and policy allows.

---

### 5.5 STD Template Activator

Responsibilities:

1. activates approved templates for tender creation;
2. suspends active templates where required;
3. supersedes active templates with replacement versions;
4. retires templates from future use;
5. records activation, suspension, supersession, and retirement reasons;
6. reviews usage impact before supersession/retirement.

Must not:

1. activate unapproved templates;
2. activate templates with stale approval/hash evidence;
3. mutate package payload;
4. erase historical usage.

---

### 5.6 STD Template Auditor

Responsibilities:

1. reads lifecycle state history;
2. reads audit events;
3. reads historical template metadata;
4. views usage records;
5. verifies who approved/activated/retired templates.

Must not:

1. mutate templates;
2. run lifecycle transitions;
3. edit audit evidence.

---

### 5.7 STD Technical Inspector

Responsibilities:

1. views package internals read-only;
2. views manifest, fields, rules, forms, sections, render templates, BoQ schema, and technical validation trace;
3. troubleshoots package errors;
4. supports admin/reviewer decisions.

Must not:

1. approve templates by inspection right alone;
2. activate templates by inspection right alone;
3. mutate protected package payload;
4. expose package internals to ordinary procurement officers.

---

### 5.8 Procurement Officer

Responsibilities:

1. uses active templates in tender configuration through guided officer UI;
2. views selected template summary where relevant;
3. configures tender-specific permitted fields;
4. does not govern reusable STD templates.

Must not:

1. import STD templates;
2. validate template packages;
3. approve templates;
4. activate templates;
5. inspect raw package internals unless separately authorized;
6. edit STD fields/rules/forms/sections/legal content.

---

### 5.9 Procurement Planning Officer

Responsibilities:

1. prepares procurement plans/packages;
2. uses planning template to STD template mappings indirectly;
3. may see which active STD template is resolved for a package.

Must not:

1. govern STD lifecycle;
2. activate templates;
3. mutate STD package content.

---

### 5.10 System Manager

Responsibilities:

1. performs technical administration;
2. manages emergency recovery;
3. may perform override actions only where policy allows;
4. must provide override reason for governance-sensitive actions.

Must not:

1. mutate used template package content;
2. delete template versions used by tenders;
3. bypass audit requirements;
4. bypass hash immutability rules.

System Manager is not a substitute for normal governance workflow.

## 6. Permission Categories

The matrix uses these permission categories.

| Category | Meaning |
|---|---|
| `R` | Read metadata/basic record |
| `RT` | Read technical package internals |
| `C` | Create/import candidate package |
| `U-DRAFT` | Update draft/imported metadata or controlled package replacement |
| `VAL` | Run validation |
| `SUBMIT` | Submit for approval |
| `REVIEW` | Review and return/recommend |
| `APPROVE` | Approve/reject |
| `ACTIVATE` | Activate approved template |
| `SUSPEND` | Suspend active template |
| `SUPERSEDE` | Supersede template with replacement |
| `RETIRE` | Retire template |
| `ARCHIVE` | Archive historical/non-operational template |
| `USAGE-R` | View usage impact |
| `AUDIT-R` | View audit events |
| `DELETE` | Delete record |

Default production rule:

```text
DELETE is not allowed for governed STD templates once imported, except in non-production test data or abandoned import cleanup before any approval/tender usage. Even then, archive is preferred.
```

## 10. Separation-of-Duty Rules

### 10.1 Default Rules

| Rule ID | Rule | Default enforcement |
|---|---|---|
| `STD-SOD-001` | Importer cannot approve own imported template | Enforce |
| `STD-SOD-002` | Approver cannot approve if they performed last package replacement | Enforce unless override |
| `STD-SOD-003` | Activation should be separate from approval | Warn or enforce by policy |
| `STD-SOD-004` | System Manager override requires mandatory reason | Enforce |
| `STD-SOD-005` | Used template cannot be mutated even by System Manager | Enforce |
| `STD-SOD-006` | Technical Inspector rights do not imply approval/activation rights | Enforce |
| `STD-SOD-007` | Procurement Officer cannot govern STD template lifecycle | Enforce |

### 10.2 Override Policy

System Manager override may be permitted for:

1. emergency activation/deactivation;
2. correcting wrongly assigned status where no tender usage exists;
3. recovering from failed transition;
4. non-production test setup.

System Manager override must not permit:

1. editing package payload after tender usage;
2. deleting used templates;
3. approving with stale/missing validation hash;
4. silently bypassing audit.

Override must record:

1. actor;
2. timestamp;
3. action;
4. previous state;
5. new state;
6. reason;
7. affected package hash;
8. whether tender usage exists.

## 11. Procurement Officer Access Boundary

Procurement Officer may access only active template summaries through tender creation/configuration workflows.

Allowed officer-visible fields:

1. template name;
2. template code;
3. template family/category;
4. version;
5. active status;
6. high-level source authority;
7. configured tender fields produced by STD package.

Not visible/editable to ordinary Procurement Officer:

1. raw package JSON;
2. manifest internals;
3. field definition internals;
4. rule expressions;
5. form activation rules;
6. render templates;
7. validation trace internals;
8. approval workflow internals beyond summary;
9. technical package payload;
10. lifecycle transition buttons.

---

## 12. Technical Inspector Boundary

STD Technical Inspector may inspect raw package internals but cannot make governance decisions by that role alone.

Allowed:

1. view package JSON;
2. view validation result JSON;
3. view rule trace;
4. view form activation trace;
5. view BoQ/Works schema trace;
6. view render diagnostics.

Not allowed by this role alone:

1. import package;
2. replace package;
3. submit for approval;
4. approve;
5. activate;
6. retire;
7. supersede;
8. mutate package in protected states.

---

## 13. Auditor Access Boundary

STD Template Auditor shall have read-only access to historical evidence.

Allowed:

1. read lifecycle status;
2. read transition history;
3. read audit events;
4. read validation summaries;
5. read approval/activation evidence;
6. read usage impact;
7. read package internals where policy permits audit review.

Not allowed:

1. transition states;
2. edit records;
3. alter audit evidence;
4. delete records;
5. run corrections.

---

## 14. Server-Side Enforcement Requirements

All governance actions must call server methods that enforce:

1. authenticated user;
2. role permission;
3. current lifecycle state;
4. transition guard conditions;
5. separation-of-duty rules;
6. package hash consistency;
7. validation status requirements;
8. approval/activation evidence requirements;
9. tender usage lock rules;
10. audit event creation.

Client-side button hiding is not sufficient.

## 16. Permission Failure Behavior

When access is denied, the system must fail clearly.

| Failure | Required response |
|---|---|
| User lacks role | Permission error with action name |
| State transition not allowed | State guard error with current status |
| SoD violation | Separation-of-duty error |
| Hash mismatch | Hash integrity error requiring revalidation or new version |
| Attempt to mutate protected package | Mutation blocked and audit event recorded |
| Attempt to use inactive template | Tender creation eligibility error |
| Attempt to delete used template | Deletion blocked and audit event recorded |

Do not silently hide server-side failures.

## 19. Recommended Frappe Permission Approach

The implementation pack shall specify exact Frappe permissions later. Recommended approach:

1. Use DocType permissions for broad read/create/write restrictions.
2. Use server methods for lifecycle actions.
3. Use state guards inside server methods.
4. Use custom permission query/user-permission logic if needed for officer summary visibility.
5. Avoid granting Write permission broadly where lifecycle-specific methods are safer.
6. Consider making raw package fields read-only in DocType and updating them only through controlled import methods.

Important:

```text
Frappe role permission alone is insufficient for lifecycle governance. Server-side action methods must enforce business rules.
```
