## 2. Purpose

The purpose of this document is to define the production admin user experience for STD Template Governance and Lifecycle.

The admin UX shall allow authorized users to import, inspect, validate, submit, approve, activate, suspend, supersede, retire, archive, and audit STD template versions through controlled actions.

The UX shall make governance status and next actions clear without allowing uncontrolled editing of package internals, legal content, rules, forms, BoQ schemas, or derived model logic.

This document defines user journeys, screens, panels, actions, visibility rules, status displays, error states, and acceptance criteria. It does not authorize implementation. The later Cursor implementation pack shall translate this UX into exact Frappe form sections, buttons, dialogs, client scripts, server methods, permissions, fixtures, and tests.

---

## 3. UX Principle

The admin UX shall implement this principle:

> STD administrators should be able to govern template versions through explicit lifecycle actions, while package internals remain controlled, traceable, and protected from casual mutation.

This means:

1. lifecycle actions are explicit buttons/actions, not ordinary field edits;
2. current status and eligibility are always visible;
3. next permitted actions are based on role and state;
4. validation, approval, and activation are visibly separate;
5. package hash and validation hash evidence are visible;
6. package internals are inspectable by authorized users but read-only in protected states;
7. usage impact is shown before suspension, supersession, retirement, or archival;
8. ordinary procurement officers never see this governance console as a template-authoring surface.

## 5. Non-Scope

The admin UX shall not include:

1. ordinary procurement officer tender configuration;
2. planning-to-tender release UI;
3. bidder portal;
4. bid submission;
5. bid opening;

7. award;

9. final PDF generation;
10. public publication;
11. manual editing of legal clauses/rules/forms inside active templates;
12. manual submission checklist builder;
13. manual evaluation criteria builder;
14. direct mutation of package payload after protected states.

## 6. Primary Admin Journeys

The admin UX shall support these journeys.

| Journey | Primary actor | Outcome |
|---|---|---|
| Import package | STD Template Importer / Administrator | New template version in `Imported` state |
| Validate package | STD Template Administrator | Template becomes `Validated` or `Validation Failed` |
| Submit for approval | STD Template Administrator | Template becomes `Submitted for Approval` |
| Review and approve | Reviewer / Approver | Template becomes `Approved`, `Returned for Correction`, or `Rejected` |
| Activate template | STD Template Activator | Template becomes `Active` and selectable for tender creation |
| Suspend template | STD Template Activator | Active template blocked from new use |
| Reinstate suspended template | STD Template Activator | Suspended template returns to Active |
| Supersede template | STD Template Activator | Old version becomes Superseded and replacement recorded |
| Retire template | STD Template Activator | Template blocked from future use |
| Inspect template | Technical Inspector / governance users | Package internals inspected read-only |
| Audit lifecycle | Auditor / governance users | Lifecycle history and evidence reviewed |

## 7. STD Template Catalogue UX

### 7.1 Purpose

The catalogue is the administrator entry point for governed STD template versions.

It shall answer:

1. Which STD templates exist?
2. Which versions are active?
3. Which templates are awaiting validation, approval, or activation?
4. Which templates are superseded, retired, or archived?
5. Which templates are allowed for tender creation?
6. Which templates are used by tenders?

### 7.2 Required Columns

The catalogue/list view shall show these columns.

| Column | Source field | Required |
|---|---|---:|
| Template Code | `template_code` | Yes |
| Title | `template_title` | Yes |
| Family | `template_family` | Yes |
| Category | `procurement_category` | Yes |
| Method Profile | `procurement_method_profile` | Recommended |
| Version | `template_version` | Yes |
| Lifecycle Status | `lifecycle_status` | Yes |
| Validation Status | `latest_validation_status` | Yes |
| Allowed for Tender Creation | `allowed_for_tender_creation` | Yes |
| Package Hash | `package_hash` shortened with full copy | Recommended |
| Usage Count | `tender_usage_count` | Yes |
| Active From | `active_from` | Recommended |
| Superseded By | `superseded_by_template` | Recommended |

### 7.3 Required Filters

| Filter | Required |
|---|---:|
| Template Family | Yes |
| Procurement Category | Yes |
| Lifecycle Status | Yes |
| Validation Status | Yes |
| Allowed for Tender Creation | Yes |
| Has Usage | Yes |
| Active Profile Key | Recommended |
| Source Authority | Recommended |
| Template Version | Recommended |

### 7.4 Catalogue Actions

| Action | Visible to | Behavior |
|---|---|---|
| Import STD Package | Importer, Administrator, System Manager | Opens import workflow |
| Open Template | Governance users | Opens detail view |
| View Active Templates | Governance users | Filter active templates |

### 9.1 Purpose

The banner shall give the administrator an immediate understanding of current governance state.

### 9.2 Required Banner Fields

| Next Required Action | derived from state |

### 9.3 Banner Message Examples

#### Imported

```text
This STD package has been imported but has not yet been validated. It cannot be used for tender creation.
```

#### Validated

```text
This STD package has passed validation but is not approved or active. Submit it for approval before activation.
```

#### Submitted for Approval

```text
This STD package is awaiting approval. Package content is locked during review.
```

#### Approved

```text
This STD package is approved but not active. Activate it before it can be used for tender creation.
```

#### Active

```text
This STD template version is active and eligible for tender creation, subject to category/method mapping.
```

#### Suspended

```text
This STD template version is suspended and cannot be used for new tenders until reinstated or superseded.
```

#### Superseded / Retired

```text
This STD template version is historical and cannot be used for new tenders. Existing tender references remain auditable.
```

| Source authority | Yes |
| Source document code | Yes |
| Source document title | Recommended |
| Source effective date | Optional |
| Import source type | Yes |
| Import note | Optional |

### 11.3 Import Output

After successful import:

1. template record created or updated only if controlled replacement is allowed;
2. package hash generated;
3. lifecycle status = `Imported`;
4. latest validation status = `Not Run`;
5. allowed for tender creation = false;
6. audit event `STD_TEMPLATE_IMPORTED` created;
7. user is routed to template detail page.

### 11.4 Import Failure States

| Failure | Required display |
|---|---|
| Missing package | Package required error |
| Malformed package | Import failed with parse error |
| Duplicate template code/version | Existing version conflict |
| Duplicate package hash | Warning or duplicate detection |
| User lacks permission | Permission error |

## 12. Controlled Package Replacement Workflow

Package replacement is allowed only in controlled replacement states:

```text
Imported
Validation Failed
Validated
Returned for Correction
```

### 12.1 Required Inputs

| Input | Required |
|---|---:|
| Replacement package | Yes |
| Replacement reason | Yes |
| Confirmation | Yes |

### 12.2 Required Effects

1. package payload replaced;
2. new package hash computed;
3. validation fields reset;
4. approval fields cleared where applicable;
5. activation fields remain empty;
6. lifecycle status becomes `Imported`;
7. replacement audit event recorded;
8. package cannot be used for tender creation.

### 12.3 Protected State Message

If replacement is attempted in protected state:

```text
Package replacement is blocked because this template is in a protected lifecycle state. Create a new template version instead.
```

## 16. Activation Workflow

### 16.1 Entry Point

Visible only when:

1. lifecycle status = `Approved`;
2. user has activation permission;
3. approval hash matches current package hash;
4. validation hash matches current package hash.

### 16.2 Activation Dialog

Required inputs:

| Input | Required |
|---|---:|
| Activation reason | Yes |
| Active from date | Recommended; default today |
| Active until date | Optional |
| Is default active version | Recommended |
| Confirmation | Yes |

The dialog shall show:

1. template family;
2. procurement category;
3. method profile;
4. active profile key;
5. existing active versions for same profile;
6. usage warning if replacing/superseding is expected;
7. approval reference;
8. package hash.

### 16.3 Existing Active Version Handling

If another active default version exists for the same active profile key, the system shall not silently activate.

Required behavior:

| Scenario | Required response |
|---|---|
| No active conflict | Activation may proceed |
| Active conflict exists | Show conflict and require explicit supersession or non-default activation policy |
| Multiple active matches | Block deterministic tender selection until resolved |

### 16.4 Output

1. lifecycle status = `Active`;
2. allowed for tender creation = true;
3. activated by/at captured;
4. activation reason stored;
5. activation package hash stored;
6. audit event recorded.

## 17. Suspension / Reinstatement Workflow

### 17.1 Suspend

Visible when status = `Active` and user has suspension permission.

Required inputs:

1. suspension reason;
2. confirmation.

Before suspension, show usage impact.

Result:

1. status = `Suspended`;
2. allowed for tender creation = false;
3. existing tender usage preserved;
4. audit event recorded.

### 17.2 Reinstate

Visible when status = `Suspended` and user has activation permission.

Required inputs:

1. reinstatement reason;
2. confirmation.

Guard conditions:

1. approval/hash evidence still current;
2. no blocking governance issue remains;
3. active profile conflict policy satisfied.

Result:

1. status = `Active`;
2. allowed for tender creation = true;
3. audit event recorded.

---

## 18. Supersession Workflow

### 18.1 Entry Point

Visible when status = `Active` or `Suspended` and user has supersession permission.

### 18.2 Required Inputs

| Input | Required |
|---|---:|
| Replacement STD Template | Yes |
| Supersession reason | Yes |
| Effective date | Recommended |
| Confirmation | Yes |

### 18.3 Supersession Dialog Must Show

1. current template identity;
2. replacement template identity;
3. replacement lifecycle status;
4. replacement package hash;
5. usage count of current template;
6. linked tenders summary;
7. warning that existing tenders remain on old version;
8. warning that new tender creation will use replacement mapping/active version.

### 18.4 Guards

Replacement template must be:

1. Approved or Active according to policy;
2. same or compatible family/category/method profile;
3. hash-valid;
4. not retired/superseded/archived;
5. eligible to replace current template.

### 18.5 Output

1. old template status = `Superseded`;
2. old template allowed for tender creation = false;
3. `superseded_by_template` populated;
4. supersession evidence stored;
5. audit event recorded;
6. historical tenders remain linked to old template.

## 24. Hash and Integrity Display UX

Hash fields shall be visible but not disruptive.

Rules:

1. show short hash in summary;
2. provide full copyable hash in detail;
3. display validation hash and current package hash side by side;
4. warn on mismatch;
5. approval and activation dialogs must show hash evidence;
6. do not use hash as primary human label.

Hash mismatch warning:

```text
The current package hash does not match the latest validation or approval hash. Revalidation and renewed approval are required before activation or tender use.
```

## 25. Empty and Blocked States

### 25.1 No Templates

```text
No STD templates have been imported. Import a controlled STD package to begin governance.
```

### 25.2 No Validation Run

```text
This package has not been validated. Run validation before submitting it for approval.
```

### 25.3 Validation Failed

```text
This package has blocking validation findings. Correct the package through controlled replacement and run validation again.
```

### 25.4 Approval Blocked

```text
Approval is blocked because validation is missing, failed, stale, or no longer matches the current package hash.
```

### 25.5 Activation Blocked

```text
Activation is blocked because approval evidence is missing, stale, or does not match the current package hash.
```

### 25.6 Mutation Blocked

```text
Package mutation is blocked in the current lifecycle state. Create a new template version or return the package for correction where allowed.
```

### 25.7 Tender Use Blocked

```text
This STD template version is not active and allowed for tender creation. It cannot be selected for new tenders.
```

## 26. Officer-Facing Boundary

Officer-facing workflows may show only a compact active-template summary.

Allowed officer summary:

1. template title;
2. template code;
3. template version;
4. template family/category;
5. active status;
6. source authority;
7. high-level description.

Officer workflows must not expose:

1. approval action buttons;
2. activation action buttons;
3. package replacement;
4. raw payload;
5. rule internals;
6. technical trace;
7. lifecycle admin panels.
