## 2. Purpose

The purpose of this document is to define the production domain model and data dictionary for STD Template Governance and Lifecycle.

This document translates the governance scope, lifecycle model, and role/permission matrix into concrete domain objects, relationships, fields, data ownership rules, state fields, audit fields, validation fields, approval fields, activation fields, versioning fields, usage fields, and transition records.

This document still does not authorize implementation. It prepares the exact data model that will later be converted into a complete, ticketed Cursor Implementation Pack.

---

## 3. Data Modelling Principle

The governance domain model shall implement this principle:

> A governed STD template version must be independently identifiable, hash-verifiable, lifecycle-controlled, historically auditable, and safely bindable to tenders without depending on mutable package content.

This means:

1. the governed unit is the STD template version;
2. every version must have stable identity and package hash;
3. lifecycle state must be explicit;
4. validation evidence must be tied to package hash;
5. approval evidence must be tied to validation and package hash;
6. activation evidence must be tied to approval and package hash;
7. usage by tenders must permanently lock package mutation;
8. package payload must be read-only after protected states;
9. future Tender STD Instance creation must reference governed active template version identity;
10. historical templates must remain queryable even after supersession or retirement.

## 4. Current Implementation Position

The current system already contains an `STD Template` DocType from the POC. It stores the package-level representation used by admin and officer POCs.

For production governance, there are two possible modelling paths:

| Option | Description | Pros | Cons |
|---|---|---|---|
| Option A — Extend existing `STD Template` | Add governance/version fields directly to existing DocType | Fastest, lower migration effort, compatible with POC | Family/version separation less clean |
| Option B — Add `STD Template Family` and `STD Template Version` | Separate stable family identity from governed versions | Cleaner production architecture | Requires more refactor |

Recommended approach for this stage:

```text
Use Option A as the implementation path, but model fields so they can migrate later to Option B without semantic loss.
```

Therefore:

1. extend `STD Template` as the governed version record in the near term;
2. add fields that distinguish family, version, source, status, validation, approval, activation, supersession, retirement, usage, and audit;
3. use child records for lifecycle events, validation findings, and usage records;
4. leave room for a future `STD Template Family` parent if needed.

The later Cursor Implementation Pack shall use this recommendation unless the repository already contains a better family/version structure.

Rules:

2. `package_hash_algorithm` shall default to `SHA-256`.

5. Any package replacement before protected state creates a new hash and resets validation/approval/activation fields as defined by transition rules.

## 23. Package Payload Canonicalization Rules

To ensure package hash stability:

1. package JSON shall be serialized with sorted keys;
2. whitespace differences shall not change hash if canonicalization is applied;
3. binary attachments shall be represented by their own hashes or references if part of package;
4. `canonicalization_version` shall be stored;
5. validation, approval, and activation shall all reference the same package hash;
6. package replacement shall always recompute hash.

Default algorithm:

```text
SHA-256 over canonical package JSON V1
```

## 24. Protected State Definition

Protected states are:

```text
Submitted for Approval
Approved
Active
Suspended
Superseded
Retired
Archived
Rejected
```

Package content mutation is blocked in all protected states.

Controlled replacement states are:

```text
Imported
Validation Failed
Validated
Returned for Correction
```

Even in controlled replacement states, replacement must:

1. recompute package hash;
2. reset validation status;
3. clear approval/activation fields as applicable;
4. write lifecycle event;
5. prevent tender use until revalidated/approved/activated.

## 25. Delete Rules

Deletion shall be disabled by default for governed templates.

| Condition | Delete allowed? |
|---|---:|
| Template imported in production | No; archive instead |
| Template used by tender | No |
| Template active/suspended/superseded/retired/archived | No |
| Test fixture in non-production | Only if explicitly marked test and no usage |
| Abandoned import before validation in development | Optional, but archive preferred |
