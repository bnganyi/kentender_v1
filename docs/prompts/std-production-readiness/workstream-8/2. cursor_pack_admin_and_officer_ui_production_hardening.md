# 1. Implementation Mandate

Cursor must harden the STD-related UI so users interact with role-specific business workflows rather than raw STD Engine internals.

This implementation must use backend action availability as the source of truth for actions. The frontend must not decide legal permission from role names alone.

The UI must make the system usable for procurement users while preserving legal controls.

The implementation must enforce these principles:

1. STD Administrator UI is Official STD Library-oriented.
2. Procurement Officer UI is Tender-oriented.
3. Procurement Assistant UI is delegated-task-oriented.
4. Approving Authority UI is read-only review-package-oriented.
5. Auditor UI is evidence/audit-oriented.
6. Advanced technical STD internals are hidden by default.
7. Frontend actions are enabled/disabled/hidden based on backend action availability.
8. Legal denials are displayed in plain language.
9. TDS/SCC are shown as business fields, not editable legal clause text.
10. BOQ preparation never shows supplier rate-entry fields.
11. Generated outputs are shown as outputs, not editable documents.
12. Approval UI does not allow silent edits.
13. Publication UI clearly warns about immutability.
14. Published tender UI routes users to addendum/reissue path for changes.
15. Evidence and audit UI allows authorized inspection and export only.

### Objective

### Required API Client

```text
frontend/src/modules/std-engine/shared/action-availability/actionAvailabilityClient.ts
```

### Required Methods

```text

```

### Backend Endpoints

```text

```

### Required Types

```typescript
type ActionAvailabilityRequest = {
  action_code: string;
  object_type: string;
  object_code: string;
  context?: Record<string, unknown>;
};

type ActionAvailabilityResponse = {
  action_code: string;
  allowed: boolean;
  denial_code?: string | null;
  message: string;
  required_permission?: string | null;
  object_state?: string | null;
  risk_level: 'Low' | 'Medium' | 'High' | 'Critical';
  requires_confirmation: boolean;
  audit_on_attempt: boolean;
};
```

### Acceptance Criteria

- Client supports single and batch requests.
- Client handles errors gracefully.
- No screen hardcodes legal enablement without calling backend availability.

## Ticket UI-HARD-0110 — Implement Action-Aware Button Component

### Objective

Create reusable button that renders based on backend action availability.

### Component

```text
<ActionAwareButton />
```

### Required Props

```typescript
type ActionAwareButtonProps = {
  actionCode: string;
  objectType: string;
  objectCode: string;
  label: string;
  variant?: 'primary' | 'secondary' | 'danger';
  hideWhenDenied?: boolean;
  onAllowedClick: () => void;
  confirmationTitle?: string;
  confirmationMessage?: string;
};
```

### Required Behavior

| Availability Result | Behavior |
|---|---|
| allowed=true, requires_confirmation=false | Enabled button triggers action. |
| allowed=true, requires_confirmation=true | Show confirmation before action. |
| allowed=false, hideWhenDenied=true | Do not render. |
| allowed=false, hideWhenDenied=false | Render disabled with reason tooltip/message. |

### Required Selectors

```text
action-aware-button-{actionCode}
action-denial-reason-{actionCode}
action-confirmation-{actionCode}
```

### Acceptance Criteria

- Disabled legal action displays reason.
- Hidden irrelevant action absent from DOM.
- Confirmation shown for critical actions requiring confirmation.
