# 1. Implementation Mandate

Cursor must implement security, authorization, and audit hardening as a cross-cutting backend control layer.

This implementation must not be treated as frontend menu hiding.

Every legally meaningful action must be checked by backend authorization using:

1. actor identity;
2. assigned roles;
3. assigned permissions;
4. object type;
5. object state;
6. object scope;
7. lifecycle context;
8. explicit negative permission rules;
9. policy constraints;
10. audit requirements.

The frontend may render actions based on backend action availability, but backend service endpoints must independently enforce the same rules.

# 8. Authorization Decision Engine

## Ticket SEC-0300 — Implement Authorization Decision Engine

### Objective

Centralize authorization decisions.

### Service Name

```text
AuthorizationDecisionEngine
```

### Required Method

```text
evaluate(actor, action_code, object_type, object_code, context = {})
```

### Required Evaluation Steps

The engine must evaluate in this order:

1. Actor exists and active.
2. Actor has required permission.
3. Actor has object scope.
4. Object exists.
5. Object state permits action.
6. Lifecycle context permits action.
7. Negative permission rules do not prohibit action.
8. Additional policy checks pass.
9. Audit requirement determined.

### Required Output

```json
{
  "allowed": true,
  "action_code": "PUBLISH_TENDER",
  "required_permission": "PERM_TENDER_PUBLISH",
  "risk_level": "Critical",
  "requires_confirmation": true,
  "audit_on_attempt": true,
  "message": "Allowed"
}
```

Denied output:

```json
{
  "allowed": false,
  "action_code": "PUBLISH_TENDER",
  "required_permission": "PERM_TENDER_PUBLISH",
  "denial_code": "PUBLISH_READINESS_NOT_READY",
  "risk_level": "Critical",
  "audit_on_attempt": true,
  "message": "Tender cannot be published until publication readiness is Ready."
}
```

### Acceptance Criteria

- Engine supports role/permission/state/scope/negative checks.
- Engine returns stable denial code.
- Engine marks audit_on_attempt for high/critical actions.

# 10. State Authorization Service

## Ticket SEC-0320 — Implement State-Based Authorization Service

### Objective

Block actions inconsistent with object state.

### Service Name

```text
StateAuthorizationService
```

### Required Methods

```text
assertTemplateStateAllows(action_code, template_state)
assertInstanceStateAllows(action_code, instance_state)
assertOutputStateAllows(action_code, output_state)
assertSnapshotStateAllows(action_code, snapshot_state)
assertTenderStateAllows(action_code, tender_state)
```

### Required Controls

#### Template

- Active templates are immutable.
- Superseded/retired templates are read-only.
- Under-review templates block configuration edits.

#### STD Instance

- Draft/In Configuration allow authorized edits.
- Ready for Publication allows limited edits but invalidates readiness.
- Locked for Approval blocks ordinary edits.
- Published Locked blocks direct edits; addendum required.

#### Outputs

- Published outputs immutable.
- Stale outputs not consumable for readiness/publication.
- Superseded outputs historical only.

#### Snapshots

- Final snapshots immutable.

### Acceptance Criteria

- Active template edit denied.
- Locked-for-approval instance edit denied.
- Published instance edit denied with addendum-required code.
- Published output overwrite denied.
- Final snapshot modification denied.
