## 1. Purpose

This document consolidates and formalizes security, permissions, state-based authorization, audit logging, and evidence controls across the STD Engine and the modules that consume STD-derived outputs.

The STD Engine is legally sensitive because it determines:

1. which standard tender document is used;
2. which tender-specific values become legally binding;
3. which submission requirements bidders must satisfy;
4. which opening fields are recorded;
5. which evaluation rules apply;
6. which contract terms carry forward;
7. which tender artifacts are published and locked.

Security cannot be treated as simple menu visibility.

The system must enforce permissions, object state, lifecycle context, and legal constraints at the backend service layer.

---

## 2. Core Security Principle

Frontend visibility is not authorization.

Every legally meaningful action must be authorized by backend rules.

The UI may display or hide actions based on backend action availability, but the backend must remain the final authority.

Correct model:

```text
User + Role + Object + State + Context + Policy
        ↓
Backend Action Availability
        ↓
Allowed / Denied with reason
        ↓
Audit event recorded
```

Incorrect model:

```text
Frontend hides button
        ↓
Assume action is secure
```

### 3.2 Out of Scope

1. identity provider integration;
2. password policy;
3. multi-factor authentication;
4. network security;
5. encryption key management;
6. database backup strategy;
7. full SOC/security operations policy.

Those are platform-level security concerns and must be handled separately.

## 7. Object Scope and Context Rules

Permissions alone are insufficient.

The authorization engine must also evaluate object scope and context.

### 7.1 Scope Dimensions

| Scope Dimension | Examples |
|---|---|
| Organization | Procuring entity, department, central governance unit. |
| Object ownership | Package assigned to officer; tender assigned to team. |
| Role context | Committee assignment for specific tender. |
| Lifecycle context | Draft, under review, published. |
| Object type | Template, STD Instance, Tender, Output, Snapshot. |
| Delegation | Temporary assistant assignment. |
| Conflict rules | Evaluator should not mutate tender configuration. |

### 7.2 Required Object-Scope Checks

| Action | Required Scope Check |
|---|---|
| Release package to tender | Actor assigned to package/procuring entity and package approved. |
| Complete STD Instance | Actor assigned to tender and instance is editable. |
| Approve tender | Actor has approval authority for procuring entity/value/category. |
| Conduct opening | Actor assigned to opening committee for tender. |
| Conduct evaluation | Actor assigned to evaluation committee for tender. |
| Export evidence | Actor has oversight/evidence export scope. |

## 8. State-Based Authorization

### 8.1 Template State Controls

| Template State | Mutation Rule |
|---|---|
| Imported Draft | STD Admin may edit/configure. |
| Needs Attention | STD Admin may correct. |
| Ready for Review | Locked except submit/review workflow. |
| Under Review | Configuration edits blocked. |
| Active | Immutable; create new revision to change. |
| Superseded | Read-only historical. |
| Retired | Read-only historical. |

### 8.2 STD Instance State Controls

| Instance State | Mutation Rule |
|---|---|
| Draft | Procurement Officer may edit. |
| In Configuration | Procurement Officer/authorized assistant may edit. |
| Validation Blocked | Edits allowed to resolve blockers. |
| Ready for Publication | Limited edits; changes invalidate readiness. |
| Locked for Approval | Ordinary edits denied. |
| Published Locked | Direct edits denied; addendum required. |
| Addendum Pending | Only addendum workflow may mutate affected data. |
| Superseded | Read-only historical. |
| Cancelled | Read-only except closure metadata. |

### 8.3 Generated Output State Controls

| Output State | Mutation Rule |
|---|---|
| Draft | May regenerate/replace according to service rules. |
| Current | May become Stale or Published; not manually edited. |
| Published | Immutable. |
| Superseded | Read-only historical. |
| Archived | Read-only. |
| Stale | Cannot be consumed for readiness/publication. |
| Failed | Diagnostic only; not consumable. |

### 8.4 Snapshot State Controls

| Snapshot State | Rule |
|---|---|
| Draft | Internal preparation only. |
| Final | Immutable. |
| Superseded | Read-only historical. |
| Archived | Read-only. |

## 9. Action Availability Service

### 9.1 Purpose

The Action Availability Service is the backend source of truth for whether a user can perform a specific action on a specific object.

The frontend shall call this service to render enabled/disabled actions.

The backend shall also enforce the same checks when the action endpoint is called.

### 9.2 Service Name

```text
ActionAvailabilityService
```

### 9.3 Required Input

```yaml
action_availability_request:
  actor_user_code: string required
  action_code: string required
  object_type: string required
  object_code: string required
  context: json optional
```

### 9.4 Required Output

```yaml
action_availability_response:
  action_code: string
  allowed: boolean
  denial_code: string optional
  message: text
  required_permission: string optional
  object_state: string optional
  risk_level: Low/Medium/High/Critical
  requires_confirmation: boolean
  audit_on_attempt: boolean
```

### 9.5 Required Action Codes

At minimum:

```text
IMPORT_OFFICIAL_STD_PACKAGE
VALIDATE_STD_TEMPLATE
ACTIVATE_STD_TEMPLATE
RELEASE_PACKAGE_TO_TENDER
CREATE_STD_INSTANCE_FROM_TENDER
```


## 10. Negative Permission Rules

Negative rules are explicit prohibitions that must be enforced even if a user has broad access elsewhere.

| Rule Code | Prohibition |
|---|---|
| NEG_STD_ADMIN_NO_INSTANCE_CREATE | STD Administrator cannot create tender STD Instances. |
| NEG_PROC_NO_TEMPLATE_CONFIG | Procurement Officer cannot edit STD template mappings/configuration. |
| NEG_ASSISTANT_NO_MARK_READY | Procurement Assistant cannot mark STD Instance ready unless explicitly delegated by policy. |
| NEG_APPROVER_NO_SILENT_EDIT | Approving Authority cannot directly edit tender content during approval. |
| NEG_OPENING_NO_EVALUATION | Opening Committee cannot perform evaluation or arithmetic correction. |
| NEG_EVAL_NO_MANUAL_CRITERIA | Evaluation Committee cannot add manual criteria. |
| NEG_CONTRACT_NO_DCM_OVERRIDE | Contract module/user cannot silently override DCM terms. |
| NEG_AUDITOR_NO_MUTATION | Auditor cannot mutate tender/template/instance records. |
| NEG_SYSADMIN_NO_OPERATIONAL_APPROVAL | System Administrator cannot approve/publish operational tenders by default. |
| NEG_PUBLISHED_NO_DIRECT_EDIT | Published tender artifacts cannot be directly edited. |

## 12. Audit Hardening Principles

### 12.1 Audit Is Mandatory for Legal Actions

All high-risk and critical actions must be audited.

This includes successful actions and denied attempts.

### 12.2 Audit Is Append-Only

Audit records shall not be edited or deleted through ordinary application workflows.

Corrections must be recorded as new audit events.

### 12.3 Audit Records Must Be Linkable

Audit events must link to:

- actor;
- object;
- action;
- result;
- state before/after where relevant;
- output/snapshot references where relevant;
- denial code where denied.

### 12.4 Denied Attempts Must Be Audited

Denied attempts are legally important because they show attempted violation of controlled workflow.

Examples:

- manual evaluation criteria attempted;
- post-publication BOQ edit attempted;
- STD Administrator attempted STD Instance creation;
- Procurement Officer attempted template mapping edit.

## 15. Evidence Exportability Controls

### 15.1 Evidence Package Must Be Complete

Evidence export must be able to assemble:

- planning release;
- tender;
- STD template/version/profile;
- STD Instance;
- completed values;
- BOQ;
- Works Requirements;
- generated outputs;
- snapshots;
- approvals;
- audit events;
- downstream consumption references.

### 15.2 Export Authorization

Only users with evidence/audit permissions may export evidence.

Allowed by default:

- Auditor;
- authorized Procurement Officer for own tender where policy allows;
- Approving Authority where policy allows.

Denied by default:

- Procurement Assistant;
- Opening Committee;
- Evaluation Committee;
- STD Administrator unless explicitly assigned audit scope;
- System Administrator unless audit role assigned.

### 15.3 Export Audit

Every evidence export must be audited with:

- who exported;
- what tender/object;
- export format;
- timestamp;
- evidence package hash;
- reason/note if required.
