## 1. Purpose

This document defines the four core operational models generated by the STD Engine from a tender-specific STD Instance:

1. Document Submission Model (DSM)
2. Document Opening Model (DOM)
3. Document Evaluation Model (DEM)
4. Document Contract Model (DCM)

These models are the formal interface between the legally structured tender document and the downstream operational modules.

They ensure that:

- submission requirements come from the STD;
- opening register fields come from the STD;
- evaluation rules come from the STD;
- contract carry-forward comes from the STD and evaluation/award outcome;
- downstream modules cannot invent, override, or silently modify legally binding rules.

---

## 2. Core Principle

The STD Instance is the source of truth.

The generated models are not advisory outputs. They are binding system contracts.

```text
STD Instance
   ↓
Bundle / DSM / DOM / DEM / DCM
   ↓
Submission / Opening / Evaluation / Contract
```

Downstream modules consume generated model versions by reference.

They must not maintain independent rule definitions.

---

## 3. Generated Model Definitions

### 3.1 Bundle

The Bundle is the supplier-facing tender document package.

It contains the complete recombined tender document, including fixed template content, tender-specific values, BOQ, specifications, drawings, and contract forms.

The Bundle is primarily consumed by:

- Tender Publication;
- Supplier Portal;
- Audit/Evidence export.

### 3.2 DSM — Document Submission Model

The DSM defines what bidders must submit and how the submission must be structured.

It is consumed by the Supplier Submission module.

### 3.3 DOM — Document Opening Model

The DOM defines what is recorded and disclosed during bid opening.

It is consumed by the Bid Opening module.

### 3.4 DEM — Document Evaluation Model

The DEM defines the complete evaluation model, including responsiveness, eligibility, qualification, technical checks, BOQ arithmetic correction, financial evaluation, and ranking.

It is consumed by the Evaluation module.

### 3.5 DCM — Document Contract Model

The DCM defines what carries forward into contract preparation and execution.

It is consumed by Contract Management.

## 4. Non-Negotiable Rules

| Rule ID | Rule |
|---|---|
| DERIVED-RULE-001 | DSM, DOM, DEM, and DCM shall be generated only from an STD Instance. |
| DERIVED-RULE-002 | Generated models shall be versioned and immutable once published or snapshotted. |
| DERIVED-RULE-003 | Downstream modules shall consume generated model references. |
| DERIVED-RULE-004 | Submission module shall not create manual submission requirements. |
| DERIVED-RULE-005 | Opening module shall not add evaluation logic or arithmetic correction. |
| DERIVED-RULE-006 | Evaluation module shall not create manual criteria. |
| DERIVED-RULE-007 | Contract module shall not override STD-derived contract terms. |
| DERIVED-RULE-008 | BOQ arithmetic correction shall occur only in DEM. |
| DERIVED-RULE-009 | DOM shall record submitted information only, not evaluation outcomes. |
| DERIVED-RULE-010 | DCM contract price source for Works BOQ shall be corrected evaluated BOQ total from DEM/Award. |
| DERIVED-RULE-011 | All generated elements must trace to STD source section, clause, parameter, form, BOQ item, structured component, or evaluation result. |
| DERIVED-RULE-012 | Stale generated models shall block publication/readiness and downstream use where legally relevant. |

## 7. DSM — Document Submission Model

### 7.1 Purpose

DSM defines the bidder submission structure and required submission artifacts.

It answers:

1. What must the bidder submit?
2. Which forms are mandatory?
3. Which documents are required?
4. What BOQ pricing fields are bidder-editable?
5. What acknowledgements are required?
6. What validation rules apply at submission time?

### 7.2 DSM Sources

| Source | Contribution |
|---|---|
| Section I — ITT | General submission rules. |
| Section II — TDS | Tender-specific submission values and deadlines. |
| Section IV — Tendering Forms | Required forms and declarations. |
| Section V — BOQ | Rate-entry structure for Works. |
| Section VI — Specifications | Technical submission requirements. |
| Section VII — Drawings | Drawing acknowledgement/technical compliance where required. |
| Addenda | Addendum acknowledgement requirements. |

### 7.3 DSM Structure

```yaml
dsm:
  output_code: string
  tender_code: string
  instance_code: string
  version_number: integer
  submission_deadline: datetime
  submission_mode: string
  requirements:
    - requirement_code: string
      requirement_type: enum Form/Document/BOQRateEntry/Declaration/TechnicalProposal/Acknowledgement/System
      label: string
      description: text optional
      mandatory: boolean
      condition: json optional
      supplier_action: enum CompleteForm/UploadDocument/EnterRates/Acknowledge/Confirm/Declare
      validation_rule_code: string optional
      source_trace: object
  boq_rate_entry:
    enabled: boolean
    editable_fields:
      - rate
    locked_fields:
      - item_number
      - description
      - unit
      - quantity
    computed_fields:
      - amount
  addendum_acknowledgements:
    - addendum_code: string
      mandatory: boolean
```

### 7.4 DSM Requirement Types

| Type | Meaning |
|---|---|
| Form | Structured STD form to complete. |
| Document | Uploaded supporting document. |
| BOQRateEntry | Supplier rate entry for structured BOQ items. |
| Declaration | Formal bidder declaration. |
| TechnicalProposal | Method statement, work programme, technical proposal, etc. |
| Acknowledgement | Addendum/drawing/specification acknowledgement. |
| System | System-required submission metadata. |

### 7.5 DSM Works-Specific Requirements

For Works BOQ tenders, DSM shall include:

- Form of Tender;
- tender security where required;
- qualification forms;
- key personnel schedule where required;
- equipment schedule where required;
- method statement where required;
- work programme where required;
- BOQ rate-entry requirements;
- addendum acknowledgements where applicable.

### 7.6 DSM Prohibitions

DSM shall not include:

- evaluation scoring;
- responsiveness outcome;
- arithmetic correction;
- ranking logic;
- contract award decision.

### 7.7 DSM Consumption Rules

Submission module shall:

1. render submission checklist from DSM;
2. validate supplier submission against DSM;
3. collect rates according to DSM BOQ rate-entry rules;
4. record DSM output version used for each bid;
5. reject manual submission requirement creation.

## 8. DOM — Document Opening Model

### 8.1 Purpose

DOM defines the bid opening register and opening disclosure structure.

It answers:

1. What is recorded at opening?
2. What is disclosed/read out?
3. What is not evaluated at opening?
4. Which DOM version governs the opening?

### 8.2 DOM Sources

| Source | Contribution |
|---|---|
| Section I — ITT | Opening procedures. |
| Section II — TDS | Opening date/time/place and disclosure details. |
| DSM | Submitted bid metadata where relevant. |
| Addenda | Addendum acknowledgement presence where opening disclosure requires it. |

### 8.3 DOM Structure

```yaml
dom:
  output_code: string
  tender_code: string
  instance_code: string
  version_number: integer
  opening_datetime: datetime
  opening_location: string optional
  register_fields:
    - field_code: string
      label: string
      field_type: enum Text/DateTime/Currency/Boolean/Number/List/System
      mandatory: boolean
      disclosure_status: enum Disclosed/RecordedOnly/Internal
      source_trace: object
  prohibited_actions:
    - arithmetic_correction
    - responsiveness_determination
    - evaluation_ranking
```

### 8.4 Required DOM Fields for Works

At minimum, DOM should support:

- bidder name;
- bid submission timestamp;
- bid withdrawal/modification status;
- submitted total bid price where applicable;
- currency;
- tender security presence;
- addendum acknowledgement presence where configured;
- opening committee attendance;
- opening timestamp;
- remarks limited to opening-record context.

### 8.5 DOM Prohibitions

Opening module shall not:

- perform arithmetic correction;
- mark bids responsive/non-responsive;
- apply qualification checks;
- rank bids;
- modify evaluation criteria;
- modify BOQ quantities or rates.

### 8.6 DOM Consumption Rules

Bid Opening module shall:

1. create opening register from DOM;
2. record only DOM-defined fields;
3. reference DOM output version;
4. preserve immutable opening record after closure;
5. reject evaluation actions.

## 9. DEM — Document Evaluation Model

### 9.1 Purpose

DEM defines the legally disclosed and executable evaluation model.

It answers:

1. What stages are used for evaluation?
2. Which responsiveness checks apply?
3. Which eligibility and qualification criteria apply?
4. How are technical requirements evaluated?
5. How is BOQ arithmetic correction performed?
6. How is financial comparison/ranking performed?

### 9.2 DEM Sources

| Source | Contribution |
|---|---|
| Section I — ITT | Evaluation procedures and correction principles. |
| Section II — TDS | Tender-specific evaluation options/values. |
| Section III — Evaluation and Qualification Criteria | Primary evaluation rules. |
| Section IV — Tendering Forms | Data sources for evaluation. |
| Section V — BOQ | Financial evaluation and arithmetic correction. |
| Section VI — Specifications | Technical compliance requirements. |
| Section VII — Drawings | Technical compliance references. |
| Addenda | Updated criteria/requirements if legally issued. |

### 9.3 DEM Structure

```yaml
dem:
  output_code: string
  tender_code: string
  instance_code: string
  version_number: integer
  evaluation_method: string
  stages:
    - stage_code: string
      stage_name: string
      sequence: integer
      stage_type: enum Responsiveness/Eligibility/Qualification/Technical/Financial/Ranking
      mandatory: boolean
      rules:
        - rule_code: string
          rule_type: enum PresenceCheck/Threshold/PassFail/ArithmeticCorrection/Comparison/Ranking/System
          label: string
          description: text optional
          data_source: string
          operator: string optional
          threshold_value: json optional
          failure_effect: enum Reject/Clarify/Adjust/RecordOnly
          source_trace: object
  boq_arithmetic_correction:
    enabled: boolean
    stage_code: string
    correction_rules: list
  ranking:
    method: enum LowestEvaluatedCost/HighestScore/QualityCostBased/Other
    source_trace: object
```

### 9.4 Required DEM Stages for Works

At minimum, Works DEM should support:

1. Preliminary responsiveness;
2. Eligibility;
3. Qualification;
4. Technical compliance;
5. Financial evaluation;
6. BOQ arithmetic correction;
7. Ranking by lowest evaluated responsive/evaluated cost where applicable.

### 9.5 BOQ Arithmetic Correction Rules

DEM is the only model where BOQ arithmetic correction may occur.

The rules must be generated from STD sources and BOQ structure.

DEM shall define:

- correction of multiplication errors;
- correction of addition errors;
- treatment of discrepancies between rates and amounts where applicable;
- recalculated corrected total;
- bidder acceptance workflow if required by applicable rules;
- corrected evaluated price.

### 9.6 DEM Prohibitions

Evaluation module shall not:

- add manual criteria;
- add hidden rules;
- alter disclosed thresholds;
- alter BOQ quantities;
- change correction rules;
- evaluate using a DEM version not linked to the applicable snapshot.

### 9.7 DEM Consumption Rules

Evaluation module shall:

1. load DEM by output reference;
2. evaluate bids according to DEM stages/rules;
3. record DEM version used;
4. record rule-level outcomes;
5. generate evaluated/corrected price where applicable;
6. reject manual criteria creation.

## 10. DCM — Document Contract Model

### 10.1 Purpose

DCM defines the contract carry-forward model from tender to contract.

It answers:

1. Which contract terms carry forward?
2. Which documents form part of the contract?
3. What is the source of contract price?
4. Which securities, completion periods, and liability periods apply?
5. What must not be changed during contract preparation?

### 10.2 DCM Sources

| Source | Contribution |
|---|---|
| Section VIII — GCC | Base contract conditions. |
| Section IX — SCC | Tender-specific contract conditions. |
| Section X — Contract Forms | Required contract forms. |
| Section V — BOQ | Contract price structure and BOQ reference. |
| Section VI — Specifications | Scope of works. |
| Section VII — Drawings | Contract drawings. |
| DEM/Award Outcome | Corrected evaluated price and awarded bidder. |
| Addenda | Updated contract-bound requirements. |

### 10.3 DCM Structure

```yaml
dcm:
  output_code: string
  tender_code: string
  instance_code: string
  version_number: integer
  contract_documents:
    - document_code: string
      label: string
      source_trace: object
  contract_terms:
    - term_code: string
      label: string
      value: json
      editable_in_contract: boolean
      source_trace: object
  price_source:
    source_type: enum CorrectedEvaluatedBOQTotal/AwardPrice/LumpSum/System
    source_output_code: string optional
    source_evaluation_result_code: string optional
    manual_override_allowed: boolean
  securities:
    performance_security: object optional
    retention: object optional
    advance_payment_security: object optional
  works_scope_references:
    specifications: list
    drawings: list
    boq: object
```

### 10.4 Required DCM Fields for Works

At minimum, Works DCM shall include:

- employer/procuring entity;
- contractor placeholder until award;
- contract title;
- completion period;
- defects liability period;
- performance security;
- retention;
- liquidated damages;
- payment currency;
- insurance requirements;
- specifications reference;
- drawings reference;
- BOQ reference;
- contract price source;
- contract forms.

### 10.5 Works Contract Price Rule

For Works BOQ procurement, DCM shall not set final contract price directly from submitted total at opening.

The contract price source shall be:

```text
corrected evaluated BOQ total from DEM/Award outcome
```

Manual override shall be prohibited unless a controlled, legally approved correction process exists.

### 10.6 DCM Prohibitions

Contract module shall not:

- change GCC/SCC-derived terms silently;
- override completion period without approved process;
- override security requirements without approved process;
- use opening price as final contract price where correction/evaluation applies;
- alter BOQ quantities after award except through contract variation process outside tender formation.

### 10.7 DCM Consumption Rules

Contract Management shall:

1. load DCM by output reference;
2. combine DCM with award result;
3. populate contractor and awarded price from approved award/evaluation outcome;
4. preserve DCM version reference;
5. block inconsistent contract preparation.

## 11. Cross-Model Boundary Rules

### 11.1 DSM vs DEM

DSM defines what is submitted.

DEM defines how it is evaluated.

DSM shall not contain scoring or ranking rules.

DEM may reference DSM-submitted artifacts as data sources.

### 11.2 DOM vs DEM

DOM defines what is recorded at opening.

DEM defines evaluation.

DOM shall not correct prices or rank bidders.

### 11.3 DEM vs DCM

DEM produces evaluation/award results, including corrected evaluated price.

DCM uses those results as contract carry-forward inputs.

DCM shall not recalculate evaluation.

### 11.4 Bundle vs Operational Models

Bundle is supplier-facing document output.

DSM/DOM/DEM/DCM are machine-readable operational models.

All must trace back to the same STD Instance and snapshot.

## 12. Versioning and Snapshot Rules

### 12.1 Output Versioning

Each generated model version shall be immutable after publication/snapshot.

New versions are created when:

- source input changes before publication;
- addendum modifies published content;
- regeneration is required due to correction in structured instance data.

### 12.2 Snapshot Binding

At publication, the system shall bind:

- Bundle version;
- DSM version;
- DOM version;
- DEM version;
- DCM version;

to the Publication Snapshot.

Opening, Evaluation, and Contract may create or reference later lifecycle snapshots where applicable.

### 12.3 Stale Model Rule

If any current model is stale, readiness must block publication.

If a downstream module attempts to consume a stale model, the system shall deny or require regeneration depending lifecycle state.

## 13. Addendum Impact Rules

Addenda may affect one or more generated models.

| Addendum Change | Affected Models |
|---|---|
| Submission deadline change | Bundle, DSM, DOM |
| Opening date/time change | Bundle, DOM |
| Tender security change | Bundle, DSM, DEM |
| Qualification threshold change | Bundle, DSM, DEM |
| Specification change | Bundle, DSM, DEM, DCM |
| Drawing change | Bundle, DEM, DCM, DSM if acknowledgement required |
| BOQ quantity/item change | Bundle, DSM, DEM, DCM |
| SCC value change | Bundle, DCM |
| Contract form change | Bundle, DCM |

Addendum regeneration must:

1. identify affected models;
2. generate new versions;
3. supersede affected prior versions;
4. create Addendum Snapshot;
5. preserve prior versions for audit.

```text
GET /api/std-engine/instances/{instance_code}/outputs/{output_type}/current
```

Supported output types:

```text
bundle
```

### 14.2 Get Model Version

```text
GET /api/std-engine/outputs/{output_code}
```

### 14.3 Validate Model Consumption

```text
POST /api/std-engine/outputs/{output_code}/validate-consumption
```

Request:

```yaml
consumer_module: Submission/Opening/Evaluation/Contract
consumer_context_code: string
```

Response:

```yaml
allowed: boolean
output_status: Current/Published/Stale/Superseded
snapshot_code: string optional
blockers:
  - code: string
    message: string
```

### 14.4 Denial Codes

| Code | Meaning |
|---|---|
| OUTPUT_NOT_FOUND | Output does not exist. |
| OUTPUT_TYPE_INVALID_FOR_CONSUMER | Consumer requested wrong model type. |
| OUTPUT_STALE | Output is stale. |
| OUTPUT_SUPERSEDED | Output has been superseded. |
| OUTPUT_NOT_LINKED_TO_SNAPSHOT | Required snapshot link missing. |
| MANUAL_RULE_INJECTION_DENIED | Consumer attempted manual rule creation. |
| CONTRACT_BINDING_VIOLATION | Contract attempted to diverge from DCM. |

## 15. Audit Requirements

The system shall audit:

1. model generation requested;
2. model generation completed;
3. model generation failed;
4. model marked stale;
5. model superseded;
6. downstream model consumed;
7. downstream model consumption denied;
8. manual submission requirement attempt denied;
9. manual opening field/evaluation action denied;
10. manual evaluation criteria denied;
11. contract divergence denied;
12. addendum regeneration completed.

Audit records shall include:

- output code;
- output type;
- version number;
- instance code;
- tender code;
- actor/system job;
- timestamp;
- source snapshot if applicable;
- consumer module if applicable;
- denial code if applicable.
