## 1. Purpose

This document defines the formal model for converting an **Active STD Template Version** into a **Tender-bound STD Instance** and then into immutable **snapshot outputs** used by the tender lifecycle.

It deliberately avoids designing the future Tender-side UI. The purpose is to define the backend, legal, state, and integration rules that the future Tender module must follow.

This artifact answers:

1. What is an STD Instance?
2. Who may create it?
3. Can it exist without a Tender?
4. What data does it contain?
5. What is a snapshot?
6. When does immutability apply?
7. How do generated outputs relate to the instance?
8. What does Tender Management consume?
9. How do addenda and supersession affect the instance and snapshots?

## 2. Core Definitions

### 2.1 STD Template Version

An STD Template Version is a reusable, legally reviewed, structured representation of an official Standard Tender Document.

Example:

```text
STDTV-WORKS-BUILDING-REV-APR-2022
```

It contains:

- locked legal sections;
- parameter definitions;
- form definitions;
- Works / BOQ rules where applicable;
- source mappings;
- readiness rules;
- generation rules for Bundle, DSM, DOM, DEM, and DCM.

It does not contain tender-specific values.

### 2.2 Tender

A Tender is the operational lifecycle object created from a procurement package or planning release.

It controls:

- tender preparation;
- approval;
- publication;
- submission;
- opening;
- evaluation;
- award;
- contract initiation.

The Tender does not own submission rules, evaluation criteria, opening structure, or contract carry-forward logic. It consumes them from STD-derived outputs.

### 2.3 STD Instance

An STD Instance is the tender-specific realization of an active STD Template Version.

It is created exclusively from a Tender context.

It contains:

- selected template version reference;
- selected applicability profile;
- tender-specific parameter values;
- section-bound attachments;
- Works Requirements data;
- BOQ data where applicable;
- addendum history;
- generated output references;
- readiness state;
- audit lineage.

### 2.4 Snapshot

A snapshot is an immutable captured version of an STD Instance or generated STD output at a legally meaningful point in time.

Snapshots exist to prove what was valid, approved, published, opened, evaluated, or carried forward at a specific lifecycle point.

### 2.5 Generated Outputs

Generated outputs are system-produced artifacts derived from the STD Instance:

| Output | Meaning | Consumed By |
|---|---|---|
| Bundle | Published tender document package | Tender Publication / Supplier Portal |
| DSM | Document Submission Model | Supplier Submission |
| DOM | Document Opening Model | Bid Opening |
| DEM | Document Evaluation Model | Evaluation |
| DCM | Document Contract Model | Contract Management |

## 3. Non-Negotiable Architectural Rules

### 3.1 Creation Rule

An STD Instance shall be created only through a Tender context.

Prohibited:

```text
STD Engine → Create STD Instance directly
```

Allowed:

```text
Tender → Create / Bind STD Instance
```

### 3.2 One-to-One Tender Binding

Each tender shall have exactly one current STD Instance for its active tender cycle.

Each STD Instance shall belong to exactly one Tender.

An STD Instance shall not be reused across tenders.

An STD Instance shall not be reassigned to another Tender.

### 3.3 Template-to-Instance Rule

An STD Instance shall be created from an Active STD Template Version only.

Draft, inactive, superseded, retired, or archived template versions shall not be used for new tender STD instances unless an explicit controlled exception exists.

### 3.4 Instance Mutability Rule

An STD Instance is mutable only during tender preparation and before publication lock.

After publication, direct mutation is prohibited.

Post-publication changes require:

- addendum; or
- tender supersession / cancellation and reissue, where applicable.

### 3.5 Snapshot Rule

Published tender artifacts shall be immutable snapshots.

No published Bundle, DSM, DOM, DEM, or DCM may be overwritten.

Changes create new versions linked by supersession/addendum lineage.

### 3.6 Downstream Consumption Rule

Downstream modules shall consume STD outputs by reference.

They shall not copy and edit STD-derived rules.

Prohibited:

- manual submission checklist in Tender module;
- manual opening fields in Bid Opening;
- manual evaluation criteria in Evaluation;
- manual contract term override in Contract Management.

| Addendum | STD Instance | many to 1 | Addendum modifies published instance through controlled flow. |
| Addendum | Generated Output Version | 1 to many | Affected outputs regenerated as new versions. |

## 6. STD Instance Lifecycle

### 6.1 States

| State | Meaning | Editable? |
|---|---|---|
| Draft | Instance created from Tender but not yet configured. | Yes |
| In Configuration | Tender-specific values/inputs being completed. | Yes |
| Validation Blocked | Readiness found blocking issues. | Yes, to resolve blockers |
| Ready for Publication | All required values, inputs, outputs, and checks are complete. | Limited; changes invalidate readiness |
| Locked for Approval | Submitted for tender approval/publication review. | No ordinary edits |
| Published Locked | Tender artifacts published; instance immutable. | No |
| Addendum Pending | Controlled post-publication change under analysis. | No direct edits |
| Addendum Regenerated | Affected outputs regenerated and awaiting issue/publishing. | No direct edits |
| Superseded | Replaced by a new tender instance or tender reissue. | No |
| Cancelled | Tender cancelled before or after publication. | No, except closure metadata |

### 6.2 Normal State Flow

```text
Draft
  → In Configuration
  → Validation Blocked
  → In Configuration
  → Ready for Publication
  → Locked for Approval
  → Published Locked
```

### 6.3 Addendum Flow

```text
Published Locked
  → Addendum Pending
  → Addendum Regenerated
  → Published Locked
```

The state returns to Published Locked after the addendum outputs are issued and the new output versions become current for the post-addendum tender state.

### 6.4 Supersession Flow

```text
Published Locked / Cancelled / Reissue Required
  → Superseded
  → New Tender / New STD Instance created through controlled tender reissue
```

## 8. STD Instance Parameter Values

### 8.1 Purpose

Parameter values are tender-specific values filled into parameter definitions from the template.

Examples:

- submission deadline;
- opening date/time;
- employer name;
- tender security amount;
- bid validity period;
- completion period;
- performance security percentage;
- defects liability period.

### 8.2 Model

```yaml
std_instance_parameter_value:
  value_code: string unique required
  instance_code: string required
  parameter_code: string required
  value: json/text required
  value_status: enum Missing/Valid/Invalid/Not Applicable
  source: enum User/Default/System/Imported/Addendum
  drives_bundle: boolean
  drives_dsm: boolean
  drives_dom: boolean
  drives_dem: boolean
  drives_dcm: boolean
  is_locked: boolean default false
  changed_by: user optional
  changed_at: datetime optional
  source_addendum_code: string optional
```

### 8.3 Rules

1. Values may be edited only before publication lock.
2. Missing required values block readiness.
3. Changing a value invalidates affected generated outputs.
4. Post-publication value change requires addendum impact analysis.
5. Parameter values shall retain source trace to parameter definitions.

## 9. Section-Bound Attachments

### 9.1 Purpose

Attachments are permitted only as section-bound supporting content.

Examples:

- specifications attached to Section VI;
- drawings attached to Section VII;
- site reports attached to Works Requirements;
- addendum attachments linked to changed sections.

### 9.2 Model

```yaml
std_instance_section_attachment:
  attachment_code: string unique required
  instance_code: string required
  section_code: string required
  component_code: string optional
  file_reference: string required
  file_name: string required
  file_hash: string optional
  classification: enum Supplier Facing/Internal Only/Contract Facing
  version_number: integer required
  status: enum Draft/Current/Published/Superseded/Archived
  source_addendum_code: string optional
  uploaded_by: user required
  uploaded_at: datetime required
```

### 9.3 Rules

1. Unbound attachments shall not satisfy STD requirements.
2. Attachments shall not redefine evaluation criteria, contract terms, or submission rules.
3. Supplier-facing attachments must be included or referenced in the Bundle.
4. Published attachments are immutable.
5. Replacement requires addendum or supersession.

## 10. Works Requirements Data

### 10.1 Purpose

Works Requirements represent tender-specific technical scope and supporting data.

They are structured components, not generic attachments.

Examples:

- specifications;
- site information;
- drawings register;
- HSE requirements;
- environmental/social requirements;
- work programme requirement;
- method statement requirement.

### 10.2 Model

```yaml
std_instance_works_requirement:
  requirement_code: string unique required
  instance_code: string required
  component_code: string required
  requirement_status: enum Missing/In Progress/Complete/Not Applicable
  structured_text: long text optional
  structured_data: json optional
  attachment_required: boolean
  attachment_status: enum Not Required/Missing/Complete
  drives_bundle: boolean
  drives_dsm: boolean
  drives_dem: boolean
  drives_dcm: boolean
  source_addendum_code: string optional
  updated_by: user optional
  updated_at: datetime optional
```

### 10.3 Rules

1. Required Works components must be complete before readiness passes.
2. Works components may drive submission, evaluation, and contract carry-forward.
3. Specifications/drawings must be section-bound.
4. Post-publication changes require addendum impact analysis.

## 11. BOQ Instance Model

### 11.1 Purpose

For Works tenders using BOQ, the STD Instance contains a tender-specific BOQ.

The BOQ contains quantities fixed by the Procuring Entity.

Suppliers later enter rates only.

### 11.2 BOQ Header

```yaml
  source_addendum_code: string optional
```

### 11.3 BOQ Bill

```yaml
std_instance_boq_bill:
  bill_instance_code: string unique required
  boq_instance_code: string required
  bill_number: string required
  bill_title: string required
  bill_type: string required
  order_index: integer required
  status: enum Draft/Current/Published/Superseded
```

### 11.4 BOQ Item

```yaml
std_instance_boq_item:
  item_instance_code: string unique required
  bill_instance_code: string required
  item_number: string required
  description: text required
  unit: string required
  quantity: decimal required
  item_type: enum Normal/Preliminary/Daywork/Provisional Sum/Summary
  supplier_input_mode: enum Rate Only/None/Fixed Amount
  rate_required_from_supplier: boolean
  fixed_amount: decimal optional
  provisional_sum_amount: decimal optional
  status: enum Draft/Current/Published/Superseded
  source_addendum_code: string optional
```

### 11.5 BOQ Rules

1. BOQ quantities are fixed by the Procuring Entity.
2. Suppliers shall not edit item number, description, unit, or quantity.
3. Supplier rates are collected during bid submission according to DSM.
4. Amounts are system-computed.
5. Arithmetic correction happens only during Evaluation according to DEM.
6. BOQ data carries forward to DCM through evaluation/award result.
7. BOQ changes after publication require addendum and regeneration of affected outputs.

## 12. Generated Output Model

### 12.1 Purpose

Generated outputs are versioned artifacts derived from an STD Instance.

They are the formal interface between the STD Engine and downstream modules.

### 12.2 Model

```yaml
std_generated_output:
  output_code: string unique required
  instance_code: string required
  output_type: enum Bundle/DSM/DOM/DEM/DCM
  version_number: integer required
  output_status: enum Draft/Current/Published/Superseded/Archived/Stale/Failed
  source_template_version_code: string required
  source_profile_code: string required
  source_instance_snapshot_code: string optional
  source_addendum_code: string optional
  content_json: json optional
  rendered_file_reference: string optional
  input_hash: string optional
  output_hash: string optional
  generated_by_job_code: string required
  generated_at: datetime required
  published_at: datetime optional
```

### 12.3 Versioning Rules

1. Outputs are never overwritten after publication.
2. New generation creates a new version when the prior output is published or locked.
3. Stale outputs block readiness.
4. Output status must clearly distinguish Draft, Current, Published, Superseded, and Stale.
5. Tender modules consume current/published output references, not mutable copies.

## 13. Snapshot Model

### 13.1 Snapshot Types

| Snapshot Type | Purpose |
|---|---|
| Configuration Snapshot | Captures instance inputs before approval/publication. |
| Publication Snapshot | Captures published tender artifacts. |
| Addendum Snapshot | Captures post-publication changed state. |
| Opening Snapshot | Captures DOM used at opening. |
| Evaluation Snapshot | Captures DEM used for evaluation. |
| Contract Snapshot | Captures DCM used for contract creation. |

### 13.2 Model

```yaml
std_instance_snapshot:
  snapshot_code: string unique required
  instance_code: string required
  tender_code: string required
  snapshot_type: enum Configuration/Publication/Addendum/Opening/Evaluation/Contract
  snapshot_reason: string required
  snapshot_status: enum Draft/Final/Superseded/Archived
  source_template_version_code: string required
  source_output_codes:
    bundle: string optional
    dsm: string optional
    dom: string optional
    dem: string optional
    dcm: string optional
  parameter_values_hash: string optional
  works_requirements_hash: string optional
  boq_hash: string optional
  attachments_hash: string optional
  complete_instance_hash: string optional
  created_by: user required
  created_at: datetime required
  source_addendum_code: string optional
```

### 13.3 Snapshot Rules

1. Snapshots are append-only.
2. Final snapshots are immutable.
3. Publication requires a Publication Snapshot.
4. Opening shall reference the DOM version captured in or linked to the applicable snapshot.
5. Evaluation shall reference the DEM version captured in or linked to the applicable snapshot.
6. Contract shall reference the DCM version captured in or linked to the applicable snapshot.
7. Addenda create new snapshots and supersede affected prior current output references without deleting history.

## 15. Generation and Snapshot Sequence

### 15.1 Pre-Publication Sequence

```text
Tender exists
  ↓
Create STD Instance from Active Template
  ↓
Fill parameter values and structured inputs
  ↓
Complete Works Requirements and BOQ
  ↓
Generate Bundle / DSM / DOM / DEM / DCM
  ↓
Run readiness
  ↓
Create Configuration Snapshot
  ↓
Lock for approval
  ↓
Approve tender publication
  ↓
Create Publication Snapshot
  ↓
Publish Bundle and output references
```

### 15.2 Post-Publication Addendum Sequence

```text
Published Locked Instance
  ↓
Proposed change submitted as Addendum
  ↓
Impact analysis identifies affected inputs and outputs
  ↓
Regenerate affected outputs as new versions
  ↓
Create Addendum Snapshot
  ↓
Issue Addendum
  ↓
Mark new affected outputs current/published
  ↓
Retain old outputs as superseded
```

## 16. Tender Binding Contract

### 16.1 Tender Required STD Fields

The future Tender module shall include references to STD objects.

```yaml
tender_std_binding:
  tender_code: string required unique
  procurement_package_code: string optional
  std_instance_code: string required
  template_version_code: string required
  applicability_profile_code: string required
  publication_snapshot_code: string optional
  current_bundle_output_code: string optional
  current_dsm_output_code: string optional
  current_dom_output_code: string optional
  current_dem_output_code: string optional
  current_dcm_output_code: string optional
  std_readiness_status: string required
  std_outputs_current: boolean required
  binding_status: enum Draft/Ready/Locked/Published/Superseded/Cancelled
```

### 16.2 Binding Rules

1. Tender cannot publish unless `std_readiness_status = Ready`.
2. Tender cannot publish unless Bundle, DSM, DOM, DEM, and DCM exist and are current.
3. Tender shall store output references, not editable copies.
4. Tender shall not create manual submission, opening, evaluation, or contract rules.
5. Tender publication locks the STD Instance and creates Publication Snapshot.

The Procurement Plan / Package does not create STD values directly, but it constrains eligible STD template selection.

|---|---|

```text

```

## 18. Addendum and Supersession Relationship

### 18.1 Addendum

An addendum modifies a published tender without creating a new tender instance.

It may change:

- parameter values;
- submission/opening deadlines;
- Works Requirements;
- BOQ quantities/items;
- specifications/drawings;
- other controlled tender document content.

Addendum effects:

- impact analysis required;
- affected outputs regenerated;
- Addendum Snapshot created;
- previous outputs superseded but retained;
- supplier acknowledgement may be required.

### 18.2 Supersession

Supersession creates a new tender issue or new STD instance when changes are too material for addendum or where legal/procurement policy requires reissue.

Supersession effects:

- old instance marked Superseded;
- new STD Instance created through Tender context;
- new generated outputs;
- new publication snapshot;
- lineage retained.

### 18.3 Distinction

| Change Type | Use Addendum | Use Supersession |
|---|---|---|
| Clarification | Yes | No |
| Deadline extension | Yes | No |
| BOQ quantity correction | Usually yes | Possibly if material |
| Change of procurement method | No | Yes |
| Change of STD template version after publication | Usually no | Yes unless formally allowed |
| Material scope change | Possibly no | Yes |

## 19. Derived Model Consumption Contracts

### 19.1 DSM Consumption

Supplier Submission shall consume DSM.

Rules:

1. DSM defines required forms/documents/BOQ rate entry.
2. Submission module shall not create manual requirement checklists.
3. DSM version used for each bid shall be recorded.
4. Addendum changes to DSM require supplier acknowledgement where configured.

### 19.2 DOM Consumption

Bid Opening shall consume DOM.

Rules:

1. DOM defines opening register fields.
2. Opening module shall not add manual fields.
3. DOM shall not contain arithmetic correction or evaluation outcome.
4. Opening record shall reference DOM version.

### 19.3 DEM Consumption

Evaluation shall consume DEM.

Rules:

1. DEM defines all evaluation stages and rules.
2. Evaluation module shall not add manual criteria.
3. DEM version used for evaluation shall be recorded.
4. Arithmetic correction for BOQ occurs in DEM only.

### 19.4 DCM Consumption

Contract Management shall consume DCM.

Rules:

1. DCM defines contract carry-forward fields.
2. Contract terms must not diverge from DCM and evaluation/award results.
3. Works contract price source is corrected evaluated BOQ total.
4. Contract record shall reference DCM version.

## 20. Readiness Rules for STD Instance

An STD Instance is Ready only if all conditions are met.

| Rule | Requirement |
|---|---|
| Active template | Template version is active. |
| Compatible profile | Profile matches tender context. |
| Required parameters | All required parameter values valid. |
| Conditional parameters | Dependencies satisfied. |
| Works Requirements | Required components complete. |
| Attachments | Required section-bound attachments present. |
| BOQ | Required BOQ complete and valid. |
| Bundle | Generated and current. |
| DSM | Generated and current. |
| DOM | Generated and current. |
| DEM | Generated and current. |
| DCM | Generated and current. |
| No stale outputs | No output stale due to input change. |
| No unresolved blockers | Critical findings resolved. |
| Audit lineage | Creation, changes, generation, and validation auditable. |

### 24.2 Instance
