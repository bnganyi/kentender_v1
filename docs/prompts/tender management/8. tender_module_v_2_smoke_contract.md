## 1. Purpose of the Smoke Contract

This Smoke Contract defines the minimum enforceable behavior that Tender Management v2 must satisfy before it can be accepted as a legally defensible, STD-native tender orchestration module.

This artifact is not a general QA plan. It is a system-invariants contract.

It must prove that:

1. Tender Management v2 cannot operate without STD Engine binding;
2. Tender Management v2 cannot redefine STD-owned rules;
3. publication cannot occur without complete and current Bundle / DSM / DOM / DEM / DCM outputs;
4. publication creates or references an immutable publication snapshot binding the exact output versions;
5. supplier submission cannot bypass the STD-derived DSM;
6. bid confidentiality is preserved;
7. deadline enforcement uses server time;
8. opening readiness uses the STD-derived DOM;
9. evaluation handoff uses the STD-derived DEM;
10. contract handoff uses the STD-derived DCM;
11. Works BOQ rules are enforced;
12. addenda regenerate affected outputs and supersede publication snapshots where required;
13. audit can reconstruct the complete lifecycle;
14. legacy v1 document-as-source paths are blocked.

The Smoke Contract must be executable through automated tests, integration tests, UI smoke tests, API/service tests, and manual audit inspection using the seed dataset.

## 2. Smoke Contract Scope

### 2.1 In Scope

| Area | Included |
|---|---|
| Tender creation | Package-to-tender creation, duplicate prevention, and STD binding. |
| STD readiness | Readiness blockers, derived model presence, publication gating, and output staleness. |
| Publication | Review, approval, publish, immutable publication record, exact output version binding through publication snapshot. |
| Supplier access | Public/login/restricted access, supplier eligibility, Bundle access, supplier isolation. |
| Clarifications | Clarification submission, response, and addendum escalation. |
| Addenda | Impact analysis, regenerated outputs, deadline changes, supplier acknowledgement, revised publication snapshot. |
| Bid submission | DSM validation, Works BOQ pricing, sealing, receipts, replacement/withdrawal where allowed. |
| Late submission | Server-time rejection and audit. |
| Bid confidentiality | Sealed bid access denial before lawful opening. |
| Closing | Deadline closure and opening readiness prerequisites. |
| Opening readiness | DOM-derived opening model and no arithmetic correction. |
| Evaluation handoff | DEM-derived evaluation model and no manual criteria injection. |
| Contract handoff | DCM-derived carry-forward and corrected evaluated BOQ total. |
| Audit | Lifecycle reconstruction and negative-path evidence. |
| Legacy lockout | v1 document-as-source and manual configuration denial. |
| UI smoke | Workbench, readiness, addendum, supplier submission, BOQ, late submission, handoff, evidence selectors. |
| API / service smoke | Guarded transition service behavior and structured denial responses. |

### 2.2 Out of Scope

| Area | Reason |
|---|---|
| Full evaluation execution UI | Owned by Evaluation module; only handoff and expected outcomes are tested here. |
| Contract drafting UI | Owned by Contract Management; only handoff source integrity is tested here. |
| STD template authoring | Owned by STD Engine; Tender consumes outputs only. |
| Supplier registration workflow | Owned by Supplier Management; Tender consumes eligibility. |
| Procurement planning workflow | Owned by Procurement Planning; Tender consumes released package. |
| Complaints adjudication | Separate module. |

## 4. Smoke Contract Severity Levels

| Severity | Meaning | Release Impact |
|---|---|---|
| Critical | Legal/source-of-truth/security invariant failure. | Blocks release. |
| High | Major governance, audit, or lifecycle failure. | Blocks release unless explicitly waived by governance for non-production only. |
| Medium | Operational issue with workaround but must be fixed before production. | Blocks production release. |
| Low | Usability or reporting issue not affecting legal correctness. | May proceed with documented remediation. |

All Critical and High tests in this contract must pass before implementation can be accepted.

## 6. Smoke Test Naming and Result Format

### 6.1 Naming Convention

All tests must use the following naming pattern:

```text
TM2-SMOKE-{AREA}-{###}-{SHORT_DESCRIPTION}
```

Examples:

```text
TM2-SMOKE-PUB-001-BLOCK_PUBLICATION_WITHOUT_STD_BINDING
TM2-SMOKE-WORKS-004-BLOCK_SUPPLIER_QUANTITY_EDIT
```

### 6.2 Test Result Format

Every smoke test result must record:

```json
{
  "test_code": "TM2-SMOKE-AREA-001",
  "fixture": "TND-MOH-2026-001",
  "actor": "USER_OR_SYSTEM",
  "preconditions": [],
  "action": "ACTION_UNDER_TEST",
  "expected_result": "PASS_OR_DENIAL",
  "expected_denial_code": "OPTIONAL",
  "expected_audit_event": "OPTIONAL",
  "severity": "Critical|High|Medium|Low"
}
```
