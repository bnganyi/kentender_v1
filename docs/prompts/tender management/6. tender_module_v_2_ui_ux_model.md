## 1. Purpose

This UI/UX Model defines the user-facing behavior, screen structure, navigation rules, interaction patterns, validation surfaces, and implementation-facing UI requirements for **Tender Management v2**.

The purpose of this artifact is to prevent two categories of failure:

1. **Legal / architectural failure** — the UI accidentally reintroduces Tender v1 behavior where uploaded documents, manual submission requirements, manual opening fields, or manual evaluation criteria become the source of truth.
2. **Usability failure** — the module becomes too complex for operational users, causing missed blockers, invalid publication attempts, confusing supplier flows, or hidden legal actions.

The UI must make the STD-native model understandable and operational without exposing ordinary users to technical implementation objects.

This document is intentionally detailed because it will be used by Cursor and developers as an implementation guide.

## 2. UI Design Principles

### 2.1 Tender Management is a workbench, not a document list

The primary internal interface must support work, review, legal transitions, and evidence. It must not be a raw list of Tender records.

Correct model:

```text
Workbench → Queue → Tender List → Tender Detail → STD Readiness → Valid Action
```

Incorrect model:

```text
Doctype List → Open Form → Upload Documents → Publish
```

### 2.2 STD status must be visible everywhere it matters

Users must always understand whether a tender is:

1. not bound to STD;
2. bound but incomplete;
3. ready for publication review;
4. invalidated by change;
5. published and locked;
6. affected by addendum.

### 2.3 Legal actions must be visually distinct

The following actions must never look like ordinary save/edit buttons:

1. Submit for Publication Review;
2. Approve Publication;
3. Publish Tender;
4. Issue Addendum;
5. Submit Bid;
6. Close Tender;
7. Prepare Opening Readiness;
8. Complete Evaluation Handoff;
9. Create Contract Handoff;
10. Cancel Tender;
11. Supersede Tender.

They require backend action availability, confirmation, summary review, reason where required, and audit messaging.

### 2.4 The UI must be state-aware and role-aware

Buttons must appear only when the current user, tender state, object state, and context allow the action.

If an action is blocked, the UI must explain why in plain business language and expose the blocker code/details for support/audit users.

### 2.5 Backend action availability is the source of truth for actions

The frontend must not determine legal permissions independently. It must render actions using backend action availability responses.

Each significant action must be represented as:

```text
Action code + object type + object code + context → backend action availability response
```

The UI may hide irrelevant actions for usability, but direct API calls must still be denied server-side when unauthorized.

### 2.6 Supplier-facing and internal-facing experiences must be strictly separated

Supplier UI must never expose:

1. internal estimates unless formally published;
2. internal review comments;
3. audit logs;
4. other suppliers’ draft or submitted bids;
5. hidden evaluation content;
6. sealed bid contents;
7. internal readiness blockers not intended for supplier display.

### 2.7 Attachments are secondary and section-bound

The UI may allow supporting attachments, but it must visually and functionally subordinate them to structured STD sections/components.

The UI must not present “Upload Tender Document” as the way to define a tender.

### 2.8 Workbench density must be controlled

Tender Management is complex. The UI must show enough information to support action without overwhelming users.

Use progressive disclosure:

1. queue/list level shows status and blockers;
2. detail panel shows lifecycle and readiness summary;
3. dedicated tabs show full STD, addendum, submission, opening, evaluation, contract, and audit information.

### 2.9 Every displayed business object must use business codes

No user-facing screen should rely on raw database IDs. Display business code plus title/name.

## 3. Navigation Architecture

### 3.1 Procurement App Sidebar Rule

Tender Management v2 must fit inside the locked Procurement information architecture.

Procurement must have one primary sidebar. Tender Management is one workflow entry point.

Recommended long-term Procurement sidebar:

```text
Procurement
├── Procurement Home
├── Demand Intake & Approval
├── Procurement Planning
├── Supplier Management
├── Tendering & Solicitation
├── Submissions & Opening
├── Evaluation & Award
├── Contracts & Execution
├── Inspection & Acceptance
├── Complaints & Oversight
└── Settings
```

Depending on naming, Tender Management v2 may be surfaced as **Tendering & Solicitation** or **Tender Management**. The product function is the same.

### 3.2 Tender Management Entry Point

Clicking Tender Management / Tendering & Solicitation must open:

```text
Tender Management Workbench
```

It must not open:

1. a raw Tender DocType list;
2. a nested sidebar of technical objects;
3. a document upload page;
4. a configuration list.

### 3.3 Configuration Placement

Configuration belongs under Settings / Governance, not primary workflow navigation.

Settings may include:

1. tender visibility policies;
2. notification templates;
3. approval routing;
4. publication channels;
5. operational thresholds.

Settings must not contain operational shortcuts that allow bypassing the STD Engine.

### 3.4 STD Engine Navigation Relationship

STD Engine is a separate governance/configuration module. Tender users consume active STD templates and tender STD instances; they do not administer template structure from Tender Management.

Tender Management may link to STD instance detail in read-only or completion mode, depending on user role, but must not expose STD template authoring controls.

### 4.1 Route

Recommended route:

```text
/desk/tender-management-v2
```

Final route may follow framework conventions, but implementation must preserve the workbench behavior.

### 4.2 Page Type

Operational Workbench.

### 4.3 Primary Users

1. Procurement Officer;
2. Senior Procurement Officer;
3. Procurement Manager;
4. Legal Reviewer;
5. Compliance Reviewer;
6. Head of Procurement / Authorized Approver;
7. Tender Secretariat;
8. Auditor / Oversight User.

### 4.4 Workbench Layout

The workbench must follow this structure:

```text
[A] Compact Header
[B] KPI / Risk Strip
[C] Scope Tabs
[D] Queue Bar
[E] Search and Filters
[F] Main Work Area
    ├── Tender List Panel
    └── Tender Detail Panel
```

The main work area must start high enough on the page that users can see active work without excessive scrolling.

## 12. State and Readiness Summary

### 12.1 Summary Cards

The detail panel must show compact status cards:

| Card | Meaning |
|---|---|
| Tender State | Current lifecycle state. |
| STD Binding | Template/version/profile/instance status. |
| Readiness | Ready, Blocked, Warning, Invalidated. |
| Output Status | Bundle/DSM/DOM/DEM/DCM current or stale. |
| Publication Snapshot | Snapshot code/status after publication. |
| Timeline | Deadline, clarification cutoff, opening time. |
| Supplier Access | Public/login/restricted/invited. |
| Current Blockers | Count and severity. |

### 12.2 Readiness Display Rules

1. Readiness status must be visible before any publication action.
2. Blocked readiness must explain exact blocker.
3. Each blocker must identify owner/resolution path.
4. Users must be able to rerun readiness if permitted.
5. Readiness invalidation must be obvious.
6. Output drift must be visible when Bundle/DSM/DOM/DEM/DCM is stale.

### 12.3 Example Blocker Display

```text
Publication blocked: DEM — Document Evaluation Model is missing.
Owner: STD Engine
Required action: Regenerate derived models after completing Section III.
Blocker code: DEM_MISSING_OR_STALE
Severity: Critical
```

## 13. Primary Action Bar

### 13.1 Action Rules

The action bar must show only actions valid for:

1. current user role;
2. tender state;
3. object state;
4. readiness status;
5. separation-of-duties rules;
6. deadline status;
7. backend action availability.

### 13.2 Common Actions by State

| Tender State | Primary Actions |
|---|---|
| Draft | Complete STD Instance, Run Readiness, Submit for Review |
| STD Instance Incomplete | Open STD Completion, Run Readiness |
| Ready for Publication Review | Approve, Return for Correction |
| Returned for Correction | Open Corrections, Run Readiness, Resubmit |
| Approved for Publication | Publish Tender |
| Published | Create Addendum, Manage Clarifications, View Supplier Participation, Cancel Tender, Close if deadline passed |
| Addendum Pending | Continue Addendum, Request Impact Analysis, Submit Approval |
| Suspended Pending Addendum | Issue Addendum, Cancel Addendum |
| Closed | Prepare Opening Readiness, Mark No Valid Submissions if applicable |
| Opening Ready | Send to Opening / View Opening Handoff |
| Opening Completed | Prepare Evaluation Handoff |
| Evaluation Ready | View Handoff |
| Awarded | Create Contract Handoff |
| Cancelled | View Evidence, Mark Retender Required |
| Retender Required | Create Replacement Tender |

### 13.3 Disabled Action Behavior

If an action is shown but disabled, the UI must explain why.

Example:

```text
Publish Tender is disabled because readiness was invalidated after addendum draft creation.
Rerun readiness after resolving addendum impact.
```

```text
[D] Derived Outputs Panel

[F] Publication Snapshot Panel

```

### 16.3 STD Binding Summary Fields

| Field | Required |
|---|---|
| Template code/title | Yes |
| Version code/label | Yes |
| Status of template version | Yes |
| Applicability profile | Conditional |
| Tender STD instance code | Yes |

### 16.4 Readiness Checklist

Checklist must include:

1. package lineage valid;
2. template version active;
3. STD instance exists;
4. parameters complete;
5. sections complete;
6. supporting attachments section-bound;
7. Bundle exists and is current;
8. DSM exists and is current;
9. DOM exists and is current;
10. DEM exists and is current;
11. DCM exists and is current;
12. timeline valid;
13. supplier access valid;
14. no critical blockers;
15. publication snapshot available after publication.

Each item must show:

1. pass/fail/warning;
2. owner;
3. source module;
4. last checked time;
5. action to resolve where allowed.

### 16.5 Derived Outputs Panel

The UI must show derived outputs as read-only references.

| Model | Display |
|---|---|
| DSM — Document Submission Model | Required forms/components; supplier-facing checklist preview. |
| DOM — Document Opening Model | Register fields; opening display rules. |
| DEM — Document Evaluation Model | Responsiveness/qualification/criteria summary. |
| DCM — Document Contract Model | Carry-forward values/sections summary. |

Tender users must not be able to edit these models inside Tender Management.

### 16.6 Generated Bundle Panel

Shows generated supplier-facing document Bundle.

Fields:

1. Bundle code;
2. generation timestamp;
3. generated by;
4. status;
5. hash/checksum where available;
6. included sections;
7. supplier-facing attachments;
8. preview/download action according to permission.

### 16.7 Publication Snapshot Panel

After publication, show:

1. publication snapshot code;
2. published Bundle output code/version;
3. published DSM output code/version;
4. published DOM output code/version;
5. published DEM output code/version;
6. published DCM output code/version;
7. snapshot hash/checksum where available;
8. publication timestamp;
9. evidence link.

### 16.8 Anti-Pattern Guard

There must be no button labeled or behaving as:

```text
Upload Tender Document as Source
```

Allowed attachment behavior must be clearly labelled:

```text
Add Supporting Attachment to Section
```

Shows permitted bid metadata and submission status without violating confidentiality.

### 21.2 Internal View Before Opening

Before formal opening, internal users may see only permitted metadata:

| Field | Visibility |
|---|---|
| Submission count | If policy permits |
| Supplier identity | If policy permits before opening; otherwise masked |
| Submission timestamp | If policy permits |
| Receipt status | Metadata only |
| Addendum acknowledgement status | Yes, where needed for readiness |
| Bid content | Never before opening |
| BOQ rates/details | Never before opening |

### 21.3 Internal View After Opening

After formal opening, visibility follows Bid Opening and Evaluation permissions.

Tender Management may show references, not become the evaluation surface.

Supplier sees only:

1. own draft status;
2. own submitted bid status;
3. own receipt;
4. own replacement/withdrawal status;
5. own late attempt rejection where applicable.

For internal users before opening:

```text
Bid contents are sealed and cannot be accessed before formal opening.
```

## 26. New Tender Flow

### 26.1 Flow Steps

```text
Step 1: Select Procurement Package
Step 2: Confirm Package Eligibility
Step 3: Select STD Template Version
Step 4: Select Applicability Profile
Step 5: Create Tender Draft and STD Instance
Step 6: Open STD Completion Surface
```

### 26.2 Step 1 — Package Selector

Must show only packages eligible for tender creation.

Columns:

1. package code;
2. package title;
3. procuring entity;
4. method;
5. category;
6. estimated value/internal indicator;
7. release status;
8. existing tender status;
9. eligibility result.

### 26.3 Step 2 — Eligibility Confirmation

Show blockers if package cannot be used:

1. not released;
2. missing method/category;
3. active tender already exists;
4. budget/package issue;
5. no eligible STD template.

### 26.4 Step 3 — STD Template Version Selector

Show only active compatible STD versions.

Fields:

1. template code/title;
2. version label;
3. method/category;
4. effective date;
5. status;
6. applicability profiles;
7. legal/policy approval status.

### 26.5 Step 4 — Applicability Profile

For Works, profile selector must include:

1. Building and Associated Civil Engineering Works;
2. Roads, Water and Bridges;
3. Small Works;
4. any configured active Works profile.

Profile selection must show activated requirements, e.g. BOQ, drawings, site information, HSE plan.

### 26.6 Step 5 — Create Draft

On confirmation:

1. create tender draft;
2. create Tender STD Binding;
3. create tender STD instance via STD Engine;
4. map known package/tender values;
5. create audit event;
6. navigate to Tender Detail / STD & Readiness tab.

### 26.7 Prohibited New Tender UI Behavior

The flow must not include:

1. free-form tender creation;
2. upload-only tender creation;
3. manual evaluation criteria creation;
4. manual submission checklist creation;
5. manual opening register creation.

## 33. State-Aware Action Visibility Rules

### 33.1 Internal Buttons

Buttons must use server-provided permission/action availability, not client-only logic.

Each action availability response should include:

1. action code;
2. allowed true/false;
3. denial reason code if false;
4. display label;
5. risk level;
6. confirmation requirement;
7. reason required true/false;
8. required permission where available.

### 33.2 Supplier Buttons

Supplier action availability must similarly use server-side action availability.

Examples:

| Button | Server Conditions |
|---|---|
| Submit Clarification | Tender published; before clarification deadline; supplier has access. |
| Acknowledge Addendum | Addendum issued; acknowledgement required; supplier has access. |
| Start Bid | Tender published; supplier eligible; submission window open. |
| Submit Bid | DSM complete/current; before deadline; all required items present. |
| Replace Bid | Replacement allowed; before deadline; existing submitted bid. |
| Withdraw Bid | Withdrawal allowed; before deadline; existing submitted bid. |

### 34.1 Error Message Requirements

Errors must be:

1. specific;
2. actionable;
3. state-aware;
4. safe for the audience;

```text
Cannot publish.
```

Good:

```text
Cannot publish because DCM — Document Contract Model is missing. Regenerate derived outputs from the STD & Readiness tab.
```

### 34.3 Empty States

| Area | Empty State |
|---|---|
| Draft queue | No draft tenders. Create a tender from an authorized procurement package. |
| STD Incomplete queue | No tenders currently blocked by STD readiness. |
| Clarifications | No clarification requests for this tender. |
| Addenda | No addenda have been created for this tender. |
| Submissions before any bid | No submissions received yet. Bid contents, if received, remain sealed until opening. |
| Opening Ready | No closed tenders are ready for opening handoff. |
