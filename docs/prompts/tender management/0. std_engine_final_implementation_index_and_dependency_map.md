## 2. Final Architecture Summary

The STD Engine is not a document upload system.

It is a structured legal and operational tender document engine.

The final architecture is:

```text
Official PPRA STD Source
        ↓
Structured STD Template Version
        ↓
Official STD Library
        ↓
Planning Package Release
        ↓
Tender
        ↓
Tender-bound STD Instance
        ↓
Tender-specific completion
        ↓
Generated Bundle / DSM / DOM / DEM / DCM
        ↓
Readiness / Approval / Publication Snapshot
        ↓
Submission / Opening / Evaluation / Contract consume outputs by reference
```

The system’s key legal principle is:

```text
Tender behavior must be derived from the structured STD Instance, not manually recreated in downstream modules.
```

## 4. Implementation Order

Cursor must implement the STD Engine in this order.

```text
1. Tender STD Instance and Snapshot backend
2. Planning-to-Tender Release backend
3. WORKS Production Tender-Stage Completion backend
4. Derived Bundle / DSM / DOM / DEM / DCM backend
5. Review / Approval / Publication Readiness backend
6. Security / Permissions / Audit Hardening backend
7. Official STD Library UI hardening
8. Admin and Officer UI Production Hardening
```

### 4.1 Why Official Library UI Is Not First in Build Order

The Official STD Library UI was conceptually clarified early because it corrected the administrative model.

However, for implementation, the backend domain and action availability layers must exist before final UI hardening.

If UI is implemented first, it will either:

- hardcode permissions;
- invent state logic;
- bypass backend action availability;
- expose controls that later become illegal.

Therefore, implementation should bias backend-first.

## 7. Non-Skippable Implementation Controls

The following controls must not be skipped.

### 7.1 No Orphan STD Instances

STD Instances must be created only through Tender context.

Required enforcement:

- service layer;
- database constraint where possible;
- smoke tests.

### 7.2 One Current STD Instance per Tender

A Tender must not have competing current STD Instances.

Replacement requires supersession/reissue logic.

### 7.3 Active Template Requirement

New STD Instances must use Active template/profile versions only.

### 7.4 Generated Outputs Are Versioned

Bundle, DSM, DOM, DEM, and DCM must be versioned and immutable once published or snapshotted.

### 7.5 Downstream Modules Consume Outputs by Reference

Submission consumes DSM.

Opening consumes DOM.

Evaluation consumes DEM.

Contract consumes DCM.

Manual downstream rule injection is prohibited.

### 7.6 Readiness Blocks Publication

Publication must be impossible if readiness is not Ready.

### 7.7 Publication Snapshot Required

Publication requires an immutable snapshot referencing exact output versions.

### 7.8 Published State Immutable

After publication, direct edits are denied.

Addendum or reissue required.

### 7.9 Backend Action Availability Required

UI actions must be based on backend action availability, not frontend role checks alone.

### 7.10 Denied Actions Audited

High-risk denied attempts must create audit events.

## 8. Smoke Test Hierarchy

Smoke tests must be layered.

### 8.1 Domain Smoke Tests

Implemented first.

Covers:

- STD Instance creation;
- state machine;
- parameter values;
- BOQ;
- outputs;
- snapshots.

### 8.2 Integration Smoke Tests

Implemented after domain tests.

Covers:

- Planning-to-Tender release;
- STD binding;
- Works completion;
- output generation;
- readiness;
- publication.

### 8.3 Downstream Contract Smoke Tests

Implemented before downstream modules.

Covers:

- DSM consumption;
- DOM consumption;
- DEM consumption;
- DCM consumption;
- manual rule denial.

### 8.4 Security Smoke Tests

Implemented before UI hardening.

Covers:

- role permission denials;
- state lock denials;
- negative permissions;
- evidence export controls;
- denied-action audit.

### 8.5 UI Smoke Tests

Implemented last.

Covers:

- STD Admin UI;
- Release UI;
- Officer completion UI;
- readiness/approval/publication UI;
- evidence/audit UI;
- action availability rendering.

## 11. Tender Module v2 Starting Point

After STD Engine implementation index is accepted, the next major design stream is:

```text
Tender Module v2 — Pre-PRD
```

Tender Module v2 must assume the following STD Engine contracts exist:

1. Release-to-Tender creates Tender + STD binding.
2. Tender has one current STD Instance.
3. Tender document completion happens through STD Engine interfaces.
4. Publication requires Bundle, DSM, DOM, DEM, DCM.
5. Submission consumes DSM.
6. Opening consumes DOM.
7. Evaluation consumes DEM.
8. Contract initiation consumes DCM.
9. Addenda use STD Engine impact mapping and regenerated output versions.
10. Tender UI uses backend action availability.

## 14. What Cursor Must Not Do

Cursor must not:

1. implement UI before backend authorization exists;
2. create STD Instances outside Tender context;
3. allow direct post-publication edits;
4. allow manual evaluation criteria;
5. allow Opening module to correct prices;
6. allow Contract module to override DCM silently;
7. treat BOQ as an opaque attachment where structure is required;
8. allow supplier rates in tender preparation BOQ UI;
9. overwrite published outputs;
10. mutate final snapshots;
11. skip audit for denied high-risk actions;
12. rename stable codes without explicit migration;
13. replace source-traceable generated models with free-form documents.
