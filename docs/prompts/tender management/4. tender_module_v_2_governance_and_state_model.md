## 1. Purpose

This document defines the governance and state model for **Tender Management v2**.

Tender Management v2 is a legally consequential public procurement module. It must not rely on informal user discipline, UI-only controls, or implicit state changes. Every legally material event must be state-aware, actor-authorized, validated server-side, action-availability checked, and auditable.

This specification defines:

1. governance principles;
2. state dimensions;
3. tender lifecycle states and transitions;
4. STD binding and readiness governance;
5. publication review and publication governance;
6. supplier access and invitation governance;
7. clarification governance;
8. addendum governance;
9. bid draft and submission governance;
10. tender closing governance;
11. opening readiness governance;
12. evaluation handoff governance;
13. contract handoff governance;
14. cancellation, supersession, and retendering governance;
15. audit and immutability rules;
16. Works-specific governance controls;
17. transition blockers and compliance gates;
18. backend action availability and denied-action handling.

This document does not define role permissions in full matrix form. That is handled in the Roles and Permissions Matrix. However, this document identifies the actor classes required for each transition.

## 2. Governance Principles

### 2.1 Public tendering is a controlled legal process

Tender creation, publication, supplier access, addendum issuance, bid submission, closing, opening readiness, and evaluation handoff are not ordinary CRUD actions. They are legally significant process events.

### 2.2 STD Engine is the source of structured tender truth

Tender Management v2 must not define submission requirements, opening register fields, evaluation criteria, or contract carry-forward terms. These are derived from the controlling STD instance through Bundle, DSM, DOM, DEM, and DCM outputs.

### 2.3 Server-side enforcement is mandatory

The UI may hide or disable invalid actions, but all action validity must be enforced by server-side transition services.

### 2.4 Backend action availability is mandatory

Every legally meaningful action must be checked through backend action availability / authorization before execution. UI role checks alone are not sufficient.

### 2.5 Separation of duties is mandatory

No single actor should be able to create, approve, publish, cancel, and hand off a tender without governance controls. Critical actions require distinct actors or explicit authorized override where legally permitted.

### 2.6 Published tender artifacts are immutable

Once published, tender artifacts, STD binding, Bundle references, DSM, DOM, DEM, DCM, deadlines, and publication snapshot references must not be silently changed.

### 2.7 Addendum is the ordinary post-publication amendment mechanism

Any material change after publication must be processed through addendum, impact analysis, approval, issuance, supplier notice, and audit.

### 2.8 Supplier equality of information must be preserved

Information that affects tender interpretation, requirements, submission, evaluation, opening, or contract formation must be disclosed to all affected suppliers according to the tender visibility/access model.

### 2.9 Bid confidentiality is absolute before lawful opening

Internal users must not access sealed bid contents before the authorized opening process. Supplier draft contents must remain supplier-confidential.

### 2.10 Server time is authoritative

All deadline, submission, late attempt, closing, and opening-readiness decisions must use authoritative server time.

### 2.11 Every material transition must be auditable

State transitions must create audit events containing actor, role, timestamp, previous state, new state, reason where required, denial code where applicable, and affected object references, including STD references where relevant.

## 4. Tender Lifecycle State Model

### 4.1 Tender Lifecycle States

| State | Meaning | Editable? |
|---|---|---|
| Draft | Tender created from authorized package and being configured. | Yes, subject to STD binding rules. |
| STD Instance Incomplete | Tender lacks complete STD instance/readiness. | Limited to completing STD instance and tender setup. |
| Ready for Publication Review | Readiness passed and tender submitted for review. | Limited; material changes return to Draft/Incomplete. |
| Returned for Correction | Reviewer returned tender for correction. | Yes, within correction scope. |
| Approved for Publication | Tender authorized for publication. | No ordinary edits. |
| Published | Tender externally visible and active. | No direct core edits; addendum only. |
| Addendum Pending | Addendum being prepared/approved while tender is published. | Addendum path only. |
| Suspended Pending Addendum | Participation/submission suspended due to material addendum impact. | Addendum path only. |
| Closed | Submission deadline passed and tender closed. | No ordinary edits. |
| Closed - No Valid Submissions | Closed without valid submissions. | No ordinary edits; retender/cancel decisions only. |
| Opening Ready | Opening readiness package prepared. | No ordinary edits. |
| Opening Completed | Bid Opening completed formal opening. | No ordinary edits. |
| Evaluation Ready | Evaluation handoff completed. | No ordinary edits. |
| Evaluation In Progress | Evaluation module accepted handoff. | No ordinary edits. |
| Awarded | Award decision completed downstream. | No ordinary edits. |
| Contract Handoff Completed | Contract handoff reference generated. | No ordinary edits. |
| Cancelled | Tender formally cancelled. | No. |
| Retender Required | Retender or replacement process required. | Limited to creating replacement tender. |
| Superseded | Tender replaced by another tender. | No. |
| Archived | Tender retained for audit. | No. |

## 7. STD Binding Governance

### 7.1 Binding States

| State | Meaning | Editable? |
|---|---|---|
| Draft | Binding created but not complete. | Yes before publication. |
| Active | Binding is controlling tender preparation. | Limited. |
| Published | Binding is locked as published basis. | No direct edits. |
| Invalidated by Change | Binding/readiness invalidated by parameter/addendum/template/timeline change. | Requires revalidation or addendum. |
| Superseded | Binding replaced through governed process. | No. |
| Cancelled | Binding no longer active due to tender cancellation. | No. |

### 7.2 STD Binding Rules

| Rule ID | Rule |
|---|---|
| TM2-STD-GOV-001 | A tender cannot proceed to publication review without active STD binding. |
| TM2-STD-GOV-002 | Only active STD template versions may be selected for new tenders. |
| TM2-STD-GOV-003 | Tender STD instance must be created by STD Engine. |
| TM2-STD-GOV-004 | Tender Management cannot manually generate Bundle, DSM, DOM, DEM, or DCM. |
| TM2-STD-GOV-005 | Published STD binding is immutable. |
| TM2-STD-GOV-006 | Addendum may update generated outputs only through STD impact and regeneration process. |
| TM2-STD-GOV-007 | Template version supersession does not change existing tender binding. |
| TM2-STD-GOV-008 | If binding becomes invalid before publication, tender must return to incomplete/draft state. |
| TM2-STD-GOV-009 | Publication must bind exact Bundle/DSM/DOM/DEM/DCM versions through publication snapshot. |

## 12. Addendum Governance

### 12.1 Addendum Principles

Addendum is the controlled mechanism for material post-publication changes.

Material changes include changes to:

1. deadlines;
2. STD parameters;
3. Works Requirements;
4. BOQ items, quantities, units, provisional sums, or pricing rules;
5. supplier forms;
6. submission requirements;
7. DOM opening register model;
8. DEM evaluation model;
9. DCM contract carry-forward;
10. supplier access obligations.
