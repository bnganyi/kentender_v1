## 1. Purpose

This document defines the roles, permissions, authorization rules, separation-of-duties requirements, supplier access controls, auditor access controls, and administrative override boundaries for **Tender Management v2**.

Tender Management v2 is a legally consequential module. The permissions model must therefore go beyond ordinary role-based access control. Authorization must evaluate:

```text
Actor + Role + Action + Tender State + Object State + Context + Separation of Duties + Governance Preconditions + Backend Action Availability
```

It must not evaluate role alone.

This artifact defines:

1. role categories;
2. role definitions;
3. action catalogue;
4. permission rules by action category;
5. state-aware permissions;
6. supplier-facing permissions;
7. separation-of-duties controls;
8. administrative override restrictions;
9. audit visibility and oversight permissions;
10. server-side enforcement rules;
11. backend action availability and denial handling.

## 2. Access Control Principles

### 2.1 State-aware authorization is mandatory

An actor may perform an action only if the tender, addendum, clarification, bid, or handoff object is in a valid state for that action.

### 2.2 Context-aware authorization is mandatory

The system must check context such as package ownership, procuring entity, supplier eligibility, invitation status, addendum acknowledgement status, deadline status, STD readiness, publication snapshot binding, and current generated output references.

### 2.3 Backend action availability is mandatory

Every legally significant UI or API action must be evaluated through backend action availability / authorization. UI visibility is not security.

### 2.4 Separation of duties is mandatory

The same actor must not normally create, approve, publish, cancel, and override the same tender process. Exceptions require explicit override authority, reason, and audit.

### 2.5 Supplier isolation is mandatory

Supplier users may access only their own participation, drafts, submissions, acknowledgements, receipts, and permitted public/shared tender information.

### 2.6 Sealed bid confidentiality is absolute

Internal users must not access sealed bid contents before lawful opening. System administrator access must not bypass this rule.

### 2.7 STD Engine ownership must be respected

Tender Management roles must not create, edit, or override STD-owned submission requirements, opening register definitions, evaluation criteria, or contract carry-forward terms.

### 2.8 Output ownership must be respected

Bundle, DSM, DOM, DEM, DCM, and publication snapshot are STD Engine-controlled artifacts. Tender Management may reference and consume them but must not manually alter them.

### 2.9 All material actions must be auditable

Every material action must create audit evidence with actor, role, state, reason where required, denial code where applicable, and object references.

## 3. Role Catalogue

### 3.1 Internal Operational Roles

| Role | Description | Typical Scope |
|---|---|---|
| Procurement Officer | Operational user responsible for creating tenders from packages, coordinating STD instance completion, managing clarification/addendum preparation, and preparing tender lifecycle actions. | Assigned procuring entity / department / package scope. |
| Senior Procurement Officer | Senior operational user with expanded tender administration capability, but not final approval authority unless separately granted. | Assigned procuring entity / department. |
| Procurement Manager | Reviews and approves publication/addenda/corrections within delegated authority. | Procuring entity or department authority scope. |
| Head of Procurement | High-authority procurement official for cancellations, retendering, supersession, and exceptional approvals. | Entity-wide authority. |
| Accounting Officer / Authorized Approver | Statutory or delegated authority for high-value/high-risk approvals where configured. | Delegation-of-authority scope. |
| Legal Reviewer | Reviews legal sufficiency, addenda, exceptions, cancellation grounds, and tender content risks. | Review-only plus legal clearance actions. |
| Compliance Reviewer | Reviews policy/regulatory compliance, readiness blockers, and exception handling. | Review-only plus compliance clearance actions. |
| Tender Secretariat | Administrative support role for notices, communications, evidence collation, and record preparation. | Limited operational support scope. |
| Opening Coordinator | Receives opening readiness package and coordinates with Bid Opening module. | Opening-specific scope only. |
| Evaluation Coordinator | Receives evaluation handoff and coordinates with Evaluation module. | Evaluation handoff visibility only. |
| Contract Officer | Receives contract handoff references after award. | Contract handoff visibility only. |
| Auditor / Oversight User | Read-only oversight of records, lifecycle, audit trail, and evidence. | Oversight scope; no modification. |
| System Administrator | Technical support role. No business authority unless explicitly granted by governance role. | Technical configuration and support only. |
| System | Automated actor executing validations, notifications, closure, sealing, and service integrations. | System-defined actions only. |

### 3.2 External Roles

| Role | Description | Typical Scope |
|---|---|---|
| Supplier User | Supplier-side participant who views tenders, submits clarifications, prepares bids, submits bids, acknowledges addenda, and accesses receipts. | Own supplier account only. |
| Supplier Admin | Supplier-side administrator managing supplier organization users and participating in tenders. | Own supplier account only. |
| Public Visitor | Unauthenticated public viewer of public notices and public tender metadata where permitted. | Public information only. |

### 3.3 Governance / Configuration Roles Referenced but Not Owned Here

| Role | Owner | Relationship |
|---|---|---|
| STD Administrator | STD Engine | Configures STD templates; not a Tender Management role. Cannot perform Tender lifecycle actions unless separately assigned Tender role. |
| STD Legal / Policy Reviewer | STD Engine | Reviews STD template versions; not tender lifecycle approval. |
| Procurement Planning Officer | Procurement Planning | Owns package creation/release; Tender consumes package only. |
| Supplier Management Officer | Supplier Management | Owns supplier registration/eligibility; Tender consumes service only. |

## 4. Role Boundary Rules

| Rule ID | Rule |
|---|---|
| TM2-RBAC-001 | Procurement Officer may create and prepare tenders but may not approve publication of their own tender where separation of duties applies. |
| TM2-RBAC-002 | Procurement Manager may approve or return publication/addenda within delegated authority but may not alter STD-derived rules. |
| TM2-RBAC-003 | Legal Reviewer may clear or reject legal sufficiency but may not publish tender unless separately assigned a publication role. |
| TM2-RBAC-004 | Compliance Reviewer may clear or reject compliance issues but may not alter tender content directly. |
| TM2-RBAC-005 | Head of Procurement / Accounting Officer handles high-risk approvals according to delegation rules. |
| TM2-RBAC-006 | Tender Secretariat may support communication and evidence but may not approve legally significant transitions. |
| TM2-RBAC-007 | Opening Coordinator may view opening readiness metadata but must not access sealed bids before formal opening. |
| TM2-RBAC-008 | Evaluation Coordinator may view evaluation handoff package but cannot modify STD-derived DEM. |
| TM2-RBAC-009 | Contract Officer may view contract handoff references but cannot alter tender terms in Tender Management or DCM. |
| TM2-RBAC-010 | Auditor / Oversight User has read-only access and cannot mutate records. |
| TM2-RBAC-011 | System Administrator cannot bypass sealed bid confidentiality, STD locks, publication snapshot binding, or business approval rules. |
| TM2-RBAC-012 | Supplier users can access only their own supplier records and permitted tender information. |
| TM2-RBAC-013 | No Tender role may manually edit Bundle, DSM, DOM, DEM, DCM, or publication snapshot. |
| TM2-RBAC-014 | Direct post-publication edits must be denied and routed to addendum, cancellation, supersession, or retender path as applicable. |

## 7. State-Aware Permission Rules

### 7.1 Tender State Rules

| Tender State | Allowed Action Families | Restricted Action Families |
|---|---|---|
| Draft | Edit draft, bind STD, run readiness, configure access, submit review | Publish, bid submission, closing, opening readiness |
| STD Instance Incomplete | Complete STD instance, run readiness | Publication review, publication, supplier access |
| Ready for Publication Review | Review, return, approve | Ordinary edit unless returned |
| Returned for Correction | Correct, rerun readiness, resubmit | Publish, supplier access |
| Approved for Publication | Publish | Ordinary edit, STD rebinding |
| Published | Supplier access, clarifications, addenda, bid submission, cancellation, closing | Direct core edits, STD rebinding, manual criteria changes, output replacement outside addendum |
| Addendum Pending | Addendum actions, controlled supplier access | Direct edits, publication rewrite |
| Suspended Pending Addendum | Addendum issue/cancel, supplier notification | Bid submission unless policy permits |
| Closed | Closing record, opening readiness, no-valid-submission decision | Supplier submission, bid replacement, bid withdrawal |
| Opening Ready | Opening handoff | Tender edits, supplier submissions |
| Opening Completed | Evaluation handoff | Tender edits, opening model changes |
| Evaluation Ready / In Progress | Evaluation references, audit visibility | Tender edits, bid changes, criteria changes |
| Awarded | Contract handoff references | Tender edits, bid changes |
| Contract Handoff Completed | Audit/reporting | Operational mutation |
| Cancelled / Superseded / Archived | Audit/reporting, retender where permitted | New submissions, publication, ordinary edits |

### 7.2 Bid State Rules

| Bid State | Supplier Permissions | Internal Permissions |
|---|---|---|
| Draft | Supplier may edit own draft before deadline | Internal users cannot view content |
| Submitted | Supplier may view own receipt; replace/withdraw if allowed before deadline | Internal metadata only; no content |
| Sealed | Supplier may view receipt/status; replace/withdraw if allowed before deadline | No content before lawful opening |
| Superseded | Supplier may view own receipt/status | Metadata/audit only |
