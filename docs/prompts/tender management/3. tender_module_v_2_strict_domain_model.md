## 1. Purpose of This Domain Model

This Strict Domain Model defines the persistent business objects required to implement **Tender Management v2** as an STD-native tender orchestration module.

The model must support:

1. creation of tenders only from authorized procurement packages;
2. binding of tenders to governed STD template versions and tender STD instances;
3. publication readiness based on STD Engine outputs;
4. controlled tender publication;
5. supplier access and participation;
6. clarification and addendum governance;
7. bid submission, sealing, replacement, withdrawal, and late-attempt rejection;
8. tender closing;
9. opening readiness handoff;
10. evaluation handoff;
11. contract handoff references;
12. auditability and legal reconstruction;
13. Works-first implementation including structured BOQ handling by reference to STD-derived models.

This document defines product-grade entities, fields, constraints, relationships, status enumerations, and ownership boundaries. It does not define UI layout, seed data, smoke tests, or implementation tickets.

| TM2-ID-004 | Each tender must have exactly one active Tender STD Binding. |

## 32. Service Boundary Requirements

### 32.0 Backend Action Availability Requirement

Tender Management v2 must not authorize legally meaningful actions through frontend role checks alone. Tender lifecycle actions, publication actions, addendum actions, submission/opening/evaluation/contract handoff actions, evidence export, and post-publication edit attempts must use the backend Action Availability / Authorization Decision Engine defined by the Security, Permissions, and Audit Hardening artifact.

Required action availability outputs must be auditable and must return allowed/denied status, denial code, risk level, and user-facing reason.
