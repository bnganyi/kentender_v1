# **1\. Executive UX Position**

Procurement Planning v3 must be a **normal-user workbench**, not a collection of module screens.

The user’s mental model must be:

I open Procurement Planning.  
I see the active plan.  
I see the work that needs attention.  
I select an item.  
I see the next action.  
I do the work.  
I view evidence only if I need it.

The user’s mental model must not be:

I need to know whether this item belongs in Planning Home, Approved Demands, Plans, Packages, or Released to Tender.

The final IA is:

Procurement Planning  
├── Workbench  
├── Procurement Plans  
└── Released to Tender

The Workbench absorbs the previous:

Planning Home  
Approved Demands  
Packages

The system still records all legal and audit artifacts, but the ordinary UI translates those artifacts into business states and next actions.

# **2\. UX Design Goals**

| Goal | Meaning |
| --- | --- |
| Make Planning obvious | A user should know where to begin: Workbench. |
| Make plan dependency visible | The active procurement plan is shown before any planning work begins. |
| Collapse scattered work | Approved demands, draft packages, review, readiness, release, and recently released items appear as Workbench queues. |
| Hide implementation complexity | Handoff records, lifecycle keys, JSON labels, audit IDs, and source/target objects are not ordinary UI content. |
| Preserve legal safety | Readiness, approval, release locking, evidence, permissions, and audit records remain enforced underneath. |
| One selected item, one next action | The user should not be presented with multiple competing primary actions. |
| Evidence on request | Evidence is available but does not dominate the work surface. |
| Plans as support, not daily work | Procurement Plans is for creating, activating, closing, and reviewing plans. |
| Released as follow-up | Released to Tender is for checking completed Planning outputs and opening the resulting tender. |

# **3\. Primary User Types**

This document focuses on ordinary internal Planning users, not suppliers.

| User Type | Primary Need |
| --- | --- |
| Procurement Planner | Find approved demand, include it in an active plan, create package, prepare package. |
| Planning Reviewer | Review package, approve or return. |
| Planning Authority | Release approved/readiness-passed package to Tender Management. |
| Procurement Officer | Continue released package in Tender Management. |
| Auditor / Oversight User | View evidence and technical details when needed. |
| Supplier | Must not access internal Planning UI or evidence. |

# **4\. Core UX Objects**

The UI must avoid exposing every backend object as a separate user destination.

| Backend / Control Object | Ordinary UI Translation |
| --- | --- |
| Approved Demand | Workbench item in Needs Planning |
| Procurement Plan | Active plan context / plan oversight object |
| Planning Inclusion Record | Evidence that demand was included in plan |
| Procurement Package | Workbench package item |
| Package Lines | Package Detail → Lines & Funding |
| Readiness Result | Package Detail → Readiness |
| Review Decision | Package Detail → Review |
| Planning Release Package | Evidence that package was released |
| Tender Consumption Record | Evidence that Tender Management consumed release |
| Tender | Open Tender action / Released to Tender follow-up |

The ordinary user sees work state and next action, not object mechanics.

# **6\. Workbench Concept**

## **6.1 Workbench Purpose**

The Workbench answers:

What planning work needs attention, and what do I do next?

It is the default entry point for Procurement Planning.

## **6.2 Workbench Responsibilities**

The Workbench must let the user:

see whether an active plan exists;  
create or activate a plan if none exists;  
see approved demands ready for planning;  
include a demand in the active plan;  
create a package;  
open a package;  
run or view readiness;  
submit for review;  
review, approve, or return where permitted;  
release to Tender Management;  
open the resulting tender;  
view evidence only when requested.

## **6.3 Workbench Must Not Become**

The Workbench must not become:

an audit log;  
a handoff registry;  
a lifecycle debugger;  
a technical object browser;  
a generic dashboard with no primary action;  
a page that pushes users to other menus before they can work.

# **7\. Workbench Active Plan Gate**

## **7.1 Why the Gate Exists**

A procurement plan must exist before approved demands can be included in planning and converted into packages.

Therefore, the Workbench must show active plan status before queue work.

## **7.2 No Active Plan State**

**Wireframe**

┌ Procurement Planning Workbench ────────────────────────────────────────────┐  
│ Plan approved demands into tender-ready procurement packages. │  
│ │  
│ No active procurement plan exists for FY 2026/2027. │  
│ Create or activate a procurement plan before planning approved demands. │  
│ │  
│ \[Create Plan\] \[Activate Existing Plan\] │  
└────────────────────────────────────────────────────────────────────────────┘  
  
┌ Work Queues ───────────────────────────────────────────────────────────────┐  
│ Planning work is unavailable until an active procurement plan is selected. │  
└────────────────────────────────────────────────────────────────────────────┘

**Behavior**

In this state:

Needs Planning queue is disabled or replaced by explanation.  
Include in Plan is not shown.  
Create Package is not shown.  
Package readiness/review/release actions are not shown unless linked to another active plan context.

**Primary Action**

Create Plan

**Secondary Action**

Activate Existing Plan

## **7.3 Active Plan State**

**Wireframe**

┌ Procurement Planning Workbench ────────────────────────────────────────────┐  
│ Plan approved demands into tender-ready procurement packages. │  
│ │  
│ Active plan: Ministry of Health Procurement Plan FY 2026/2027 │  
│ \[Change Plan\] \[View Plan\] │  
└────────────────────────────────────────────────────────────────────────────┘

**Behavior**

When an active plan exists:

Workbench queues are enabled.  
Needs Planning shows approved demands that can be planned.  
Included demand/package states flow through the same Workbench.

# **8\. Workbench Queues**

## **8.1 Queue List**

Workbench queues are:

Needs Planning  
Draft Packages  
Needs Review  
Ready to Release  
Blocked  
Recently Released

No more than six default queues may appear.

## **8.2 Queue Definitions**

| Queue | Contains | Primary User Question | Primary Action |
| --- | --- | --- | --- |
| Needs Planning | Approved demands that can be added to the active plan | What approved demand can I plan now? | Include in Plan |
| Draft Packages | Packages created but still being prepared | What package am I preparing? | Open Package |
| Needs Review | Packages submitted for review | What needs review? | Review Package |
| Ready to Release | Packages approved and readiness-passed | What can be released to Tender Management? | Release to Tender Management |
| Blocked | Demands/packages with blockers | What is stuck and why? | Resolve Blocker / Open Package |
| Recently Released | Packages released or consumed by Tender Management | What left Planning recently? | Open Tender |

## **8.3 Queue Behavior**

Each queue must show:

work item title;  
short business metadata;  
business state;  
blocker indicator if any;  
next action.

Each queue must not show:

handoff code;  
source object;  
target object;  
JSON field name;  
audit ID;  
internal lifecycle key;  
implementation-stage copy.

# **10\. Workbench State Model**

The Workbench must show one planning item moving through business states, even though the underlying object changes.

| Workbench State | Underlying Object | User Sees | Primary Action |
| --- | --- | --- | --- |
| Needs Planning | Approved Demand | Approved demand ready for planning | Include in Plan |
| Included in Plan | Planning Inclusion | Demand added to active plan | Create Package |
| Draft Package | Procurement Package | Package being prepared | Open Package |
| Needs Review | Procurement Package | Package waiting for review | Review Package |
| Returned | Procurement Package | Package returned for correction | Open Package |
| Ready to Release | Procurement Package | Package approved and ready | Release to Tender Management |
| Released | Planning Release Package | Package sent to Tender Management | Open Tender |
| Tender Created | Tender | Tender created from package | Open Tender |
| Blocked | Demand or Package | Something prevents progress | Resolve Blocker / Open Package |

The user should not need to understand the transition from demand to planning inclusion to package to release to tender.

# 30\. No-Go Conditions

The UI fails if any of these occur:

The user must choose between Planning Home, Approved Demands, and Packages.  
There are more than three persistent Planning navigation entries.  
Plans appears as an ordinary third menu required before work can start, instead of being visible as active plan context in Workbench.  
Approved demands are outside the Workbench.  
Packages are outside the Workbench.  
Planning Home exists as a separate ordinary screen.  
The Workbench lacks active plan status.  
Include in Plan is available without an active plan.  
Evidence appears before the user asks for it.  
Technical details appear before explicit expansion.  
The user must understand Planning Inclusion to continue.  
The user must understand Planning Release Package to continue.  
The UI looks like an audit log, handoff registry, lifecycle debugger, or implementation status board.
