**1\. Executive Decision**

The current five-screen Procurement Planning UI model is rejected.

The rejected model is:

Procurement Planning  
├── Planning Home  
├── Approved Demands  
├── Plans  
├── Packages  
└── Released to Tender

This model remains too fragmented for ordinary users. It asks users to understand where planning work lives before they can do the work.

A normal user should not have to decide whether to start in:

Planning Home  
Approved Demands  
Plans  
Packages  
Released to Tender

The approved model is:

Procurement Planning  
├── Workbench  
├── Procurement Plans  
└── Released to Tender

This is now the controlling product decision for the Procurement Planning ordinary user interface.

Planning work happens in **Workbench**.

Procurement Plans supports setup and oversight.

Released to Tender shows completed Planning outputs.

Everything else is contextual.

**2\. Why This Decision Is Necessary**

The previous UI reset correctly identified a major problem: the Planning interface was becoming an audit/evidence browser rather than a workbench.

It tried to hide:

handoff cards  
lifecycle trace panels  
raw technical identifiers  
JSON labels  
audit IDs  
evidence clutter  
implementation-stage copy

That was directionally correct.

However, it did not fully fix the information architecture. It still preserved five persistent Planning surfaces:

Planning Home  
Approved Demands  
Plans  
Packages  
Released to Tender

That structure created a second problem: even without handoff clutter, the planning workflow was still scattered.

The problem is no longer only visual complexity.

The problem is workflow fragmentation.

The UI must not make a planner ask:

Do I go to Planning Home, Approved Demands, Plans, or Packages?

The UI must answer:

Here is your planning work.  
Here is the active plan.  
Here is the next action.

**3\. Root Cause of the Earlier Failure**

The earlier documentation tried to simplify individual screens while keeping too many screens.

That approach failed because the screen split itself was wrong.

The previous model treated these as separate destinations:

| Previous Surface | Intended Purpose | Why It Failed |
| --- | --- | --- |
| Planning Home | What needs attention? | Duplicated work queues that belong in the Workbench. |
| Approved Demands | What can be planned? | Should be a Workbench queue, not a separate destination. |
| Plans | Which plan owns the work? | Should be setup/oversight and visible as active context in the Workbench. |
| Packages | Which package needs work? | Should be part of the Workbench because packages are the main planning work items. |
| Released to Tender | What left Planning? | Valid as a separate follow-up surface. |

In reality, the first four are not independent destinations for ordinary daily work.

They are parts of one planning workstream:

approved demand  
→ active plan inclusion  
→ package creation  
→ package preparation  
→ readiness  
→ review  
→ release

Therefore:

Planning Home  
Approved Demands  
Packages

must be absorbed into one Workbench.

Procurement Plans should remain separate only because it is setup/oversight.

Released to Tender should remain separate only because it is completed-output follow-up.

**4\. Final Approved IA**

The final approved Procurement Planning IA is:

Procurement Planning  
├── Workbench  
├── Procurement Plans  
└── Released to Tender

This IA is binding for Procurement Planning v3 UI documentation and implementation.

**4.1 Workbench**

Workbench is the daily operational Planning surface.

Workbench answers:

What planning work needs attention, and what do I do next?

Workbench absorbs the previous:

Planning Home  
Approved Demands  
Packages

Workbench owns these queues:

Needs Planning  
Draft Packages  
Needs Review  
Ready to Release  
Blocked  
Recently Released

Workbench is where the user:

sees approved demands ready for planning  
confirms the active procurement plan  
creates or activates a plan if none exists  
includes an approved demand in the active plan  
creates a package from the planned demand  
opens package detail  
runs readiness checks  
submits for review  
reviews, returns, or approves where permitted  
releases to Tender Management  
opens the resulting tender  
views evidence only when requested

**4.2 Procurement Plans**

Procurement Plans is setup and oversight.

Procurement Plans answers:

Is there an active procurement plan?  
Which plan owns this work?  
What demands and packages belong to the plan?  
How is the plan progressing?

Procurement Plans is **not** the daily package workbench.

Procurement Plans supports:

Create Plan  
Activate Plan  
Close Plan  
View Active Plan  
View Plan Progress  
View Demands Included in Plan  
View Packages Under Plan  
View Evidence

A user should not need to enter Procurement Plans to process ordinary package work unless they are creating, activating, closing, changing, or reviewing a procurement plan.

**4.3 Released to Tender**

Released to Tender is follow-up and completed-output visibility.

Released to Tender answers:

Which packages have left Planning?  
Was the tender created?  
Can I open the tender?  
Can I view release evidence?

Released to Tender is not where package preparation work happens.

It shows outputs after Planning has released a package to Tender Management.

**5\. Plan Creation Rule**

A procurement plan must exist before approved demands can be planned into packages.

The previous design made this too implicit by showing an “Include in Plan” modal that assumed the existence of a plan.

That is not good enough.

The Workbench must show the active plan state immediately.

**5.1 If No Active Plan Exists**

If no active procurement plan exists for the relevant fiscal year and procuring entity, the Workbench must show a blocking setup card:

No active procurement plan exists for FY 2026/2027.  
  
Create or activate a procurement plan before planning approved demands.  
  
\[Create Plan\] \[Activate Existing Plan\]

In this state:

Needs Planning must not behave like normal planning work can proceed.  
Include in Plan must not be available.  
Create Package must not be available.  
The user must be guided to create or activate a procurement plan first.

**5.2 If an Active Plan Exists**

If an active procurement plan exists, the Workbench must show active plan context at the top:

Active plan: Ministry of Health Procurement Plan FY 2026/2027  
  
\[Change Plan\] \[View Plan\]

Then the Workbench queues become available.

**5.3 Plan Creation Must Be Lightweight**

Plan setup must be simple for the ordinary planning workflow.

Minimum Create Plan fields:

Procuring entity  
Fiscal year  
Plan title  
Currency  
Optional description  
Create and Activate action

The Create Plan flow must not become a complex procurement package workflow.

Plan setup is a prerequisite. It is not the main daily planning activity.

**6\. Correct User Journey**

The normal user journey must be:

Open Procurement Planning  
→ Workbench opens  
→ Workbench shows active plan status  
→ If no active plan exists, create or activate plan  
→ Select District Hospital Renovation Works from Needs Planning  
→ Include demand in active plan  
→ Create package  
→ Open package detail  
→ Complete lines/funding/readiness/review/release  
→ Release to Tender Management  
→ Open Tender  
→ View evidence only when requested

The user must not need to know whether the item is internally an approved demand, planning inclusion, procurement package, release record, or tender consumption record.

The Workbench owns that state translation.

**7\. Workbench State Model**

The Workbench must treat demand/package/release progression as one planning work item moving through states.

| Workbench State | Underlying Object | User Meaning | Primary Action |
| --- | --- | --- | --- |
| Needs Planning | Approved Demand | Approved demand is ready to be planned. | Include in Plan |
| Included in Plan | Planning Inclusion | Demand has been added to the active plan. | Create Package |
| Draft Package | Procurement Package | Package is being prepared. | Open Package |
| Needs Review | Procurement Package | Package is waiting for review. | Review Package |
| Returned | Procurement Package | Package was returned for correction. | Open Package |
| Ready to Release | Procurement Package | Package is approved and ready for release. | Release to Tender Management |
| Released | Planning Release Package | Package was sent to Tender Management. | Open Tender / View Release |
| Tender Created | Tender | Tender exists in Tender Management. | Open Tender |
| Blocked | Demand or Package | Something prevents progress. | Resolve Blocker / Open Package |

The user should see the business state, not the internal object model.

**11\. Earlier UI Implementation Treatment**

The existing five-screen UI implementation should be treated as unsafe to continue.

Do not continue building on it.

Cursor must inventory it, then remove, fold, or refactor it.

| Current Piece | Treatment |
| --- | --- |
| Planning Home | Discard as a separate persistent destination. Fold any useful summary logic into Workbench. |
| Approved Demands | Discard as a separate persistent destination. Fold list and include-in-plan logic into Workbench → Needs Planning queue. |
| Packages | Discard as a separate persistent destination. Fold package list and selected summary logic into Workbench queues. Package Detail may remain contextual. |

**16\. Non-Negotiable Usability Rules**

The UI fails if:

the user must choose between Planning Home, Approved Demands, and Packages;  
Plans appears as a third ordinary menu even though an active plan is required before planning work;  
Approved demands are outside the daily Workbench;  
Packages are outside the daily Workbench;  
Planning Home duplicates the Needs Planning queue;  
the user must understand Planning Inclusion to continue;  
the user must understand Planning Release Package to continue;  
evidence or handoff records appear before the user asks for them;  
there are more than three persistent Planning navigation entries;  
there is more than one primary next action for the selected item;  
the UI looks like an audit log, handoff registry, lifecycle debugger, or implementation status board.
