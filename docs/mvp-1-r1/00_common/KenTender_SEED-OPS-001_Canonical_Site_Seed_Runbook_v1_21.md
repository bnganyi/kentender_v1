**Controlling decision:** a KenTender site has exactly one canonical world — the KT-STD-001 §8 configuration and the SEED-001 module chain. Everything else on the site (browser-test fixtures, isolated test profiles, hand-made drafts, demo journeys from retired seed packs) is disposable. One command removes the disposable rows and reseeds the canonical ones, progressively, one module stage at a time, and refuses to report success unless the result validates.

## 1. The command

Run from the repository root (`apps/kentender_v1/`), never from the bench root — the `make` targets live in this repository's `Makefile`.

```bash
cd /home/midasuser/frappe-bench/apps/kentender_v1
make seed-canonical SITE=kentender.midas.com THROUGH=budget
make seed-canonical SITE=kentender.midas.com THROUGH=award                            # the full chain (the default stops at requisitions, §4); since v1.16 (v1.13–v1.15 read: THROUGH=bid_opening # the full chain … since v1.13; v1.12 read: THROUGH=tenders)
make seed-canonical SITE=kentender.midas.com WIPE=True FORCE=True                    # full wipe, empty database — nothing rebuilt (default since v1.5)
make seed-canonical SITE=kentender.midas.com WIPE=True FORCE=True RESEED=True        # full wipe + rebuild from nothing, §4
make seed-canonical SITE=kentender.midas.com REBUILD=True                            # drop and rebuild the canonical module rows, §4
```

Companions:

```bash
make seed-canonical-dry-run SITE=kentender.midas.com    # list what would be removed; deletes nothing
make seed-canonical-validate SITE=kentender.midas.com   # validate the canonical world only; no writes
```

`WIPE` and `FORCE` are plain make variables (`WIPE ?= False`, `FORCE ?= False` in the Makefile) — `make seed-canonical` alone never wipes or forces anything. Underneath, the target calls the `bench execute` entry point directly; use that form yourself for any switch in §4 the Makefile doesn't expose as a variable:

```bash
cd /home/midasuser/frappe-bench
bench --site kentender.midas.com execute kentender_core.seeds.canonical.run \
  --kwargs '{"through": "budget", "reset": True, "validate": True}'
bench --site kentender.midas.com execute kentender_core.seeds.canonical.dry_run
bench --site kentender.midas.com execute kentender_core.seeds.canonical.validate \
  --kwargs '{"through": "budget"}'
```

Success prints one line, `CANONICAL_SEED_OK through=<stage> removed={…}`, followed by the JSON report. Any failure raises, and the whole run — clear and reseed — is rolled back as one transaction; the site is never left half-cleared.

### 1.1 Prerequisites

- The site's apps are migrated (`bench --site <site> migrate` clean).
- `developer_mode` is on in `site_config.json`, or `allow_canonical_seed` is set there, or `"force": True` is passed. The seed refuses otherwise: it deletes rows and sets the fixture password on the register's actors (v1.11 read: "in developer mode, sets the fixture password"; since v1.12 it does so whenever it is allowed to run, so the actors can log in on a new site seeded with `FORCE=True`). The password is `kentender_core.seeds.constants.TEST_PASSWORD`, also in `.env.ui`. Every run resets it on the register's actors. Since v1.13 the same rule sets it on the public observer (Jane Wanjiku) and on the canonical supplier people (Mary Wanjiku, David Ouma) (Project Owner, 30 September 2026: "Maintain the same universal password").
- The site is configured as `PE-MOH` or not configured at all. A site configured as a different Procuring Entity fails the seed rather than being repaired (KT-STD-001 §8.6).
- Run it as `Administrator` (the `bench execute` default).
- Since v1.16, stated for every stage after `tenders`: `bid_submission`, `bid_opening`, `bid_evaluation` and `award` use the simulated signing, tender-box, attestation, notice-delivery and Contracting services, which answer only on a test site — `site_config.json` sets `kt_bds_simulation_environment`. Elsewhere those stages refuse (§7). `force` does not make a site a test site.

### 3.2 Never touched

- A real person's account: any user on a non-fixture domain, whatever its name.

| Switch | Default | Effect |
|---|---|---|
| `through` / `THROUGH` | `requisitions` | Last stage to seed (`site`, `strategy`, `budget`, `needs`, `planning`, `requisitions`, `tenders`, `bid_submission`, `bid_opening`, `bid_evaluation`, `award`). Default stays `requisitions`; pass `THROUGH=award` explicitly for the full chain (v1.13–v1.15 read: "…`bid_opening`). | `reset` | `True` | Run the §3.1 clear before seeding. `False` seeds only. |
| `rebuild` | `False` | Also drop the canonical module rows before seeding — Tenders, then Requisitions, then Planning, then Needs, then Budget, then Strategy (downstream first, since each consumes the one before it) — and rebuild from scratch. Since v1.16, stated: the Tenders step takes the canonical bid, opening, evaluation and award with it (§3.1). Use it when a canonical record is wrong, not merely missing. Stages beyond `through` are cleared but not reseeded. |
| `wipe` | `False` | Drop the `site` stage too — the Procuring Entity, Organisation Units, Fiscal Years, Regulatory Reference, method/schedule rule profiles and the §8.3 actors themselves — then rebuild everything from nothing. Implies `rebuild` (the site stage is what every module stage's rows reference, so it is only ever safe to drop after they are already gone). This is the one option that deletes real user accounts (the register's own); it never touches a non-fixture account. Use it for a genuinely fresh canonical world, not a targeted correction — `rebuild` alone is enough when only a module's own rows drifted. | `reseed` | `None` → `not wipe` | Defaults to the opposite of `wipe`: a plain `reset`/`rebuild` (no `wipe`) still reseeds immediately, matching every call site from before this parameter existed. `wipe=True` alone (the common case) now means what the word says — clear everything and stop, no stage rebuilt, `through`/`validate` ignored: the actual "empty database, no data at all" mode, leaving the site in the same unconfigured state CFG-CHG-002 calls CONFIG-FIRST. Pass `reseed=True` explicitly (`RESEED=True` on the make target) alongside `wipe=True` for the old "wipe then immediately rebuild everything" behaviour. Exposed on `make seed-canonical` as `RESEED` since v1.4; default flipped in v1.5 after `wipe`'s old always-reseeds default kept silently repopulating the site on the exact command meant to empty it. |
| `validate` | `True` | Run §5 after seeding; a failure rolls the run back. |
| `force` | `False` | Bypass every fixture-build guard this run touches — this orchestrator's own (§1.1) and, for the duration of the run only, each module seed's independent `developer_mode`/`allow_tests` guard (`needs`/`planning`/`requisitions`/`tenders`; `tender_preparation` until its retirement), by setting `frappe.flags.in_test` rather than requiring `developer_mode` on the site. It does not make the site a test site: the four stages after `tenders` still need `kt_bds_simulation_environment` (§1.1). |
| `commit` | `True` | Commit at the end (tests pass `False`). |

## 6. Adding the next module stage

When a module's canonical seed is cut over to the one-site model:

1. Append the stage name to `canonical.STAGES` after the stage it depends on, and add a branch in `canonical.seed()` that calls the module's own upsert with its canonical-only shape (no test edges, no isolated profiles, no commit).
2. Keep the module's canonical namespace in `canonical.CANONICAL_NAMESPACES` and make sure the module's rows are stamped with it; unstamped rows are treated as disposable by §3.1.
3. Extend `canonical.collect_non_canonical()` with the module's disposable-row rule, and `clear_canonical_modules()` with its canonical clear, in dependency order (downstream modules before the ones they reference). A module whose rows hang off a Tender (as Bid Submission, Bid Opening, Bid Evaluation and Award do) registers a `kt_tender_removal_consumers` hook instead, and is removed with its Tender.
4. Add the stage's facts to `canonical.validate()`.
5. Add the stage's actors to `site_setup.ACTORS`/`ASSIGNMENTS` if KT-STD-001 §8.3 lists them and no earlier stage seeds them; never create actors inside the module seed.
6. Extend `kentender_core.tests.test_canonical_seed`, run it, then run the full command on a dirtied site and confirm the dry run and the removal report match.
7. Update §2 and §3 of this document, the seeds README and the command card in `CLAUDE.md`. Also (since v1.16) §4's stage list and §5, the `make help` line and the comment above `THROUGH` in the `Makefile`, the module docstring of `canonical.py`, and `test_stage_ladder_is_ordered_and_closed`; `bid_evaluation` and `award` were added without them. If the module has demo profiles, add their release to `canonical.release_demo_profiles()` and a section beside §9–§9B.

Everything the module seed writes must go through the same commands the UI uses, as the named actors, never Administrator, and must be idempotent (KT-STD-001 §8.6; SEED-001 §8).

## 7. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `make: No rule to make target 'seed-canonical'` | Run from `apps/kentender_v1/`, not the bench root. |
| Tenders accept a submission deadline closer than 7 days, or the Open Tender bid-opening minimum reads blank in System setup (v1.20) | The site was seeded before v1.20 and has no minimum, so Tenders treats the schedule as having none and blocks nothing. Run `bench --site <site> execute kentender_core.patches.v1_28.open_tender_preparation_minimum.execute`, then `bench --site <site> clear-cache`. A reseed with `wipe` also writes it. The patch never overwrites a minimum an administrator entered. |
| `Canonical seed refused: enable developer_mode…` | The site is not in developer mode; set `developer_mode` or `allow_canonical_seed` in `site_config.json`, or pass `"force": True` on the `bench execute` form. |
| `NameError: name 'true' is not defined` (or `'false'`) | `bench execute --kwargs` evaluates the string as a Python literal, not JSON — it needs `True`/`False`, capitalised, never lowercase `true`/`false`. Every example in this document uses the correct casing; a value copied from elsewhere (or typed from habit) is the usual cause. |
| `This site is configured as PE-XXX, not PE-MOH` | The seed never overwrites a different site identity (§8.6). Reconfigure the site deliberately, or use a different site. |
| Validation fails on "no non-canonical Fiscal Years" or "no fixture-domain users outside the register" | Something referenced the row so the clear skipped it (a year referenced by a Need, a user holding a canonical assignment). The dry run shows the plan; resolve the reference, then rerun. |
| `BUDGET_CONFIG_MISSING` from the Budget stage | The `site` stage did not complete (fiscal year or funding source absent). The whole run rolled back; read the earlier error. |
| Strategy stage `STRATEGY_CONFIG_MISSING` | Same — FY 2027-2028 is created by the `site` stage. |
| `NameError: name 'kentender_core' is not defined` (or another app's name) from `make seed-canonical`, usually on the run after a large clear | The background-job queue is full, not missing code. This bench runs no job worker by default; deletions enqueue background jobs, and past 500 queued jobs Frappe refuses every new one (`QueueOverloaded`). `bench execute` then hides the real error behind a `NameError` naming the app. Since v1.11 `make seed-canonical` drains the queue before and after the run, and `canonical.run` lifts the ceiling for its own process while it runs (a full wipe alone queued 650 jobs); if this still appears, it came from something else — run `make ui-queue-check FIX=1` from the repository root, then rerun. AGENTS.md §8.1 has the detail. |
| A seeded actor (for example the Strategy Author) cannot log in on a new site | Before v1.12 the fixture password was set only when `developer_mode` was on, so a new site seeded with `FORCE=True` got actors with no password. Since v1.12 any allowed run sets it; rerun `make seed-canonical` and use the password in `.env.ui`. |
| After `make ui-budget-gate`, a plain `make seed-canonical` fails validation on the budget's lines and on `requisitions.v111.reservations.*` | Expected: the Budget browser specs work on the one canonical budget (a Version 2, isolation fiscal years, replacement reservations) and release the canonical Requisition's reservations, which a plain reset cannot recreate. Run `make seed-canonical SITE=… THROUGH=tenders REBUILD=True`. |
| A Tender from an interrupted browser run is still there after a reseed | Fixed in v1.10: the clear now removes every Tender not on the canonical Requisition (§3.1). If one survives, it is a new regression. |
| Every Desk page load logs two console 404s afterwards | Unrelated to the seed: the dev server's socket.io long-poll and Frappe's sidebar divider image (see the Budget tracker, 2026-09-06). |
| `Required procurement rules or their calculation basis are missing or unverified` at the `submission` stage, with `wipe` or `rebuild` through `planning`/`requisitions`/`tender_preparation` | Closed as of v1.3 (Planning's own v1.23 work landed the missing verification step). If this recurs, it is a new regression, not the old known gap — report it rather than assuming `through=needs` is your only option. |
| `wipe` reports success and reseeds cleanly, but a stray account from before the run (e.g. `test@example.com`) is still on the site afterwards | Fixed in v1.3: `wipe`/`reset` only ever delete a user on a recognised fixture e-mail domain (`FIXTURE_EMAIL_DOMAINS` in `canonical.py`), by design, so a real person's login is never at risk — but the list previously missed the plain RFC 2606 placeholder domains (`example.com`/`.org`/`.net`) that a manually-created test account is likely to use. If a stray account still survives on a different, non-fixture domain, that is correct behaviour, not a bug — delete it by hand. |
| `make seed-canonical WIPE=True` has no effect, or `force`/`wipe` errors say the site is not in developer mode | Before v1.3, the `make seed-canonical` target never passed `wipe` or `force` through at all — only the raw `bench execute … canonical.run` form (§1) could reach them. `WIPE=True FORCE=True` are now plain make variables on the same target; make sure you're on v1.3 of this Makefile target, not typing `wipe`/`force` into `THROUGH` or expecting the bare command to pick them up. |
| `wipe`/`WIPE=True` runs clean, but Strategy/Budget/Needs/Planning/etc. all still show data afterwards | Was `reseed` defaulting to `True` regardless of `wipe` — every documented example through v1.4 reseeded the full chain right after clearing it. **Fixed in v1.5**: `wipe=True` alone now defaults `reseed` to `False`. If this still happens, you have `RESEED=True` set (or `"reseed": True` explicitly) — drop it for an empty database. |
| A wipe with `reseed=False` throws `That financial year does not exist` (masked as a `NameError` from `bench execute`) | Fixed in v1.4 — this was `wipe` not being idempotent when run twice with `reseed=False` back to back: Planning's own playwright teardown tried to reopen DPP intake on a Fiscal Year the first run had already deleted. If this recurs, it's a new regression, not the known v1.4 gap. |
| `The canonical bid evaluation signs with the test attestation service, which exists only on a test site` or `The canonical award uses the simulation adapters and is seeded on a test environment only` | The site is not a test site. Set `kt_bds_simulation_environment` in `site_config.json` (§1.1), or seed only `THROUGH=tenders`. The same applies to `bid_submission` and `bid_opening`. |
| After a demo walkthrough, every live page shows a June or July 2027 date | A Bid Opening or Award demo profile set the site test clock. Since v1.16 a plain `make seed-canonical` clears it; `make seed-bop-profile-restore` or `make seed-awd-profile-restore` also clear it. |
| Validation fails right after a Requisitions or Tenders browser run, on `pw.req.*` / `pw.tnd.*` users, a 2099 fiscal year, a `BUD-PWREQ-0001` budget or a second Requisition | Those browser worlds were found left on the site after their runs (1 October 2026). They are not canonical; `make seed-canonical` removes them. |

## 8. Relationship to other seed entry points

- `make seed-kentender-mvp-v1` (`kentender_core.seeds.kentender_mvp_v1.orchestrator`) is the earlier multi-PE-era pack: it still creates a second Procuring Entity and legacy personas through `org.py`/`users.py`. Do not run it on a site you have just made canonical unless you intend to reintroduce that data; `make seed-canonical` will remove the legacy personas again.

- `make awd-seams-gate` builds a real Evaluation test world whose Planning and Tenders fixtures persist (Award run book, `docs/mvp-1-r1/16_award/RUNBOOKS.md` §2); run `make seed-canonical THROUGH=award` afterwards.
