# SEED-OPS-001 — Canonical Site Seed Runbook

| Control | Value |
|---|---|
| Document ID | SEED-OPS-001 |
| Version | 1.10 |
| Date | 26 September 2026 |
| Status | Maintained — update whenever a module stage is added to the seed or the canonical world changes |
| Purpose | The one command that resets a KenTender site to the canonical seed world and how to keep it truthful as modules land |
| Standards | KT-STD-001 v1.3 §8 (shared fixture register, §8.6 seed execution rules, §10 prohibited shortcuts); SEED-001 v1.0 (harmonized end-to-end fixture). The baseline register now lists KT-STD-001 v1.8 and SEED-001 v1.3 as approved; this runbook has not been re-verified against them. |
| Owner | `kentender_core` (`kentender_core/kentender_core/seeds/canonical.py`) |

**Controlling decision:** a KenTender site has exactly one canonical world — the KT-STD-001 §8 configuration and the SEED-001 module chain. Everything else on the site (browser-test fixtures, isolated test profiles, hand-made drafts, demo journeys from retired seed packs) is disposable. One command removes the disposable rows and reseeds the canonical ones, progressively, one module stage at a time, and refuses to report success unless the result validates.

---

## 1. The command

Run from the repository root (`apps/kentender_v1/`), never from the bench root — the `make` targets live in this repository's `Makefile`.

```bash
cd /home/midasuser/frappe-bench/apps/kentender_v1
make seed-canonical SITE=kentender.midas.com THROUGH=budget
make seed-canonical SITE=kentender.midas.com THROUGH=tenders                          # the full chain (the default stops at requisitions, §4)
make seed-canonical SITE=kentender.midas.com WIPE=True FORCE=True                    # full wipe, empty database — nothing rebuilt (default since v1.5)
make seed-canonical SITE=kentender.midas.com WIPE=True FORCE=True RESEED=True        # full wipe + rebuild from nothing, §4
make seed-canonical SITE=kentender.midas.com REBUILD=True                            # drop and rebuild the canonical module rows, §4
```

Companions:

```bash
make seed-canonical-dry-run SITE=kentender.midas.com    # list what would be removed; deletes nothing
make seed-canonical-validate SITE=kentender.midas.com   # validate the canonical world only; no writes
```

`WIPE` and `FORCE` are plain make variables (`WIPE ?= False`, `FORCE ?= False` in the Makefile) — `make seed-canonical` alone never wipes or forces anything. Underneath, the target calls the `bench execute` entry point directly; use that form yourself for any switch in §4 the Makefile doesn't expose as a variable:

```bash
cd /home/midasuser/frappe-bench
bench --site kentender.midas.com execute kentender_core.seeds.canonical.run \
  --kwargs '{"through": "budget", "reset": True, "validate": True}'
bench --site kentender.midas.com execute kentender_core.seeds.canonical.dry_run
bench --site kentender.midas.com execute kentender_core.seeds.canonical.validate \
  --kwargs '{"through": "budget"}'
```

Success prints one line, `CANONICAL_SEED_OK through=<stage> removed={…}`, followed by the JSON report. Any failure raises, and the whole run — clear and reseed — is rolled back as one transaction; the site is never left half-cleared.

### 1.1 Prerequisites

- The site's apps are migrated (`bench --site <site> migrate` clean).
- `developer_mode` is on in `site_config.json`, or `allow_canonical_seed` is set there, or `"force": True` is passed. The seed refuses otherwise: it deletes rows and, in developer mode, sets the fixture password on the register's actors.
- The site is configured as `PE-MOH` or not configured at all. A site configured as a different Procuring Entity fails the seed rather than being repaired (KT-STD-001 §8.6).
- Run it as `Administrator` (the `bench execute` default).

The *Seed of record* column names the version each stage's seed was built against. As of 26 September 2026 the baseline register lists later approved versions for four of them — STR-CHG-001 v1.8, BUD-CHG-001 v1.11, NDS-CHG-001 v1.14 and PLN-CHG-001 v1.27 — and this runbook has not re-verified that those versions leave the seeded world unchanged. REQ-CHG-001 v1.13 is in Project Owner review; the `requisitions` stage stays on v1.11 until it is approved and built.

Every stage's seed is idempotent: a second run creates nothing and changes nothing (KT-STD-001 §8.6), which the validator and `kentender_core.tests.test_canonical_seed` both assert. Every stage calls its owning module's canonical-shaped seed function directly — never `kentender_core.seeds.kentender_mvp_v1.orchestrator` (the legacy multi-PE-era pack) — so seeding through any stage never creates `PE-CGKIS` or a second Procuring Entity.

Because `requisitions` and `tenders` each consume exactly one Plan Item / Requisition from the stage before them, seeding past `planning` legitimately advances that earlier stage's own state in ways its own module validator (written for "seeded alone") cannot see coming — `validate(through=…)` accounts for this (§5).

## 3. What the clear removes, and what it never touches

Selection is by explicit identity, namespace or fixture e-mail domain — never "everything in a table". `make seed-canonical-dry-run` shows the exact list before anything is deleted.

### 3.1 Removed

| Area | Rule |
|---|---|
| Budget | Every Procurement Budget other than `MOH-BUD-2027-001`, with its versions, lines, reservations, commitments, audit events and attachments. On the canonical budget: any version that is not Active, and any Funding Reservation not stamped `KENTENDER_MVP_1_R1_REQ` (§8.6 — that stamp is this orchestrator's own evidence of the canonical Requisition, not a stray). |
| Departmental Needs | Every Need (with its versions, decisions, review tasks, events, projections) whose `fixture_namespace` is not `KENTENDER_MVP_1_R1_NDS`, including unstamped rows. Review tasks are "retained permanently" through the document API, so the purge uses the module's own raw-delete mechanism (`departmental_needs.seeds.playwright_ui_fixtures.purge_fixture_needs`). |
| Procurement Planning | Annual Plans and Departmental Plans (and their submissions, validations, items, allocations, finance and governance rows) outside `KENTENDER_MVP_1_R1_PLN`, through `procurement_planning.seeds.kentender_mvp_v1.clear_planning_fixture_rows`. |
| Procurement Requisitions | Requisitions carry no `fixture_namespace` column; "canonical" means rows tied to the one eligible combined Plan Item. `include_canonical=False` on `procurement_requisitions.seeds.clear.clear_requisition_fixture_rows` — run unconditionally on every `reset`, not gated on a namespace check — removes only Playwright-owned residue, so the canonical Requisition survives. |
| Tenders | Every `Tender` that is not on the canonical Requisition (the Requisition of the one eligible combined Plan Item — the same rule `validate_tenders_seed()` checks), together with its versions, decisions, tasks, publication, channel confirmations, addenda, clarifications, candidate registrations, candidate notices, bid definitions, cancellation, events, documents and submission handoff, their child-table rows, command-journal entries and attached files; and every such row whose Tender is already gone. Through `tenders.seeds.clear.clear_tender_fixture_rows`, run first, since a Tender consumes a Requisition's handoff. Tenders are not selected by namespace: the canonical Tender carries no `fixture_namespace` stamp. (Before v1.10 this row described the clear as namespace-based through a function that did not exist; in fact no clear step looked at Tenders, so a Tender left by an interrupted browser run survived every reseed.) |
| Leftover child rows and files | Child-table rows of any KenTender doctype whose parent record no longer exists, and files attached to a named KenTender record that no longer exists — computed last, after every other deletion. A module clean-up that deletes records directly leaves both behind and no screen can reach them again; on 26 September 2026 the dev site held about 49,000 such Requisitions rows, 749 Tenders rows, 43 Regulatory Reference rows and 1,734 files from deleted Tender documents. A file goes through its own document, so the stored file is removed unless another file record still shares it. This replaces the earlier Budget-only attachment sweep. |
| Regulatory Reference | Versions outside the `KT_STD_001_S8` namespace (isolation-year references from test fixtures), through the document's own `kt_fixture_purge` flag. |
| Legacy demo journeys | Every `Procurement Handoff Card` and `Procurement Journey` (the retired stable-platform Works demo). |
| Responsibility assignments | Rows outside the canonical namespaces (`KT_STD_001_S8`, `KENTENDER_MVP_V1`, `KENTENDER_MVP_1_R1_NDS`, `KENTENDER_MVP_1_R1_PLN`, `KENTENDER_MVP_1_R1_REQ`, `KENTENDER_MVP_1_R1_TND`, `str-chg-001-mvp1`; v1.9 and earlier listed `KENTENDER_MVP_1_R1_TPR`, which the code never used) or held by a fixture-domain user who is not in the §8.3 register. |
| Users | Accounts on a fixture e-mail domain (`@moh.example.test`, `@example.test`, `@test.local`, `@moh.test`, `@moe.test`, and since v1.3 the reserved `@example.com`, `@example.org` and `@example.net`) that are not in the §8.3 register (which includes the canonical Tenders service account `tender.inquiry.producer@moh.example.test`) — any user type, with their Contact, User Permission, User Scope Assignment and notification rows. |
| Organisation Units | Units that no canonical row points at (the root, the register's assignments, canonical Needs and Departmental Plans, and Budget Line Versions keep theirs, with ancestors), children before parents. |
| Fiscal Years | KenTender-created years other than 2026-2027 and 2027-2028 that nothing references any more (the isolation years test suites create) — recomputed fresh after every other deletion in the same clear, since a year can go from referenced to unreferenced as a side effect of them (its own Annual Plan or stray Budget going with it). |

### 3.2 Never touched

- A real person's account: any user on a non-fixture domain, whatever its name.
- ERPNext-owned records: Company, UOM, ERPNext `Budget`/`Cost Center` (KT-STD-001 §10; BUD-CHG-001 §18). Exception: `_Test Fiscal Year …` rows are ERPNext-owned but `wipe` purges them anyway as of v1.6 (§9) — they aren't rare, they're a side effect of routine `bench run-tests` and left unchecked they clutter every fiscal-year picker.
- The pre-cutover legacy reference doctypes owned by AUTH-ADR-001's removal phase RM-1xx: `Procuring Entity`, `Financial Year`, `PE Fiscal Year Context`, `Procuring Department`, `PE Type` (KT-STD-001 §10: legacy records go with the cutover, not with a module cleanup).
- Frappe Roles, Module Defs, Pages, Workspaces and other metadata.

## 4. Options

| Switch | Default | Effect |
|---|---|---|
| `through` / `THROUGH` | `requisitions` | Last stage to seed (`site`, `strategy`, `budget`, `needs`, `planning`, `requisitions`, `tenders`). Default stays `requisitions`; pass `THROUGH=tenders` explicitly for the full chain. |
| `reset` | `True` | Run the §3.1 clear before seeding. `False` seeds only. |
| `rebuild` | `False` | Also drop the canonical module rows before seeding — Tenders, then Requisitions, then Planning, then Needs, then Budget, then Strategy (downstream first, since each consumes the one before it) — and rebuild from scratch. Use it when a canonical record is wrong, not merely missing. Stages beyond `through` are cleared but not reseeded. |
| `wipe` | `False` | Drop the `site` stage too — the Procuring Entity, Organisation Units, Fiscal Years, Regulatory Reference, method/schedule rule profiles and the §8.3 actors themselves — then rebuild everything from nothing. Implies `rebuild` (the site stage is what every module stage's rows reference, so it is only ever safe to drop after they are already gone). This is the one option that deletes real user accounts (the register's own); it never touches a non-fixture account. Use it for a genuinely fresh canonical world, not a targeted correction — `rebuild` alone is enough when only a module's own rows drifted. As of v1.4 also unconditionally clears every row in Requisitions, Planning, Contact, Method/Schedule Profile, Regulatory Reference (+ Set), Delivery Location and Contact Office — not just rows the seed itself recognises as canonical or namespaced — since those doctypes were found accumulating orphaned rows from unrelated test suites that no selective clear could ever reach. |
| `reseed` | `None` → `not wipe` | Defaults to the opposite of `wipe`: a plain `reset`/`rebuild` (no `wipe`) still reseeds immediately, matching every call site from before this parameter existed. `wipe=True` alone (the common case) now means what the word says — clear everything and stop, no stage rebuilt, `through`/`validate` ignored: the actual "empty database, no data at all" mode, leaving the site in the same unconfigured state CFG-CHG-002 calls CONFIG-FIRST. Pass `reseed=True` explicitly (`RESEED=True` on the make target) alongside `wipe=True` for the old "wipe then immediately rebuild everything" behaviour. Exposed on `make seed-canonical` as `RESEED` since v1.4; default flipped in v1.5 after `wipe`'s old always-reseeds default kept silently repopulating the site on the exact command meant to empty it. |
| `validate` | `True` | Run §5 after seeding; a failure rolls the run back. |
| `force` | `False` | Bypass every fixture-build guard this run touches — this orchestrator's own (§1.1) and, for the duration of the run only, each module seed's independent `developer_mode`/`allow_tests` guard (`needs`/`planning`/`requisitions`/`tenders`; `tender_preparation` until its retirement), by setting `frappe.flags.in_test` rather than requiring `developer_mode` on the site. |
| `commit` | `True` | Commit at the end (tests pass `False`). |

## 5. Validation

`validate(through=…)` asserts the canonical facts for every stage up to `through` and raises listing every failed check. It is the definition of "the site is canonical":

- `site`: the site Procuring Entity is `PE-MOH`; exactly one root unit and exactly one unit per §8.2 name, four units in total; both site fiscal years exist and no other non-`_Test` fiscal year does; the funding source is Available; every §8.3 actor exists with the assignments `site_setup.ASSIGNMENTS` lists; **every unit-scoped role those assignments name has a holder in force at the moment of validation** — counting an ancestor unit's grant, since a grant reaches that unit's descendants — so a world whose only heads are expired or not yet started fails instead of validating; no fixture-domain account outside the register.
- `strategy`: exactly one plan in the `str-chg-001-mvp1` namespace with exactly one Active version.
- `budget`: `MOH-BUD-2027-001` is the only budget, on FY 2027-2028, with exactly one version (`MOH-BUD-2027-001-V1`, Active); `MOH-BL-DHI-2027` approved 100,000,000 and `MOH-BL-HWD-2027` approved 60,000,000 and Entity-wide; no Funding Reservation and no Procurement Commitment outside `KENTENDER_MVP_1_R1_REQ`.
- `needs`: exactly the four canonical Needs (`NDS-MOH-2027-0001..0004`), each in the exact state `departmental_needs.seeds.kentender_mvp_r1.NEEDS` declares.
- `planning`: the canonical FY 2027-2028 Annual Plan is Active. When `through="planning"` exactly, additionally the module's own `validate_planning_seed()` in full (2 items, KES 130,000,000, no actuals) — not re-asserted past `planning`, because `requisitions`/`tenders` legitimately advance this same Plan Item's schedule (see §2).
- `requisitions`: the module's own `validate_requisitions_seed()` (the combined item's Requisition Authorised, the exact §16.3 package, both drawdown lines).
- `tenders`: the module's own `validate_tenders_seed()` (one Tender on the handoff walked through the §13.3 primary lifecycle; the handoff consumed by it) — from TPR-CHG-001 v0.8 Phase 8. Since v0.12 it also checks that the original bid definition is Superseded and the addendum's successor Effective, that Afya Digital Supplies Limited is the one registered candidate, that the one supplier clarification is Answered to all registered candidates, and that one clarification notice and one addendum notice are Delivered.

Automated coverage: `bench --site <site> run-tests --app kentender_core --module kentender_core.tests.test_canonical_seed` (selection rules, dry-run safety, stage ladder, idempotent double run through Budget and through the full chain, validator failing closed on a stray budget, a fiscal year only unreferenced by the same clear pass, a stray Tender removed while the canonical one is kept, leftover child rows and files removed). The Tenders side of the clear is covered by `kentender_procurement.tenders.tests.test_seed_clear`. The test module uses `frappe.tests.IntegrationTestCase`; a `FrappeTestCase`-based module in `kentender_core` triggers Frappe's app-wide test-record preload, which fails on this site's overlapping Fiscal Years.

## 6. Adding the next module stage

When a module's canonical seed is cut over to the one-site model:

1. Append the stage name to `canonical.STAGES` after the stage it depends on, and add a branch in `canonical.seed()` that calls the module's own upsert with its canonical-only shape (no test edges, no isolated profiles, no commit).
2. Keep the module's canonical namespace in `canonical.CANONICAL_NAMESPACES` and make sure the module's rows are stamped with it; unstamped rows are treated as disposable by §3.1.
3. Extend `canonical.collect_non_canonical()` with the module's disposable-row rule, and `clear_canonical_modules()` with its canonical clear, in dependency order (downstream modules before the ones they reference).
4. Add the stage's facts to `canonical.validate()`.
5. Add the stage's actors to `site_setup.ACTORS`/`ASSIGNMENTS` if KT-STD-001 §8.3 lists them and no earlier stage seeds them; never create actors inside the module seed.
6. Extend `kentender_core.tests.test_canonical_seed`, run it, then run the full command on a dirtied site and confirm the dry run and the removal report match.
7. Update §2 and §3 of this document, the seeds README and the command card in `CLAUDE.md`.

Everything the module seed writes must go through the same commands the UI uses, as the named actors, never Administrator, and must be idempotent (KT-STD-001 §8.6; SEED-001 §8).

## 7. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `make: No rule to make target 'seed-canonical'` | Run from `apps/kentender_v1/`, not the bench root. |
| `Canonical seed refused: enable developer_mode…` | The site is not in developer mode; set `developer_mode` or `allow_canonical_seed` in `site_config.json`, or pass `"force": True` on the `bench execute` form. |
| `NameError: name 'true' is not defined` (or `'false'`) | `bench execute --kwargs` evaluates the string as a Python literal, not JSON — it needs `True`/`False`, capitalised, never lowercase `true`/`false`. Every example in this document uses the correct casing; a value copied from elsewhere (or typed from habit) is the usual cause. |
| `This site is configured as PE-XXX, not PE-MOH` | The seed never overwrites a different site identity (§8.6). Reconfigure the site deliberately, or use a different site. |
| Validation fails on "no non-canonical Fiscal Years" or "no fixture-domain users outside the register" | Something referenced the row so the clear skipped it (a year referenced by a Need, a user holding a canonical assignment). The dry run shows the plan; resolve the reference, then rerun. |
| `BUDGET_CONFIG_MISSING` from the Budget stage | The `site` stage did not complete (fiscal year or funding source absent). The whole run rolled back; read the earlier error. |
| Strategy stage `STRATEGY_CONFIG_MISSING` | Same — FY 2027-2028 is created by the `site` stage. |
| `NameError: name 'kentender_core' is not defined` (or another app's name) from `make seed-canonical`, usually on the run after a large clear | The background-job queue is full, not missing code. This bench runs no job worker by default; deletions enqueue background jobs, and past 500 queued jobs Frappe refuses every new one (`QueueOverloaded`). `bench execute` then hides the real error behind a `NameError` naming the app. Run `make ui-queue-check FIX=1` from the repository root, then rerun the seed. AGENTS.md §8.1 has the detail. |
| A Tender from an interrupted browser run is still there after a reseed | Fixed in v1.10: the clear now removes every Tender not on the canonical Requisition (§3.1). If one survives, it is a new regression. |
| Every Desk page load logs two console 404s afterwards | Unrelated to the seed: the dev server's socket.io long-poll and Frappe's sidebar divider image (see the Budget tracker, 2026-09-06). |
| `Required procurement rules or their calculation basis are missing or unverified` at the `submission` stage, with `wipe` or `rebuild` through `planning`/`requisitions`/`tender_preparation` | Closed as of v1.3 (Planning's own v1.23 work landed the missing verification step). If this recurs, it is a new regression, not the old known gap — report it rather than assuming `through=needs` is your only option. |
| `wipe` reports success and reseeds cleanly, but a stray account from before the run (e.g. `test@example.com`) is still on the site afterwards | Fixed in v1.3: `wipe`/`reset` only ever delete a user on a recognised fixture e-mail domain (`FIXTURE_EMAIL_DOMAINS` in `canonical.py`), by design, so a real person's login is never at risk — but the list previously missed the plain RFC 2606 placeholder domains (`example.com`/`.org`/`.net`) that a manually-created test account is likely to use. If a stray account still survives on a different, non-fixture domain, that is correct behaviour, not a bug — delete it by hand. |
| `make seed-canonical WIPE=True` has no effect, or `force`/`wipe` errors say the site is not in developer mode | Before v1.3, the `make seed-canonical` target never passed `wipe` or `force` through at all — only the raw `bench execute … canonical.run` form (§1) could reach them. `WIPE=True FORCE=True` are now plain make variables on the same target; make sure you're on v1.3 of this Makefile target, not typing `wipe`/`force` into `THROUGH` or expecting the bare command to pick them up. |
| `wipe`/`WIPE=True` runs clean, but Strategy/Budget/Needs/Planning/etc. all still show data afterwards | Was `reseed` defaulting to `True` regardless of `wipe` — every documented example through v1.4 reseeded the full chain right after clearing it. **Fixed in v1.5**: `wipe=True` alone now defaults `reseed` to `False`. If this still happens, you have `RESEED=True` set (or `"reseed": True` explicitly) — drop it for an empty database. |
| A wipe with `reseed=False` throws `That financial year does not exist` (masked as a `NameError` from `bench execute`) | Fixed in v1.4 — this was `wipe` not being idempotent when run twice with `reseed=False` back to back: Planning's own playwright teardown tried to reopen DPP intake on a Fiscal Year the first run had already deleted. If this recurs, it's a new regression, not the known v1.4 gap. |

---

- **`PLN_ITEM_SCOPE_LOCKED` or "already has an authorised Requisition" at the `requisitions` stage.** Since REQ-CHG-001 v1.11 an item's scope lock is permanent (REQ-CHG-001 §7.2), even after revocation, so an item once authorised by a Requisition that no longer exists cannot be reused by a plain reset. Run `make seed-canonical SITE=… REBUILD=True` once; `upsert_requisitions_base` and the §9 profiles restore the Planning namespace themselves when they find it locked, held or changed.

## 8. Relationship to other seed entry points

- `make seed-kentender-mvp-v1` (`kentender_core.seeds.kentender_mvp_v1.orchestrator`) is the earlier multi-PE-era pack: it still creates a second Procuring Entity and legacy personas through `org.py`/`users.py`. As of v1.1 every module through `tender_preparation` (since v1.7, `tenders`) has its own canonical stage in `make seed-canonical`, so this pack is no longer needed to reach any of them — its `departmental_needs`/`planning`/`requisitions`/`tender_preparation` result keys call the exact same module-owned upsert functions `seed-canonical` does, just behind the legacy `org`/`users`/`strategy`/`budget` stages this pack still seeds its own way. Do not run it on a site you have just made canonical unless you intend to reintroduce that data; `make seed-canonical` will remove the legacy personas again.
- `make ui-budget-fidelity-gate` and the module Playwright gates seed their own isolated fixtures (namespaced or on isolation fiscal years). They are disposable by design; `make seed-canonical` removes them.
- `bench execute kentender_core.seeds.site_setup.run` is the `site` stage alone, without a clear.

## 9. Requisitions demo profiles (REQ-CHG-001 v1.11 §16.4A)

Thirteen named, **mutually exclusive** states of the canonical world, each on the one eligible combined laptop item (`PPI-MOH-2027-002`), built through the same commands the screens call as the canonical actors. They are demo data for walkthroughs and persona testing; none is part of the canonical world, and loading one replaces the `requisitions` stage's base fixture until it is restored.

```bash
cd /home/midasuser/frappe-bench/apps/kentender_v1
make seed-req-profiles SITE=kentender.midas.com                                # list them
make seed-req-profile SITE=kentender.midas.com PROFILE=REQ-SC-SHARED-LINE-SHORT # load one (replaces any loaded one)
make seed-req-profile-restore SITE=kentender.midas.com                         # undo it; restore the base Authorised requisition
```

Underneath: `kentender_procurement.procurement_requisitions.seeds.profiles.load_profile(profile=…)`, `.list_profiles()`, `.restore_base()` (`bench execute`, same kwargs).

**How a load works.** Every load starts from a clean item: any profile hold, and the reservations of a requisition a stand-in Tender consumed, are released through Budget's own release command; every Requisition on the item is removed (an unconsumed authorisation is revoked through the real command first); and if the item is then scope-locked, held by a correction request, ineligible, failing a compatibility check, or has an open Plan update, the Planning namespace is rebuilt through this orchestrator (`clear_canonical_modules()` then `seed(through="planning")`). The profile is then built and recorded as loaded (global default `kt_req_loaded_profile`). `make seed-canonical` undoes a loaded profile first, through the same path, so a plain reseed after a demo is always safe.

**The report.** Each load prints `PROFILE_OK <name>` or `PROFILE_FAILED <name>`, one `[ok]`/`[FAIL]` line per §16.4A required result as actually observed, `look:` lines naming who to log in as and which route shows the state, and `limit:` lines stating what the canonical world cannot show. A `PROFILE_FAILED` load stays loaded for inspection but the command exits non-zero (`REQ_PROFILE_RESULT_MISSING`).
