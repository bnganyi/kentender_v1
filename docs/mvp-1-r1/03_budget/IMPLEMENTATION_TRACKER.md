## Tracker rules

1. Rows are permanent and use `Planned`, `In progress`, `Blocked`, `Done`.
2. `Done` requires the row's own evidence (a command, a test name, a diff, a described screenshot) — not "looks right."
3. If a touched file still references a concept §1.1 or §18 prohibits (`procuring_entity`/`procuring_entity_id`, `financial_year` as a fieldname, KenTender `Financial Year` as a Link target, `Budget Viewer`, `Budget Reviewer`, `Budget Authority`, `Budget Activation Authority`, `cost_center`, `erpnext.accounts` imports, `BUDGET_SCOPE_REQUIRED`, `BUDGET_PERMISSION_DENIED`, or any disposed concept from §1.1's register), the row that touches it is not `Done`.
4. No row may introduce an alias, redirect, dual-write, compatibility shim, or parallel legacy+new surface. If one appears, treat it as a defect in that row, not a valid completion.
5. §11 (Claude Design contract) governs visual/content fidelity only. §1–10 and §12–19 govern behaviour. A row implementing behaviour from §11 content instead of §12 is a defect, not a shortcut.
6. Deletion lands in the same phase as its replacement. "Delete later" is not a valid row state.
7. The DocType rename (Phase 2) and the ERPNext `Budget` restoration (Phase 3) are both first-of-their-kind operations with no in-repo precedent — a row in either phase claiming `Done` on "it looks like the other renames in this codebase" is not acceptable; cite the actual verification run.
8. A row claiming a cross-app file (`kentender_core`, `kentender_procurement`) is unaffected must cite the specific file:line checked, not assume from this tracker's own file-in-scope list.
