## 2. Current state: what already matches BUD-CHG-001 (verify before touching)

Before scoping removals, three load-bearing pieces of the current implementation independently arrived at conclusions BUD-CHG-001 now mandates — these should be **confirmed, not rebuilt**:

- **Baseline-registration posture already correct.** `Budget.registration_source` (Select, only option `Direct capture`), `authoritative_reference`, `approval_date`, `external_approved_total`, `approval_evidence` — this is exactly BUD-CHG-001 §1's "registers an already-authorized baseline" model, not a re-approval workflow. `register_budget()`'s own docstring: *"Create a Draft Budget via direct capture (BUD-FR-003–006). No lines."* Matches §9 BUD-FR-003–006 by name.
- **No re-approval language in the lifecycle actions.** The four lifecycle service functions are `submit_budget`, `return_budget`, `mark_budget_reviewed`, `activate_budget` — no `approve_budget` function exists anywhere. This already satisfies §5's "Budget approval → rename to baseline verification/activation" instruction; the underlying action names were seemingly never called "approval" in code, only in the older docs' prose.
- **The core arithmetic formula is already exactly right.** `Budget Line.validate()` computes `available = approved_amount - amount_reserved - amount_committed` — no separate subtraction of `amount_actual`. This is precisely BUD-CHG-001 §6.1's canonical formula (*"Line Available = Approved − Active Reservation Balance − Current Total Commitment... Actual is NOT subtracted again since it is already inside Commitment"*) and directly resolves problem-table row 4 in BUD-CHG-001 §2 ("no double-subtracted actual expenditure"). `Procurement Commitment.validate()` separately computes `outstanding_amount = max(0, current_amount - actual_expenditure)`, which is the correct, distinct "Outstanding Commitment" formula from the same section. **This does not mean the bug is fully absent** — §6 below flags that the Funding Performance / Check-Reserve read surfaces duplicate treatment-summary logic in two places, and whether either of them re-derives a *different* available/outstanding figure needs direct confirmation during implementation, not assumed clean from this DTO-level read.
- **No legacy PVO/"Plan Value Commitment" terminology survives.** Zero hits for "Public Value Objective" or "Plan Value Commitment" anywhere in the app. The codebase already uses "PVC" purely as an abbreviation for "Strategy Value Commitment" (matching Strategy's own post-cleanup terminology) — no rename work needed here, unlike Strategy's own Phase 1.
- **No `Allocation` doctype exists.** The legacy `Budget Allocation` doctype was already force-dropped by `patches/mvp1_teardown_drop_legacy_budget_doctypes.py`; only a single UI label ("Budget Allocation" as a section heading on the Check/Reserve line-picker) remains, with no backing doctype — a cosmetic label fix, not a data-model change.

## 4. Duplicated/contradictory API surface — `dia_budget_control.py`

Prior documentation (doc 05) lists `kentender_budget/api/dia_budget_control.py` as a file the MVP-1 preparatory teardown deleted. It exists live today with 10 whitelisted functions including `create_reservation`, `release_reservation`, `get_active_reservation_for_source`. Its module docstring — *"Budget control adapters for Demand/Planning — thin shims over MVP-1 contracts"* — strongly suggests this is a **legitimate post-teardown rebuild**, not a leftover violation (directly analogous to Strategy's own `demand_module_gate.py`, legitimately recreated mid-engagement as a clean existence-check utility). This audit does not treat its mere existence as a defect.

What *is* a genuine, concrete finding: **`dia_budget_control.py` does not delegate to the same named service-layer contracts `budget_api.py` re-exports.** `budget_api.py` is a pure pass-through over `services/*.py` (32 functions, one per service function, verified 1:1 in the inventory). `dia_budget_control.py` instead carries its own inline logic under different names (`create_reservation` vs. the services-layer `reserve_funding`; `release_reservation` here has no services-layer counterpart at all — see §5). Whether `create_reservation` internally calls `budget_check_reserve_contracts.reserve_funding()` or duplicates its validation independently was **not resolved by this audit** — it requires reading both function bodies directly, which is implementation-phase work, not audit work. Flagged as **high-priority to resolve first**, because if these are two independent code paths for the same mutation, that is a structural cause of exactly the kind of oversubscription/double-count risk BUD-CHG-001 §11 and §2 warn about, and BUD-CHG-001 §12's closing line — *"consumers must not import Budget DocType controllers or query Budget tables directly"* — reads most naturally as requiring exactly one contract implementation per operation, consumed from both the Desk UI and any downstream API adapter.

## 6. Stale requirement-ID citations — evidence of drift against an earlier spec

**Correction recorded during Phase 1 implementation (see `03_Budget_Cleanup_Tracker.md` BCL-101..105):** the UI-numbering half of this section's finding was too hasty. Direct evidence found during implementation (`test_budget_ui_stitch_layout_guard.py` actively asserting the registry maps `"BUD-UI-02"` to Funding Performance specifically) shows the `BUD-UI-XX` numbers are a deliberate, internally-consistent, already-tested internal convention of their own — not stale drift as characterized below. The `reserve_funding` docstring citation (`BUD-FR-062–066`) finding is unaffected by this correction and remains open for Phase 6.

Two independent, concrete signals show parts of the current code were built against a requirements/UI numbering scheme that predates BUD-CHG-001's final numbering, and were never updated when the spec was renumbered:

- `budget_check_reserve_contracts.reserve_funding()`'s own docstring cites **"BUD-FR-062–066."** BUD-CHG-001's actual functional requirements run **BUD-FR-001 through BUD-FR-030** — there is no BUD-FR-062. This function's cited authority does not exist in the current spec. Combined with its signature taking `demand_name` directly (not a Plan Item reference), this is a high-confidence — not yet fully confirmed — signal that `reserve_funding` currently reserves against Demand acceptance directly, which is exactly the pattern BUD-CHG-001 §2 row 2 ("no reservation at Departmental Need acceptance") and §9's BUD-FR-009/012 explicitly forbid: funding checks must occur only once a Plan Item is complete, one task before Requisition. **This needs a direct read of `reserve_funding`'s body before Phase work claims a defect** — it is possible the `demand_name` parameter is retained only for audit/correlation labeling and the actual gating check happens elsewhere (e.g. only ever called from a Plan-Item-complete trigger, never from Demand acceptance directly) — but the docstring's own stale citation is independent evidence this function was not written against BUD-CHG-001 and should not be assumed compliant.
- **UI screen numbering has drifted further and in more places.** BUD-CHG-001 §10 names exactly 10 screens, BUD-UI-01 through BUD-UI-10 (Workspace, Register Approved Budget, Budget Overview, Budget Lines, Baseline Verification, Finance Confirmation, Funding Activity, Budget Revision, Revision Review, Neutral Funding Record). The current code's own self-labeled docstrings/test-file names go **beyond UI-10**: `budget_funding_performance_contracts.py` labels itself `"BUD-UI-02"` (spec's UI-02 is *Register Approved Budget*, not Funding Performance); `budget_line_contracts.get_budget_line` labels itself `"BUD-UI-05"` (spec's UI-05 is *Baseline Verification*, not the Line Editor); `test_budget_readiness.py` labels itself `"BUD-UI-11"`; `test_budget_audit.py` labels itself `"BUD-UI-12"`; `test_budget_downstream_usage.py` labels itself `"BUD-UI-10"` (spec's actual UI-10 is *Neutral Funding Record*, not Downstream Usage). One case lines up cleanly by function even though the label differs: `test_budget_check_reserve.py`'s self-labeled `"BUD-UI-06 Check and Reserve"` matches spec UI-06's slot number even though spec calls the same screen *"Finance Confirmation"* — almost certainly the same screen, cosmetic label difference only. The Readiness/Review workflow (self-labeled UI-11) is very likely the same concept as spec's UI-05 *Baseline Verification* by function (Draft→Submitted→Active), just misnumbered. The Audit screen (self-labeled UI-12) is very likely spec's UI-10 *Neutral Funding Record* by function. Downstream Usage (self-labeled UI-10) has no clean slot in the new 10-screen list at all — BUD-CHG-001 §10's closing line, *"does not reproduce the legacy twelve-screen pack,"* suggests it should either fold into Budget Overview (UI-03) as a drill-down or drop from top-level workspace navigation rather than keep an independent top-level slot. **This full 13-route-to-10-screen mapping is a decision for the plan, not fully resolved here** — the audit's job is surfacing that the drift exists and is real, concrete, and traceable to specific files.

## 7. Fixture-naming reconciliation — the arithmetic substance already matches

Prior docs flagged an unresolved naming inconsistency across their own examples (`MOH-BUD-2027-2028` / `MOH-BUD-0001` / `KENTENDER_MVP_V1` / `MOH_MVP_V1`). Checking this against the *live* seed (`seeds/kentender_mvp_v1_portfolio.py`, module docstring *"KENTENDER_MVP_V1 portfolio seed — Contract v2.0 Budget fixtures"*) resolves most of that ambiguity in practice: `KENTENDER_MVP_V1` is the surviving name (the sibling `moh_mvp_v1_portfolio.py` is an explicit, single-purpose *"Deprecated shim — use kentender_mvp_v1_portfolio"* re-export, not a live second naming scheme).

What does **not** match BUD-CHG-001 §13's illustrative fixture codes is the reference-code *format*: the spec's example (`MOH-BUD-2027-001`, `MOH-BL-DHI-01`, `MOH-BL-CAP-01`) implies a fiscal-year-and-programme-coded reference, while the live seed produces `MOH-BUD-0002`, `MOH-BL-0003`, `MOH-BL-0004` — because these codes are not hardcoded fixture strings at all, they are generated at insert time by `budget_reference.py::allocate_budget_reference()` (`{PE}-BUD-####`) and `allocate_budget_line_reference()` (`{PE}-BL-####`), a live, sequential, auto-numbering service already used by every real (non-seed) Budget creation path too.

**The underlying financial substance BUD-CHG-001 §13.1 actually cares about is already present and matches almost exactly:** the live seed contains approved amounts of **480,000,000** and **80,000,000** on MoH lines — the exact two figures §13.1's canonical arithmetic fixture requires (480M approved → 455M reservation → 310M commitment → 145M remaining reservation → 25M available). Whether the seed's *reservation and commitment* amounts also hit the exact 455M/310M figures was not directly confirmed by the codebase inventory and must be checked directly during Phase work — but the presence of the two approved-amount anchors is strong evidence this fixture story was already built toward the same numbers BUD-CHG-001 later formalized.

**Judgment call, flagged for the plan (same precedent as Strategy Phase 4/8):** forcing the seed's auto-generated reference codes into the spec's illustrative fiscal-year-coded format would mean either hardcoding fixture-only reference strings (bypassing the live generator, inconsistent with every other Budget the generator produces) or redesigning the generator itself for every future Budget in the system — a disruptive change to a working, tested numbering scheme, justified only if BUD-CHG-001's illustrative codes are meant literally rather than illustratively. Recommend auditing-and-confirming the arithmetic substance (§13.1's dollar figures, PE/FY scoping, source-authority fields) rather than renaming working, tested reference codes to match an illustrative example — pending explicit product-owner confirmation if this reading is wrong.

## 9. Role-model gap (§8)

Current: `ROLE_VIEWER`("Budget Viewer")/`ROLE_OFFICER`("Budget Officer")/`ROLE_REVIEWER`("Budget Reviewer")/`ROLE_AUTHORITY`("Budget Authority")/`ROLE_AUDITOR`("Auditor") — 5 roles.

BUD-CHG-001 §8 names 9 actor rows, of which Budget genuinely owns: Budget Viewer/Auditor, Budget Officer, Budget Reviewer, **Budget Activation Authority**, **Finance Confirmation Officer**, **Revision Authority** (Accounting Officer, Procurement Planner/HoP, and System Administrator are external-to-Budget accountability/consumer roles, not new Budget-owned roles to create).

The single current `ROLE_AUTHORITY` already gates at least two, and structurally conflates, two of BUD-CHG-001's distinct capabilities: `budget_revision_contracts.py` gates **both** `reject_budget_revision`/`apply_budget_revision` (Revision Authority's job) **and**, via `budget_readiness_contracts.py`'s `_ACTIVATE_ROLES = (ROLE_AUTHORITY,)`, Budget activation itself (Budget Activation Authority's job) under the identical role string. Whether Finance Confirmation (the `check_funding`/`reserve_funding` gate) is also folded into `ROLE_AUTHORITY` or into `ROLE_OFFICER` was not directly confirmed by this audit's inventory pass and needs a direct read of the role-gating constants in `budget_check_reserve_contracts.py` before Phase work — that file's role constants were not captured in the inventory grep. This is a materially bigger structural gap than anything in Strategy's own Phase 5, which only had to remove a bypass, not split an already-real-but-too-coarse role into three separate capabilities used by three different high-consequence action families (activate a baseline, confirm/reserve funds, apply a revision).

## 11. Cross-module coupling assessment

**Already clean:** `hooks.py`'s `required_apps = ["kentender_core", "kentender_strategy"]` — correct, expected dependency (Budget Line's Strategy-reference fields need it). `Budget Line.validate()`'s Strategy resolution already imports through `kentender_strategy.services.strategy_consumer` (the STR-CHG-001 §12 contract layer) with a defensive `ImportError` fallback — consistent with, not in violation of, either module's contract discipline.

**No workspace-sidebar entry found** — like Strategy, Budget & Funding does not route through `kentender_procurement/workspace_sidebar/procurement.json`; nav is client-side via `budget_workspace_shell.js`'s hardcoded 7-tab list plus a `budget_funding_workspace_redirect.js` that redirects any navigation to the legacy `["Workspaces", "Budget Management"]` placeholder workspace (itself created only by the teardown patch, as a link-preservation stub) back to `budget-funding`. ## 12. Summary of what this audit changes about scope

Unlike Strategy's "already shipped, needs surgical correction" posture, Budget & Funding's audit surfaces a module that is **partially built against a since-superseded spec**, with three distinct kinds of gap that need different treatment in the plan:

1. **Confirmed-clean, do-not-touch:** the baseline-registration model, the core arithmetic formula, the absence of legacy PVO/Allocation terminology (§2).
2. **Real, well-scoped mechanical corrections:** the value-treatment removal (§3, larger than Strategy's PVO removal but the same shape of work), the Administrator/PE-MOH fallback removal (§8, smaller and more surgical than Strategy's equivalent), fixture-naming reconciliation (§7, resolves to "confirm substance, don't rename working codes").
3. **Genuine new construction, not renames:** 6 of BUD-CHG-001's 11 named integration contracts have no service-layer implementation at all (§5) — this is the largest single lift in the whole change unit, exceeding Strategy's own §12 phase. The role-model split (§9) and the `demand_name`-coupled reservation flow (§6) are the two highest-uncertainty findings and should be resolved *early* in implementation, since several other phases (contracts, seed verification) depend on knowing their actual answer rather than this audit's necessarily-incomplete read.

The plan that follows sequences these three categories so confirmed-clean items are verified (not rebuilt) early, the high-uncertainty findings (§4, §6, §9) are resolved before the phases that depend on their answers, and the large new-construction phase (§12 contracts) comes only after the terminology/role/fallback corrections it will otherwise have to redo.
