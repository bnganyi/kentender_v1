## Tracker rules

1. Rows are permanent and use `Planned`, `In progress`, `Blocked`, `Done`.
2. `Done` requires the row's own evidence (a command, a test name, a diff, a screenshot description) — not "looks right."
3. If a touched file still imports, calls, or reads `kentender_procurement.std_engine.*` directly (as opposed to going through a published Phase 5/7 STD-CHG-001 contract), the row that touches it is not Done — this is the equivalent of Strategy's "no forbidden concept survives" rule, scoped to this module's own retirement target (plan §1, §3.1).
4. No row may introduce a new alias, redirect, dual-write, compatibility shim, or parallel legacy+new maintenance path for anything `std_engine`/`tender_management`'s STD desk pages own today, except the deliberate, time-boxed coexistence window described in plan §5 item 2 — and that window must close in Phase 12/13, not be left open.
5. A row that reuses `std_engine`'s already-extracted `KE-PPRA-IT-2022-04` content must go through the §17 `STDAssistanceBatch` proposal-and-accept path (Phase 10) — never a direct copy into an Active package or a Draft record bypassing review.
6. Every save/command row must state which §13.3 error code(s) it implements or explicitly note none apply.
7. A PCFG-area row is not `Done` on a passing area-save test alone if the spec's §11 coverage/validation checklist has an item for that area still unresolved — cross-check against the Phase 6 coverage/validation work before closing.

**Retroactive fix made during Phase 3 (documented here since it changes this phase's own STD-106/STD-107 shape, not silently backfilled into the rows above):** `STD Cfg Content Block` was originally scoped only to `section_id` (i.e. shared package-wide, identical across every Version). Building Phase 3's `CreateNextSTDDraft` content-copy logic surfaced that this was wrong against the spec's own §6.2 ("Only changed locked blocks... are amended" across a revision implies content *does* differ per Version) — a package-wide-shared content block can never actually change between STD revisions, contradicting the entire point of Section II's wording being able to differ between Version 1 and Version 2. Fixed by adding the same `reference_doctype`/`reference_name` Dynamic Link "owning Draft or Version" shape Phase 2's schemas already use; `STD Cfg Section` itself (the stable structural container — 13 required sections, coverage-area numbers) correctly stays package-scoped, since the document's *shape* doesn't change between revisions, only its *content*. `display_order` uniqueness is now scoped to `(section_id, reference_doctype, reference_name)` rather than `section_id` alone. All 11 Phase 1 tests updated to attach content blocks to a Draft and re-verified green (26/26 combined with Phase 2, zero regressions) before Phase 3 work continued.

**Second retroactive fix made during Phase 3, same root cause:** `validate_std_cfg_draft`'s "one open Draft maximum" guard originally queried `STD Cfg Draft.state IN (Draft, In review, Returned)` directly. This is a real bug, not just a style issue — `STD Cfg Draft.state`'s 3-value enum (§7.2) has no terminal state an activated Draft moves to, so once a package's first Draft reached "In review" and was activated, this guard would have permanently refused that package a second Draft forever (the old "In review" row would match the query eternally). Fixed by switching the guard's source of truth to `STD Cfg Package.current_draft_id` — the field the domain model itself names for exactly this purpose ("One open Draft maximum," §7.1) — set automatically by a new `STD Cfg Draft.after_insert()` hook (a thin local invariant, not orchestration) and cleared by Phase 3's `activate_package()` service function on activation. `test_one_open_draft_per_package` (Phase 1) still exercises the *symptom* correctly; a new Phase 3 test (`test_new_draft_allowed_after_activation`) exercises the specific scenario the old guard would have gotten wrong.
