## 1. Governing approach

This is new construction on a genuinely new architecture surface — public/external identity, a self-service supplier portal, sealed tender-box custody, licensed digital signature — landing in a repository whose default construction pattern (Vue-in-Desk, internal `User Responsibility Assignment`) does not fit that surface, combined with a **bounded** retirement of an unrelated, disconnected legacy bid-submission implementation that happens to occupy the same problem space. Per `feedback-rebuild-vs-patch-threshold`, this is not a "rebuild" of the legacy `tender_configurations`/TM2 code — none of its concepts (Stitch design, "any logged-in user" identity, an IT-sector-only `Tender Configuration` record) are being carried forward or refactored. It is new work that must retire a predecessor as a side effect, the shape Tenders v0.8 followed for Tender Preparation, applied here to a smaller, better-isolated slice.

AGENTS.md §6 states the default Vue-in-Desk construction standard and separately carves out the exception this module lives in: *"Public supplier/bidder experiences: a dedicated frontend, per existing convention."* This plan's research confirms no such convention currently exists in a finished, current form (§2, §4 D3) — BDS-CHG-001 is the module that establishes it, not one that can port an existing pattern.

**Order of work** follows the spec's own §15.1 order where it maps onto this repository's layering: identity/authorisation foundations before anything that depends on them; the STD-to-bid publication pipeline before any bidder-facing preparation screen; preparation before submission; submission before replacement/withdrawal/close; every service phase before its own UI slice. Phases 2–7 are horizontal (Python only, TDD per behaviour, no portal/product code). Phase 8 is vertical per board — API adapter → screen → live browser check → fidelity assertion — per `feedback-rebuild-phase-sequencing`.

**Done means** the spec's own §13.3 primary lifecycle completes in a browser as real actors, in a labelled test environment, using the seed's own Test Trust Service and Test Tender Box simulations: Mary Wanjiku and David Ouma register and verify Afya Digital Supplies Limited; David starts the bid and completes the five tasks; the Tender owner issues an addendum and David acknowledges it; Charles Mutiso records the physical tender-security receipt without seeing bid content; Mary reviews, signs and submits — the bid is deposited, sealed and receipted; the submission period closes on schedule and one immutable Bid Opening handoff exists containing no bid content. Every §13.4 isolated fixture (20 named profiles) is proven in the test world. **"Done" explicitly excludes an enabled production `Submit bid`** — spec §5.10/§15.4/§18.5 keep that disabled regardless of code completeness until the Project Owner approves a real operating profile (trust service, custody service, State Portal semantics, legal basis). This is purely a deployment-time fact, not a build-process gate: nothing about designing, building, or testing this module is blocked or slowed by it. The only engineering consequence is that the signature and custody code is written against a swappable interface with a test double (D6) — which is simply how any external integration is written, spec or no spec — plus one off-by-default flag (D15) checked in a single place. This plan's own completion claim states the scoping honestly rather than treating §5.10 as an ordinary acceptance criterion to "pass."

Non-negotiables inherited from AGENTS.md: business rules in services, never in client code, on both the internal Desk slice and the portal; every command re-checks responsibility/authority/state/record version server-side; no `frappe.db.commit()` in request services; the internal Desk slice (BDS-DES-15) is Industry-only, boards ported class-for-class, machine-enforced fidelity gate; the portal reuses the same `kt_industry_tokens.css` design tokens the Desk pages use (confirmed — the design board uses the identical `_ds/kentender-industry-…` bundle) even though it is not Desk-hosted; portal calls never surface a raw Frappe Message dialog for user-correctable input — inline errors only; every test module registers a purge; cross-app access goes through an explicit owned service, never a deep import (`kentender_suppliers` ↔ `kentender_procurement.bid_submission` ↔ `kentender_procurement.tenders` each stay behind a gateway module, the same shape Tenders already uses for its own REQ/PLN/CFG boundaries).

## 2. Baseline facts (verified 21 September 2026)

- **Two disconnected legacy bid-submission systems live today**, neither referencing the dropped Tender Preparation doctypes, neither integrating with the new `Tenders` module: `tender_configurations` (Stitch design system, `Electronic Bid Submission`/`IT Bid Opening Record`/`Electronic Bid Audit Event` doctypes, ~90 whitelisted APIs, a real seal/receipt/opening/withdrawal state machine, IT-sector scope only, wired live via `hooks.py` `page_js`, `app_include_js`, and a 20+ route `website_route_rules` tree under `/tenders/<publication_ref>/…`) and `tender_management`/"TM2" (`tm2_bid_*` doctypes filed under the base `Kentender Procurement` module, package itself absent from `modules.txt`, one live route `/supplier/tenders/<code>`, no cross-app dependents).
- **A real cross-app dependent exists**: `kentender_core/kentender_core/seeds/demo_platform_seed/{transitions,actionable}.py` imports directly from `kentender_procurement.tender_configurations.services.bid_submissions` to build and smoke-probe demo "sealed bid → opening" scenarios. This is architecturally backwards versus the repo's own dependency direction and must be replaced or safely stubbed in Phase 1, not silently broken.
- **The `Bid Opening` Workspace tile is a placeholder stub** ("This lifecycle step is not implemented yet… reserved for the G0-012 spine") that does not even link to the working legacy `bid-submissions` Page — today's officer discovery path to bid handling is already broken independent of this cycle.
- **The `Tenders` module (TPR-CHG-001 v0.8) has no candidate/bidder registry at all** — `services/candidate_gateway.py` does not exist and `kt_tender_candidate_registry` is not referenced anywhere in the repo. The one bidder-adjacent mechanism, `services/inquiries.py`, authenticates a single shared service **User** carrying the `Tender Inquiry Producer` role, which asserts an unverified free-text `candidate_identity` string — a gateway pattern to reuse (D9), not a registry to extend.
- **`Tender Submission Handoff` exists, is immutable, and is currently in-process-only and unredacted.** `submission_close.py`'s `get_submission_handoff()` is not `@frappe.whitelist()`'d, has no Guest-safe wrapper, and returns the full internal payload (digests, `template_release_id`, `rule_snapshot_id`) — unsafe to serve directly to a bidder. The module's own docstring already names `TenderSubmissionPeriodEnded`'s `consumer="bid-submission"` and states this consumer "does not exist in this release" — BDS-CHG-001 is that consumer.
- **`kentender_suppliers` has a real, User-linked identity model but no portal.** `KTSM Supplier Profile.external_user` links to a Frappe `User` (created as a Website User via `_ensure_website_user_for_registration`); `smw_public.py`'s `ktsm_register(...)` is a genuine `allow_guest=True` public endpoint; a real per-user ownership check (`external_user == frappe.session.user`) already exists. But this model is qualification/eligibility-oriented (`eligibility.check_supplier_eligibility`), `templates/pages/` is empty (no rendered portal page exists), and it has never been connected to Tenders or any bid flow.
- **No settled public-frontend convention exists repo-wide.** The only `www/` folder in the repository is `kentender_procurement/kentender_procurement/www` (legacy, retiring). `website_user_home_page` and `role_permissions … Guest` return zero hits repo-wide; the universal external-actor gate everywhere today is `_require_login()` — "any logged-in Frappe user," not a dedicated supplier identity check.
- **`business_role_registry.py` has no "Bidder"/"Supplier" entry**, and its scope model supports only `Site-wide` and `Organisation Unit` — no representation for an external actor.
- **The canonical seed `STAGES` tuple ends at `("site", "strategy", "budget", "needs", "planning", "requisitions", "tenders")`** — no bid-submission stage exists yet.
- **Verified: the `IT-EQUIPMENT-OPEN-V1` template bundle (STD-TPL-001, release 1.1) is a document-rendering system only — it does not contain the structured response/evaluation/contract-mapping layer this plan needs**, and neither does STD-TPL-001's own spec text at any approved version to date (checked directly — v0.6 §9-10 describe evaluation/contract treatment at a policy/prose level only, "no weighted scoring screen and no criterion builder," never as a structured per-row register). This is a **genuinely separate, independently-owned piece of work** — not something BDS-CHG-001 authors itself. It is now tracked entirely inside STD-TPL-001's own plan/tracker as a proposed "Version 1.2 delta," gated on the document owner authorising a spec revision (`STD-TPL-001_IMPLEMENTATION_TRACKER.md`, gate `TPL-G08`, currently `Blocked — owner`). A complete draft of the needed content exists as input for that decision: `docs/mvp-1-r1/07_std_configuration/STD-TPL-001_Bid_Response_Definition_Proposal_IT-EQUIPMENT-OPEN-V1.md`, authored directly from the approved bundle's own source. **BDS-CHG-001's Phase 3 depends on this delta shipping — it does not own, build, or track the work itself** (D7/D20, revised). Tenders' own tracker separately shows the unrelated `TPL-G07` gate open (the already-complete Version 1.1 delta, awaiting only sign-off) — a different item, not to be confused with `TPL-G08`.
- **Design board anomaly**: `kt-notice is-info` is used 9× on the board with no matching CSS rule (falls back to the plain `.kt-notice` look) — a genuine tokens/structure defect, not placeholder data; needs a fix in `kt_industry_tokens.css` or an explicit decision to leave the fallback, before Phase 8 treats the board as literal.
- **Route-naming note**: the spec's own §9/§10.1 give the one internal screen's route as `/desk/tender-security-receipts`; this bench's actual Frappe routing prefix is `/app/…` (confirmed against every existing module) — built as `/app/tender-security-receipts` (C8).
