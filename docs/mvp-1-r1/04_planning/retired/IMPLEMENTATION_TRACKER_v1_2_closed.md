## Tracker rules

1. Rows are permanent. Vocabulary: `Planned` / `In progress` / `Blocked` / `Done`. Reversed decisions are struck through in place, never deleted.
2. `Done` requires the row's **own** evidence in its Evidence cell — a command with its result counts, a named test, a diff, or a described browser observation with the literal rendered strings. "Looks right" is not evidence. Never record a result that was not actually observed.
3. A row that touches a file still referencing a spec-prohibited concept is not `Done`. Prohibited here: Demands (any import, doctype read or fixture), Value Commitment / `pvc_snapshot`, recommended method / method basis, lotting, contract-period/multi-year fields, preference/reservation scheme, actual-milestone entry, readiness score, capability store / Operational Scope Assignment / core `Workflow Task` for Planning decisions, Stitch markup or `kt-stitch-*` tokens, `kt_cl_surface_registry.js` entries for Planning, sidebar work-queue entries, browser-stored context as authority, legacy routes/aliases/dual-writes.
4. **Deletion lands in the same phase as its replacement.** "Delete later" is not a valid row state; the legacy surface a slice replaces dies inside that slice's phase.
5. §11 of the authority governs visual fidelity only. Implementing behaviour from artboard content instead of §12 is a defect. Screens are built from the `.dc.html` artboard's markup class-for-class, not from the prose spec or memory of sibling screens.
6. Slice gates (PLN-G03..G10) close only on browser evidence: per-role logins (each §6 actor the slice serves plus one out-of-scope actor), first paint **and** one interactive re-render, absence assertions on refusal paths, zero page-specific console errors. Component tests (D9) and request-shaped endpoint tests are gate conditions, not substitutes for this.
7. Static/architecture guards are `Done` only when verified by planting a violation.
8. Playwright spec files each own their own fixture Procuring Entity; fixture instants are pinned, never `now`-relative; fixture resets clear actor context preferences.
9. Diagnosis follows the §16.2 ladder; a full-suite run is never the first diagnostic step.

## Headline findings (read before touching code)

1. The live module implements a superseded product: Demand-sourced consolidation, professional-review approval chain, Stitch UI, capability permissions. Its nav entry is parked at `coming-soon` (`setup/sidebar_availability.py:29-32`); its `api.py` was import-dead until CTX-CHG-001 Phase E. CTX-FU-03 (Demand-based Planning tests/Playwright) is closed by this rebuild.
2. The DPP aggregate (§4.1–§4.6) has no existing counterpart at all. `Plan Need Allocation` is the nearest thing and sits at the wrong layer.
3. Needs' side of §7.1 is **already done**: `DepartmentalNeedAccepted.v2` exists at exactly that version with exactly the six-facts payload; there was never a `.v1`. Superseded/Withdrawn are published but have **no consumer**; `NeedPlanningUsageChanged.v1` has a receiver (`project_need_planning_usage`) and **no publisher** — both are net-new Planning work.
4. Budget's reservation states already match §4.11 exactly (`Funding Reservation.status` incl. `Needs Attention`, `remaining_amount`, `plan_source_allocation` link). The gaps are on the Planning side: no `list_eligible_budget_lines` caller (direct table reads instead), release via the legacy `dia_budget_control` adapter (full-remainder only, synthetic idempotency key), no `revalidate_reservations` caller, reservation refs persisted onto the deleted `Demand Funding Allocation` doctype.
5. `check_funding` returns a token cached for **300 seconds**; `reserve_funding` consumes it all-or-none under row locks. The Finance confirmation command must be designed around that TTL.
6. The NDS retrospective's defect classes are standing gate conditions here (tracker rules 6–8): request-shaped endpoint tests (NDS-914), per-role browser logins (NDS-911/912), read-offer-vs-command assertions (NDS-807), seed-persona browser pass, pinned fixture instants, planted-violation guard proof.
7. Slug landmines: DocType `Procurement Plan Item` owns `procurement-plan-item` today; Workspace "Procurement Planning" relates to `/app/procurement-planning`; Page module "Procurement Planning" is a real Module Def, so 3-segment routes trigger Frappe's auto-sidebar swap (NDS boot-key/setup-skip mitigation applies).
8. `docs/mvp-1-r1/04_planning/design/` carries two `_ds` bundles; the PLN artboards reference `kentender-industry-82d82607-…`. The orphan is resolved in Phase 0.
9. **Test base class matters in this app:** deriving from legacy `frappe.tests.utils.FrappeTestCase` routes the runner through a compat preparation that imports *every* `test_*.py` in the whole app — so any stale import anywhere in kentender_procurement kills the run. Use `frappe.tests.IntegrationTestCase` (the NDS convention). Two such stale imports were fixed in Phase 1 (PLN-114); more may lurk in unrelated modules — fix them only when they block, and record each.
10. `frappe.delete_doc("DocType", …, force=True, delete_permanently=True)` does **not** reliably drop the backing table — `tabProcurement Plan` survived the doctype delete. Always follow with `drop table if exists` (the drop patch now does).
11. `kentender_strategy.services.strategy_consumer.resolve_strategy_context`'s own docstring promised its `primary_plan` carried the Active Version id "from resolve_strategy_context" for `list_strategy_objectives`/`create_strategy_snapshot` to consume — the return value never actually included it (only the Strategic Plan *root* id). Zero-covered by kentender_strategy's own tests (which only assert the error paths); found live the first time Planning's Phase 6 actually called the gateway against real data. Fixed at the source (additive `version_id` key); Planning's `strategy_gateway.py` updated to read it.
12. A plain composite DB unique cannot express "released rows don't block re-formation" (§4.10) on MariaDB — there is no partial/filtered unique index. Phase 1's `pln_uniq_entry_per_version` on `(plan_version, dpp_entry)` silently violated this invariant from the day it shipped; found live by Phase 6's dissolve-then-re-form test. Dropped; the Annual Plan Version row lock `FormPlanItems` already takes covers the same correctness guarantee without the false constraint (see PLN-606).
13. A Page doctype's fixture sync compares the JSON file's `modified` timestamp against the DB row's before re-importing — editing a Page's `roles` list without bumping `modified` leaves the stale role list live through a `bench migrate`, with no error or warning. Two new Pages' roles needed a second, deliberately-bumped `modified` before the fix actually took effect on the site (PLN-609).
14. Budget's published `list_eligible_budget_lines`/Strategy's `list_strategy_objectives` contracts expose only an internal `id` (a hash autoname) and a free-text `title` — neither publishes a human business reference (Budget Line's own `generated_reference`, e.g. `BL-PLNT-0001`, exists but is never returned). Every screen that displays a Budget Line or Strategic Objective by "id" therefore shows the raw hash; PLN-DES-09's own fixture text ("OBJ-MOH-2023-001 —…", "MOH-BL-DHI-2027") assumed a business code neither contract actually carries. Planning's own Strategic Objective label was fixed to drop the hash entirely (finding 11's fix, present title only); the Budget Line case is cross-cutting (also affects the Phase 4 DPP screens, not only Phase 6) and is deferred to FOLLOW_UPS.md at Phase 12 rather than patched narrowly here.
15. Budget's `check_funding`/`reserve_funding` (§7.3's Finance boundary) run their own internal capability check requiring a `Finance Confirmation Officer` role — a Budget-side vocabulary distinct from Planning's own `Budget Officer` role that `RequestFinanceConfirmation`/`ConfirmFunding` already authorise against. Uncaught, a correctly-authorised Planning Budget Officer would be refused by Budget's own gate. `budget_gateway.check_funding`/`reserve_funding` now run as a system principal, exactly like `list_eligible_budget_lines` already does, for the same documented reason.
16. `frappe.throw(msg, exc, title=...)` never attaches `title` to the raised exception instance (`frappe/utils/messages.py` — `title` only labels the client-facing dialog); a Python caller in the same process gets no structured error code back from a sibling app's contract, only the message text. `ConfirmFunding` matches on Budget's exact "Insufficient funding" substring to distinguish a shortfall from every other reservation failure — coupled to Budget's wording, the best signal available without a published error-code contract.
17. A Playwright fixture reset that only wipes rows reachable by joining through the CURRENT parent chain (e.g. `Plan Reservation Reference` filtered by `plan_item IN (existing Annual Plan Item rows)`) misses a reservation whose parent item a PRIOR reset already deleted — the orphan survives indefinitely and a real Budget `Funding Reservation` behind it keeps reducing "Available" on every later run of the same Budget Line, eventually turning a sufficient-funding spec into a flaky shortfall. `_wipe_pe` now scopes this cleanup by the stable `plan_item_id` business-reference prefix instead, which stays findable after its parent row is gone.
18. MVP-1 has no dedicated statutory-jurisdiction-routing table for §4.12's "resolved from governed PE data" — `Procuring Entity.entity_type` is the one governed field that actually distinguishes a Ministry from a County Government from a State Corporation, so Phase 8's capacity resolution reads it directly rather than inventing a new configuration doctype. Recorded as a modelling decision, not a gap: if a future revision needs finer-grained jurisdiction routing (e.g. two Ministries with different statutory authorities), a real table replaces this function's body without changing its callers.
19. Python `IntegrationTestCase` tests and Playwright fixture resets in this rebuild share ONE live dev site, never an isolated per-run database — an unscoped `frappe.db.count("Plan Reservation Reference")` in a Phase 7 test passed for weeks and then failed the moment enough Playwright Finance/Governance fixture runs left real reservation rows sitting in the same table from a DIFFERENT PE. Every count/exists assertion in this module must filter by `fixture_namespace` or the test's own PE-prefixed business reference; a bare count is a latent flake, not a working assertion, on this test topology.
20. `plan_workbench._item_doc_name`/`plan_read.get_plan_item` resolved a Plan Item's business id with a bare `frappe.db.get_value("Annual Plan Item", {"plan_item_id": …})` — correct through Phase 8, where at most one live document ever carried a given id. Phase 9's BeginPlanUpdate legitimately creates a second one (the Draft successor's copy of a carried-over item, invariant 22), and the bare filter then returns whichever row the database happens to return first — observed live as the Active predecessor's own frozen copy, so `RemovePlanItemInSuccessor` and any edit inside the new Draft successor would silently operate on (or refuse against) the wrong Version's document. Fixed with `plan_read.resolve_item_doc_name`: prefer the Annual Plan's open successor when two rows exist, the same precedence `_open_version` already uses for the Plan itself; every command-layer caller now goes through it.
21. `references.publication_reference(plan_reference, attempt_number)` scoped its counter per-Version but its string per-Plan — a Version's own first publication attempt and its predecessor's first attempt both compute to `attempt 1` against the identical Plan reference, so activating a second Version ever (BeginPlanUpdate's whole purpose) raised a `DuplicateEntryError` on the very first `PublishAnnualPlan` call. No phase before this one ever activated a second Version of the same Plan. Fixed by keying the reference off the Version's own reference instead of the Plan's.
22. `cancel_plan_update`'s "which reservations does only this successor hold" check called `frappe.get_all(..., pluck="reservation")` — which already returns bare values, not row objects — and then indexed `.reservation` on each one, an `AttributeError` on CancelPlanUpdate's first real invocation. No caller of this command existed before this phase's own tests. Fixed.
23. `needs_intake.current_accepted_sources` indexed `event["payload"]` on `current_accepted_events`'s return value, but that function already returns the decoded §7.1 payload dicts directly — confirmed by its other real caller (`procurement_home/services/home_pipeline.py`, whose own loop variable is named `payload`) and by NDS's own test. Every DPP command test in this whole rebuild had mocked `current_accepted_sources` to an empty list since Phase 6, so a genuine Need-origin DPP entry had never actually been intaken for real until this phase's cross-app test called the real function — a `KeyError` on first contact. Fixed; the projected entry, its funding, its Plan Item and its Active-Plan usage event now round-trip correctly against a real accepted Need.
24. `_activate_version`'s reservation-release bookkeeping stamped `release_reference`/`release_correlation` only onto the successor's own copy of a shared `Plan Reservation Reference`, leaving the now-Superseded predecessor's own separate reference row to the identical, already-released reservation permanently unmarked — a silent audit-trail inconsistency (the underlying Budget reservation genuinely was released; only its Planning-side history disagreed). Fixed: every reference row naming a released reservation, predecessor's and successor's alike, is now stamped from one shared release call per distinct reservation.
25. A Phase 6-vintage D1/D5 boundary violation: `plan_read.get_plan_item` and `dpp_read.py`'s entry projection both read `Departmental Need Version.version_number` directly via `frappe.db.get_value`, bypassing the published-contract boundary the Phase 2 AST guard (`test_departmental_needs_architecture`) exists to enforce. It went undetected because no phase's own regression pass between Phase 2 and Phase 9 actually ran that test module — this phase's first full cross-app regression was the first to.
