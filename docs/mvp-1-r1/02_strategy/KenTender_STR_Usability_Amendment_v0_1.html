Build the strategy. Review the changes.

Usability amendment v0.1 · 13 September 2026
Proposed for Project Owner review.

Strategy needs a focused usability revamp. The main work should be clear to an Author and a decision-maker without learning the system’s hierarchy, version and validation mechanisms first.

Keep the existing Strategy Author → Strategy Approver governance. Preserve typed strategy structure, immediate activation, immutable Active versions and historical procurement snapshots. This proposal changes presentation and task handling; it adds no approval stage or performance-management workflow.

1. What needs to change

The reviewed baseline is STR-CHG-001 v1.7, marked Approved on 3 September 2026. This is a requirements and screen-contract review, not a review of running code or evidence from user testing. The established Planning and Departmental Needs usability direction supplies the reading standard: meaningful tasks first, concise supporting detail, full evidence available and authority preserved.

3. Make authoring direct and predictable

Start with plan identity once

Use Create strategic plan, followed by Plan title, Plan type, Start date and End date. Map Main strategic plan to Primary and Supporting framework to Supporting Framework. Only the latter reveals Main plan, the existing required eligible parent. Explain it in one line: A supporting framework sits under a main strategic plan. These are labels for existing fields and enums, not new classifications.

The primary action is Create plan and add objectives; Cancel creates nothing. Save the identity and first Draft through the existing command, then open its structure editor. This is a useful boundary because the structure needs a persisted plan identity. Do not add a wizard, show an empty “Not assigned” reference field or ask for the first version’s dates twice. If saving succeeds but navigation fails, reopen that same Draft; an unknown save outcome must be resolved before attempting another creation.

Edit structure without administering records

Keep the navigable hierarchy beside one selected-item editor on a wide screen; stack them with a clear return to the selected item on a narrow screen. Show short, meaningful action labels at the correct place. A Programme offers Add objective and Add sub-programme; only the Sub-programme layer is optional under the current hierarchy rule. Never automatically flatten or insert a layer.

Move up and Move down replace the editable Display order input. They reorder siblings through the existing validated command and have keyboard equivalents. Replace Delete node with the actual item type, such as Delete objective. Show descendants and why deletion is blocked; no new cascade-delete shortcut and no deletion after first submission.

For structure editing, one page-level Save changes saves the accumulated validated structure change set. The selected-item card has no second competing Save. Submit for approval saves pending valid edits before submitting the confirmed version. If separate existing commands are needed, partial success is explicit: Your changes were saved, but the plan was not submitted. A stale tree is never overwritten, an unresolved retry creates no duplicate version/task, and permissions are rechecked. Plan-identity edits remain a separately scoped existing command; the full successor must specify the exact token and response sequencing rather than claim cross-command atomicity.

4. Put the decision first

For a successor, open Review plan changes with the server-calculated comparison. Show changed objectives, indicators, definitions, targets and effective dates, including additions and removals. Retain the full proposed content under Proposed plan and the exact record under Submission and history. Existing Overview, Structure, Changes and History routes/tabs remain reachable with their exact submitted-version binding. The opening summary brings useful information together; it creates no new approval record.

For a first plan, use Review strategic plan, show the complete proposed strategy with readable navigation and definitions, and omit an empty predecessor comparison. Do not require a decision-maker to open every tab, expand every item, download a file or tick a review checklist. All content remains available; material errors are never hidden in supporting detail.

Replace green technical readiness rows with specific actionable issues when checks fail. Do not hide a conflict behind an apparently ready header. Validity checks continue server-side at submit and approval; removing their visual checklist removes none of them. Do not raise minimum completeness from the existing at-least-one Objective, Indicator and Target rule to an invented requirement for every branch.

5. Supporting detail, status and recovery

For the current plan, lead with the plan name, Current, its period, objectives and targets. Show approval actor/time and exact version under Approval details. Put structure counts and technical references in secondary detail, not the first screen. Indicators and targets express intended results; they never become achieved-result figures or progress charts.

A pending update does not replace the current plan: show Update awaiting Strategy Approver review. The current plan remains in use. A returned Draft shows Changes requested, the full reviewer comment and Correct and resubmit. Historical routes stay pinned to their exact version, with a separate permitted link to the current plan. Consumer snapshots remain historical evidence and are not silently refreshed.

7. A short usability check before implementation

Use these tasks without explaining the intended button names. Record completion, wrong turns, hesitation, requests for help and the participant’s explanation of what happened. These sketches have not been tested with representative users and are not deployed interfaces.

A mistaken belief that approval is scheduled, that a Draft is already current, that history is rewritten, or that a title alone grants approval authority blocks design acceptance. Repeated dependence on coaching requires revision. Technical implementation checks remain separate: permissions, concurrency, complete comparisons, exact version binding, snapshots, server-side readiness, date boundaries and failure recovery.
