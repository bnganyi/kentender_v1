## Tracker rules

1. Rows are permanent. Vocabulary: `Planned` / `In progress` / `Blocked` / `Partial` / `Done`. Reversed decisions are struck through in place.
2. `Done` requires the row's own evidence: a command with result counts, a named test, a diff, or a described browser observation with literal rendered strings. Never record a result that was not observed.
3. §11 (of NDS-CHG-001 v1.13) governs visual/content fidelity only; §12/§12.10 governs behaviour; §9 governs error copy.
4. No alias, redirect, dual-write, compatibility shim or parallel surface. A row that reintroduces `procuring_entity`, `Needs Intake Window`, `PEFiscalYearContext` or a `User Permission`-based authority read is not `Done` regardless of what else it achieves.
5. Every visible action maps to one existing §8.2 command; no new command, status, role, queue or approval stage — v1.13 is explicit that it introduces none.
6. A row that repeats work the v1.10 cycle already completed and evidenced (see the superseded tracker) is scope creep unless it names the specific v1.6→v1.7 (or v1.10→v1.13) delta it is closing.
7. Never run the Python suite while a Departmental Needs Playwright process is active on the site (FU-01: the 5 specs share one fixture Need, single-worker only).
