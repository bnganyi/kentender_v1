## Tracker rules

1. Rows are permanent and use `Planned`, `In progress`, `Blocked`, `Done`.
2. `Done` requires the row's own evidence (a command, a test name, a diff, a described screenshot) — not "looks right."
3. If a touched file still references a concept the Gap Analysis or NDS-CHG-001 v1.6 §17/KT-STD-001 §10 prohibits (`procuring_entity`, `Needs Intake Window`, the custom `Financial Year` or `Unit Of Measure` doctypes, `User Permission` used as authority, `PE Fiscal Year Context`), the row that touches it is not `Done`.
4. No row may introduce an alias, redirect, dual-write, compatibility shim, or parallel legacy+new mechanism. If one appears, treat it as a defect in that row, not a valid completion.
5. §11 (Claude Design contract) governs visual/content fidelity only. §1–10 and §12–20 govern behaviour. A row implementing behaviour from §11 content instead of §12 is a defect, not a shortcut.
6. Deletion lands in the same phase as its replacement. "Delete later" is not a valid row state.
7. This cycle corrects an already-working module. A row that rewrites something the Gap Analysis §3 found already compliant, without a stated reason, is scope creep — record the reason or don't touch the file.

## Headline findings (read before touching code)

1. **This is not a from-scratch rebuild.** The v1.1 cycle's domain model, lifecycle, command surface and Vue-in-Desk frontend are sound and already verified (246/23/16 tests green at close). Re-verified against the current v1.6 spec in `02_NDS_Rebuild_Gap_Analysis.md` §3 — the foundational disposition register is compliant across the board except the authorization mechanism.
2. **The authorization gap is the largest item by far.** Zero use of `kentender_core.services.authorization` anywhere in `kentender_procurement`; every scope check runs on `frappe.get_all("User Permission", ...)` across PE/OU/FY. Budget's `budget_authorization.py` is the pattern to mirror.
3. **Two doctype substitutions were half-anticipated, half-missed.** `kentender_core`'s Fiscal Year flag fields and site-configuration commands already exist — built ahead of this module's own migration. The custom `Unit Of Measure` doctype, by contrast, was a v1.1-era defect: ERPNext's own `UOM` existed the whole time.
4. **The command surface (§8.2) survives almost unchanged.** The rewrite is concentrated in the read/context contracts and the authorization layer underneath every contract, not in the lifecycle commands themselves.
5. **The business-role registry was pre-updated.** `kentender_core/services/business_role_registry.py::REGISTRY` already carries `Departmental Author`/`Head of User Department` citing `NDS-CHG-001 v1.4` — a sign this cutover was expected, just not yet executed in the module itself.
6. **`bench migrate` does not drop a removed column.** Field removal from a DocType's JSON updates the metadata but leaves the DB column in place — confirmed live: `procuring_entity` survived a clean migrate after being deleted from both `field_order` and `fields`. An explicit patch (`alter table ... drop column`) is required, following `nds_chg_001_v11_decision_review_task`'s own established pattern. Don't assume a schema field removal is complete just because the JSON changed and migrate ran clean.
7. **`Departmental Need`/`Version`/`Review Task`/`Decision` cannot be hard-deleted via `frappe.delete_doc()`, even with `force=True`.** Their `on_trash()` controllers unconditionally `fail()` (§13 "retained permanently") — `force` skips certain framework link checks but never a controller's own validation. Any future test cleanup (including Phase 7's own suites) must use `frappe.db.delete(doctype, filters)` (raw SQL, bypasses the document lifecycle entirely) for this module's graph, matching the pattern the repo's own retirement patches already use.
8. **A freshly-inserted `User` with zero roles is silently demoted to `user_type = "Website User"`**, regardless of what `user_type` was set to at insert — Frappe's own `User.validate()` recomputes it from `has_desk_access()`. Any script or seed creating a disposable System User for a `User Responsibility Assignment` grant must call `user.add_roles("Desk User")` (or another desk-access role) before `grant()`'s own `_require_enabled_user` check will pass — `kentender_core/seeds/_common.py`'s existing seed-user helper already does this; a naive throwaway user does not.
9. **Phase 5 browser verification caught a real Phase 2 defect, live**: `services/permissions.py::creation_contexts()` treated a technical reader (Administrator/System Manager) as eligible to author in every Organisation Unit, but `require_create()` (the actual command gate) never grants a technical reader create authority — only a real `Departmental Author` `User Responsibility Assignment` does, matching §6's "no Need decision unless the person also has the applicable business responsibility assignment." The client therefore offered a "Create need" action (including the full NDS-DES-15 department picker) that the server would always refuse. Fixed by dropping `creation_contexts()`'s `is_technical` short-circuit — it now returns `permitted_ou_scopes(principal, ROLE_DEPARTMENTAL_AUTHOR)` unconditionally, matching `require_create()`'s real rule. `viewing_contexts()`'s own `is_technical` branch is correct and untouched (technical read-all is a real, intended view-only grant). Live-verified before and after: Administrator's "Create need" button correctly disappeared once the fix landed; a disposable user holding a real Departmental Author `User Responsibility Assignment` (granted via `kentender_core.services.responsibility_administration.grant()`, cleaned up after) completed `create_need()` → `submit_need()` successfully end to end.
10. **`upsert_departmental_needs()` (the module's own MVP seed builder) is currently non-functional** — confirmed live via `bench execute`: it throws `ModuleNotFoundError`/`ImportError` trying to insert a `Needs Intake Window` document, a doctype Phase 1 deleted outright. Every Phase-2/3/4-era Python test class whose `setUp`/`setUpClass` calls this function (nearly all of `test_departmental_needs_permissions.py`, `test_departmental_needs_lifecycle.py`, `test_departmental_needs_seed.py`, `test_departmental_needs_contracts.py`) now errors at fixture setup regardless of any later fix to that test file's own body — Phase 6 (seed rewrite onto `User Responsibility Assignment` grants, ERPNext `Fiscal Year`/`UOM`, no `Needs Intake Window`) is a hard, blocking prerequisite for almost this whole suite, not an independent, deferrable phase. Phase 7's test-suite rewrite cannot meaningfully proceed file-by-file until Phase 6 lands.
11. **A single broken import in one test file aborts Frappe's *entire app* test discovery**, not just that file: `frappe/testing/discovery.py::discover_all_tests` wraps its whole `os.walk` of every `test_*.py` in the app in one `try/except`, so `bench run-tests --app kentender_procurement` (no `--module` filter) could not run **at all** — for any module, including unrelated ones like Planning or Tender Management — while any of `test_departmental_needs_navigation.py`, `test_departmental_needs_permissions.py`, `test_departmental_needs_lifecycle.py` or `test_departmental_needs_seed.py` raised `ImportError` at import time (each imported a name Phase 2 had already deleted from `services/context.py`, e.g. `save_intake_window`/`intake_window`, or — `test_departmental_needs_lifecycle.py` only — the retired `INTAKE_SCHEDULED` constant). Fixed this session by removing/replacing the dead imports in all four files (and, where the tested concept was retired outright with no successor — the windowed `TestNeedsIntakeWindow` class, the intake-window sidebar-authorization test — deleting the now-inapplicable test rather than leaving it importable-but-wrong). This was necessary regardless of Phase 6/7 timing: it was silently disabling every other module's test suite too.
