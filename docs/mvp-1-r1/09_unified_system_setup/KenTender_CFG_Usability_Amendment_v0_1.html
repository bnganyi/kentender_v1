1. Assessment and approved direction

A usability amendment is warranted. The baseline already protects shared accounting records, limits configuration authority and avoids an approval workflow. Its weakness is presentation: it asks users to navigate reference sets, applicability bases, supersession, intake and schedule profiles as if they already understand the internal model.

Configuration is less frequent and more specialist than Planning. The right improvement is therefore a short route to everyday tasks, with structured detail for the people maintaining procurement rules. The Accounting Officer and other business users should encounter an understandable explanation in their own work, not be sent through setup screens.

Usability rule. One clear primary action per focused task. Display the few facts needed to act; group supporting facts under short headings. Show all blocking issues immediately. Keep historical evidence and technical identifiers available in detail. A shorter screen must never imply that missing evidence is acceptable.

Adoption of KT-STD-001 v1.5

Approved and adopted on 14 September 2026. Technical-read behavior is inherited by citation to §3A.6 rather than locally restated. CFG v0.11 registers its record types and read entry points with the shared search/conformance mechanism. The four sketches remain explanatory specimens; production design inputs follow the standard’s closed-input and separate-labelled-fact rules.

Explicit domain exceptions carried into CFG v0.11: (1) The standard’s technical-read command suppression does not remove the direct setup-maintenance commands assigned to Administrator/System Manager by CFG; its business technical-read rule remains controlling. (2) CFG preserves shared native UOM records and accounting/payroll usage instead of applying §8.5’s blanket “All others disabled” instruction. (3) The narrowly authorised missing-root recovery is retained; it exposes no nested-set fields, reparent/delete controls or generic tree-repair tool. These exceptions preserve approved CFG v0.10 domain decisions under KT-STD §1; they add no approval stage.

Owner follow-up: KT-STD v1.5 cites AUTH-DES-09 and AUTH §9 technical-read conformance, but the supplied AUTH v1.7 does not contain those specifications. The standard is adopted as controlling; a matching AUTH owner update and implementation evidence remain required. Its absence does not defer the standard’s technical-read right.

3. Approved journeys and screen structure

3.1 One setup page, predictable entry points

Keep System setup in the existing Frappe shell. Keep its five tabs and stable route anchors; relabel the visible Fiscal years tab Financial years. Procurement settings contains Funding sources, Procurement rules, Procurement schedules and Reminders. Each section gets one sentence explaining its purpose. Do not add a global setup score, an approval queue or a forced wizard.

First run opens the entity form; the remaining tabs stay unavailable until entity/root creation succeeds. Thereafter honour the requested route. Outstanding source checks appear where they matter and do not prevent unrelated setup work. Missing-root recovery retains the baseline's limited tab restrictions.

3.2 Forms should remember context, not invent evidence

Preselect the year, rule kind, exact version and other known context. Preserve unsaved work during validation failures and retry. Generate or propose a rule key from its name only as an editable, validated setup identifier before the first version; expose it under Rule identifier, not as a business concept. Never auto-fill missing legal amounts, applicability dates, interpretations, source-check dates or reasons from the demonstration examples.

Add rule transaction boundary: validate the full proposed content using the existing preview capability before creating the stable reference set. Reject structural or unsupported-schema errors; display legally incomplete but structurally saveable content as pending, preserving the baseline’s permitted incomplete versions. The UI then calls CreateRegulatoryReference and SaveRegulatoryReferenceVersion in order, with a separate idempotency key for each. These remain separate transactions. If the set exists but the version save fails, show “Rule created; version not saved”, retain the form and returned set ID/token, and retry the version operation against that set. Never create another set on retry, imply rollback, or show the rule as usable. An ambiguous timeout first recovers the original command result with its original key. The list must also allow an authorised user to complete an empty set later. No persisted Draft lifecycle is introduced.

Source checks: a successful version save shows the saved version and Check sources as its next action. Recording verification is separate and must be reported separately if it fails. A pre-save impact computation is refreshed as fields change; the save command still checks current tokens and authoritative rules. Do not hide a known blocking consequence inside collapsed detail.
