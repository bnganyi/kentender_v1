# CFG-CHG-002 v0.11 — System setup usability + domain completion — implementation plan

## Context

The Project Owner approved the System setup Usability Amendment v0.1 (CFG-UX-001..014) plus adoption of KT-STD-001 v1.5 on 14 September 2026, consolidated into **CFG-CHG-002 v0.11** (`docs/mvp-1-r1/09_unified_system_setup/KenTender_CFG-CHG-002_Site_Configuration_and_System_Setup_v0_11.md`). v0.11 supersedes v0.10 in full: 59 carried acceptance criteria (CFG10-AC-001..059), 28 usability criteria (CFG-UX-AC-01..28), 4 standards-adoption criteria (CFG11-AC-029..032) — 91 total; 41 change rows (26 retained v0.10 rows in §17.2, 15 v0.11 rows in §17.3).

Unlike Strategy v1.8 / Budget v1.9, this is **not a pure re-port**. System setup already runs on `kentender_core.desk_page.register` and the Industry design system — no chrome migration is needed. But the live domain model has real gaps against v0.11, found during planning (not assumed):

- Only 2 of the spec's 7 regulatory rule kinds exist (Method eligibility via a separate `Procedure Method Profile` doctype; Reservation rules as fields on a monolithic `Regulatory Reference`). Exclusive preference, Preference margins, Market price index, Approval applicability and Publication obligations do not exist as rule kinds anywhere in the codebase, though two of their fields (exclusive-preference amounts, market-price-index flag) already sit unused on the monolithic doctype.
- `Regulatory Reference` is one record per fiscal year with an Active/Superseded status flag — not v0.11's per-kind independently-created, immutably-versioned "set" with append-only verification events. No `Reference Verification Event` doctype exists at all.
- No `disposal_plan` intake flag (only `needs` and `dpp` exist and work).
- No `IntakeControl` doctype; the current lock is a raw `SELECT … FOR UPDATE` on `tabFiscal Year` inside `_open_intake_flag`, not a per-module-key serialization token.
- No `Business Day Calendar` doctype at all, though `Procedure Schedule Profile` already has a WorkingDays counting rule that needs one.

**Owner decision (16 Sep 2026): close the domain gaps as part of this cycle**, not just the usability pass. This makes CFG-CHG-002 v0.11 a hybrid: a domain rebuild of the regulatory-reference subsystem (Decision D1 below), plus a usability re-port of already-working screens (Procuring entity, Financial years, Funding sources, Reminders), plus net-new UI for schedules/calendars. Size this like a module rebuild, not a one-session usability cycle — but keep the phase-sequencing discipline that made Budget/Strategy's *usability* cycles fast: horizontal domain work first, then vertical per-route screens, never all-screens-then-all-tests.

## Decisions to record in Phase 0

- **D1 — Regulatory Reference remodel keeps proven mechanics, restructures the envelope.** Build one generic `Regulatory Reference Set` / `Regulatory Reference Version` / `Reference Verification Event` envelope implementing §4.6's immutable-version + append-only-verification contract for all 7 kinds. Do **not** discard `Procedure Method Profile` — its condition-row/evidence/authorization-stage model is sound and matches §4.7's Method-condition contract closely; front it with the same generic Set/Version/VerificationEvent envelope so Method eligibility is reachable through the one `CreateRegulatoryReference`/`SaveRegulatoryReferenceVersion`/`RecordReferenceVerification` contract as the other 6 kinds. **No data migration** (owner, 16 Sep 2026: the dev site may be torn down freely, no migration needed) — drop the monolithic `Regulatory Reference` doctype's existing records outright and reseed fresh Reservation-rules/Exclusive-preference/Market-price-index examples as real Version 1 rows through `site_setup.py`/the new commands, instead of writing a migration patch that maps old rows forward. Retire the monolithic per-FY doctype once the new envelope is seeded (no compatibility shim, no dual-write).
- **D2 — AUTH-owned and Owner-evidence artboards are out of this board set.** `OrganisationStructureTab.vue`/`UserResponsibilitiesTab.vue` inherit AUTH v1.7's own compositions; technical-read/Auditor evidence inherits KT-STD §3A.6's shared surface. This cycle verifies CFG's citation/registration of both, not their content.
- **D3 — IntakeControl generalizes the existing per-flag pattern to three module keys** (`needs`, `dpp`, `disposal_plan`) through one shared internal helper, replacing the two hand-duplicated needs/dpp function pairs — not a rewrite of the audit-field pattern, which is sound.

- **D5 — `ui-system-setup-fidelity-gate` and `ui-system-setup-procurement-settings-gate` are extended in place**, not replaced; a new `ui-system-setup-rules-gate` is added for the 7-kind rule-creation/versioning/verification journeys given their size (mirrors Budget's per-route gate split).

## Regulatory Reference remodel — detailed design (Phase 2b/2c, recorded 16 Sep 2026)

Dependency research before building 2b found: **`resolve_regulatory_rule` (the spec's `GetRegulatoryReference`-shaped resolver) has zero production callers anywhere in the repo** — only its own unit tests call it. Every real reader goes through two other functions: `get_regulatory_reference(fiscal_year)` (the FY-in-force lookup Planning's `readiness.py` calls via `reference_for()`) and `_projection(name)`/`get_regulatory_reference_version` (the full-record read behind System Setup's detail view). This means the redesign can replace the resolver wholesale, but must keep serving those two read shapes with the specific sub-fields listed below — verified by tracing every consumer, not assumed:

- **Must preserve** (live Planning business logic reads these): `reservation.target_percent`, `reservation.county_target_percent` (annual reservation-obligation check, `reservation_allocations()`); `reservation.categories[].category` (only the name, not rank/regional/statutory-reference); `threshold_matrix[].{procurement_category, procurement_method, max_amount}` (splitting-advisory / low-value cumulative-breach checks); `market_price_index.{published, rows[].{item, unit, indicative_price}}` (Plan Item editor helper — currently unpopulated in the canonical seed, but the code path is live); the exact 3-value `verification_status` vocabulary (`Production verification pending` / `Fixture-verified — not production law` / `Verified`, already the shared constant in `procurement_settings.py` that Planning's own `profiles.py` imports).
- **Safe to change freely** (zero production readers, only the seed/tests round-trip them): `exclusive_preference_works_amount`/`goods_services_amount`, `schedule_buffers`, `reservation_categories[].{advantage_rank, is_regional, statutory_reference}` (System Setup detail view only).
- **Real pre-existing data-quality gap, not this cycle's to fix**: `threshold_matrix` and `Procurement Method Profile`'s own condition-row `maximum_amount` are two independently-writable copies of the identical Second Schedule figures, seeded from one Python constant, with no runtime link. D9 below resolves this *within CFG's own read function* (derive `threshold_matrix` from Method Profile at read time instead of a separately stored table) without touching Planning's `readiness.py` — but does not attempt a deeper unification; recorded as FU-08.
- A test-fixture hard dependency exists outside the service layer: `kentender_procurement/procurement_planning/seeds/playwright_ui_fixtures.py` writes directly to `Regulatory Reference` via `frappe.db.set_value` on the old field names — this file needs a matching update in the same commit as the doctype rewrite (D2b below), or Planning's own Playwright fixtures will silently stop working.

**D7 — one JSON-validated typed payload per version, not seven child-table schemas.** `Regulatory Reference`'s kind-specific fields (§4.7's per-kind tables) live in one `payload_json` field, validated in Python against a strict per-kind schema (exact required keys, comparator/operator whitelist, typed values) — never a raw editor exposed to users (§10.7's "No JSON or script editor" prohibits the *UI*, not the storage format; the Vue layer always renders proper typed fields per kind, reading/writing the validated dict). This avoids seven new child-table doctypes with dozens of fields apiece in one pass while still meeting every functional requirement in §4.7/§10.7 (exact fields, rejection of unsupported values, condition grouping). The existing `Regulatory Threshold Band`/`Regulatory Reservation Category`/`Regulatory Market Price`/`Regulatory Schedule Buffer` child doctypes are left in place, unused, rather than deleted — candidates for a later cleanup once confirmed dead (FU-09).

**D8 — a minimal `Regulatory Reference Set` header (key/kind/display name only) plus `Regulatory Reference` redefined in place as the version doctype.** §7.3's two-command recoverable creation ("Rule created; version not saved") needs a set to exist with zero versions, which a single-doctype-per-version pattern (Schedule Profile's/Calendar's proven shape) cannot represent on its own — so the Set stays a genuinely separate, minimal doctype (`reference_key` unique, `reference_kind`, `display_name`, immutable key/kind once any version exists). `Regulatory Reference` itself is *redefined in place* (same doctype name, same folder, rewritten schema) rather than replaced by a new doctype name — its old per-FY fields (`fiscal_year`, `gazette_reference`, `reservation_target_percent`, `county_resident_target_percent`, `exclusive_preference_*_amount`, `market_price_index_published`) are dropped for a `reference_set` Link + `reference_key`/`reference_kind` (denormalized from the Set for query convenience) + `version_number`/`status` Active-Superseded (Schedule Profile's proven supersession pattern, reusing `_next_version`/`_supersede_overlapping`/`_in_force`) + the common §4.6 version fields (`applicability_basis`, `applicability_entity_types`/`_county`/`_categories`/`_currency`, `source_instrument`/`provision`/`source_document`, `interpretation`, `supersedes_version_ids`, `change_reason`) + `verification_status` + `payload_json` (D7). No data migration (owner instruction, D6) — existing Reservation-rules rows are dropped and reseeded fresh as real Version 1 rows through the new commands.

**D9 — a shared, generic `Reference Verification Event` doctype (append-only) drives `verification_status` as a maintained projection**, covering both `Regulatory Reference` and `Business Day Calendar` via a `target_doctype`/`target_name` (Dynamic Link) pair, per §7.1's "explicit target kind ... where applicable." The target's own `verification_status` field (already proven, already what Planning's `reservation_allocations()` reads) stays a fast denormalized read of "the latest event's outcome" — recording an event updates it — so no consumer needs to change how it reads verification state, while the append-only event history the spec requires (§4.6, §5, §8.1) genuinely exists.

**D10 — Method eligibility stays owned by `Procedure Method Profile`; the "Method eligibility" kind is a thin delegation, not duplicated storage.** Creating/versioning a "Method eligibility" rule through the generic `CreateRegulatoryReference`/`SaveRegulatoryReferenceVersion` contract calls the existing `register_method_profile_version` underneath rather than writing a parallel copy into `payload_json` — consistent with D1. `get_regulatory_reference(fiscal_year)`'s `threshold_matrix` output is derived at read time from `Procurement Method Profile`'s in-force conditions instead of a separately maintained table, closing the "two independently-writable copies" gap the dependency research found — entirely inside CFG's own read function, without touching Planning's `readiness.py`.
