## 1. Reason for Redesign

The previous STD Administrator UI model exposed too much of the underlying STD Engine too early. It treated the administrator’s work as if the normal daily task were manual configuration of template internals, mappings, parameters, forms, and readiness rules.

That is not the correct primary workflow.

PPRA-style Standard Tender Documents rarely change. They are official controlled documents. The ordinary administrative workflow is therefore not continuous manual configuration. It is controlled onboarding, validation, activation, reuse, and occasional supersession.

The UI must reflect that reality.

---

## 2. Corrected First-Principles Model

The STD Engine must remain structurally powerful, but the administrator UI must present the work in operationally understandable terms.

The correct administrator mental model is:

```text
Official Standard Library
        ↓
Import or Register Official STD Package
        ↓
Validate Structured Model
        ↓
Preview Recombined Tender Document
        ↓
Activate for Tender Use
        ↓
Supersede only when official STD changes
```

The administrator should not begin from raw mappings, nested data structures, or XML/JSON-like internals.

---

## 3. Primary Use Cases

The STD Administrator has five primary use cases.

### 3.1 View Official STD Library

The administrator views all official STD template versions available to the system.

Examples:

- PPRA Works — Building and Associated Civil Engineering Works — Rev April 2022
- PPRA Works — Roads and Bridges — Rev April 2022
- PPRA Goods — Standard Tender Document
- PPRA Consultancy — RFP Standard Document

### 3.2 Import Official STD Package

The administrator imports or registers a structured STD package prepared from an official source document.

The preferred import source is a structured seed package, not a raw PDF.

The raw official document remains evidence, but it is not the runtime rule source.

### 3.3 Validate the Structured STD

The administrator confirms that the imported STD package is structurally complete:

- sections exist;
- parameters exist;
- forms exist;
- BOQ rules exist where applicable;
- mappings are complete;
- generated models can be produced;
- bundle can be rendered.

### 3.4 Preview the Final Tender Document Bundle

The administrator previews the recombined tender document that procurement officers and suppliers will eventually see.

This preview is critical because users understand documents better than internal mappings.

### 3.5 Supersede an Existing STD Version

When PPRA or another authority issues a revised STD, the administrator creates a new version by importing a new package or cloning/superseding an existing version.

This is an exceptional workflow, not a daily activity.

---

## 4. What the UI Must Stop Doing

The UI must not lead with:

1. raw clause trees;
2. JSON/XML-like data structures;
3. mapping tables;
4. DSM/DOM/DEM/DCM acronyms without explanation;
5. database object lists;
6. manual template construction as the normal path;
7. STD Instance management as the main administrator task.

These capabilities may exist, but must be hidden behind advanced views.

## 5. Replacement Information Architecture

### 5.1 STD Administrator Navigation

The STD Administrator should see the following navigation inside STD Engine:

```text
STD Library
Official STD Packages
Validation
Bundle Preview
Supersession History
Advanced Technical View
Audit Trail
```

### 5.2 Primary Navigation Purpose

| Navigation Item | Purpose |
|---|---|
| STD Library | View active, draft, superseded, and historical official STD template versions. |
| Official STD Packages | Import or register structured official STD packages. |
| Validation | Review structural health, blockers, warnings, and readiness to activate. |
| Bundle Preview | Preview the recombined tender document generated from the structured STD. |
| Supersession History | See revisions, replacements, and usage impact. |
| Advanced Technical View | Inspect sections, parameters, forms, BOQ rules, mappings, and generated model definitions. Hidden by default. |
| Audit Trail | Review configuration and activation events. |

### 5.3 STD Instances

STD Instances are not part of the primary STD Administrator workspace.

They may appear only as read-only usage references under:

```text
STD Library → Selected STD → Usage
```

The STD Administrator UI must not create STD Instances.

## 6. Main Screen: STD Library

### 6.1 Purpose

The STD Library is the default landing page for the STD Administrator.

It answers:

1. Which official STDs are available?
2. Which revision is active?
3. Which procurement method/category does each STD support?
4. Is the STD validated and ready for use?
5. How often has it been used?
6. Is there a newer/superseding version?

### 6.2 Page Title

```text
Official STD Library
```

### 6.3 Subtitle

```text
Manage official standard tender documents available for tender preparation.
```

### 6.4 Header Actions

## 7. Official STD Package Import Workflow

### 7.1 Purpose

This workflow imports a structured official STD package and prepares it for validation and activation.

This must be the primary onboarding path.

### 7.2 Entry Action

```text
Import Official STD Package
```

### 7.3 Import Wizard Steps

```text
1. Select Package
2. Confirm Source Evidence
3. Review Detected Structure
4. Validate Structured Model
5. Preview Tender Bundle
6. Submit for Review / Activate
```

This replaces the older 10-step template configuration wizard.

### 7.4 Step 1 — Select Package

Purpose:

Select a structured package from an approved source.

Fields:

| Field | Type | Required |
|---|---|---|
| Package Source | Select | Yes |
| Package File / Registry Entry | File or registry picker | Yes |
| Package Type | Auto-detected | Yes |
| Expected STD Category | Auto-detected | Yes |

Allowed package sources:

| Source | Meaning |
|---|---|
| Built-in Seed Package | Package included with system deployment. |
| Uploaded Structured Package | A reviewed YAML/JSON package prepared by authorized technical/legal team. |
| Connected Registry | Future official registry source, if available. |

Not allowed as runtime package:

| Source | Reason |
|---|---|
| Raw PDF only | Evidence only, not enough for structured engine. |
| Word document only | Evidence only, not enough for structured engine. |
| Spreadsheet only | May support BOQ import, but not full STD structure. |

### 7.5 Step 2 — Confirm Source Evidence

Purpose:

Confirm the official document and revision that the structured package represents.

Fields:

| Field | Example |
|---|---|
| Source Authority | PPRA |
| Source Document Title | Standard Tender Document for Procurement of Works — Building and Associated Civil Engineering Works |
| Revision | Rev April 2022 |
| Source Evidence File | Official PDF reference |
| Source Hash | SHA/hash if available |
| Prepared By | Technical/legal team or seed package author |
| Review Status | Pending / Reviewed |

Guidance:

```text
The official document is retained as evidence. The structured package provides the system-readable template used for validation and generation.
```

### 7.6 Step 3 — Review Detected Structure

Purpose:

Show the administrator what the package contains without exposing raw nested data.

Show summary sections:

| Area | Example Status |
|---|---|
| Parts and Sections | 3 parts, 10 sections detected |
| Locked Legal Text | ITT and GCC detected |
| Parameters | 48 TDS/SCC parameters detected |
| Forms | 14 tendering forms, 9 contract forms detected |
| BOQ Rules | Works BOQ rules detected |
| Mappings | Bundle, DSM, DOM, DEM, DCM mappings detected |
| Readiness Rules | 16 rules detected |

Default view is summary only.

Expand details only when needed.

### 7.7 Step 4 — Validate Structured Model

Purpose:

Run validation before the STD can be used.

Validation checks:

| Check | Required Result |
|---|---|
| Mandatory sections | Present |
| Locked sections | ITT and GCC locked |
| Parameter sections | TDS and SCC parameterized |
| Forms | Structured and mapped |
| BOQ | Rules complete for Works |
| Mappings | Complete |
| Bundle render | Successful |
| Generated models | Bundle, DSM, DOM, DEM, DCM can be generated |

Validation result should display:

```text
Passed
```

or:

```text
Needs attention
```

Do not show raw stack traces or JSON.

### 7.8 Step 5 — Preview Tender Bundle

Purpose:

Show the final recombined tender document output.

The bundle preview must show:

```text
Invitation to Tender
Section I — Instructions to Tenderers
Section II — Tender Data Sheet
Section III — Evaluation and Qualification Criteria
Section IV — Tendering Forms
Section V — Bills of Quantities
Section VI — Specifications
Section VII — Drawings
Section VIII — General Conditions of Contract
Section IX — Special Conditions of Contract
Section X — Contract Forms
```

The preview must also clearly show placeholder areas that will be filled during tender preparation.

Example:

```text
[To be completed during tender preparation: Submission Deadline]
```

### 7.9 Step 6 — Submit for Review / Activate

Depending on governance configuration:

| Condition | Action |
|---|---|
| Legal review required | Submit for Review |
| Legal review already completed in controlled seed process | Activate |
| Validation failed | Block activation |

The UI must not allow activation if validation fails.

## 8. Selected STD Detail View

### 8.1 Purpose

The detail view must summarize the selected official STD and provide access to deeper views only when needed.

### 8.2 Detail Tabs

Use a simplified tab set:

```text
Summary
Validation
Bundle Preview
Usage
Supersession
Advanced Technical View
Audit Trail
```

This replaces the previous tab-heavy design.

### 8.3 Summary Tab

Shows:

| Area | Content |
|---|---|
| STD identity | title, revision, authority, category |
| Current status | Draft / Under Review / Active / Superseded |
| Supported use | methods, contract type, profile |
| Health | validation passed / needs attention |
| Output status | bundle available; generated models available |
| Next action | preview, validate, submit, activate, create revision |

### 8.4 Validation Tab

Shows health checks by business category:

```text
Sections
Parameters
Forms
BOQ Rules
Mappings
Generated Models
Bundle Rendering
```

Each category has:

- status;
- blocker count;
- warning count;
- expand option.

Detailed mapping tables are hidden unless a category is expanded.

### 8.5 Bundle Preview Tab

Shows the recombined tender document.

Required actions:

| Action | Purpose |
|---|---|
| Preview in Browser | View generated document. |
| Download PDF | Download rendered PDF. |
| Download DOCX | Download editable/formatted document if supported. |
| View Placeholder List | Show fields completed during tender preparation. |

### 8.6 Usage Tab

Shows read-only usage:

| Field | Meaning |
|---|---|
| Tenders using this STD | Count and list |
| Active tender instances | Read-only references |
| Published bundles | Read-only references |
| Addenda affecting STD instances | Read-only references |

No edit actions.

### 8.7 Supersession Tab

Shows:

| Field | Meaning |
|---|---|
| Previous version | Version superseded by this one |
| Next version | Version superseding this one |
| Reason for supersession | PPRA revision, correction, policy update |
| Effective date | Date from which new version applies |
| Existing tender impact | Whether existing tenders continue using old version |

### 8.8 Advanced Technical View

This view is collapsed by default and labelled clearly:

```text
Advanced Technical View
```

Subtitle:

```text
For administrators reviewing structured sections, parameters, mappings, BOQ rules, and generated model definitions.
```

Subsections:

```text
Sections and Clauses
Parameters
Forms
Works / BOQ Rules
Source Mappings
Readiness Rules
Generated Model Definitions
Raw Package Data
```

Raw package data must be read-only unless the template is draft and the user explicitly chooses advanced edit mode.

## 9. Bundle Output Requirement

The final Bundle is a first-class output.

### 9.1 What the Bundle Is

The Bundle is the recombined supplier-facing tender document generated from the structured STD template and, later, tender-specific STD instance values.

### 9.2 Template-Level Bundle Preview

At template level, the bundle preview shows:

- fixed legal text;
- parameter placeholders;
- structured form placeholders;
- BOQ schema placeholders;
- sections that will receive tender-specific attachments or data.

### 9.3 Instance-Level Bundle Output

At tender instance level, the bundle includes:

- filled TDS values;
- filled SCC values;
- tender-specific BOQ quantities;
- specifications;
- drawings register;
- section-bound attachments;
- generated/addendum references.

### 9.4 Download Formats

The system should support, in priority order:

| Format | Requirement |
|---|---|
| PDF | Required for publication/audit. |
| DOCX | Strongly recommended for internal review and formal tender record. |
| HTML Preview | Required for browser review. |
| JSON Manifest | Internal/audit use only. |

## 10. Handling Deep Structure and XML/JSON Complexity

### 10.1 Rule

Deep structured data must not be the primary UI.

### 10.2 Presentation Layers

Use three layers:

| Layer | Audience | Purpose |
|---|---|---|
| Business Summary | STD Administrator / reviewer | Understand health and usability. |
| Structured Detail | STD Administrator | Inspect sections, parameters, mappings. |
| Raw Data | Technical admin/developer | Debug import/package issues. |

### 10.3 Raw Data Visibility

Raw JSON/XML-like structures must be:

- hidden by default;
- read-only by default;
- labelled as technical;
- unavailable to ordinary procurement users.

## 11. Revised State Model for STD Library

### 11.1 Template Version States

| State | Meaning | Primary UI Action |
|---|---|---|
| Imported Draft | Structured package imported but not validated. | Validate |
| Needs Attention | Validation failed or warnings require review. | Resolve issues |
| Ready for Review | Validation passed and awaiting governance review. | Submit for review |
| Under Review | Legal/policy review in progress. | View status |
| Active | Available for tender use. | Preview / Create new revision |
| Superseded | Replaced by newer version. | View history |
| Retired | No longer available for new tenders. | View audit |

### 11.2 State Principle

The normal path is:

```text
Imported Draft → Validation → Ready for Review → Active
```

Manual construction path is exceptional:

```text
Advanced Technical View → Manual Draft Configuration
```

## 13. Acceptance Criteria

This redesign is accepted only if:

| Criterion | Required Outcome |
|---|---|
| UI starts from STD Library | Administrator sees official standards, not database internals. |
| Import is package-based | Structured package import is the normal path. |
| Raw PDF is evidence only | UI does not imply PDF upload creates system rules. |
| Validation is central | Admin validates imported structure before use. |
| Bundle preview is central | Admin can see final recombined tender document. |
| Technical views are hidden by default | Mappings/JSON/nested data are not primary. |
| STD Instances are not created here | Instance creation remains Tender-only. |
| Supersession is supported | New official revisions create new versions. |
| UI is understandable to non-developer administrators | Plain language first, technical detail second. |
| Active versions are immutable | View/preview/supersede only. |
