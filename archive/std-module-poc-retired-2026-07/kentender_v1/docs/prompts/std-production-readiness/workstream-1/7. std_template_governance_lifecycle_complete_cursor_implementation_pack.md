## 2. Purpose

This implementation pack converts the STD Template Governance and Lifecycle design artefacts into a complete, ticketed, non-interpretive Cursor implementation plan.

Cursor shall implement a production-grade governance layer for STD templates. The implementation shall control template import, package hash, validation, submission, approval, activation, suspension, reinstatement, supersession, retirement, archival, usage tracking, mutation blocking, audit events, and governance snapshots.

This pack deliberately avoids a minimal implementation. Cursor must not invent alternative DocTypes, fieldnames, lifecycle states, permissions, method names, audit event codes, snapshot schemas, or transition behavior.

---

## 3. Non-Negotiable Scope Boundaries

Cursor must not implement any of the following in this workstream:

1. procurement officer tender configuration changes;
2. bidder portal;
3. bid submission;
4. bid opening;
5. evaluation execution;
6. award;
7. contract execution;
8. final PDF generation;
9. public tender publication;
10. addenda workflow;
11. supplier clarification workflow;
12. external integrations;
13. manual submission checklist builder;
14. manual opening register builder;
15. manual evaluation criteria editor;
16. manual contract terms editor;
17. free-form editing of active STD rules, forms, sections, legal text, or package payload.

The implementation must govern reusable STD templates only.

## 4. Implementation Strategy

Use the current `STD Template` DocType as the governed STD template version record.

Do not create a separate `STD Template Family` or `STD Template Version` in this workstream. Field names shall be compatible with later migration to a cleaner family/version model.

Required implementation pattern:

```text
STD Template
→ child table: STD Template Lifecycle Event
→ child table: STD Template Validation Finding
→ child table: STD Template Usage
→ governance service methods
→ audit/snapshot service methods
→ admin UI actions
→ seed migration for existing WORKS POC template
→ tests
```

Optional linked DocTypes such as `STD Template Validation Run` and `STD Template Mapping` may be deferred unless already easy in the repository. Do not invent them unless this pack explicitly tells you to create them. For this implementation pack, use JSON fields and child tables instead.

## 14. Core State Transition Behavior

### 14.1 Import

`import_std_template_package` shall:

1. check role: Importer, Administrator, or System Manager;
2. canonicalize payload;
3. compute SHA-256 package hash;
4. create `STD Template` record;
5. set lifecycle status `Imported`;
6. set validation status `Not Run`;
7. set `allowed_for_tender_creation = 0`;
8. set package fields;
9. write `STD_TEMPLATE_IMPORTED` event;
10. return record name, status, package hash.

### 14.2 Replace Package

`replace_std_template_package` shall:

1. check role: Importer for own package, Administrator, or System Manager;
2. verify status is in controlled replacement states;
3. verify no usage exists;
4. compute new package hash;
5. replace payload fields;
6. reset validation fields;
7. clear approval/activation fields;
8. set lifecycle status `Imported`;
9. set allowed for tender creation false;
10. write `STD_TEMPLATE_PACKAGE_REPLACED` event.

### 14.3 Validate

`run_std_template_validation` shall:

1. check role: Administrator or System Manager;
2. write validation started event;
3. validate package payload;
4. clear and write validation findings;
5. update latest validation fields;
6. set lifecycle status `Validated` if no critical findings;
7. set lifecycle status `Validation Failed` if critical findings or service failure;
8. write validation completed event;
9. return structured result.

### 14.4 Submit

`submit_std_template_for_approval` shall:

1. check role: Administrator or System Manager;
2. require lifecycle status `Validated`;
3. require current validation;
4. set status `Submitted for Approval`;
5. set submitted fields;
6. lock payload;
7. write submission event.

### 14.5 Approve

`approve_std_template` shall:

1. check role: Approver or System Manager;
2. require lifecycle status `Submitted for Approval`;
3. require validation current and no critical findings;
4. enforce separation of duty unless System Manager override reason provided;
5. set status `Approved`;
6. set approval fields;
7. keep `allowed_for_tender_creation = 0`;
8. write approval event;
9. if override used, write override event too.

### 14.6 Activate

`activate_std_template` shall:

1. check role: Activator or System Manager;
2. require lifecycle status `Approved`;
3. require approval hash, validation hash, and current package hash match;
4. check active profile conflict;
5. set status `Active`;
6. set `allowed_for_tender_creation = 1`;
7. set activation fields;
8. set default active version flag if requested;
9. write activation event.

### 14.7 Suspend / Reinstate / Supersede / Retire / Archive

Implement exactly according to state model and audit catalogue.

All require reason. All write lifecycle events. Supersession and retirement must call usage impact before transition.
