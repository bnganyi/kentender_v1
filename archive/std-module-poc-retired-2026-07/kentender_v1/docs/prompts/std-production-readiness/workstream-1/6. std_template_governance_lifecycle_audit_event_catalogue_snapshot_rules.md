## 2. Purpose

The purpose of this document is to define the audit event catalogue, audit payload rules, snapshot rules, hash rules, and evidence requirements for STD Template Governance and Lifecycle.

This audit model ensures that every governance-significant action on an STD template version is reconstructable, attributable, hash-verifiable, and legally defensible.

The audit model must answer:

1. who imported the template;
2. what package hash was imported;
3. who validated it and what findings existed;
4. who submitted it for approval;
5. who approved, rejected, or returned it;
6. who activated it for tender creation;
7. who suspended, superseded, retired, or archived it;
8. whether any protected mutation was attempted;
9. whether any inactive/disallowed template was blocked from tender creation;
10. which tenders or tender STD instances used which exact template version and hash.

---

## 3. Audit Principle

The audit model shall implement this principle:

> A governed STD template version must be reconstructable from its source package, lifecycle events, validation evidence, approval evidence, activation evidence, usage evidence, package hash, and snapshot records.

This means:

1. audit events must be append-only;
2. audit events must not be editable by ordinary users;
3. lifecycle transitions must write audit events in the same transaction where practical;
4. package hash must be captured in relevant events;
5. validation, approval, and activation must reference the same package hash unless revalidation/reapproval occurs;
6. template usage must be recorded when a tender or tender STD instance binds to a template;
7. snapshots must be deterministic and hashable;
8. blocked sensitive actions must also be auditable.

## 6. Audit Object Strategy

The implementation may use either:

1. a child table on `STD Template` called `STD Template Lifecycle Event`; or
2. a linked DocType called `STD Template Audit Event`; or
3. an existing audit framework if already implemented.

For this workstream, the required event structure shall be the same regardless of storage.

Recommended first implementation:

```text
STD Template
→ STD Template Lifecycle Event[]
```

Reason:

1. simpler implementation;
2. keeps lifecycle history visible in the template detail page;
3. aligns with the Domain Model and Data Dictionary;
4. can be migrated later to a central audit framework.

The implementation pack must choose the exact storage path and fieldnames. It must not leave this to Cursor inference.

## 14. Snapshot Hash Rules

Snapshot hash shall be generated as follows:

1. build snapshot JSON;
2. remove transient UI-only fields;
3. serialize JSON with sorted keys;
4. use UTF-8 encoding;
5. compute SHA-256 hex digest;
6. store snapshot hash;
7. store snapshot hash algorithm as `SHA-256`;
8. write `STD_TEMPLATE_SNAPSHOT_GENERATED` audit event.

Snapshot hash shall not replace package hash. They have different meanings:

| Hash | Meaning |
|---|---|
| Package hash | Integrity of STD package payload/content |
| Snapshot hash | Integrity of governance evidence snapshot |
| Validation result hash | Optional integrity of validation output |
| Tender configuration hash | Tender-specific configuration snapshot |

## 15. Approval Baseline Snapshot Rules

Before approval, the system shall generate or be able to reconstruct an approval baseline.

Required contents:

1. current package hash;
2. validation status;
3. validation run ID;
4. validation findings summary;
5. template identity;
6. source authority;
7. package manifest summary;
8. reviewer/approver identity after approval;
9. approval comments after approval.

Approval must be blocked if:

1. validation is missing;
2. validation is failed/blocked;
3. validation package hash differs from current package hash;
4. critical findings exist.

---

## 16. Activation Baseline Snapshot Rules

Before activation, the system shall generate or be able to reconstruct an activation baseline.

Required contents:

1. template identity;
2. approval evidence;
3. approval package hash;
4. validation package hash;
5. current package hash;
6. active profile key;
7. active conflict check result;
8. activation actor/reason/effective date.

Activation must be blocked if:

1. template is not Approved;
2. approval package hash differs from current package hash;
3. validation package hash differs from current package hash;
4. active profile conflict is unresolved;
5. activation reason missing.

---

## 17. Usage Baseline Snapshot Rules

When an STD template is bound to a tender or tender STD instance, the system shall capture a usage baseline.

Required contents:

1. template identity;
2. template lifecycle status;
3. package hash at use;
4. activation package hash;
5. tender reference;
6. procurement package reference if available;
7. tender STD instance reference if available;
8. user/system actor;
9. timestamp;
10. tender configuration hash if available.

Usage baseline postconditions:

1. usage row created;
2. usage event created;
3. locked due to usage set true;
4. mutation/delete blocked permanently.

## 18. Retention Rules

Retention policy:

| Data | Retention rule |
|---|---|
| STD Template record | Retain permanently or according to public procurement retention law/policy |
| Package payload | Retain permanently for used templates |
| Package hash | Retain permanently |
| Lifecycle events | Retain permanently |
| Validation findings | Retain at least latest; preferably all runs for production |
| Approval evidence | Retain permanently |
| Activation evidence | Retain permanently |
| Usage records | Retain permanently |
| Snapshot JSON/hash | Retain permanently for approval/activation/usage baselines |
| Blocked mutation/delete/use events | Retain under audit policy; recommended permanent for used templates |

Deletion should not be used as normal lifecycle management. Archive instead.

---

## 19. Immutability Rules

Audit records and snapshots must be protected.

Rules:

1. lifecycle events are append-only;
2. event rows cannot be edited through UI;
3. event rows cannot be deleted by ordinary users;
4. snapshot hash cannot be manually edited;
5. package hash cannot be manually edited;
6. historical snapshots remain readable;
7. correction is handled by new events, not editing old events;
8. System Manager override must write new audit events, not mutate old ones.

1. lifecycle event timeline;
2. event table with filters;
3. package hash visibility;
4. validation/approval/activation baseline visibility;
5. usage list and usage events;
6. blocked action events;
7. override events;
8. snapshot hash display;
9. copyable full hashes;
10. downloadable/exportable audit summary later, if required.

Audit UI must not allow event editing.

---

## 21. Error and Failure Audit Rules

The system should record failed/blocked sensitive attempts.

Required blocked events:

1. mutation blocked;
2. delete blocked;
3. usage blocked for non-active template;
4. activation blocked due to hash mismatch;
5. approval blocked due to stale validation;
6. active conflict blocked;
7. System Manager override attempt/success.

For routine permission-denied UI access, audit may be optional. For sensitive governance action attempts, audit is recommended or required as specified above.
