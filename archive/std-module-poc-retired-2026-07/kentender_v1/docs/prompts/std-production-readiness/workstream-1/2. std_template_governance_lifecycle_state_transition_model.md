## 2. Purpose

The purpose of this document is to define the formal governance lifecycle and state-transition model for Standard Tender Document templates.

This model governs how an STD package moves from import to validation, review, approval, activation, supersession, retirement, and archival preservation. It also defines the guard conditions, user actions, system actions, blocked transitions, audit requirements, and immutability rules required for production use.

This document does not yet specify exact Frappe DocTypes, fieldnames, or implementation tickets. Those shall be locked in later artefacts, especially the Domain Model and Data Dictionary and the complete Cursor Implementation Pack.

---

## 3. Governance Principle

The STD template lifecycle shall implement this principle:

> A Standard Tender Document template version may be used for tender creation only after it has passed structural validation, received formal approval, been explicitly activated, and become protected against uncontrolled mutation.

This means:

1. import is not approval;
2. validation is not approval;
3. approval is not activation;
4. activation is version-specific;
5. active templates are immutable;
6. used templates are historically locked;
7. superseded and retired templates remain auditable;
8. every lifecycle transition must be role-checked, audit-recorded, and server-enforced.

---

## 4. Lifecycle Object Under Governance

The governed object is the STD template version, whether implemented initially as an extended `STD Template` record or later as a separate `STD Template Version` record.

Conceptually, the governed unit is:

```text
STD Template Family
→ STD Template Version
→ Package Payload / Manifest / Hash
```

For production governance, state belongs to the **version**, not merely the family.

Example:

```text
Family: WORKS Building Works STD
Version: KE-PPRA-WORKS-BLDG-2022-04-POC / V1
Package Hash: <sha256>
Lifecycle Status: Active
```

## 5. Lifecycle State Catalogue

The STD template lifecycle shall use the following states.

| State | Meaning | Tender creation allowed? | Package mutation allowed? |
|---|---|---:|---:|
| `Imported` | Package has been imported but not validated | No | Controlled replacement allowed |
| `Validation Failed` | Validation ran and blocking findings exist | No | Controlled replacement allowed |
| `Validated` | Current package hash passed validation | No | Controlled replacement allowed, but resets validation |
| `Submitted for Approval` | Template submitted for formal approval | No | No, unless returned to correction |
| `Returned for Correction` | Reviewer/approver returned package for correction | No | Controlled replacement allowed |
| `Rejected` | Template rejected | No | No operational mutation; new import/version required |
| `Approved` | Template approved but not active | No | No package mutation |
| `Active` | Template version usable for tender creation | Yes | No package mutation |
| `Suspended` | Temporarily blocked from new use pending review | No | No package mutation |
| `Superseded` | Replaced by newer approved/active version | No for new tenders | No package mutation |
| `Retired` | Removed from future tender creation | No | No package mutation |
| `Archived` | Historical record retained only | No | No package mutation |

`Suspended` is included to support emergency governance where an active template must be blocked immediately without losing historical status. It is optional in UI prominence but should be supported in the state model if production governance requires emergency control.

## 6. State Meaning and Operational Rules

### 6.1 Imported

A template enters `Imported` after package import succeeds at the storage level.

Rules:

1. package payload exists;
2. package hash exists;
3. source metadata should exist;
4. validation has not yet passed;
5. template cannot be used for tender creation;
6. package may be replaced through controlled re-import;
7. ordinary procurement officers cannot view or use it.

Allowed next states:

1. `Validated`;
2. `Validation Failed`;
3. `Archived` if abandoned.

---

### 6.2 Validation Failed

A template enters `Validation Failed` when structural/package validation produces blocking findings.

Rules:

1. template cannot be submitted for approval;
2. template cannot be activated;
3. template cannot be used for tender creation;
4. correction requires controlled replacement or new import;
5. validation result must be retained.

Allowed next states:

1. `Imported` after controlled replacement;
2. `Validated` after revalidation passes;
3. `Archived` if abandoned.

---

### 6.3 Validated

A template enters `Validated` when package validation passes against the current package hash.

Rules:

1. current validation result must reference current package hash;
2. template is eligible for submission for approval;
3. template is not yet approved;
4. template is not yet active;
5. template cannot be used for tender creation;
6. any package content change resets status to `Imported` or `Validation Failed` depending on validation outcome.

Allowed next states:

1. `Submitted for Approval`;
2. `Imported` after controlled replacement;
3. `Validation Failed` after failed revalidation;
4. `Archived` if abandoned.

---

### 6.4 Submitted for Approval

A template enters `Submitted for Approval` when an authorized user submits a validated template for formal approval.

Rules:

1. approval request must reference validation run and package hash;
2. package mutation is blocked;
3. template cannot be used for tender creation;
4. reviewer/approver must be able to inspect package summary, validation result, forms, rules, BoQ/Works readiness where applicable, render preview, and audit metadata;
5. template may be approved, rejected, or returned for correction.

Allowed next states:

1. `Approved`;
2. `Returned for Correction`;
3. `Rejected`.

---

### 6.5 Returned for Correction

A template enters `Returned for Correction` when reviewer/approver requires changes before approval.

Rules:

1. return reason/comment is mandatory;
2. template cannot be used for tender creation;
3. correction requires controlled replacement or new package version;
4. after correction, validation must run again;
5. previous review history must remain auditable.

Allowed next states:

1. `Imported` after controlled replacement;
2. `Validated` only after revalidation passes;
3. `Archived` if abandoned.

---

### 6.6 Rejected

A template enters `Rejected` when approval is refused.

Rules:

1. rejection reason/comment is mandatory;
2. template cannot be used for tender creation;
3. template cannot be activated;
4. rejected package should not be mutated into a new candidate; a new import/version should be created for resubmission unless policy allows reopening;
5. rejection record must remain auditable.

Allowed next states:

1. `Archived`;
2. optional `Imported` only through explicit governed reopen action. Default: not allowed.

---

### 6.7 Approved

A template enters `Approved` when an authorized approver approves it.

Rules:

1. approval must reference current validation run;
2. approval must reference current package hash;
3. package mutation is blocked;
4. template is not yet usable for tender creation until activated;
5. activation requires a separate authorized action unless policy explicitly merges approval and activation. Default: separate.

Allowed next states:

1. `Active`;
2. `Returned for Correction` only through explicit approval withdrawal policy. Default: not allowed;
3. `Retired` if approved but never activated and no longer needed;
4. `Archived` if abandoned under governance.

---

### 6.8 Active

A template enters `Active` when an approved version is explicitly activated for tender creation.

Rules:

1. template can be used for new tender creation;
2. `allowed_for_tender_creation` must be true;
3. package mutation is blocked;
4. activation must reference approval record and package hash;
5. usage must be tracked;
6. if used by any tender, template version becomes historically locked forever;
7. template can later be suspended, superseded, retired, or archived only according to governance rules.

Allowed next states:

1. `Suspended`;
2. `Superseded`;
3. `Retired`.

---

### 6.9 Suspended

A template enters `Suspended` when an active template must be temporarily blocked from new tender creation pending review.

Rules:

1. new tender creation is blocked;
2. existing tenders remain linked to the template version used;
3. suspension reason is mandatory;
4. package mutation remains blocked;
5. template can be reactivated only after review/authorization;
6. suspension must be audit-recorded.

Allowed next states:

1. `Active` after authorized reinstatement;
2. `Superseded`;
3. `Retired`.

---

### 6.10 Superseded

A template enters `Superseded` when a newer approved/active version replaces it.

Rules:

1. new tender creation is blocked from superseded version;
2. existing tenders remain linked to superseded version;
3. superseding version must be identified;
4. supersession reason and effective date are mandatory;
5. package mutation is blocked;
6. usage and historical audit remain visible.

Allowed next states:

1. `Archived` when no longer operationally needed but still historically retained;
2. `Retired` if policy distinguishes retired from superseded.

Default: superseded versions remain in `Superseded`, not archived, while tenders using them remain active or legally relevant.

---

### 6.11 Retired

A template enters `Retired` when it is removed from future operational use without necessarily being replaced by a newer version.

Rules:

1. new tender creation is blocked;
2. retirement reason is mandatory;
3. package mutation is blocked;
4. existing tenders remain linked;
5. historical audit remains visible;
6. reactivation should be disallowed by default unless an explicit governed reinstatement policy exists.

Allowed next states:

1. `Archived`;
2. optional `Active` only through explicit governed reinstatement. Default: not allowed.

---

### 6.12 Archived

A template enters `Archived` when it is preserved as historical record only.

Rules:

1. new tender creation is blocked;
2. package mutation is blocked;
3. archive reason is mandatory;
4. template remains discoverable to auditors/admins;
5. template remains linked to historical tenders;
6. deletion is not allowed if ever used by a tender.

Allowed next states:

None by default.

## 7. State Transition Matrix

| From state | Action | To state | Actor | Guard condition |
|---|---|---|---|---|
| Imported | Run validation: pass | Validated | Template Administrator | Package complete and no blocking findings |
| Imported | Run validation: fail | Validation Failed | Template Administrator | Blocking findings exist |
| Imported | Archive abandoned import | Archived | Template Administrator / System Manager | No tender usage |
| Validation Failed | Replace package | Imported | Template Administrator | Controlled replacement uploaded; new hash |
| Validation Failed | Re-run validation: pass | Validated | Template Administrator | Findings resolved |
| Validation Failed | Archive abandoned package | Archived | Template Administrator / System Manager | No tender usage |
| Validated | Submit for approval | Submitted for Approval | Template Administrator | Current validation passes and package hash unchanged |
| Validated | Replace package | Imported | Template Administrator | Controlled replacement; validation reset |
| Validated | Re-run validation: fail | Validation Failed | Template Administrator | New blocking findings |
| Validated | Archive abandoned package | Archived | Template Administrator / System Manager | Not submitted; no usage |
| Submitted for Approval | Approve | Approved | Template Approver | Current validation hash matches; approval permission |
| Submitted for Approval | Return for correction | Returned for Correction | Reviewer / Approver | Return comment provided |
| Submitted for Approval | Reject | Rejected | Template Approver | Rejection comment provided |
| Returned for Correction | Replace package | Imported | Template Administrator | Controlled replacement; new hash |
| Returned for Correction | Re-run validation: pass | Validated | Template Administrator | Correction validated |
| Returned for Correction | Archive abandoned package | Archived | Template Administrator / System Manager | No usage |
| Rejected | Archive | Archived | Template Administrator / System Manager | Rejection retained |
| Approved | Activate | Active | Template Activator / System Manager | Approval exists; hash unchanged; activation reason provided |
| Approved | Retire before activation | Retired | Template Activator / System Manager | Retirement reason provided; no usage |
| Active | Suspend | Suspended | Template Activator / System Manager | Suspension reason provided |
| Active | Supersede | Superseded | Template Activator / System Manager | Superseding approved/active version identified |
| Active | Retire | Retired | Template Activator / System Manager | Retirement reason provided; impact reviewed |
| Suspended | Reinstate | Active | Template Activator / System Manager | Reinstatement reason and authorization |
| Suspended | Supersede | Superseded | Template Activator / System Manager | Superseding approved/active version identified |
| Suspended | Retire | Retired | Template Activator / System Manager | Retirement reason provided |
| Superseded | Archive | Archived | System Manager / Auditor policy | Historical retention policy permits |
| Retired | Archive | Archived | System Manager / Auditor policy | Historical retention policy permits |

Transitions not listed are disallowed by default.

## 8. Transition Guard Catalogue

### 8.1 Validation Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-VAL-001` | Package payload exists | Run validation |
| `STD-GUARD-VAL-002` | Package hash exists | Run validation |
| `STD-GUARD-VAL-003` | Required manifest fields exist | Run validation |
| `STD-GUARD-VAL-004` | Fields/rules/forms/sections parse successfully | Run validation |
| `STD-GUARD-VAL-005` | Rule references resolve to known fields/forms/sections | Run validation |
| `STD-GUARD-VAL-006` | Render/preview test can run where required | Run validation |
| `STD-GUARD-VAL-007` | Category-specific checks pass or findings recorded | Run validation |

### 8.2 Submission Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-SUB-001` | Status is `Validated` | Submit for approval |
| `STD-GUARD-SUB-002` | Latest validation status passes | Submit for approval |
| `STD-GUARD-SUB-003` | Latest validation package hash equals current package hash | Submit for approval |
| `STD-GUARD-SUB-004` | Submission comment captured if required | Submit for approval |

### 8.3 Approval Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-APP-001` | Status is `Submitted for Approval` | Approve/reject/return |
| `STD-GUARD-APP-002` | Approver has permission | Approve |
| `STD-GUARD-APP-003` | Latest validation package hash equals current package hash | Approve |
| `STD-GUARD-APP-004` | No critical validation findings | Approve |
| `STD-GUARD-APP-005` | Approval comments captured | Approve |
| `STD-GUARD-APP-006` | Separation-of-duty rule satisfied or override recorded | Approve |

### 8.4 Activation Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-ACT-001` | Status is `Approved` | Activate |
| `STD-GUARD-ACT-002` | Approval record exists | Activate |
| `STD-GUARD-ACT-003` | Approval package hash equals current package hash | Activate |
| `STD-GUARD-ACT-004` | Activator has permission | Activate |
| `STD-GUARD-ACT-005` | Activation reason captured | Activate |
| `STD-GUARD-ACT-006` | Active version policy satisfied | Activate |
| `STD-GUARD-ACT-007` | `allowed_for_tender_creation` set consistently | Activate |

### 8.5 Supersession / Retirement Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-END-001` | Current status is Active or Suspended | Supersede/retire |
| `STD-GUARD-END-002` | Impact analysis has been generated | Supersede/retire |
| `STD-GUARD-END-003` | Reason captured | Supersede/retire |
| `STD-GUARD-END-004` | Superseding template identified, if superseding | Supersede |
| `STD-GUARD-END-005` | Superseding template is Approved or Active | Supersede |
| `STD-GUARD-END-006` | Existing tender usage remains linked | Supersede/retire |

### 8.6 Mutation Guards

| Guard code | Guard | Applies to |
|---|---|---|
| `STD-GUARD-MUT-001` | Package mutation allowed only in Imported, Validation Failed, Validated, Returned for Correction | Package replacement |
| `STD-GUARD-MUT-002` | Mutation blocked in Submitted for Approval, Approved, Active, Suspended, Superseded, Retired, Archived | Package replacement |
| `STD-GUARD-MUT-003` | Mutation blocked permanently if template has tender usage | Package replacement/delete |
| `STD-GUARD-MUT-004` | Any package replacement creates new package hash | Package replacement |
| `STD-GUARD-MUT-005` | Package replacement resets validation and approval evidence | Package replacement |

## 9. Allowed Actions by State

| State | Allowed user actions |
|---|---|
| Imported | Run validation; replace package; archive |
| Validation Failed | View findings; replace package; rerun validation; archive |
| Validated | View findings; submit for approval; replace package; rerun validation; archive |
| Submitted for Approval | Review; approve; return; reject; view package/read-only diagnostics |
| Returned for Correction | View return comments; replace package; rerun validation; archive |
| Rejected | View rejection comments; archive |
| Approved | Activate; retire before activation; view read-only package |
| Active | View; inspect; suspend; supersede; retire; view usage; bind to tender |
| Suspended | View; inspect; reinstate; supersede; retire; view usage |
| Superseded | View; inspect; view usage; archive if policy permits |
| Retired | View; inspect; view usage; archive if policy permits |
| Archived | View historical record only |

Actions not shown are disallowed by default.

---

## 10. Blocked Actions

The following actions shall be blocked server-side.

| Attempted action | Block condition | Required response |
|---|---|---|
| Use template for tender | Status not Active | Block and show lifecycle status |
| Use template for tender | `allowed_for_tender_creation` false | Block and show eligibility reason |
| Approve template | Latest validation not passing | Block and show validation result |
| Approve template | Package hash changed since validation | Block and require revalidation |
| Activate template | Status not Approved | Block |
| Activate template | Approval missing or hash mismatch | Block |
| Edit package payload | Status protected | Block and audit mutation attempt |
| Delete template | Template used by tender | Block and audit deletion attempt |
| Supersede without replacement | Superseding template missing | Block |
| Retire without reason | Reason missing | Block |
| Self-approve | Separation-of-duty policy violated | Block or require audited override |

## 11. Template Creation and Import Flow

```text
Authorized importer/admin
→ Import STD package
→ System stores package payload and computes package hash
→ Status = Imported
→ System records STD_TEMPLATE_IMPORTED audit event
```

Postconditions:

1. package payload exists;
2. package hash exists;
3. lifecycle status is `Imported`;
4. validation status is `Not Run` or equivalent;
5. allowed for tender creation is false;
6. template is not selectable for tenders.

---

## 12. Validation Flow

```text
Imported / Validation Failed / Validated / Returned for Correction
→ Run Validation
→ Validation passes or fails
→ Status = Validated or Validation Failed
```

Validation pass postconditions:

1. lifecycle status = `Validated`;
2. latest validation status = `Pass` or `Pass with Warnings` if no blocking findings;
3. validation package hash = current package hash;
4. validation result stored;
5. allowed for tender creation remains false.

Validation fail postconditions:

1. lifecycle status = `Validation Failed`;
2. validation result stored;
3. critical findings visible;
4. allowed for tender creation remains false.

---

## 13. Submission for Approval Flow

```text
Validated
→ Submit for Approval
→ Status = Submitted for Approval
```

Postconditions:

1. submission actor stored;
2. submission timestamp stored;
3. submission comment stored where required;
4. validation run reference stored;
5. package hash at submission stored;
6. package mutation blocked;
7. allowed for tender creation remains false.

---

## 14. Approval Decision Flow

### 14.1 Approve

```text
Submitted for Approval
→ Approve
→ Status = Approved
```

Postconditions:

1. approver stored;
2. approval timestamp stored;
3. approval comments stored;
4. approved package hash stored;
5. validation run reference stored;
6. package mutation blocked;
7. allowed for tender creation remains false until activation.

### 14.2 Return for Correction

```text
Submitted for Approval
→ Return for Correction
→ Status = Returned for Correction
```

Postconditions:

1. return actor stored;
2. return timestamp stored;
3. return comments stored;
4. package remains not usable;
5. controlled replacement allowed;
6. validation must run again after correction.

### 14.3 Reject

```text
Submitted for Approval
→ Reject
→ Status = Rejected
```

Postconditions:

1. rejection actor stored;
2. rejection timestamp stored;
3. rejection comments stored;
4. package remains not usable;
5. default path is archival or new import/version, not mutation.

---

## 15. Activation Flow

```text
Approved
→ Activate
→ Status = Active
→ allowed_for_tender_creation = true
```

Postconditions:

1. activator stored;
2. activation timestamp stored;
3. activation reason stored;
4. active-from date stored;
5. approval reference stored;
6. package hash at activation stored;
7. template selectable for tender creation;
8. package mutation blocked.

Activation must fail if approval hash and current package hash differ.

---

## 16. Suspension Flow

```text
Active
→ Suspend
→ Status = Suspended
→ allowed_for_tender_creation = false
```

Postconditions:

1. suspension actor stored;
2. suspension timestamp stored;
3. suspension reason stored;
4. new tender creation blocked;
5. existing tender links preserved;
6. package mutation remains blocked.

Suspension is temporary. It is intended for emergency blocking pending review.

---

## 17. Supersession Flow

```text
Active / Suspended
→ Supersede with approved or active replacement
→ Status = Superseded
→ allowed_for_tender_creation = false
```

Postconditions:

1. supersession actor stored;
2. supersession timestamp stored;
3. supersession reason stored;
4. superseding template/version recorded;
5. superseded-by reference stored;
6. new tender creation blocked from old version;
7. historical tender usage remains linked to old version;
8. package mutation remains blocked.

---

## 18. Retirement Flow

```text
Active / Suspended / Approved
→ Retire
→ Status = Retired
→ allowed_for_tender_creation = false
```

Postconditions:

1. retirement actor stored;
2. retirement timestamp stored;
3. retirement reason stored;
4. new tender creation blocked;
5. historical usage remains linked;
6. package mutation remains blocked.

---

## 19. Archival Flow

```text
Rejected / Retired / Superseded / abandoned Imported/Validated candidates
→ Archive
→ Status = Archived
```

Postconditions:

1. archive actor stored;
2. archive timestamp stored;
3. archive reason stored;
4. package mutation blocked;
5. new tender creation blocked;
6. historical visibility retained.

If a template has ever been used by a tender, archival must not delete or obscure historical access.

## 20. Active Version Policy

The active version policy must be explicit.

Recommended default policy for production:

| Scope | Policy |
|---|---|
| Same template family + same procurement category + same method profile | Only one active default version |
| Multiple variants | Allowed only where variant keys differ clearly |
| Supersession | New active version should supersede previous default version |
| Historical tenders | Continue to reference original version |

Example:

```text
WORKS / Building Works / Open Tender / National
→ only one active default STD template version
```

If multiple active templates exist for the same category/method, tender creation must require deterministic resolution. It must not guess.

---

## 21. Versioning Rules

### 21.1 New Version Required

A new version is required when any of these change:

1. legal clause text;
2. section structure;
3. configurable field definitions;
4. rule definitions;
5. required form definitions;
6. form activation logic;
7. BoQ structure for Works;
8. derived submission model logic;
9. derived opening model logic;
10. derived evaluation model logic;
11. contract carry-forward logic;
12. package schema affecting tender output.

### 21.2 New Version Not Required

A new version may not be required for:

1. admin-only metadata correction;
2. typo in internal admin note;
3. non-operational description correction;
4. archival tag update.

However, any metadata change after approval/activation must be audit-recorded.

---

## 22. Mutation Control Rules

### 22.1 Protected Content

The following package content is protected:

1. manifest;
2. fields;
3. rules;
4. forms;
5. sections;
6. rendering templates;
7. validation tests;
8. sample tender used for validation;
9. Works BoQ schema;
10. derived model definitions;
11. legal text or legal references.

### 22.2 Mutation Behavior

| Lifecycle status | Package content mutation |
|---|---|
| Imported | Allowed only through controlled replacement |
| Validation Failed | Allowed only through controlled replacement |
| Validated | Allowed only through controlled replacement; validation resets |
| Submitted for Approval | Blocked |
| Returned for Correction | Allowed only through controlled replacement |
| Rejected | Blocked by default |
| Approved | Blocked |
| Active | Blocked |
| Suspended | Blocked |
| Superseded | Blocked |
| Retired | Blocked |
| Archived | Blocked |

Controlled replacement must create a new package hash and invalidate prior validation/approval evidence.

---

## 23. Tender Creation Eligibility Rules

A template is eligible for new tender creation only if all are true:

1. lifecycle status = `Active`;
2. allowed for tender creation = true;
3. package hash exists;
4. activation package hash equals current package hash;
5. approval package hash equals current package hash;
6. latest validation package hash equals current package hash;
7. not suspended;
8. not superseded;
9. not retired;
10. not archived;
11. method/category/profile mapping allows this template for the tender package.

If any condition fails, tender creation must fail closed.

---

## 24. Usage Tracking Rules

When a template is used for a tender or tender STD instance, the system shall record usage.

Required usage event:

```text
STD_TEMPLATE_USED_FOR_TENDER
```

Usage postconditions:

1. template version becomes historically locked;
2. package deletion blocked;
3. package mutation blocked permanently;
4. usage count increments or becomes derivable;
5. tender reference appears in usage list where permissions allow;
6. future supersession/retirement does not alter existing tender binding.

| Return | actor, timestamp, reason, package hash |
| Reject | actor, timestamp, reason, package hash |
| Activate | actor, timestamp, approval reference, package hash, active-from, reason |

| Supersede | actor, timestamp, replacement template, reason, usage impact |
| Retire | actor, timestamp, reason, usage impact |

## 26. Separation of Duties Policy

Default policy:

| Rule | Default |
|---|---|
| Importer may submit for approval | Yes |
| Importer may approve own template | No |
| Validator may approve own validation | Allowed only if also approver, but discouraged |
| Approver may activate | Allowed only if policy permits; recommended separation for production |
| System Manager override | Allowed only with mandatory audit reason |
| Same user can approve and activate in POC | Not preferred; production must make policy explicit |

The Role and Permission Matrix artefact shall finalize these rules.

---

## 27. Governance Failure Modes

The system must fail closed for these failure modes.

| Failure mode | Required outcome |
|---|---|
| Validation result missing | Block approval |
| Validation package hash mismatch | Block approval and activation |
| Approval package hash mismatch | Block activation |
| Package hash missing | Block validation approval activation and tender creation |
| Approval missing | Block activation |
| Activation missing | Block tender creation |
| Template inactive | Block tender creation |
| Template superseded/retired | Block new tender creation |
