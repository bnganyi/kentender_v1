## 1. Purpose

This document defines the formal release process from **Procurement Planning** into **Tender Management**, with STD Engine integration.

The release process is the bridge between:

```text
Procurement Package
        ↓
Tender
        ↓
STD Instance
```

It ensures that a tender is not created arbitrarily or without a compatible active STD where an STD is required.

This artifact answers:

1. When may a procurement package be released to tender?
2. What package data constrains the tender?
3. How does the system find eligible STD templates?
4. When is an STD Instance created?
5. What release blockers prevent tender creation?
6. What audit evidence is required?
7. What does the future Tender module receive from Planning and STD Engine?

---

## 2. Core Principle

A Tender is not an isolated record.

A Tender is created from a released Procurement Package and must preserve the package’s approved procurement intent.

The STD Engine then provides the legally structured tender document model that operationalizes that intent.

The correct flow is:

```text
Approved Procurement Package
        ↓
Release Eligibility Check
        ↓
Eligible STD Template/Profile Lookup
        ↓
Tender Creation
        ↓
STD Instance Creation
        ↓
Tender Preparation
```

## 3. Key Objects

### 3.1 Procurement Plan

A Procurement Plan is the approved planning container for procurement activities within a planning period.

It may contain multiple procurement packages.

### 3.2 Procurement Package

A Procurement Package is the planning-level unit that will eventually become one or more tenders depending on procurement strategy.

It contains:

- procurement category;
- procurement method;
- estimated value;
- procuring entity;
- funding source;
- procurement description;
- lotting strategy;
- contract type;
- timing information;
- approvals;
- budget confirmation;
- release status.

### 3.3 Tender

A Tender is the operational procurement lifecycle object created from a released package.

It inherits approved package context but obtains legal tender behavior from the STD Engine.

### 3.4 STD Template Version

An active structured official standard tender document version available for use.

### 3.5 Applicability Profile

The method/category/contract-type-specific compatibility profile that determines whether a template can be used for a package.

### 3.6 STD Instance

The tender-specific realization of the selected STD Template Version, created only after Tender creation or during Tender creation transaction.

## 4. Planning-to-Tender Release Boundary

### 4.1 What Planning Owns

Planning owns:

| Area | Planning Responsibility |
|---|---|
| Procurement need | Defines what is being procured. |
| Package identity | Defines package code/title. |
| Procurement category | Works/Goods/Consultancy/etc. |
| Procurement method | Open Tender, Restricted Tender, RFQ, etc. |
| Estimated cost | Planning estimate and budget linkage. |
| Funding | Budget/funding confirmation. |
| Lotting strategy | Whether package will be tendered as one or multiple lots. |
| Release approval | Whether package may proceed to tendering. |

### 4.2 What Tender Owns

Tender owns:

| Area | Tender Responsibility |
|---|---|
| Tender lifecycle | Preparation, approval, publication, submission, opening, evaluation, award, contract initiation. |
| Tender calendar | Tender-specific milestones after release. |
| Committee workflows | Opening/evaluation/approval committees. |
| Publication workflow | Publishing tender documents and addenda. |
| Tender status | Operational lifecycle status. |

### 4.3 What STD Engine Owns

STD Engine owns:

| Area | STD Responsibility |
|---|---|
| Eligible template lookup | Finds compatible active templates/profiles. |
| STD Instance creation | Creates tender-specific STD instance through Tender context. |
| Structured tender document | Generates Bundle. |
| Submission rules | Generates DSM. |
| Opening register model | Generates DOM. |
| Evaluation model | Generates DEM. |
| Contract carry-forward | Generates DCM. |
| Readiness | Confirms STD is complete before publication. |

## 5. Release Preconditions

A procurement package may be released to tender only when all required conditions are met.

| Precondition | Required Result |
|---|---|
| Package approved | Package must be approved under Planning governance. |
| Budget/funding confirmed | Required if system enforces budget control. |
| Procurement category present | Required for STD eligibility. |
| Procurement method present | Required for STD eligibility. |
| Contract type present | Required where template/profile compatibility depends on it. |
| Lotting strategy resolved | Required before tender creation. |
| Procurement description complete | Required for tender title/scope. |
| No unresolved planning blockers | Required. |
| Eligible STD exists if STD required | Required. |
| User authorized to release | Required. |

---

## 6. Release Blockers

The release service shall block tender creation if any critical condition is false.

| Blocker Code | Meaning | Severity |
|---|---|---|
| PLAN_PACKAGE_NOT_APPROVED | Package has not completed planning approval. | Critical |
| PLAN_BUDGET_NOT_CONFIRMED | Budget or funding is not confirmed where required. | Critical |
| PLAN_CATEGORY_MISSING | Procurement category is missing. | Critical |
| PLAN_METHOD_MISSING | Procurement method is missing. | Critical |
| PLAN_CONTRACT_TYPE_MISSING | Contract type required for compatibility is missing. | High/Critical |
| PLAN_LOTTING_UNRESOLVED | Lotting strategy has not been resolved. | High |
| STD_NO_ELIGIBLE_TEMPLATE | No active compatible STD template/profile found. | Critical |
| STD_MULTIPLE_ELIGIBLE_REQUIRES_SELECTION | Multiple eligible STD options exist and user must select one. | High |
| RELEASE_PERMISSION_DENIED | Actor lacks release permission. | Critical |
| PACKAGE_ALREADY_RELEASED | Package has already been released to a current tender. | Critical unless multi-tender strategy allowed |

## 7. Eligible STD Lookup

### 7.1 Service

The STD Engine shall expose an eligibility service:

```text
get_eligible_std_templates(package_context)
```

### 7.2 Input Contract

```yaml
package_context:
  package_code: string required
  procuring_entity_code: string required
  procurement_category: string required
  procurement_method: string required
  contract_type: string optional
  works_profile_type: string optional
  estimated_value: decimal optional
  lotting_strategy: string optional
  funding_source_type: string optional
  procurement_description: text optional
```

### 7.3 Output Contract

```yaml
eligible_std_options:
  - template_version_code: string
    template_title: string
    revision_label: string
    source_authority: string
    applicability_profile_code: string
    profile_title: string
    procurement_category: string
    supported_methods:
      - string
    contract_types:
      - string
    requires_boq: boolean
    requires_drawings: boolean
    requires_specifications: boolean
    compatibility_status: Compatible
    compatibility_notes: text optional
```

### 7.4 Compatibility Rules

A template/profile is eligible only if:

1. template version status is Active;
2. applicability profile status is Active;
3. procurement category matches;
4. procurement method is allowed by profile;
5. contract type matches where required;
6. Works profile type matches where required;
7. template is not retired or superseded for new tenders;
8. effective dates permit use, if configured.

## 8. Release Modes

### 8.1 Single Eligible STD

If exactly one eligible STD template/profile exists, the system may auto-select it, subject to user confirmation.

Required confirmation:

```text
The package will be released to tender using: [STD title/version/profile].
```

### 8.2 Multiple Eligible STDs

If multiple eligible options exist, the user must select one.

The system must not silently choose if compatibility differs materially.

### 8.3 No Eligible STD

If no eligible STD exists and STD use is mandatory, release is blocked.

If STD use is optional for a specific procurement pathway, release may proceed only under an explicit exception rule.

### 8.4 Non-STD Procurement Route

For future procurement types that do not use a full STD, the system must still have a structured method package or controlled document model.

This document assumes STD is required for the relevant formal tender routes.

## 9. Tender Creation Contract

### 9.1 Tender Creation Service

The Tender module shall expose or implement:

```text
create_tender_from_package(package_code, selected_std_option, actor)
```

### 9.2 Required Transaction

Tender creation and STD Instance creation should be transactionally linked.

Preferred transaction:

```text
Begin transaction
  validate package release eligibility
  resolve selected STD template/profile
  create Tender
  create Tender STD Binding
  create STD Instance
  initialize STD Instance placeholders
  write audit events
Commit transaction
```

If STD Instance creation fails, Tender creation should fail or remain in a clearly blocked/incomplete release state. It must not silently create a tender without required STD binding.

### 9.3 Tender Fields Initialized from Package

```yaml
tender:
  tender_code: generated or assigned
  package_code: source package
  procuring_entity_code: from package
  title: from package or user-confirmed derivative
  procurement_category: from package
  procurement_method: from package
  contract_type: from package
  lotting_strategy: from package
  estimated_value: from package
  tender_status: Draft / Preparation
  source_release_code: generated release event
```

### 9.4 STD Binding Created at Tender Creation

```yaml
tender_std_binding:
  tender_code: created tender
  package_code: source package
  std_instance_code: created instance
  template_version_code: selected template
  applicability_profile_code: selected profile
  binding_status: Draft
  std_readiness_status: Not Run
```

## 10. STD Instance Initialization from Package

When the STD Instance is created, the system shall initialize known values from the package context where safe.

### 10.1 Auto-Initialized Values

| Source Package Field | STD Instance Target | Rule |
|---|---|---|
| procuring entity | employer/procuring entity parameter | Auto-fill if parameter exists. |
| package title | tender title parameter | Auto-fill, user may adjust before publication. |
| procurement method | method parameter/profile | Locked/inherited from package unless tender governance permits change. |
| procurement category | category field | Locked/inherited. |
| lotting strategy | lot-related configuration | Initialize if template supports lots. |
| contract type | profile/contract parameter | Initialize if mapped. |
| estimated value | internal planning reference | Not supplier-facing unless configured. |

### 10.2 Values Not Auto-Initialized

The following generally require tender-stage input:

| Value | Reason |
|---|---|
| submission deadline | Tender calendar decision. |
| opening date/time | Tender calendar decision. |
| tender security amount | Tender-specific risk/threshold decision. |
| BOQ quantities/items | Technical preparation required. |
| specifications | Technical documents required. |
| drawings | Technical documents required. |
| SCC contract-specific details | Tender/contract preparation required. |

## 11. Package Release Record

### 11.1 Purpose

The release record proves that an approved package was handed off to Tender Management and STD Engine.

### 11.2 Model

```yaml
planning_tender_release:
  release_code: string unique required
  package_code: string required
  tender_code: string required
  std_instance_code: string optional
  template_version_code: string optional
  applicability_profile_code: string optional
  release_status: enum Pending/Released/Blocked/Cancelled/Superseded
  release_mode: enum Single STD Auto-Selected/STD Selected by User/Exception/No STD Required
  release_requested_by: user required
  release_requested_at: datetime required
  release_approved_by: user optional
  release_approved_at: datetime optional
  blocker_count: integer
  blocker_summary: json optional
  audit_event_code: string required
```

### 11.3 Rules

1. Every Tender created from Planning must have a release record.
2. Release record must reference selected STD where STD applies.
3. Blocked release attempts must be recorded for audit.
4. Release record is append-only after completion except controlled status transitions.

## 12. Release Status Model

| Status | Meaning |
|---|---|
| Pending | Release requested but not completed. |
| Blocked | Release failed due to blockers. |
| Released | Tender and STD binding created. |
| Cancelled | Release attempt cancelled before tender creation. |
| Superseded | Release replaced by later release due to package/tender reissue. |

Normal flow:

```text
Pending → Released
```

Blocked flow:

```text
Pending → Blocked → Pending → Released
```

Cancellation flow:

```text
Pending → Cancelled
```

## 13. Authorization Rules

### 13.1 Required Permissions

| Action | Required Permission |
|---|---|
| Request release to tender | PERM_PACKAGE_RELEASE_TO_TENDER or equivalent |
| Create tender from package | PERM_TENDER_CREATE |
| Select STD option | PERM_TENDER_CREATE or controlled release permission |
| Create STD Instance | PERM_INSTANCE_CREATE |
| Override release blocker | Controlled high-risk permission; discouraged |

If `PERM_PACKAGE_RELEASE_TO_TENDER` does not yet exist, it must be added to the permissions seed.

### 13.2 Role Rules

| Role | Release Package? | Select STD? | Create Tender? |
|---|---|---|---|
| Procurement Officer | Yes, if assigned to package | Yes | Yes |
| Procurement Assistant | No unless delegated | No by default | No |
| Approving Authority | Approves release where required | May approve, not configure | No operational creation unless role combined |
| STD Administrator | No | No | No |
| Auditor | No | No | No |
| System Administrator | No operational release | No | No |

---

## 14. Audit Requirements

The system shall audit:

1. release eligibility checked;
2. release blocked;
3. eligible STD options returned;
4. STD option selected;
5. Tender created;
6. STD Instance created;
7. Tender STD binding created;
8. release completed;
9. release cancelled;
10. release superseded;
11. unauthorized release attempt;
12. blocker override attempt.

Audit events must preserve:

- package code;
- tender code if created;
- selected template/profile;
- actor;
- timestamp;
- blockers;
- decision outcome.

## 16. UI Boundary

This artifact does not design the full Tender UI.

However, the future Planning or Tender release UI must support:

1. displaying release blockers;
2. showing eligible STD options;
3. confirming selected STD;
4. creating tender;
5. showing created Tender and STD Instance references.

It must not expose STD internals at this stage.

The user-facing label should be:

```text
Release to Tender
```

not:

```text
Create STD Instance
```

## 18. Smoke Contracts

### 18.1 Release Eligibility Tests

| Test | Expected Result |
|---|---|
| Approved Works package with active Works STD | Eligible |
| Package missing procurement method | Blocked |
| Package not approved | Blocked |
| No compatible active STD | Blocked |
| Multiple eligible STD options | Requires selection |

### 18.2 Release Creation Tests

| Test | Expected Result |
|---|---|
| Release valid package with selected STD | Tender and STD Instance created |
| STD Instance creation fails | Tender creation rolled back or release blocked |
| Package already released | Denied unless strategy allows multiple tenders |
| Unauthorized actor releases package | Denied and audited |

### 18.3 Binding Tests

| Test | Expected Result |
|---|---|
| Tender created from package | Tender has package reference |
| Tender created with STD | Tender has STD binding |
| STD binding missing where required | Release fails |
| Tender stores output references later | Supported by binding model |
