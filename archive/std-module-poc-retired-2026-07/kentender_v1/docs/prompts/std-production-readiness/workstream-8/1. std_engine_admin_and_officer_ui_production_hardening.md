## 1. Purpose

This document defines how the STD Engine should be presented in production UI surfaces after the backend governance, instance, output, publication, and security models have been defined.

The purpose is to prevent the system from exposing internal STD Engine complexity to users who should be completing procurement work, not managing data structures.

This document defines:

1. what each role sees;
2. what each role does;
3. how backend action availability controls UI actions;
4. how STD Administrator workflows remain library-oriented;
5. how Procurement Officer workflows remain tender-oriented;
6. how readiness, approval, publication, and evidence are surfaced;
7. how advanced technical views are hidden;
8. how UI avoids illegal operations such as manual criteria injection or direct post-publication edits.

---

## 2. Core UI Principle

The UI must present the work, not the engine.

Correct model:

```text
User role + object state + backend action availability
        ↓
Task-specific screen
        ↓
Allowed actions only
        ↓
Clear blockers and next steps
```

Incorrect model:

```text
Show all tabs, mappings, parameters, rules, JSON, and actions
        ↓
Expect user to understand the engine
```

The STD Engine remains structurally powerful, but ordinary users interact with business tasks:

- manage official STDs;
- release package to tender;
- configure tender document;
- complete Works requirements;
- generate outputs;
- run readiness;
- submit for approval;
- publish tender;
- view evidence.

## 4. Role-Specific UI Philosophy

### 4.1 STD Administrator

The STD Administrator manages official standards.

The UI must be:

```text
Official STD Library-oriented
```

The STD Administrator should see:

- official STD versions;
- structured package import;
- template validation;
- bundle preview;
- supersession;
- audit trail;
- advanced technical view only when necessary.

The STD Administrator should not see primary actions for:

- creating STD Instances;
- releasing procurement packages;
- completing tender-specific data;
- approving tenders;
- publishing tenders.

### 4.2 Procurement Officer

The Procurement Officer prepares and publishes tenders.

The UI must be:

```text
Tender-oriented
```

The Procurement Officer should see:

- release package to tender;
- configure tender document;
- complete TDS/SCC values;
- complete Works Requirements;
- upload specifications/drawings;
- complete BOQ;
- generate outputs;
- run readiness;
- submit for approval;
- publish after approval where permitted;
- view evidence.

The Procurement Officer should not see:

- raw template mappings;
- JSON package structure;
- template activation controls;
- legal template revision internals;
- manual evaluation criteria controls.

### 4.3 Procurement Assistant

The Procurement Assistant supports completion but does not own legal gates.

The UI must emphasize delegated tasks and limited authority.

The assistant may see:

- assigned tender completion tasks;
- draft data entry forms;
- document upload panels;
- BOQ import/entry if delegated;
- validation messages.

The assistant must not see enabled actions for:

- release package to tender by default;
- mark ready by default;
- submit for approval by default;
- approve;
- publish;
- override blockers.

### 4.4 Approving Authority

The Approving Authority reviews, returns, rejects, or approves.

The UI must be:

```text
Review package-oriented
```

The approver should see:

- read-only tender summary;
- readiness result;
- Bundle preview;
- output summaries;
- BOQ summary;
- Works Requirements summary;
- warnings/blockers;
- audit/evidence summary;
- decision actions.

The approver must not edit tender content directly.

### 4.5 Auditor

The Auditor reviews evidence.

The UI must be:

```text
Evidence-oriented
```

The auditor should see:

- tender evidence package;
- audit trail;
- generated output versions;
- snapshots;
- denied actions;
- publication record;
- downstream consumption references.

The auditor must not mutate objects.

## 5. Backend Action Availability Requirement

### 5.1 Rule

Every meaningful UI action must come from backend action availability.

The UI must not enable legal actions from frontend role checks alone.

### 5.2 Required UI Pattern

For each screen, frontend must request action availability for visible actions.

Example:

```text
GET/POST action availability for:
- IMPORT_OFFICIAL_STD_PACKAGE
- RELEASE_PACKAGE_TO_TENDER
- GENERATE_STD_OUTPUTS
- SUBMIT_TENDER_FOR_APPROVAL
- APPROVE_TENDER_PUBLICATION
- PUBLISH_TENDER
```

### 5.3 Button States

| Backend Result | UI Behavior |
|---|---|
| allowed=true | Button enabled. |
| allowed=false and action is relevant | Button disabled with reason. |
| allowed=false and action should not be exposed to role | Button hidden. |
| audit_on_attempt=true | Confirmation or explicit action logging where required. |
| requires_confirmation=true | Show confirmation dialog before execution. |

### 5.4 Disabled Reason Display

Disabled legal actions must explain why.

Example:

```text
Cannot publish: approval is not complete.
```

or:

```text
Cannot edit: this tender has been published. Use addendum workflow.
```

Do not show raw denial codes to ordinary users unless in advanced/admin/audit context.

## 6. STD Administrator UI Hardening

### 6.1 Landing Page

The default STD Administrator page shall remain:

```text
Official STD Library
```

Not:

- template object workbench;
- parameter table;
- mapping table;
- STD Instance list;
- raw package viewer.

### 6.2 Official STD Library Required Features

The library page must show:

- active STDs;
- draft/imported STDs;
- versions needing attention;
- superseded versions;
- validation status;
- bundle preview status;
- usage count;
- source authority and revision.

### 6.3 Primary Actions

Allowed primary action:

```text
Import Official STD Package
```

Secondary actions:

```text
Register Source Document
Validate Library
```

Prohibited primary actions:

```text
Create STD Instance
Release to Tender
Configure Tender Document
Approve Tender
Publish Tender
```

### 6.4 Advanced Technical View

Advanced Technical View must be:

- hidden by default;
- permission-gated;
- clearly labelled technical;
- read-only for Active template versions;
- unavailable to Procurement Officer.

### 6.5 STD Administrator Empty State

If no STD exists:

```text
No official STDs are available.
Import a structured official STD package before tenders can use standard documents.
```

Do not suggest creating STD Instances.

## 7. Planning / Package Release UI Hardening

### 7.1 Purpose

The release UI bridges approved procurement package to Tender creation and STD binding.

The user-facing label must be:

```text
Release to Tender
```

not:

```text
Create STD Instance
```

### 7.2 Required Release Screen Content

The release screen must show:

1. package summary;
2. release eligibility result;
3. blockers if any;
4. eligible STD options;
5. selected STD confirmation;
6. release action;
7. resulting Tender and STD Instance references after release.

### 7.3 Release Blocker Display

Blockers must be grouped as:

- Planning blockers;
- STD eligibility blockers;
- Permission blockers;
- Already released blockers.

Example:

```text
Release blocked: No active compatible STD template was found for this Works package.
Resolution: Activate a compatible Works STD template or correct the package category/method.
```

### 7.4 Multiple Eligible STDs

If multiple eligible STDs exist, user must select one.

The UI must show:

- STD title;
- revision;
- authority;
- profile;
- supported methods;
- requires BOQ/specifications/drawings.

### 7.5 Release Success State

After release:

```text
Package released to Tender successfully.
Tender: [tender code]
STD Instance: [instance code]
Next step: Configure Tender Document.
```

## 8. Tender STD Configuration Overview

### 8.1 Purpose

The Tender STD Configuration Overview is the Procurement Officer’s entry point after package release.

The user-facing label should be:

```text
Configure Tender Document
```

not:

```text
Edit STD Instance
```

### 8.2 Required Overview Content

The overview must show:

1. Tender and package context;
2. selected STD template/profile;
3. completion progress;
4. stage statuses;
5. generated output statuses;
6. readiness status;
7. next required action.

### 8.3 Required Completion Stages

For Works:

```text
Tender Data Sheet
Evaluation and Qualification Options
Works Requirements
Drawings
Bills of Quantities
Special Conditions of Contract
Generated Outputs
Readiness
Approval / Publication
```

### 8.4 Stage Status Values

```text
Not Started
Incomplete
Needs Attention
Complete
Stale
Locked
Not Applicable
```

### 8.5 Output Status Display

Show Bundle, DSM, DOM, DEM, DCM status clearly:

```text
Bundle: Current
DSM: Current
DOM: Stale
DEM: Missing
DCM: Current
```

Do not require the user to know acronyms without labels.

Display as:

```text
Submission Rules (DSM)
Opening Register (DOM)
Evaluation Rules (DEM)
Contract Carry-Forward (DCM)
```

## 9. Works Completion Workspace

### 9.1 Purpose

The Works Completion Workspace allows the Procurement Officer to complete tender-specific Works content.

It must be structured around the natural work of completing a tender, not around database tables.

### 9.2 Required Layout

```text
[A] Tender Context Header
[B] Completion Progress Sidebar
[C] Main Completion Panel
[D] Validation / Blockers Panel
[E] Output Impact Panel
[F] Save / Generate / Readiness Actions
```

### 9.3 Tender Context Header

Must show:

- tender title;
- package code;
- procurement category;
- procurement method;
- selected STD template;
- instance state;
- publication state.

### 9.4 Completion Progress Sidebar

Must show stages:

1. TDS;
2. Evaluation Options;
3. Works Requirements;
4. Drawings;
5. BOQ;
6. SCC;
7. Outputs;
8. Readiness.

### 9.5 Validation / Blockers Panel

Must show blockers in plain language:

```text
Bills of Quantities is incomplete.
Item 2.1 is missing quantity.
```

Do not show raw JSON validation errors.

### 9.6 Output Impact Panel

When user edits a field, show affected outputs:

```text
Changing this value will require regeneration of:
- Tender Document Bundle
- Submission Rules (DSM)
- Opening Register (DOM)
```

This reduces confusion when outputs become stale.

## 10. TDS and SCC UI Rules

### 10.1 TDS

TDS must be shown as grouped business fields:

- Tender Identity;
- Dates and Deadlines;
- Tender Security;
- Site Visit / Pre-Tender Meeting;
- Bid Validity;
- Submission Instructions;
- Language/Currency;
- Complaints/Review.

The UI must not show ITT clauses as editable text.

### 10.2 SCC

SCC must be shown as grouped contract fields:

- Completion Period;
- Defects Liability;
- Performance Security;
- Retention;
- Liquidated Damages;
- Payment;
- Insurance;
- Dispute Resolution.

The UI must not show GCC clauses as editable text.

### 10.3 Field-Level Help

Fields should provide short explanatory help where legal meaning is likely to be misunderstood.

Example:

```text
Completion period is carried into the contract and cannot be changed after publication except through controlled addendum/reissue workflow.
```

---

## 11. Works Requirements UI Rules

### 11.1 Required Components

Show Works Requirements as component cards:

- Specifications;
- Site Information;
- HSE Requirements;
- Environmental/Social Requirements;
- Method Statement Requirement;
- Work Programme Requirement;
- Quality Requirements.

### 11.2 Attachment Binding

When uploading files, the UI must require section/component binding.

Do not allow generic unbound attachment upload to satisfy readiness.

### 11.3 Supplier-Facing Classification

The user must specify or confirm whether attachment is:

- Supplier Facing;
- Internal Only;
- Contract Facing.

Supplier-facing and contract-facing classifications affect Bundle/DCM readiness.

---

## 12. Drawing Register UI Rules

### 12.1 Required Drawing Fields

The UI must collect:

- drawing code;
- title;
- revision;
- file;
- section binding;
- issue status.

### 12.2 Drawing Register Presentation

Drawings should be shown as a register/table:

```text
Drawing Code | Title | Revision | File | Status | Section
```

Section must be fixed/defaulted to Section VII for drawings.

### 12.3 Revision Warning

If a user replaces or revises a drawing after outputs are generated, show:

```text
Changing this drawing will make the Bundle, Evaluation Rules (DEM), and Contract Carry-Forward (DCM) stale.
```

---

## 13. BOQ UI Rules

### 13.1 BOQ Purpose

The BOQ UI must make it clear that the Procuring Entity controls item structure and quantities.

Supplier rates are not entered at tender preparation.

### 13.2 Required BOQ Layout

```text
BOQ Header
Bills
Items
Validation Summary
Import / Export Controls
```

### 13.3 BOQ Item Columns

At minimum:

```text
Item No. | Description | Unit | Quantity | Item Type | Supplier Input Mode | Provisional/Fixed Amount
```

Do not include supplier rate entry fields in Tender preparation UI.

### 13.4 BOQ Warnings

If user attempts to enter rate:

```text
Supplier rates are entered during bid submission, not during tender preparation.
```

If user changes BOQ after outputs are generated:

```text
Changing the BOQ will make the Tender Document Bundle, Submission Rules, Evaluation Rules, and Contract Carry-Forward stale.
```

### 13.5 BOQ Import

BOQ import must validate before acceptance and show structured import errors.

Do not accept a spreadsheet as a final opaque attachment if BOQ structure is required.

## 14. Generated Outputs UI

### 14.1 Purpose

The Outputs screen shows the generated legal/operational models.

### 14.2 Required Output Cards

| Card Label | Technical Code | Purpose |
|---|---|---|
| Tender Document Bundle | Bundle | Supplier-facing tender document. |
| Submission Rules | DSM | Defines bidder submission requirements. |
| Opening Register | DOM | Defines opening record. |
| Evaluation Rules | DEM | Defines evaluation stages/rules. |
| Contract Carry-Forward | DCM | Defines contract formation data. |

### 14.3 Output Card Status

Each card must show:

- status;
- version;
- generated at;
- stale/current indicator;
- source snapshot if applicable;
- actions.

### 14.4 Output Actions

Allowed actions:

- Generate / Regenerate;
- Preview;
- Download where applicable;
- View summary;
- View traceability where permission allows.

Prohibited actions:

- manual edit generated output;
- manual add evaluation criterion;
- manual add submission requirement;
- manual override contract term.

## 15. Readiness UI

### 15.1 Purpose

Readiness screen shows whether the tender can proceed to approval/publication.

### 15.2 Required Sections

1. Overall readiness status;
2. critical blockers;
3. warnings;
4. completion categories;
5. output statuses;
6. evidence readiness;
7. next action.

### 15.3 Readiness Status Display

Use clear statuses:

```text
Ready
Blocked
Incomplete
Warning
Invalidated
```

### 15.4 Blocker Display

Each blocker must show:

- what is wrong;
- where it is;
- why it blocks;
- how to fix it;
- link to relevant completion stage.

Example:

```text
Blocker: Evaluation Rules (DEM) are stale.
Why it matters: Evaluation cannot legally proceed from outdated rules.
Fix: Regenerate outputs, then rerun readiness.
```

---

## 16. Approval Review UI

### 16.1 Purpose

Approving Authority reviews a stable snapshot package.

The UI must be read-only except approval decision controls.

### 16.2 Required Review Sections

- Tender summary;
- Package reference;
- STD template/profile;
- Readiness result;
- Bundle preview;
- Output summaries;
- BOQ summary;
- Works Requirements summary;
- warnings/blockers;
- audit/evidence summary;
- decision history;
- approval decision controls.

### 16.3 Decision Controls

Allowed:

```text
Approve for Publication
Return for Correction
Reject
Request Clarification
```

Where workflow supports them.

### 16.4 Return for Correction

Return action must require:

- reason code;
- comment;
- affected area;
- criticality.

### 16.5 No Silent Edit Rule

The approval UI must not render editable controls for:

- TDS;
- SCC;
- BOQ;
- Works Requirements;
- drawings;
- generated outputs.

---

## 17. Publication UI

### 17.1 Purpose

Publication UI confirms the legal transition from approved tender to published tender.

### 17.2 Required Publication Confirmation

Before publishing, show:

- approval status;
- readiness status;
- output status;
- evidence package status;
- publication snapshot readiness;
- immutability warning.

### 17.3 Required Warning

```text
Publishing will lock the tender document, STD Instance, generated outputs, BOQ, attachments, and publication snapshot. After publication, changes require an addendum or controlled reissue.
```

### 17.4 Publication Success State

After publication, show:

- tender status Published;
- publication snapshot code;
- published Bundle version;
- published DSM/DOM/DEM/DCM versions;
- evidence package link;
- next lifecycle step.

## 18. Evidence and Audit UI

### 18.1 Evidence Package View

Evidence view must show:

- package and tender lineage;
- STD template/profile;
- STD Instance;
- outputs;
- snapshots;
- approval decisions;
- audit events;
- downstream consumption references;
- evidence export actions.

### 18.2 Audit Trail View

Audit trail must support filters:

- event type;
- actor;
- object;
- result;
- denied actions;
- date range;
- risk level.

### 18.3 Denied Action Visibility

Auditors should be able to see denied high-risk actions such as:

- manual criteria attempted;
- post-publication edit attempted;
- unauthorized publication attempted;
- contract override attempted.

---

## 19. UI State and Error Handling

### 19.1 General Error Rules

The UI must not display raw stack traces, raw JSON errors, or database errors.

It must show:

- user-readable message;
- resolution action;
- reference code if needed;
- link to affected area.

### 19.2 Legal Denial Messages

Examples:

```text
You cannot edit this tender because it has been published. Use the addendum workflow.
```

```text
You cannot add evaluation criteria. Evaluation rules are generated from the published STD Evaluation Model.
```

```text
You cannot publish this tender because approval is not complete.
```

### 19.3 Loading States

For long operations:

- output generation;
- readiness checks;
- publication;
- evidence export;

show progress and prevent duplicate submissions.

## 20. Accessibility and Usability Requirements

The UI must support:

1. keyboard navigation;
2. visible focus states;
3. form labels;
4. readable disabled reasons;
5. status text not color-only;
6. table summaries for BOQ/drawings;
7. meaningful page titles;
8. screen-reader-friendly validation messages;
9. confirmation dialogs for high-risk actions.
